# 选型：推到底，然后交给人拍板

**这份 skill 的核心不是推导方法，是一条纪律：不自己拍板。**

推导做得再漂亮，选型也是产品方向的一部分，归人。你的活是把选项、依据、代价摆清楚到
**人看一眼就能判**的程度。

## 什么时候触发

- 引入一个新依赖（任何 `pnpm add`）
- 选一个工具（打包器、测试框架、构建方式）
- 定一个契约面（服务名、协议形状、包名、URL 约定）
- 判「这件事进内核，还是做成插件」
- 决定要不要做某个功能

**不触发**：实现细节（变量名、函数怎么拆）、已经定过的事情的执行。

## 推导七步

### 1. 目的一句话

不是「要做 X」，是「要解决什么」。写不出一句话就是还没想清楚。

### 2. 从目的出发，什么是不可消去的

一件一件问：**去掉它，目的还成立吗？** 成立就不是必需的。

这一步会砍掉大部分「看起来需要」的东西。

### 3. 候选各是什么

至少两个，包括「什么都不做」。

### 4. 各自的代价——要事实，不要印象

**这一步必须去查，不能凭记忆。** 看代码、数行数、跑一次、查 npm 上的版本与状态。

印象是这样的：「共享组件库更整齐」。事实是这样的：「8 个插件 8 张 64KB 的表，彼此差不到
6%——CSS 一分没省，省的只有 JS，代价是 3 个包严格同号 + 每插件 4 处版本钉死 + 8 类静默失败」。

后者能判，前者不能。

### 5. 代价对称吗

**选错的两个方向，代价一样重吗？**

服务名加不加前缀就是不对称的：该加没加、将来撞了要改名（破坏性变更，所有消费方跟着改）；
不该加而加了，只是名字长几个字符。**不对称时，往代价轻的那边倒。**

### 6. 可逆吗

**现在做，以后能不能改？以后加，比现在做贵多少？**

React 共享那次：现在做是一次性成本；以后加意味着所有插件改构建配置重新发版。所以现在做。
反过来「先共享再拆」更贵，那就更该现在定。

不可逆的决定要更谨慎；可逆的可以先选一个跑起来。

### 7. 交给用户

给三样：**结论（你倾向哪个）、依据（第 4 步的事实）、代价（选了要付什么）**。

用 `AskUserQuestion`，选项写成人能对比的样子——不是「A / B」，是「A：省什么、赔什么」。

**推荐一个**，别把球原样踢回去。人要的是判断，不是选择题。

## 拍板之后：记进 decisions.mdx

文档站的 `decisions.mdx`，每条固定六段：

```
### <一句话说这是什么选择>

**问题**：要解决什么
**候选**：各是什么
**判据**：靠什么分出高下（第 4-6 步里真正起作用的那条）
**定了**：选的是哪个
**代价**：选了要付什么——写清楚，将来后悔时才认得出是不是这一条在疼
**日期**：YYYY-MM-DD
```

**decisions 与 walls 的分工**：decisions 是**事前的选择**，walls 是**事后的教训**。
一个选择后来撞了墙，两边各记各的，walls 那条指回来。

## 三条这条线上反复用到的判据

写在这里，因为它们已经定过好几次了：

1. **代价不对称时往轻的那边倒**（服务名前缀、依赖 peer/dev）
2. **可逆性优先于完美**（React 共享现在做、打包器到期再选）
3. **「真遇到需求才加」**——不是「将来可能要」，是某件事此刻就干不成，而且现场说得出来：
   谁、在做什么、卡在哪。答不上来就是还没到期

## 一个反面例子

不要这样推：「最小内核所以不共享 React」。那是**为规则服务**，不是为结果服务。

要这样推：「共享的代价实测是 3 个包同号 + 8 类静默失败，省下的只有 JS 体积；而插件窗格
本来就是孤立的 React 树，多份技术上能跑——所以除非体积真成问题，不共享」。

**规则是推导的产物，不是推导的前提。**
