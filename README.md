# gwb-kernel

god 工作台的正线：**最小的、能正常运行插件的那个版本**。

目标不是「内核行数最少」，是「能把插件正常跑起来」所需的最小集——后者带着一条验收
标准，插件得真能干活。

母仓 `god-workbench` 与它的件仓 `gwb-plugins` 准备废弃，此后只作参考；插件全部重做
一份。母仓走到今天约 5100 行，其中约 3600 行服务于同一件事——让失败变得体面（自动
升级的四路判定、盘上对账、失败还原、图形界面上的兜底页与阶段页、配置文件的自愈）。
这条线把那些东西背后的前提拿掉：不自动升级，判定连同它制造的麻烦一起消失。

## 内核只做四件事

|        | 是什么                         |
| ------ | --------------------------- |
| **载体** | 起一个 node 进程挂 cordis，开一扇窗    |
| **取址** | 读 yml 知道装了哪些，找到文件在哪，挂上      |
| **装机** | 把包名转发给 pnpm，装进 home         |
| **桥**  | 命令与事件双向，`gwb://` 交出插件的浏览器那半 |

外加一份只命名不做事的词汇表。

准入判据两道关：**一、凡是「第一个插件存在之前必须发生的事」，才进内核，其余一律皆
插件。二、真遇到需求才加**——不是「将来可能要」，是某件事此刻就干不成，而且现场说得
出来。加功能的默认形态是加一个插件。

## 跑起来

```powershell
pnpm install
pnpm start     # electron-vite build && electron .
pnpm check     # typecheck + oxlint + vitest,提交前跑
```

home 落在 `%APPDATA%/gwb-kernel/home`。第一次启动它是空的——要看到界面，往里装一个
声明了 `gwb.shell` 的件，并在 `cordis.yml` 写上条目。

## 刻意不做的

不是还没做，是决定不做：自动升级、盘上对账与失败还原、图形界面上的兜底页与阶段页、
插件之间的准入核对、配置文件的模板与自愈。每一条的理由都在文档站里写着；要做，得先
推翻上面那句准入判据。

## 文档

文档站在 `docs-site/`，用 fumadocs 起：

```powershell
pnpm --filter gwb-kernel-docs-site dev     # http://localhost:4314
```

**代码注释只写现状**——为什么这么写、撞过什么、症状是什么，全在文档站的「撞过的墙」
那一页，并且用 livedoc 钉在对应代码上：代码一改文档就报黄，得有人复核。

`livedoc check` **不在 `pnpm check` 里**——它要起文档站的解析链，太慢，每次跑测试都带上
不值。单独两条 `pnpm doc` / `pnpm doc:confirm`，改了被钉住的代码就跑一次。

这份 README 是生成物，正本是 `docs-site/content/docs/readme.mdx`，改完在 `docs-site` 跑
`pnpm livedoc render --target ai` 重摆，一起提交。
