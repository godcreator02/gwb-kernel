**本页回答**：插件怎样写日志、写到哪里、文件里一条长什么样；插件挂没挂上、在等什么从哪里看；要显示或查询日志的插件从哪里读；内核应用和插件各保证什么。

## 连接的模块

- [内核应用](/docs/desktop)：注册唯一的 exporter，写 `gwb.log` 与 stderr；把页面上的 console 输出转成日志；按条目写挂载日志
- 任何插件：写日志都用 `ctx.logger`；要显示或查询日志的插件（日志插件 `@godcreator/gwb-logger`）读 `gwb.log`

## 接口

**写**：插件用 cordis 的 `ctx.logger(名字)` 拿到一个 logger，调它的 `info` / `warn` / `error` / `debug`。内核自己用名字 `kernel`；页面上的 console 输出由内核转成名字 `renderer` 的日志，级别照搬（console 的 `warning` 记成 `warn`）。

**`gwb.log` 里的一条**：一行一个 JSON 对象，以换行结尾；五个键、顺序固定。正文里的换行留在 JSON 字符串里，所以一条记录永远是一行，按行读、按行解析就够了。

| 键 | 值 |
| --- | --- |
| `ts` | ISO 8601 的 UTC 时间字符串，毫秒精度 |
| `level` | `error` / `warn` / `info` / `debug`，cordis 的其余类型记成 `info` |
| `source` | `kernel`（内核自己，以及 cordis 的 loader、include）/ `renderer`（页面 console）/ `plugin`（其余） |
| `name` | logger 名 |
| `msg` | 正文 |

正文由 cordis 自己的 `Logger.format` 格式化，所有级别都写，包括 `debug`。两处补救：插件传进来的参数 cordis 格式化不了时（`%o` 用 `JSON.stringify`，遇到循环引用、BigInt 就抛），内核退回把参数逐个转成字符串拼起来，这一行照样写进去；cordis 格式化 Error 用的是 stack，而 loader 在包 import 失败时把 stack 换成了只剩条目路径，错误原文只在 `message` 里，内核发现正文里没有某个 Error 的 `message`，就把「名字: message」补在正文最前面（[条目状态时机的实验](/trajectory/2026-09-27-entry-state-timing)）：

**挂载日志**：内核按条目写，logger 名是 `loader`（`source` 是 `kernel`）。每个插件条目挂上了（带 apply 的耗时，从进入 LOADING 算到 ACTIVE）、挂载失败（错误的第一行）、卸载、因为提供方被卸载而退回等待（缺哪几个服务）各写一行；include 这类只装条目的容器，以及插件里再 `ctx.plugin` 出来的子插件不写。

{/* ref file="../apps/desktop/src/entry-log.ts" lines="96-120" */}

一开始就缺服务的条目不发任何状态事件，只能靠汇总报出来：条目树有变化（启动时逐条加载、插件管理换包）停下来 300 毫秒之后，等 `ctx.loader.await()` 返回，再写一行「条目加载完：N 个挂上；在等：…；挂载失败：…；没导入成功：…」。有挂载失败或没导入成功的是 error，只有在等的是 warn，全部挂上是 info。退出时卸载插件树，不写卸载与汇总。

{/* ref file="../apps/desktop/src/entry-log.ts" lines="42-69" */}

**读**：要显示或查询日志的插件读 `<home>/gwb.log`，要更早的再读 `gwb.log.1`，按时间顺序是先 `gwb.log.1` 再 `gwb.log`。文件跨重启留着，所以上一次运行的日志也查得到。

**上限与轮转**：`gwb.log` 写到 128 MB 就改名为 `gwb.log.1`（只留这一份旧的，磁盘占用最多 256 MB），再开一份新的。128 MB 的依据是实测：平常一天约写 48 MB，某个插件出错、反复写同样的日志时一小时能写约 675 MB；128 MB 平常能留住两天半的日志，那种情况下十几分钟轮转一次。读数记录在仓根 `probes/2609201430_log-cap-rotation/`。

## 约定

**内核应用**保证：

- 只有一个输出：stderr 上的文本加 home 里的 `gwb.log`，每一条都进这两处
- `gwb.log` 每一行都是一个完整的 JSON 对象，五个键、顺序如上表；改键、改取值、改格式都是改接缝，内核包升 x
- 内核自己的日志也走 `ctx.logger`；只有 cordis 实例建好之前的几行与启动失败那一行直接写 stderr 与 `gwb.log`（`gwb.log` 打不开造成的启动失败只写 stderr）
- 插件里没被处理的异常与 rejection 记成 `kernel` 的 error，不让内核退出
- 每个插件条目的挂载结果都有一行 `loader` 日志，条目树安定之后有一行汇总
- `gwb.log` 启动时打不开就启动失败：只写 stderr，错误框写明文件路径与原因，退出码 1（[启动与退出](/docs/desktop/boot)）
- 打开之后写日志出问题都只告警一句，不让内核崩溃：写不进只告警一次；轮转失败就继续写原来的文件，再写满一个上限后重试；轮转之后重新打开失败只告警一次，之后日志只写 stderr、不再重试；没有终端时写 stderr 报的错被忽略，文件照写
- 每条 error 都触发一次 `gwb:shell` 的推送（200 毫秒内的多次合并成一次），没有外壳时最近的错误行显示在只读状态页上；warn 只进日志、不触发推送，下一次推送时随最近的错误行一起出现

**插件**保证：

- 日志一律经 `ctx.logger`，不直接写 `gwb.log`；直接写 stderr 的内容不会进文件
- logger 的名字用自己能被认出的名字（通常是插件名或服务名），读日志的人靠它区分来源；不用 `kernel`、`loader`、`include`、`renderer`，这几个名字的日志算内核或页面的
- 读 `gwb.log` 的插件按行解析，认不出的行直接报错，不猜
- 自己注册 cordis exporter 的，`export` 不抛异常、不做耗时的同步操作：它在别人写日志的那次调用里同步执行，抛出的异常会抛给写日志的一方，排在它后面的 exporter 收不到这一行（内核的 exporter 注册在所有插件之前，不受影响）

## 不负责的事

- 内核应用不为页面或窗格建日志通道：页面上要显示日志的插件自己读 `gwb.log`，再用自己的命令交给页面
- 内核应用不给日志分级过滤、不按插件分文件、不提供查询
- 内核应用不保证 `gwb.log` 留着全部历史：只留当前一份与一份旧的
