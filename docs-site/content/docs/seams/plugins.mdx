<Diagram name="plugin-seam" title="内核不认识任何插件，插件只从 ctx 拿内核的东西">
- 内核在 cordis 的根上下文提供 `gwbKernel`：`dataDir`、`version`、`emit`、`setShell`；内置的命令插件提供命令总线 `gwbCommands`
- 分界线上面是内核（连同内置的命令插件与插件管理），不认识 `cordis.yml` 里任何插件、服务、命令的名字；下面是插件，每个都是 home 里的一个 npm 包
- 换插件的地方：`cordis.yml` 里的条目（一条写一个包名），包从 home 的 `node_modules` 按真实路径找到
- 插件之间通过 cordis 的服务和命令交互，不经过内核
</Diagram>

## 接口

插件是一个 npm 包，入口导出 cordis 认识的形状；内核给它两个服务：`ctx.gwbKernel`，和内置的命令插件提供的命令总线 `ctx.gwbCommands`：

```ts
// 插件的入口（函数式写法；也可以默认导出一个继承 Service 的类）
export const name = '@godcreator/gwb-demo'
export const inject = ['gwbData']           // 依赖的服务都在了，cordis 才调用 apply
export function apply(ctx: GwbContext): void { /* … */ }

// 内核提供的服务：在根上下文上，早于任何插件，永不撤销，不用写进 inject
interface GwbKernelApi {
  dataDir: string                     // 这个 home 的目录
  version: string                     // 内核的版本号
  emit(payload: unknown): void        // 往页面推一条事件
  setShell(url: string): () => void   // 把页面交给这个模块，返回撤销函数
}

interface GwbContext extends Context {
  gwbKernel: GwbKernelApi
  gwbCommands: GwbCommands            // 命令总线，见命令插件
}
```

## 插件怎么进来

1. home 的 `package.json` 列出插件包，pnpm 把它们装进 `node_modules`——这一步由内置的[插件管理](/docs/plugin-manager)负责，用的是安装包里那份 pnpm
2. `cordis.yml` 的每一条条目写一个包名；内核注册 cordis 官方的 loader，把两个内置插件和 include 作为 loader 根层的条目交给它（内置的排在前面），include 读这个文件，loader 按条目加载
3. loader 要 import 一个包名时，内核替它解析：先把 `<home>/node_modules/<包名>` 解析成磁盘上的真实路径，再按包的 `exports` 找到入口文件
4. cordis 调用插件的 `apply(ctx)`（或实例化它的 `Service` 类）；`inject` 里的服务缺一个，插件就停在等待状态，补齐后自动加载

第 3 步从真实路径开始，是为了运行中换了版本能拿到新版本：pnpm 布局里真实路径带版本号，不会命中 Node 为上一版记下的解析缓存。这几步的顺序本身就是约束（比如 `gwbKernel` 必须在注册 loader 之前提供），每一步为什么这样写见 `main.ts` 里的注释。

## home 里有什么

| 文件 | 谁写 |
| --- | --- |
| `package.json` | 缺了内核补一份最小清单，之后归 pnpm 和 plugin-manager |
| `cordis.yml` | 缺了内核补一个空表，之后归 include 和 plugin-manager |
| `node_modules/` | pnpm |
| `gwb.log` | 内核（见[系统地图](/docs/map#日志)） |
| `runtime.json` | 内核每次启动整份重写：pid、版本、调试端口；退出时不删，**读它的一方负责确认进程还活着** |
| 其余目录 | 各插件自己的数据 |

`GWB_HOME` 给一个名字，home 就在 `<appData>/gwb-kernel/homes/<名字>`；给一个路径就直接用那个目录。同一个 home 只能运行一个实例。

## 两边各保证什么

内核保证：
- `gwbKernel` 与命令总线 `gwbCommands` 在 `cordis.yml` 里的任何插件加载之前就已提供
- 一个插件抛错只让它自己进入失败状态，内核只记录、不退出
- 退出时卸载整棵插件树，等各插件的清理结束，最多等 5 秒，超时就强制退出

插件保证：
- 自己启动、创建的东西在卸载时清理掉，并把清理返回成 promise——内核等的就是这个 promise
- 要 home 路径只从 `gwbKernel.dataDir` 取，数据写在自己的目录里
- 和别的插件只通过服务和命令交互

## 内核不管什么

- 不给插件提供安装接口：装插件、升级插件只经内置插件管理的 `plugin-manager.*` 命令；插件之间的依赖齐不齐不核对
- 不监听 `cordis.yml`：运行中加载、卸载插件要调用 loader 的条目接口（plugin-manager 在调）
- 不判断插件是否加载成功：看 cordis 给这个插件的状态，`ACTIVE` 才算

## 怎么单独测

`bare-import.ts` 不依赖 electron 与 cordis：传入一个手工构造的临时 home，验证主入口与带 scope 的包都能解析到、子路径写法等价、链接改指向新版本后拿到新版本、包不存在时报错并带完整路径（`tests/bare-import.test.ts`）。加载顺序、运行中重新加载、退出清理只能在隔离 home 里实机验证。

## 代码从哪读

- 内核提供什么：`packages/gwb-plugin-api/src/index.ts` 的 `GwbKernelApi`；实现是 `main.ts` 里的 `kernel` 对象
- 加载插件：`main.ts` 的 `main()` 里注册 loader 那几行
- 包名解析：`bare-import.ts`
- 退出清理：`main.ts` 的 `will-quit`
