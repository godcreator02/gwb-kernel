**本页回答**：插件在页面里运行的代码写 `import 'react'` 时，页面凭什么能找到文件；谁来声明、内核应用怎么拼、名字冲突怎么办；换版本之后什么时候生效。

<Diagram name="shared-names" title="内核包与插件在包清单里声明，内核每次推送时拼成 importmap">
- 内核包自己的清单声明 react 的四个包名，指向内核包 `dist/react/` 里打包好的文件；内核启动时解析一次，每次推送都先放进表里
- 插件在自己的清单里写 `gwb.shared` 声明别的名字；内核的 `collectImports` 扫描 home 清单里的每个包，按 home 解析成真实文件的 `file://` 地址，随 `gwb:shell` 推给页面
- 插件声明了内核给了的名字：忽略这条声明，记一条 warn（同一句只记一次）
- 两个插件声明同一个名字：两个都不收录，记一条 warn，页面 import 它直接报解析错误；别的名字不受影响
</Diagram>

## 连接的模块

- [内核应用](/docs/desktop)：扫描 home、拼 importmap、推给页面入口；它自己的包清单也是一个提供方
- 在包清单里声明 `gwb.shared` 的插件（提供方）：react 以外的名字由插件提供，目前是块笔记线的 `@godcreator/block-note`（它声明的是自己的包名）

页面上使用这些包名的代码是第三方：它只需要构建时把这些名字外置。

## 接口

提供方只写一个清单字段：包名 → 自己 `exports` 里的子路径。内核包自己写的是 react 的四个：

{/* ref file="../apps/desktop/package.json" lines="10-31" */}

这四个文件由 `scripts/build-react.ts` 在构建时用 esbuild 把 react 与 react-dom 打成浏览器能直接 import 的 ESM；react-dom 两个文件把 `react` 外置，页面上四个名字共用同一个 react 实例。打包有三处容易出错：

- **react 没有 ESM 入口**：react 19 的包清单 `exports` 只有 `react-server` 与 `default`，`default` 指向 CJS 的 `index.js`，所以不能把 home 里的 react 按包名直接交给浏览器，必须先打包
- **只能用 esbuild**：rolldown 在 browser 平台对「CJS 里 require 一个外置的包」有意保留 `require`，浏览器里没有 `require`，产物一加载就报错；esbuild 会把它提升成顶层 `import`
- **react-dom 在工厂函数内部 `require('react')`**：esbuild 提不到顶层，产物里留一个 `__require` 探针。构建脚本在文件头加一句 `import * as __gwb_react from "react"`，再把探针换成只认 react 的同步解析器（返回 `default`，react-dom 要用 React 的内部成员）。认的是 esbuild 生成代码的样子，认不出就让构建失败，不把带探针的产物发出去：

{/* ref file="../apps/desktop/scripts/build-react.ts" lines="22-44" */}

入口文件里具名导出要逐个列出：esbuild 从 react 的 CJS 转发链上推不出具名成员，只打出一个 `default`。名单少一个，用到它的窗格加载时报「does not provide an export named」、整个窗格空白，构建与类型检查都发现不了；`apps/desktop/tests/react-bundles.test.ts` 查产物里没有探针、react-dom 的修补在、`react.js` 的具名导出齐。

`gwb.shared` 是内核应用读包清单时唯一认识的字段。声明写在包清单里，不由提供方在运行时调用接口登记：共享出去的模块只在页面上运行，在主进程里没有代码可以去登记，包清单是它唯一能声明的地方。子路径按包的 `exports` 解析，用的是和加载插件同一个函数 `resolveFromHome`（见[插件加载](/docs/seams/loading)）。这张表每次推送 `gwb:shell` 时重新计算，作为 `imports` 字段推给页面（通道见 [IPC 通道](/docs/seams/ipc)）；同一句警告只记第一次，不然开机时每次推送都刷一遍日志：

## 约定

内核应用保证：
- **react 的四个包名由内核给**：插件对这几个名字的声明一律忽略、记一条 warn，不算撞名；内核包升级 react 就是内核升版
- **其余名字一个名字只有一个提供方**：两个插件声明了同一个名字，全部拒绝、记一条 warn，不比版本、不挑谁更新
- **插件的声明解析不到只报 warn**：一个提供方出问题，只损失它自己声明的那几个名字
- **提供方换了版本，下一次推送就是新地址**：每次推送都重新计算，而且从真实路径开始解析，不会命中上一版的解析缓存（[importmap 也会遇到 Node 解析缓存](/trajectory/2026-09-17-wall-importmap-resolver-cache)）。但页面上的 importmap 只注入一次，**整页重新加载**之后才用上新版本；内核自己的那几条要重启才换

提供方保证：
- **只有插件与内核包做提供方**：进 importmap 的只能是整个页面必须只有一份的运行时代码，库不声明 `gwb.shared`
- 声明的子路径在自己的 `exports` 里写明
- 自己是 home 清单的直接依赖（内核应用只扫这一层）

使用这些包名的页面代码保证：打包时把这些名字外置，不打进包里、留给 importmap；外置名单从声明它的包的清单取，不手抄。插件在 peer 里写了内核包，react 的四个名字就从内核包的清单取。

## 不负责的事

- 内核应用不知道页面有没有真的 import 某个名字
- 内核应用只看 home 清单里的直接依赖，不扫描传递依赖
- 提供方不管谁在用它声明的名字
