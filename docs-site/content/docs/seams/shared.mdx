**本页回答**：页面上运行的代码写 `import 'react'` 时，页面凭什么找到文件；importmap 里有哪些名字、从哪来、什么时候算；页面代码构建时哪些名字不打进自己的产物；别的包在清单里写了 `gwb.shared` 会怎样。

<Diagram name="shared-names" title="内核包清单里声明的四个包名，内核启动时解析一次，随 gwb:shell 推给页面">
- 内核包自己的清单在 `gwb.shared` 里声明 react 的四个包名，指向内核包 `dist/react/` 里的文件
- 内核启动时解析一次，得到「包名 → `file://` 地址」的表；解析不到就启动失败（内核包本身不完整）
- 这张表就是整张 importmap，每条 `gwb:shell` 推送都带着它；页面入口注入之后，外壳和插件的页面代码写 `import 'react'` 就找到内核包里的文件
- home 里别的包在清单里写的 `gwb.shared`，内核不读
</Diagram>

## 连接的模块

- [内核应用](/docs/desktop)：它的包清单声明 react 的四个包名；启动时解析成 importmap，随 `gwb:shell` 推给页面入口
- 页面上运行的代码：外壳和插件的浏览器端产物（窗格等）。构建时把这几个名字外置，运行时经 importmap 找到内核包里的文件

页面入口什么时候注入 importmap，写在[外壳接管](/docs/seams/shell)。

名单写在内核包清单里、不写死在内核代码里：页面代码的构建脚本和 devkit 的发版检查都要知道这份名单，它们读的是装着的内核包清单。

## 约定

内核应用保证：
- **importmap 只有内核包声明的名字**：home 里别的包在清单里写了 `gwb.shared`，内核不读、不收，也不记日志。拦下这种写法是 devkit 发版检查的事，见 devkit 仓文档站
- **启动时算一次**：解析不到就启动失败，说明内核包本身不完整；这次运行里每条推送带的都是同一张表。换 react 就是换内核包，重启内核后生效
- **这份名单是接缝的一部分**：加一个名字是兼容的改动，内核升 y；删掉一个名字、改掉一个名字指向的东西，已经外置了它的页面代码会找不到文件，内核升 x

{/* has file="../apps/desktop/tests/imports.test.ts" text="kernelSharedImports：声明的文件不在就抛出" */}

页面代码保证：
- **构建时把这几个名字外置**，不打进自己的产物、留给 importmap；外置名单从装着的内核包清单的 `gwb.shared` 读，不手抄。插件的 peer 里写了内核包，pnpm 把它装进插件仓的 `node_modules`，构建脚本从那里读
- **别的依赖都打进自己的产物**：页面上没有别的共享包名，两个插件用同一个库就各带一份
- 自己的包清单里不写 `gwb.shared`

## 不负责的事

- 内核应用不知道页面有没有真的 import 某个名字，也不检查文件能不能在浏览器里运行
- 内核应用不看 home 里别的包：不读它们的清单，也不因为它们写了 `gwb.shared` 而警告
- 内核应用不替页面代码打包：除了 react 的四个文件，页面代码的产物由各自的构建决定
- 检查插件产物只 import 这几个名字、拒绝非内核包写 `gwb.shared`，是 devkit 发版检查的事

## 测试

`apps/desktop/tests/imports.test.ts` 用手工构造的包目录保护 `kernelSharedImports`：按内核包自己的 `exports` 解析出真实文件，声明的文件不在就抛出；另外核对本仓内核包清单：react 的四个包名都声明了、`exports` 指到打包脚本产出的文件。`apps/desktop/tests/main.test.ts` 用真实的内核包启动，home 里装一个写了 `gwb.shared` 的测试包，确认每条推给页面的 importmap 都只有那四个名字、react 指向内核包、日志里没有那个包的名字；`apps/desktop/tests/index-html.test.ts` 确认页面只注入一次 importmap。页面上真的用上内核包里的 react，只能在隔离 home 里实机验证（见[开发](/docs/develop)）。
