**本页回答**：插件在页面里运行的代码写 `import 'react'` 时，页面凭什么能找到文件；谁来声明、内核应用怎么拼、名字冲突怎么办；换版本之后什么时候生效。

<Diagram name="shared-names" title="提供方在包清单里声明，内核每次推送时拼成 importmap">
- 提供方在自己的包清单里写 `gwb.shared`：包名 → 包里的导出子路径。目前唯一的提供方是 shell，声明了 react 的四个包名
- 内核的 `collectImports` 扫描 home 清单里的每个包，把声明按 home 解析成真实文件的 `file://` 地址，随 `gwb:shell` 推给页面
- 页面按这张表解析包名 import，整个页面只有一份 react
- 同一个名字有两个提供方：两个都不收录，内核记一条 warn，页面 import 它直接报解析错误；别的名字不受影响
</Diagram>

## 连接的模块

- [内核应用](/docs/desktop)：扫描 home、拼 importmap、推给页面入口
- 在包清单里声明 `gwb.shared` 的包（提供方）：目前只有外壳插件 `gwb-shell`

页面上使用这些包名的代码是第三方：它只需要构建时把这些名字外置。

## 接口

提供方只写一个清单字段：

```jsonc
// 提供方的 package.json（外壳插件）
"gwb": {
  "shared": {
    "react": "./react",
    "react/jsx-runtime": "./react-jsx-runtime",
    "react-dom": "./react-dom",
    "react-dom/client": "./react-dom-client"
  }
}
```

内核应用把它拼成一张普通的 importmap（形如 `{ "react": "file:///…/node_modules/.pnpm/…/react.js", … }`）：

`gwb.shared` 是内核应用读包清单时唯一认识的字段。声明写在包清单里，不由提供方在运行时调用接口登记：共享出去的模块只在页面上运行，在主进程里没有代码可以去登记，包清单是它唯一能声明的地方。子路径按包的 `exports` 解析，用的是和加载插件同一个函数 `resolveFromHome`（见[插件加载](/docs/seams/loading)）。这张表每次推送 `gwb:shell` 时重新计算，作为 `imports` 字段推给页面（通道见 [IPC 通道](/docs/seams/ipc)）：

## 约定

内核应用保证：
- **一个名字只有一个提供方**：两个包声明了同一个名字，全部拒绝、记一条 warn，不比版本、不挑谁更新
- **解析不到只报 warn**：一个提供方出问题，只损失它自己声明的那几个名字
- **提供方换了版本，下一次推送就是新地址**：每次推送都重新计算，而且从真实路径开始解析，不会命中上一版的解析缓存（[importmap 也会遇到 Node 解析缓存](/trajectory/2026-09-17-wall-importmap-resolver-cache)）。但页面上的 importmap 只注入一次，**整页重新加载**之后才用上新版本

提供方保证：
- **只有插件做提供方**：进 importmap 的只能是整个页面必须只有一份的运行时代码（比如 react），库不声明 `gwb.shared`
- 声明的子路径在自己的 `exports` 里写明
- 自己是 home 清单的直接依赖（内核应用只扫这一层）

使用这些包名的页面代码保证：打包时把这些名字外置，不打进包里、留给 importmap；外置名单从外壳插件取，不手抄。

## 不负责的事

- 内核应用不认识 react 或任何包名，只转交提供方的声明
- 内核应用只看 home 清单里的直接依赖，不扫描传递依赖
- 内核应用不知道页面有没有真的 import 某个名字
- 提供方不管谁在用它声明的名字
