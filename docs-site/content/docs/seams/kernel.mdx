**本页回答**：内核直接给插件的服务 `gwbKernel` 有哪几个成员、各是什么意思；内核应用和插件使用它时各保证什么。

## 连接的模块

- [内核应用](/docs/desktop)：在 cordis 的根上下文上提供 `gwbKernel`
- 任何插件：从 `ctx.gwbKernel` 直接取用，不写进 `inject`

业务插件通过 `handleRequest` 主动登记请求处理器；内核不读取任何业务插件服务（[请求通道](/docs/seams/requests)）。

## 接口

`gwbKernel` 的形状就是包根导出的 `GwbKernelApi`，插件的 `apply` 拿到的上下文类型是 `GwbContext`：

- `dataDir`：这个 home 目录在磁盘上的真实路径——大小写、junction、斜杠写法不同的同一个目录得到同一个字符串
- `version`：内核包 `@godcreator/gwb-kernel-desktop` 清单里的版本号
- `emit(payload)`：往页面推一条事件，页面用 `window.gwb.on` 收（[IPC 通道](/docs/seams/ipc)）
- `handleRequest(channel, handler)`：登记页面请求处理器，同名拒绝，注销函数交给 `ctx.effect`；语义见[请求通道](/docs/seams/requests)
- `registerImports(mapping)`：登记浏览器模块映射，返回幂等撤销函数；用 `ctx.effect` 管理（[浏览器模块](/docs/seams/page-react)）
- `setShell(url)`：把页面交给这个地址指向的模块，返回撤销函数（[外壳接管](/docs/seams/shell)）

这段说明三件事：`emit` 只是往当前窗口发一条 `gwb:event`，窗口不在就什么都不发；`setShell` 每次都立刻推一次整份外壳状态；撤销函数只在当前外壳地址仍是自己交出的那个时才清空。

## 约定

**内核应用**保证：

- `gwbKernel` 在注册 loader 之前就已提供，任何插件加载时它都在；永不撤销
- `dataDir` 在一次运行中不变
- `emit` 只转交、不保留：窗口不在时这条事件就丢了，不补发
- `setShell` 后调用的替换先调用的；撤销只在自己仍是当前外壳时清空，否则什么都不做

**插件**保证：

- 数据写在 `dataDir` 下归自己的目录或文件里，不碰别的插件的；home 里已有的文件各归谁见[总表](/docs/wiring#home-布局与文件)，比如 home 根上的 `settings.json` 归设置插件、`package.json` 与 `cordis.yml` 归插件管理（[home 布局与条目树](/docs/seams/home)）
- `emit` 的 payload 能经 Electron 的 IPC 传过去（结构化克隆：函数、Promise 传不过去）
- 把 `setShell` 返回的撤销函数交给 `ctx.effect`，插件卸载时把页面交还

## 不负责的事

- 内核应用不给插件分数据目录，也不检查插件写了哪里
- 内核应用的 `emit` 不知道谁在听，不区分事件类型，不给事件编号；页面要区分来源，由发事件的插件写进 payload
- 内核应用的 `setShell` 不挑外壳：谁调用谁就是，也不检查地址指向的模块能不能加载
- `version` 只是内核包的版本：安装包（启动器）的版本插件拿不到，插件的版本由插件管理报告

## 测试

形状由类型检查保护：内核里这个对象标成同一个 `src/api.ts` 里的 `GwbKernelApi`，对不上时本仓 `pnpm check` 失败。行为由 `apps/desktop/tests/main.test.ts` 保护：一个从 `cordis.yml` 加载进来的测试插件取到 `gwbKernel`，证明它有五个成员、`dataDir` 是 home 的真实路径、`version` 是内核包的版本、`emit` 推到页面、后调用的 `setShell` 替换先调用的、撤销只在自己仍是当前外壳时清空。
