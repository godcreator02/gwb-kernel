**本页回答**：内核直接给插件的服务 `gwbKernel` 有哪几样、各是什么意思；内核应用和插件使用它时各保证什么。

## 连接的模块

- [内核应用](/docs/desktop)：在 cordis 的根上下文上提供 `gwbKernel`
- 任何插件：从 `ctx.gwbKernel` 直接取用

类型从内核包的包根导出（[包根导出的接口类型](/docs/desktop/api)）：插件写 `import type { GwbContext } from '@godcreator/gwb-kernel-desktop'`，内核包本来就在插件的 peer 里，不用另加依赖。上下文上的命令服务 `gwbCommands` 不是内核服务：它由命令插件提供，内核应用只调用它转交页面发来的命令（[命令转交](/docs/seams/commands)）。

- `dataDir`：这个 home 目录的真实路径，大小写、链接、斜杠写法都已统一
- `version`：内核包 `@godcreator/gwb-kernel-desktop` 清单里的版本号
- `emit(payload)`：往页面推一条事件，页面用 `window.gwb.on` 收（通道见 [IPC 通道](/docs/seams/ipc)）
- `setShell(url)`：把页面交给这个地址指向的模块，返回撤销函数（页面怎么接管见[外壳接管](/docs/seams/shell)）

## 约定

**内核应用**保证：

- `gwbKernel` 在加载 `cordis.yml` 之前就在根上下文上提供，任何插件加载时都已存在；永不撤销，所以插件不用写进 `inject`
- `dataDir` 在一次运行中不变，同一个 home 的不同写法得到同一个字符串
- `emit` 只转交、不保留：窗口不在时这条事件就丢了
- `setShell` 后调用的替换先调用的；撤销函数只在当前外壳地址仍是它当初交出的那个地址时才清空，否则什么都不做；每次变化都向页面推一次整份外壳状态

**插件**保证：

- 数据写在 `dataDir` 下自己的目录里，不碰别的插件的目录，也不改 home 根上的 `package.json`、`cordis.yml`（那两份归插件管理，见[home 布局与条目树](/docs/seams/home)）
- `emit` 的 payload 能经 Electron 的 IPC 传过去（结构化克隆：函数、Promise 传不过去）
- 把 `setShell` 返回的撤销函数交给 `ctx.effect`，插件卸载时把页面交还

## 不负责的事

- 内核应用不给插件分数据目录，也不检查插件写了哪里
- 内核应用的 `emit` 不知道谁在听，不区分事件类型，不给事件编号
- 内核应用的 `setShell` 不挑外壳：谁调用谁就是；也不检查地址指向的模块能不能加载
- 内核应用的 `version` 只报内核自己的版本；插件的版本由插件管理报告
- 内核应用不提供命令服务：命令的登记与执行归命令插件（[命令转交](/docs/seams/commands)）

## 测试

`gwbKernel` 的形状由类型检查保护：内核应用里这个对象标成同包 `src/api.ts` 里的 `GwbKernelApi`，对不上 `pnpm check` 就失败。行为由 `apps/desktop/tests/main.test.ts` 保护：一个测试插件从 `cordis.yml` 加载进来取到 `gwbKernel`，证明 `dataDir` 是 home 的真实路径、`version` 是内核包的版本、`emit` 推到页面、`setShell` 后调用的替换先调用的、撤销只在自己仍是当前外壳时清空。
