**本页回答**：内核直接给插件的服务 `gwbKernel` 有哪几样、各自的语义；内核应用和插件在使用它时各保证什么。

## 连接的模块

- [内核应用](/docs/desktop)：`main.ts` 里的 `kernel` 对象，在 cordis 的根上下文上提供成 `gwbKernel`
- 任何插件：从 `ctx.gwbKernel` 直接取用

类型在[词汇表包](/docs/vocab) `@godcreator/gwb-plugin-api` 里：只有类型、没有运行时代码，插件在开发依赖里列它、只用 `import type`。上下文上的命令服务 `gwbCommands` 不是内核服务：它由命令插件 `@godcreator/gwb-commands`（在基础插件仓）提供，类型也由命令插件导出，不在词汇表包里；内核应用只经它转交页面发来的命令（见 [IPC 通道](/docs/seams/ipc)）。

## 约定

内核应用保证：
- `gwbKernel` 在注册 loader 之前就在根上下文上提供，任何插件加载时都已存在；永不撤销，所以插件不用写进 `inject`
- `dataDir` 在一次运行中不变，而且同一个 home 的不同写法得到同一个字符串
- `emit` 只转交、不保留：窗口不在时事件就丢了
- `setShell` 后调用的替换先调用的；撤销函数只在自己仍是当前外壳时才清空，已被别人替换就什么都不做。每次变化都向页面推一次整份状态

插件保证：
- 数据写在 `dataDir` 下自己的目录里，不碰别的插件的目录，也不改 home 根上的 `package.json`、`cordis.yml`（那两份归插件管理，见 [home 布局与条目树](/docs/seams/home)）
- `emit` 的 payload 能经 Electron 的 IPC 传过去（结构化克隆：函数、Promise 传不过去）
- 把 `setShell` 返回的撤销函数交给 `ctx.effect`，插件卸载时把页面交还

## 不负责的事

- 内核应用不给每个插件分数据目录，也不检查插件写了哪里
- 内核应用的 `emit` 不知道谁在听，不区分事件类型，不给事件编号
- 内核应用的 `setShell` 不挑外壳：谁调用谁就是；不检查地址指向的模块能不能加载
- 内核应用的 `version` 只是内核的版本号，不管插件的版本（插件的版本在 home 的 `node_modules` 里，由插件管理报告）
- 内核应用不提供命令服务：`gwbCommands` 的方法、命令的注册与执行都归命令插件

## 测试

`kernel` 对象依赖窗口，没有单元测试；它的形状由类型检查保护：对象的类型标成词汇表包的 `GwbKernelApi`，仓根 `pnpm check` 先构建词汇表包再做类型检查，对不上就失败。行为只能在隔离 home 里实机验证（见[开发](/docs/develop)）：插件读到的 `dataDir` 是 home 的真实路径，`emit` 的事件页面收得到，装上外壳插件后页面被接管、卸载后回到只读状态页。
