**本页回答**：`cordis.yml` 里的一个插件怎样被找到、加载、卸载；这一步内核应用和插件各保证什么；换一个插件要改哪里。

<Diagram name="plugin-seam" title="内核不认识任何插件，插件只从 ctx 拿内核的东西">
- 内核在 cordis 的根上下文提供 `gwbKernel`：`dataDir`、`version`、`emit`、`setShell`；命令服务 `gwbCommands` 由 `cordis.yml` 里的命令插件提供
- 分界线上面是内核，不认识 `cordis.yml` 里任何插件、服务、命令的名字；下面是插件，每个都是 home 里的一个 npm 包，命令插件与插件管理也在下面
- 换插件的地方：`cordis.yml` 里的条目（一条写一个包名），包从 home 的 `node_modules` 按真实路径找到
- 插件之间通过 cordis 的服务和命令交互，不经过内核
</Diagram>

## 连接的模块

- [内核应用](/docs/desktop)：用 cordis 官方的 loader（`@cordisjs/plugin-loader`）与 include（`@cordisjs/plugin-include`）读 `cordis.yml`、加载其中的插件，并替 loader 把包名解析成文件
- `cordis.yml` 里写到的任何插件：每个都是装在 home 里的一个 npm 包。命令插件 `@godcreator/gwb-commands` 与插件管理 `@godcreator/gwb-plugin-manager` 也在这一侧，加载方式和别的插件没有区别

运行中怎么增删条目、home 里的文件归谁写，是另一条接缝：[home 布局与条目树](/docs/seams/home)。

## 接口

**`cordis.yml` 的条目**：一条写一个手写的 `id`、一个包名 `name`、可选的 `config`。内核在 loader 的根层只放一条 include 条目，id 固定是 `home`，由它读 `cordis.yml`；所以只读状态页和插件管理看到的条目都在 `home` 之下：

{/* ref file="../apps/desktop/src/main.ts" lines="328-335" */}

这段说明两件事：include 是经 `loader.builtins` 交给 loader 的（条目名 `cordis:include`），loader 的 `internal.import` 换成了内核的按 home 解析；两者都在加载第一条条目之前设好。

**包名怎么变成文件**：loader 要 import 一个包名时，内核先把 `<home>/node_modules/<包名>` 解析成磁盘上的真实路径，再从那里按 Node 的 `require.resolve` 规则读包清单的 `exports` 找到入口文件，最后按 ESM import：

{/* ref file="../apps/desktop/src/bare-import.ts" lines="6-18" */}

从真实路径开始，是为了运行中换了版本能拿到新版本：pnpm 布局里真实路径带着版本号，不会命中 Node 为上一版记下的解析缓存（[Node 的 CJS 解析缓存会返回旧版本](/trajectory/2026-09-09-wall-resolver-cache)）。页面上的包名不走这套解析，见[页面上的 react](/docs/seams/page-react)。

**插件包的入口**导出 cordis 认识的形状，函数式写法如下，也可以默认导出一个继承 cordis `Service` 的类：

```ts
import type { GwbContext } from '@godcreator/gwb-kernel-desktop'

export const name = '@godcreator/gwb-demo'
export const inject = ['gwbData']           // 这些服务都在了，cordis 才调用 apply
export function apply(ctx: GwbContext): void { /* … */ }
```

`GwbContext` 从内核包的包根导出（[包根导出的接口类型](/docs/desktop/api)），上面由内核提供的服务见[内核服务](/docs/seams/kernel)。`inject` 里的服务缺一个，插件就停在等待状态，补齐后 cordis 自动加载它。

## 约定

**内核应用**保证：

- `gwbKernel` 在任何插件加载之前就已提供（[内核服务](/docs/seams/kernel)）
- 包名一律从 home 的 `node_modules` 按真实路径解析，不从内核包自己的目录找
- 一个插件出错不让内核退出：没被处理的 rejection 和未捕获的异常只记一行名字为 `kernel` 的 error 日志
- 退出时卸载整棵插件树，等各插件的清理结束，最多等 5 秒，到时没清理完也照样退出（[启动与退出](/docs/desktop/boot)）

{/* has file="../apps/desktop/src/main.ts" text="QUIT_CLEANUP_TIMEOUT_MS = 5000" */}

**插件**保证：

- 包清单的 `exports` 让 `require.resolve` 解析得到入口（有 `default`、`require` 或 `node` 条件），import 这个入口拿到上面那种形状
- 依赖的服务写进 `inject`（包括命令插件提供的 `gwbCommands`）；`gwbKernel` 总在，不用写；要 home 路径只从 `gwbKernel.dataDir` 取
- 卸载时清理自己启动、创建的东西；异步的清理把 promise 从 effect 的清理函数里返回出来，内核退出时等的就是它
- 和别的插件只经服务和命令交互

## 不负责的事

- 内核应用不提供安装接口，也不带 pnpm：装插件、升级插件由插件管理的 `plugin-manager.*` 命令做；插件之间的依赖齐不齐，内核应用不核对
- 内核应用不监听 `cordis.yml` 的改动：include 只在有 `hmr` 服务时才监听文件，内核不提供这个服务。运行中加载、卸载插件要经 loader 的条目树（[home 布局与条目树](/docs/seams/home)）
- 内核应用不判断插件加载成功没有：以 cordis 给这个条目的 fiber 状态为准，`ACTIVE` 才算；没有外壳时只读状态页列出每个条目加载到哪一步
- 插件不管自己的包放在哪、怎么被找到

## 测试

`apps/desktop/tests/bare-import.test.ts` 在临时目录里手写 `node_modules` 布局，证明普通包与带 scope 的包都解析得到、junction 换指向后拿到新版本、包不存在时报错里带着 `node_modules` 下的那条路径。`apps/desktop/tests/main.test.ts` 用真的 loader 与 include 从临时 home 的 `cordis.yml` 加载测试插件，证明插件出错不退出、退出时先卸载插件树。运行中换版本后重新加载，只能在隔离 home 里实机验证（[开发](/docs/develop#在隔离-home-里验证)）。
