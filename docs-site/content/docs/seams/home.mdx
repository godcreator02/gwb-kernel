**本页回答**：内核和 plugin-manager 之间交换什么、各保证什么；为什么这条接缝的另一边放在内核仓。plugin-manager 自己怎么分块、每块功能怎么工作，见[插件管理](/docs/plugin-manager)。

<Diagram name="plugin-home" title="只有 plugin-manager 写 home：包经 pnpm，条目经 loader 的条目树">
- 左边是 plugin-manager 用到的两样：从自己的条目上取的条目树（`EntryTreeLike`）、唯一运行 pnpm 的入口 `applyToHome`
- 右边是内核里对应的两样：loader 与 include（条目树的结构、读写 `cordis.yml`）、按真实路径解析包名
- 跨过接缝的是条目树的 `create` / `update` / `remove` / `resolve`——loader 没写进文档的内部结构
- 下面是 home：`applyToHome` 经 pnpm 改 `package.json` 与 `node_modules`；条目树写回 `cordis.yml` 并当场加载；loader import 包名时按真实路径读 `node_modules`
- 条目树的结构、home 的布局、解析规则都由内核决定，所以 plugin-manager 和内核放在同一个仓，测试一起跑
</Diagram>

改 `cordis.yml` 只走这棵树：它把写回文件和当场加载一起做；绕过它直接写文件，内存里的条目不知道，下一次写回会把磁盘上的改动覆盖掉。

## 两边各保证什么

内核保证：
- home 的布局：`package.json` 列出装了哪些包，`cordis.yml` 列出条目，包在 `node_modules`（见[插件与内核](/docs/seams/plugins)）
- loader 与 include 的版本固定在 `apps/desktop/package.json`；升级它们时先跑 plugin-manager 的测试
- 包名按真实路径解析：包换了版本、真实路径跟着换，停用再启用就能拿到新版本

plugin-manager 保证：
- **只有它写 home**：所有 `pnpm add` / `pnpm remove` 都经同一个入口 `applyToHome` 排进串行队列（见[唯一写入者](/docs/plugin-manager/home#只有插件管理写-home)）
- 升级与重新加载在**同一条命令**里做完，自己排在最后、回执发出之后才重新加载自己（见[热升级](/docs/plugin-manager/upgrade)、[重新加载一条条目](/docs/plugin-manager/remount)）
- 卸载先删条目、后卸包，pnpm 失败不回滚；数据与设置留在磁盘上（见[卸载](/docs/plugin-manager/install#卸载先删条目后卸包)）
