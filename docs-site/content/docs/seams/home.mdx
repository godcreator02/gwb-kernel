- 下面是 home：`applyToHome` 经 pnpm 改 `package.json` 与 `node_modules`；条目树写回 `cordis.yml` 并当场加载；loader import 包名时按真实路径读 `node_modules`
- 条目树的结构、home 的布局、解析规则都由内核决定；plugin-manager 内置在内核里，和内核同仓、测试一起跑

## 接口

对调用方，plugin-manager 是 12 条命令，参数与回执见[对外只有命令](/docs/plugin-manager/commands)。

对内核，plugin-manager 是一个内置插件：内核把它作为 loader **根层的条目**加载（和命令插件一样，都排在承载 `cordis.yml` 的 include 条目之前），它不是 `cordis.yml` 里的条目。有了自己的条目，数据插件、说明书插件这类按调用方条目认身份的服务才认得出它。内核经 config 告诉它两个字符串——那条 include 条目的 id 与 pnpm 可执行文件的路径：

**用到时再取**：plugin-manager 从自己条目所在的那一层（loader 根层）按 config 给的 id 找到 include 条目，取它的子树。它加载时 include 条目排在后面、子树还没建好，所以不在构造时取；取的时候用构造时保存的它自己的 ctx，用调用方的会取到别人条目所在的那一层。按 loader 自己的类型 `EntryTree` 取，再赋给上面的收窄接口：loader 改了这几个方法的签名，类型检查就在这里失败。

条目 id 的前缀（`home`）也不用猜：plugin-manager 要条目的完整 id 时，读 loader 条目对象上已经拼好前缀的 `id`。

改 `cordis.yml` 只走这棵树：它把写回文件和当场加载一起做；绕过它直接写文件，内存里的条目不知道，下一次写回会把磁盘上的改动覆盖掉。

## 两边各保证什么

内核保证：
- 命令插件与 plugin-manager 作为 loader 根层的条目、排在承载 `cordis.yml` 的 include 条目之前加载；plugin-manager 的 config 是 `{ home, pnpm }`
- home 的布局：`package.json` 列出装了哪些包，`cordis.yml` 列出条目，包在 `node_modules`（见[插件与内核](/docs/seams/plugins)）
- loader 与 include 的版本固定在 `apps/desktop/package.json`；升级它们时先运行 plugin-manager 的测试
- 包名按真实路径解析：包换了版本、真实路径跟着换，停用再启用就能拿到新版本

plugin-manager 保证：
- **只有它写 home**：所有 `pnpm add` / `pnpm remove` 都经同一个入口 `applyToHome` 排进串行队列（见[唯一写入者](/docs/plugin-manager/home#只有插件管理写-home)）
- 升级与重新加载在**同一条命令**里做完（见[热升级](/docs/plugin-manager/upgrade)、[重新加载一条条目](/docs/plugin-manager/remount)）；它自己与命令插件不在 home 里，不在它升级、重新加载的范围内
- 卸载先删条目、后卸包，pnpm 失败不回滚；数据与设置留在磁盘上（见[卸载](/docs/plugin-manager/install#卸载先删条目后卸包)）

## 代码从哪读

`plugins/plugin-manager/src/tree.ts` 是条目树这份约定的全部；`index.ts` 的 `PluginManagerConfig` 是内核交来的全部；用条目树的地方在 `index.ts` 与 `remount.ts`。
