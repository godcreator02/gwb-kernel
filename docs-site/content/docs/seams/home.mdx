**本页回答**：内核应用对写 home 的插件管理承诺了哪几样；home 里的包清单、条目清单与 `node_modules/` 归谁写（其余文件见总表）；这几样变了，插件管理和别的插件怎样发现。插件管理自己怎么装包、怎么改条目，写在 `gwb-lifecycle-plugins` 仓的文档站。

## 连接的模块

- [内核应用](/docs/desktop)：决定 home 的文件布局；带着 loader 与 include，条目树的形状、`cordis.yml` 怎么读写都由这两个包决定；按真实路径解析包名
- 插件管理 `@godcreator/gwb-plugin-manager`（生命周期插件仓 `gwb-lifecycle-plugins`）：`cordis.yml` 里的普通插件，也是唯一写 home 的包与条目的插件——经 loader 的条目树改 `cordis.yml`，运行机器上的 pnpm 改 `package.json` 与 `node_modules/`

## 接口

**home 的文件布局**：home 里每个文件谁写、谁读，总表在[插件之间怎么连](/docs/wiring#home-布局与文件)。这条接缝管其中与插件管理有关的三样：

| 文件 | 谁写 |
| --- | --- |
| `package.json` | 列出装了哪些包：内核包 `@godcreator/gwb-kernel-desktop`、内核包 peer 里那个版本的 `cordis`、各个插件。清单照 pnpm 默认写 `^` 范围，只有 `cordis` 写精确版本号。由创建 home 的一方写好（安装步骤 `INSTALL.md` 或 `devkit.home.new`），缺了内核启动失败、不补；之后只由插件管理运行的 pnpm 改 |
| `cordis.yml` | 列出条目。由创建 home 的一方写好，缺了内核启动失败、不补；之后由 include 写回，写回只经条目树发生 |
| `node_modules/` | pnpm，由插件管理调用 |

**cordis 只有一份，loader 与 include 不在 home 根上**：内核包把 `cordis` 写在 peer 里、写精确版本号，由 home 清单里列的那一份满足，loader、include 与在 peer 里写 `cordis` 的插件都解析到它。loader 与 include 是内核包自己的依赖，同样写精确版本号、不带范围，随内核包一起装进 home：

**条目树**：loader 服务 `ctx.loader` 上的 `create` / `update` / `remove` / `resolve` 与 `root`，以及条目带前缀的 `id`。它没有写进 `gwbKernel`，也没有写进内核包导出的类型：它的形状就是上面这两个版本的 loader 与 include 的内部结构，换版本就可能变。loader 根层只有一条 include 条目，id 是 `home`，`cordis.yml` 里的条目都在它的子树里（[插件加载](/docs/seams/loading)）。

**按真实路径解析包名**：包换了版本，`node_modules/<包名>` 的真实路径跟着换，停用再启用那条条目就拿到新版本（规则见[插件加载](/docs/seams/loading)）。

## 约定

**内核应用**保证：

- home 的文件布局如[总表](/docs/wiring#home-布局与文件)；启动时 `package.json` 与 `cordis.yml` 缺一个就启动失败，报错写明缺哪个、home 在哪，内核不补、也不改这两个文件
- `cordis` 写在内核包的 peer 里，loader 与 include 写在内核包的依赖里，版本都如内核包清单所写
- 包名一律从 home 的 `node_modules` 按真实路径解析，不从内核自己的目录找
- 上面任何一样变了（包括升级 `cordis`、loader、include 的版本），就是改了这条接缝，内核版本号升 x（[开发](/docs/develop#发版)）

**插件管理**保证：

- **改 `cordis.yml` 只走条目树**：条目树把写回文件和当场加载、卸载一起做；绕过它直接写文件，内存里的条目不知道，下一次写回会把磁盘上的改动覆盖掉
- **只有它写 home 的包**：`package.json` 与 `node_modules/` 只经它运行的 pnpm 改；别的插件只写归自己的数据（哪个文件归谁见[总表](/docs/wiring#home-布局与文件)）
- **home 根上的 `cordis` 等于内核包 peer 里写的版本**：升级全部插件或指定几个插件时不动内核包与 `cordis`；指定换内核包时它把 `cordis` 一起对齐到新内核包 peer 里的版本，装完要重启工作台才生效

### 兼容性怎么发现

插件在自己 `package.json` 的 peer 里写内核包的 `^` 范围，插件管理拿它和运行中的内核版本比对、把范围不包含的插件标出来（[插件在 peer 里写兼容哪个内核](/docs/design#插件在-peer-里写兼容哪个内核)）。内核升级之后看这张表，就知道哪些插件要复查。

## 不负责的事

- 内核应用不知道插件管理存在：loader 与 include 照常读写 `cordis.yml`、加载条目，不为插件管理留任何接口；home 里没有插件管理时，运行中就没人能装包、改条目
- 内核应用不带 pnpm，不装包、不升级包
- 内核应用不读插件 peer 里的内核包范围：范围不包含当前内核的插件照常加载
- 插件管理不决定 home 的布局、条目树的形状、包名怎么解析

## 测试

`apps/desktop/tests/main.test.ts` 保护内核准备 home 的那部分：名字与路径两种写法选定 home，userData 设在 `<home>/electron`，缺 `package.json`、`cordis.yml`（缺两个或只缺一个）时启动失败、报错写明缺哪个，不补文件。包名解析的测试见[插件加载](/docs/seams/loading)。条目树的形状由插件管理那边保护：`gwb-lifecycle-plugins` 仓里用与内核相同版本的 loader、include 建一个 home 运行条目树的测试，内核升级这两个包、改了条目树的形状时，那组测试最先失败。
