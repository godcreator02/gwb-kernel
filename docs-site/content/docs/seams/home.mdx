**本页回答**：插件管理和 loader、include 之间交换什么——条目树的哪几个方法、从哪一层取、什么时候取；它依赖 home 的哪些文件布局；两边各保证什么；怎么单独测。插件管理自己怎么分块、每个机制怎么工作，见[插件管理](/docs/plugin-manager)。

## 两侧

- 一侧是[插件管理](/docs/plugin-manager)：唯一写 home 的插件
- 另一侧是[内核应用](/docs/desktop)里的 loader 与 include（`@cordisjs/plugin-loader`、`@cordisjs/plugin-include`，版本固定在 `apps/desktop/package.json`）：条目树的结构、读写 `cordis.yml`；以及内核决定的 home 布局与包名解析规则

- 左边是插件管理用到的两样：从自己条目所在的那一层取出的条目树（`EntryTreeLike`）、唯一运行 pnpm 的入口 `applyToHome`

- 条目树的结构、home 的布局、解析规则都由内核决定；插件管理内置在内核里，和内核同仓、测试一起跑

## 两边各保证什么

内核一侧保证：
- 承载 `cordis.yml` 的 include 条目和插件管理在 loader 的同一层（根层），id 经 config 交来
- `create` / `update` / `remove` 把写回 `cordis.yml` 与当场加载、卸载一起做；`update` 的值给 `null` 是删掉那个字段
- home 的布局如上；布局与 home 里有什么的全貌见[插件加载](/docs/seams/loading)
- 包名按真实路径解析：包换了版本、真实路径跟着换，停用再启用就能拿到新版本
- loader 与 include 的版本固定在 `apps/desktop/package.json`；升级它们时先运行插件管理的测试

插件管理保证：
- **改 `cordis.yml` 只走条目树**：它把写回文件和当场加载一起做；绕过它直接写文件，内存里的条目不知道，下一次写回会把磁盘上的改动覆盖掉
- **只有它写 home**：所有 `pnpm add` / `pnpm remove` 都经同一个入口 `applyToHome` 排进串行队列（见[唯一写入者](/docs/plugin-manager/home#只有插件管理写-home)，pnpm 这一侧见 [pnpm](/docs/seams/pnpm)）
- 升级与重新加载在**同一条命令**里做完（见[热升级](/docs/plugin-manager/upgrade)、[重新加载一条条目](/docs/plugin-manager/remount)）；它自己与命令插件不在 home 里，不在它升级、重新加载的范围内
- 卸载先删条目、后卸包，pnpm 失败不回滚；数据与设置留在磁盘上（见[卸载](/docs/plugin-manager/install#卸载先删条目后卸包)）

## 一侧不管什么

- loader 与 include 不知道插件管理的存在：它们照常读写 `cordis.yml`、加载条目，不为插件管理留任何接口
- 插件管理不猜 include 条目叫什么、不自己拼完整 id，都从内核给的 config 和条目对象上读
- 插件管理不管条目加载成没成功：`create` 只等写入、不等加载，成没成功看 `list` 的 `active`（见[安装与卸载](/docs/plugin-manager/install#建条目只等写入不等加载)）

## 代码从哪读

`plugins/plugin-manager/src/tree.ts` 是条目树这份约定的全部；`index.ts` 的 `tree` 取值器与 `fullId` 是用到它的入口，用条目树的地方在 `index.ts` 与 `remount.ts`；读 home 清单在 `home.ts`。内核一侧的顺序与 config 在 `apps/desktop/src/main.ts` 的 `root.update`。
