**本页回答**：内核应用对写 home 的插件管理承诺了哪几样；home 里每个文件归谁写；这几样变了，插件管理和其他插件怎么发现。插件管理自己怎么装包、怎么改条目，见 devkit 仓的文档站。

## 连接的模块

- [内核应用](/docs/desktop)（`apps/desktop`）：决定 home 的文件布局；带着 loader 与 include（`@cordisjs/plugin-loader`、`@cordisjs/plugin-include`），条目树的形状、`cordis.yml` 怎么读写都由这两个包决定；按真实路径解析包名
- 插件管理（`@godcreator/gwb-plugin-manager`，在 devkit 仓，和 devkit 一起开发）：`cordis.yml` 里的普通插件，也是唯一写 home 的插件——用 loader 的条目树改 `cordis.yml`，用机器上装好的 pnpm 12（两个固定位置之一，见 devkit 仓文档站「插件管理的 pnpm」）改 `package.json` 与 `node_modules/`

## 接口

**home 的文件布局**：home 里每样东西归谁写，全站只在这里列一份：

| 文件 | 谁写 |
| --- | --- |
| `package.json` | 列出装了哪些包：内核包 `@godcreator/gwb-kernel-desktop`、内核包 peer 要的那个版本的 `cordis`、各个插件。缺了内核补一份最小清单（从仓里启动一个新 home 时会缺）；之后归插件管理（经它运行的 pnpm） |
| `cordis.yml` | 列出条目。缺了内核补一个空表，之后归 include 和插件管理 |
| `node_modules/` | pnpm，由插件管理调用 |
| `gwb.log`、`gwb.log.1` | 内核（见[日志](/docs/seams/log)） |
| `runtime.json` | 内核每次启动整份重写，退出时不删（见 [runtime.json](/docs/seams/runtime)） |
| `electron/` | Chromium 的 userData，每个 home 一份（见[内核应用](/docs/desktop)） |
| 其余目录 | 各插件自己的数据 |

**home 根上只有一份 cordis**：内核包把 `cordis` 写成 peer、版本写死，由 home 清单里列的那一份满足；loader、include 与写 peer `cordis` 的插件也解析到这同一份。**loader 与 include 不在 home 根上**：它们是内核包自己的依赖，版本同样写死、不带范围，随内核包一起装进 home：

**条目树**：loader 条目的 `create` / `update` / `remove` / `resolve`，以及条目对象上带前缀的 `id`。它既没有写进 `gwbKernel`，也没有写进内核包导出的接口类型：它的形状就是上面这两个版本的 loader 与 include 的内部结构，换版本就可能变。loader 根层只有一条 include 条目，id 是 `home`，`cordis.yml` 里的条目都在它的子树里（见[插件加载](/docs/seams/loading)）。

**按真实路径解析包名**：loader import 一个包名时，内核应用从 `<home>/node_modules/<包名>` 的真实路径开始解析；包换了版本、真实路径跟着换，停用再启用这条条目就拿到新版本。解析规则见[插件加载](/docs/seams/loading)。

## 约定

内核应用保证：
- home 的文件布局如上表；`package.json` 与 `cordis.yml` 只在缺的时候补，已有的不覆盖
- `cordis` 写在内核包的 peer 里，loader 与 include 写在内核包的依赖里，版本都如 `apps/desktop/package.json` 所写；条目树的形状随 loader 与 include 的版本走
- 包名一律从 home 的 `node_modules` 按真实路径解析，不从内核自己的目录找
- 上面这些任何一样变了（包括升级 `cordis`、loader、include 的版本），就是内核改了对外承诺：内核版本号升 x（0.x 的第二位）

插件管理保证：
- **改 `cordis.yml` 只走条目树**：条目树把写回文件和当场加载、卸载一起做；绕过它直接写文件，内存里的条目不知道，下一次写回会把磁盘上的改动覆盖掉
- **只有它写 home**：`package.json` 与 `node_modules/` 只经它运行的 pnpm 改；别的插件不写这两样，也不写 `cordis.yml`，只写自己的数据目录
- **内核包与 `cordis` 按精确版本装**：home 根上的 `cordis` 等于内核包 peer 里写的那个版本；一键热升级不动这两个包，由单独的升内核命令一起装，装完重启才生效

### 兼容性怎么发现

每个插件在自己 `package.json` 的 `peerDependencies` 里写内核包 `@godcreator/gwb-kernel-desktop` 的 `^` 范围。插件管理的 `plugin-manager.list` 把它和运行中的内核版本（`gwbKernel.version`）比对，范围不包含的标出来（[插件在 peer 里写兼容哪个内核](/docs/design#插件在-peer-里写兼容哪个内核)）。内核升级之后看这张表，就知道哪些插件要复查。

## 不负责的事

- 内核应用不知道插件管理的存在：loader 与 include 照常读写 `cordis.yml`、加载条目，不为插件管理留任何接口；home 里没有插件管理时，运行中就没人能装包、改条目
- 内核应用不带 pnpm，不装包、不升级包
- 内核应用不读插件 peer 里的内核包范围：范围不包含当前内核的插件照常加载，比对只在插件管理里做
- 插件管理不决定 home 的布局、条目树的形状、包名怎么解析

## 测试

`apps/desktop/tests/main.test.ts` 保护内核准备 home 的那部分：缺 `package.json`、`cordis.yml` 时补最小形态，已有的不覆盖，userData 设在 `<home>/electron`；包名解析的测试见[插件加载](/docs/seams/loading)。条目树的形状由插件管理那边保护：devkit 仓里用与内核相同版本的 loader、include 搭一个 home 跑条目树的测试，内核升级这两个包、改了条目树的形状，那组测试最先失败。
