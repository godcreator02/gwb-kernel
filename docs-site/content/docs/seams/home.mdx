**本页回答**：内核和 plugin-manager 之间交换什么、各保证什么；为什么这条接缝的另一边放在内核仓；过渡期里还留着哪些做法。plugin-manager 自己怎么分块、每块功能怎么工作，见[插件管理](/docs/plugin-manager)。

<Diagram name="plugin-home" title="只有 plugin-manager 写 home：一次 pnpm，再经 loader 条目树改 cordis.yml">
- 两侧：内核决定 home 的布局、注册 loader 与 include、按真实路径解析包名；plugin-manager 是唯一写 home 的插件
- 交换的东西：loader 条目树（`create` / `update` / `remove` / `resolve` 与 `store`，loader 没写进文档的内部结构）、home 里的 `package.json` / `node_modules` / `cordis.yml`
- 安装：调用 `plugin-manager.install` → 经 `applyToHome` 一次 `pnpm add` → 经条目树 `create` 写回 `cordis.yml` 并当场加载，loader import 包名时由内核按真实路径解析
- 热升级：`outdated` 查出过期包 → 一次 `pnpm add` 精确版本 → 同一条命令里逐条停用再启用（真实路径换了，重新解析就是新版本；plugin-manager 自己最后）→ `shell.reload` 整页重新加载
- 换这一边：plugin-manager 的源码在内核仓 `plugins/plugin-manager/`，内核升级 loader 或改解析方式时，它的测试一起跑
</Diagram>

## 两边各保证什么

内核保证：
- home 的布局：`package.json` 列出装了哪些包，`cordis.yml` 列出条目，包在 `node_modules`（见[插件与内核](/docs/seams/plugins)）
- loader 与 include 的版本固定在 `apps/desktop/package.json`；升级它们时先跑 plugin-manager 的测试
- 包名按真实路径解析：包换了版本、真实路径跟着换，停用再启用就能拿到新版本

plugin-manager 保证：
- **只有它写 home**：所有 `pnpm add` / `pnpm remove` 都经同一个入口 `applyToHome` 排进串行队列（见[同一时刻只允许一个改动](/docs/plugin-manager/pnpm#同一时刻只允许一个改动)）
- 升级与重新加载在**同一条命令**里做完，自己排在最后、回执发出之后才重新加载自己（见[一键热升级](/docs/plugin-manager/upgrade#一键热升级)）
- 卸载先删条目、后卸包，pnpm 失败不回滚；数据与设置留在磁盘上（见[卸载](/docs/plugin-manager/install#卸载)）

## 过渡期里还留着的做法

peer 提升、peer 版本警告、「库不加条目」这三样，是替还没改成[关键判据 K2](/docs/criteria/k2)、[K3](/docs/criteria/k3) 写法的插件留的：今天块笔记插件的页面代码直接 import `@godcreator/block-note`，这个名字靠 block-note 声明的 `gwb.shared` 进 importmap，而内核只从 home 的直接依赖收集 importmap。K2、K3 执行完就删，那是破坏性变更，要升 plugin-manager 的 x。各自做什么见[安装与卸载](/docs/plugin-manager/install#过渡期的-peer-那一步)。

## 怎么单独测

`tests/loader.test.ts` 用内核实际使用的 loader 与 include 版本，照 `main.ts` 的顺序搭一个 home，把上面这份约定跑一遍：取条目树与自己的 entryId、`create` / `update` / `remove` 写回 `cordis.yml`、停用再启用后 `ACTIVE`；另断言这几个版本和 `apps/desktop` 一致。其余测试见[插件管理](/docs/plugin-manager#怎么测)。

## 代码从哪读

`plugins/plugin-manager/src/tree.ts` 是这份约定的全部；用它的地方在 `index.ts` 与 `remount.ts`。
