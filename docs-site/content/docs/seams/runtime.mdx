**本页回答**：`runtime.json` 里写了什么、什么时候写、谁读；内核应用和读它的程序各保证什么。

## 连接的模块

- [内核应用](/docs/desktop)：启动时写这份文件
- 工作台进程之外的读者，都不在本仓：
  - **devkit**（插件 `@godcreator/gwb-devkit` 的命令）：按 home 名找到一个正在运行的工作台时，从这份文件取调试端口，并用 `pid` 确认进程还在；删除运行中的 home 时按 `pid` 找到要结束的进程
  - **安装工作台的 agent**：照仓根 `INSTALL.md`（正本 `docs-site/content/outputs/install.mdx`）轮询这份文件判断这次启动写好了，核对 `version`，用 `pid` 关闭窗口

两边之间没有代码接口：字段名写在内核的 `main.ts` 里，读者在各自的仓里按名字读。

## 接口

文件在 home 根上：`<home>/runtime.json`，两个空格缩进的 JSON，末尾一个换行。内核写的字段：

{/* ref file="../apps/desktop/src/main.ts" lines="92-122" */}

| 字段 | 内容 |
| --- | --- |
| `pid` | 内核主进程的进程号 |
| `startedAt` | 启动时刻，毫秒时间戳 |
| `version` | 内核包的版本号，与 `gwbKernel.version` 相同 |
| `cdp` | Chromium 调试端口；启动时没给 `--remote-debugging-port` 就没有这个字段。给了但不是 1–65535 的整数时内核启动失败，报错带着给的原值，不写这份文件 |

调试端口只有启动进程的一方知道，页面和插件都读不到，所以由内核写下来。没开调试端口时不写这个字段，而不是写 0 或 `null`：读的一方只看字段在不在。

MCP 入口插件 `@godcreator/gwb-mcp` 在端口开好之后往同一份文件里补一个 `mcp` 字段（MCP 入口的地址）。文件在上一次运行之后一直留着，所以只看 `mcp` 在不在会把上一次的地址当成这一次的；安装工作台的 agent 同时核对 `startedAt` 晚于它启动的时刻、`pid` 是活着的进程。

## 约定

**内核应用**保证：

- **每次启动整份重写**：上一次运行留下的字段（包括别的插件补写的）都被覆盖。这一份描述的是当前这个进程
- 同一个 home 已有实例在运行时，第二个实例拿不到单实例锁就退出，不动这份文件：`app.exit(1)` 当场结束进程，后面写文件的代码不会执行（测试用的假 electron 模拟不出这一点，靠隔离 home 里实机验证）
- 退出时不删；写不进时启动失败，错误框与日志写明文件路径与原因：读者靠这份文件找到运行中的工作台，照常启动却没写进这份文件，读者就找不到它

**读者**保证：

- **自己确认进程还在**：崩溃、被结束的进程来不及清理，这份文件总留着上一次的内容。至少核对 `pid` 是活着的进程；要用调试端口的，还要核对这个端口确实属于这个 `pid`
- 文件不在、读不出、内容不完整时当成「没有在运行」，不报错退出

**往这份文件补字段的插件**（如 `@godcreator/gwb-mcp`）保证：先读、合并、再写回，保留自己不认识的字段；整份覆盖会抹掉内核写的那几项。

## 不负责的事

- 内核应用自己不读 `runtime.json`，也不知道谁在读
- 内核应用不给这份文件加锁，也不保证原子写入
- 读者不能用它判断「这个 home 装好没有」：那是 `cordis.yml` 与 `node_modules` 的事

## 测试

`apps/desktop/tests/main.test.ts` 保护内核写文件的那一段：写哪几个字段、每次整份重写、没给调试端口时没有 `cdp`、给了合法端口时写进 `cdp`、给的不是 1–65535 的整数或文件写不进时启动失败。读者那一侧没有代码接口，只能实机验证（[开发](/docs/develop#在隔离-home-里验证)）：带 `--remote-debugging-port=<端口>` 在隔离 home 里启动，`pid` 是正在运行的内核进程、`cdp` 是给的那个端口，关掉工作台后文件还在。
