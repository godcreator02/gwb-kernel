**本页回答**：`runtime.json` 里写了什么、什么时候写、谁读；内核应用和读它的程序各保证什么。

## 连接的模块

- [内核应用](/docs/desktop)：启动时写这份文件
- 工作台进程之外的读者，不在本仓：
  - **devkit**（插件 `gwb-devkit` 的命令）：在一个工作台里按 home 名连接另一个正在运行的工作台时，从这份文件取调试端口，并用 `pid` 确认进程还在；删除一个 home 时按 `pid` 找到要结束的进程
  - **安装工作台的 agent**：照 `INSTALL.md` 安装，第 4 步轮询到 `mcp` 字段出现就算启动完成，核对 `version`；用 `pid` 关闭窗口（正本 `docs-site/content/outputs/install.mdx`）

内核应用与读者之间没有代码接口，只靠这份约定：字段名写在内核的 `main.ts` 里，读者在各自的仓里按名字读。

## 接口

文件在 home 根上：`<home>/runtime.json`，两个空格缩进的 JSON，末尾一个换行。内核写这几项：

| 字段 | 内容 |
| --- | --- |
| `pid` | 内核主进程的进程号 |
| `startedAt` | 启动时刻，毫秒时间戳 |
| `version` | 内核的版本号，与 `gwbKernel.version` 相同 |
| `appDir` | 应用目录，即 Electron 的 `app.getAppPath()`：从安装包启动是启动器所在的 `resources\app.asar`，从仓里 `pnpm start` 运行是 `apps/desktop` |
| `cdp` | Chromium 调试端口；启动时没给 `--remote-debugging-port` 就没有这个字段 |

调试端口只有启动进程的一方知道，页面和插件都读不到，所以要由内核写下来。没开调试端口时不写这个字段，而不是写 0 或 `null`：读的一方只要看字段在不在，不用再判断这个值有没有意义。

MCP 入口插件 `gwb-mcp` 在它的端口开好之后往同一份文件里补一个 `mcp` 字段（MCP 入口的地址）；安装工作台的 agent 就是等这个字段出现来判断工作台启动完成。

## 约定

内核应用保证：
- **每次启动整份重写**：上一次运行留下的字段（包括别的插件补写的）都会被覆盖。home 里的 `package.json`、`cordis.yml` 是缺了才补，这一份不同，它描述的是当前这个进程
- 同一个 home 已有实例在运行时，第二个实例拿不到单实例锁就退出，**不动**这份文件
- 退出时不删；写入失败只记一条 warn，不影响启动

{/* ref file="../apps/desktop/src/main.ts" lines="78-81" */}

读者保证：
- **自己确认进程还在**：文件在不等于工作台在运行——崩溃、被结束的进程来不及清理，这份文件总是留着上一次的内容。至少核对 `pid` 是一个活着的进程；要用调试端口的，还要核对这个端口确实属于这个 `pid`
- 文件不在、读不出、内容不完整时当成「没有在运行」，不报错退出

往这份文件补字段的插件（如 `gwb-mcp`）保证：先读、合并、再写回，保留自己不认识的字段；整份覆盖会抹掉内核写的那几项。

## 不负责的事

- 内核应用自己不读 `runtime.json`，也不知道谁在读
- 内核应用不给这份文件加锁，也不保证原子写入
- 读者不能用它判断「这个 home 有没有装好」：那是 `cordis.yml` 与 `node_modules` 的事
