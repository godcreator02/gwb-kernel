# 写一个件

内核认的东西非常少。下面这些就是全部。

## 最小的一个件

一个件就是一个普通的 npm 包，装在 `<home>/node_modules` 下：

```json
{
  "name": "@you/thing",
  "version": "0.0.1",
  "type": "module",
  "exports": { ".": "./index.js" }
}
```

```js
export const name = 'thing'

export function apply(ctx) {
  // ctx 是 cordis 的 Context。你在这里注册服务、挂监听、开东西
}
```

`apply` 的签名与语义全归 cordis，不归这个内核——内核只负责把模块 `import` 进来交给
`ctx.plugin`。

## 让它被挂上

`<home>/cordis.yml` 是条目表，顶层是一个数组：

```yaml
- id: thing
  name: "@you/thing"
  config:
    port: 2870
- id: 先关着的
  name: "@you/other"
  disabled: true
```

`name` 要写**完整包名**。`config` 原样交给 `apply` 的第二个参数。`disabled: true` 的条目不挂。

**`id` 一律手写一个短名。** 不写的话 loader 当场发一个 8 位随机十六进制串
（`Math.random().toString(16).slice(2, 10)`），**而且首次加载不写回 yml**——它会一直漂到
某次 `write()` 才固化，在那之前每次启动都是新的。按条目身份存东西的件（外壳的窗格布局、
设置件的 home 级设置）于是每次都对不上，而那是**静默的**：没有报错，只是东西没了。

同一个包可以挂**多条**条目，各是一份独立的配置与 fiber——但 id 必须不同，而且
**provide 服务的件挂不了两条**（第二条 provide 同名服务会当场抛）。

**新 home 首启时内核会建一份空表 `[]`**——那是「一个件都没装」的表达，也是 home 起得来的
最小形态（读不到这个文件的话 `include` 会抛，宿主整个退出）。除此之外它不会替你写任何条目。

### 包清单里内核只读一个字段

**`gwb.shared`**（我给页面提供这几个裸名），下面「运行时环境」那节讲。除此之外的
`gwb.*` 内核一个都不读——`pluginMeta` 连解析都不解析。

**件的其余声明全走运行时**：我是外壳（provide `gwbShell`）、我叫什么
（`ctx.gwbShell.describeSelf`）、我有哪几格窗格（`registerPane`）。

`shared` 留在清单里是**硬的，不是还没搬**：共享包**不是件**——它在 home 的
`dependencies` 里但不在 `cordis.yml` 里，没有 `apply`、没有 fiber、没有 ctx，压根没有
运行时可言。而且 importmap 必须赶在第一句动态 import 之前注入，比任何运行时都早：
共享包的运行时只能靠 import 它自己跑起来，而那一句 import 就已经晚了。

所以**给人看的东西别往包清单里放**。曾经有过一个 `gwb.title`，四个包都写着，而它从来
没有过读者；这种字段死掉的时候没有任何机制会发现，因为「没人读」跟「读了没用上」在
盘上长得一模一样。运行时那条路上，少一个消费方是当场看得见的。

## 界面那半

件要在窗口里画东西，就多导出一个 `./client` 子路径：

```json
{
  "exports": {
    ".": "./index.js",
    "./client": "./client.js"
  }
}
```

页面按这条 URL 取它：

```
gwb://asset/plugins/<完整包名>/<exports 子路径>
```

末尾那段就是 `exports` 表里的键去掉开头那两个字符（`./client` → `client`）。包名带 scope
是两段，所以规则是「`@` 开头吃两段、否则吃一段，剩下的全是子路径」。

**不在 `exports` 里的文件一概取不到**——那张表是内核唯一的取址依据。想把样式表交出去，
就得把它也列进 `exports`。

`client.js` 由浏览器直接加载、不经过打包器。裸名 `import` 只有一种情况能用：**那个名字在
页面的 importmap 里**（见下一节）。其余依赖一律打进自己这一份束——外置成裸名而 importmap
里没有它，就是运行期一句 `Failed to resolve module specifier`。

## 运行时环境：`gwb.shared`

浏览器里 `import 'react'` 这种裸名，只有 importmap 说得出它在哪。这张表由**内核**在页面
起步时拼好注入——内核不认识 `react` 这个词，它只搬运声明。

**提供方**在包清单里说「我给页面提供这几个裸名」，值是自己的 `exports` 子路径：

```json
{
  "gwb": {
    "shared": {
      "react": "./react",
      "react-dom/client": "./react-dom-client"
    }
  }
}
```

内核扫 `<home>/package.json` 的 `dependencies`，把所有这类声明收齐拼成一张 importmap。
**扫的是 home 清单不是条目表**——提供运行时的包通常不是件，它不在 `cordis.yml` 上。

三条要记住的：

- **一个裸名只许一个提供方**。撞了内核报出来、只认先来的那个；浏览器那边后注的表本来
  也覆盖不掉已经解析过的名字，静默让谁赢的结果是「页面上跑的是哪一份说不清」
- **提供运行时的包必须装在 home 顶层**（`pnpm add` 进去）。内核按包名直接拼路径找它，
  不走 node 的解析算法，只在 `.pnpm` 里躺着的包它够不着
- npm 上的 `react` **不能直接用**——它至今没有 ESM 出口。要有人把它打成 ESM 再发一个包出来

## 样式

件的样式表跟 `client.js` 走同一条路：列进 `exports`，件自己注 `<link>`。

```json
{
  "exports": {
    "./client": "./client.js",
    "./style.css": "./dist/style.css"
  }
}
```

**注了不等于到位**：`<link>` 是异步取的，束里第一帧 DOM 完全可能落在表到位之前，那一瞬间
是一堆没有样式的裸元素。等 `link.onload` 再渲染。

设计令牌（颜色、圆角那些 CSS 变量）共享一份，件的表里只有 `var(--background)` 这样的引用。
所以**换主题＝换那一份值，所有件当场跟着变，一个都不用重新构建**。件的表整张 scope 在
`[data-gwb-plugin="<完整包名>"]` 之下，容器上不挂这个属性，一个类名都不生效。

## 组件怎么来

**每个件自己从 shadcn 官方拉**。件里放一份 `components.json`，然后就是一行命令：

```
pnpm dlx shadcn@latest add button
```

**没有「工作台的组件库」这种东西，也不建 registry。** 件之间的组件不需要一致 —— shadcn 的
组件源码本来就是给你改的，A 件的 button 跟 B 件的不一样完全没关系。**统一风格由令牌保证，
不由组件源码一致保证**，这两层是正交的。

各件的组件版本会随着各自拉取的时间漂移，那正是想要的：件独立发版，各自决定什么时候跟进。

配置上有三处要对齐，`@/` 一律指向 `src/client`：

| 在哪 | 配什么 |
| --- | --- |
| `components.json` 的 `aliases` | `@/components`、`@/components/ui`、`@/lib`、`@/lib/utils` |
| 两份 `tsconfig.json`（件根一份给 CLI 读、`src/client` 一份给 typecheck） | `paths: { "@/*": [...] }` |
| 打包器 | esbuild 的 `alias`，指同一个目录 |

两个容易撞的点：

- **别写 `baseUrl`** —— TS 7 把它移除了（`TS5102`），而 shadcn 文档给的还是 `baseUrl + paths`
  的老写法。TS 7 里 `paths` 直接相对 tsconfig 所在目录解析
- `components.json` 的 **`tailwind.css` 必须指一个真实存在的文件**（`tailwind` 那个对象整个是
  必填的）。件因此有一个 `src/client/styles.css` —— 它同时也是件写自己 CSS 规则的地方

## 外壳

窗口里的那个界面根只交给一个件，叫**外壳**。件这样声明自己是外壳——**provide 一个叫
`gwbShell` 的服务**：

```ts
import { Service } from 'cordis'

export default class MyShell extends Service {
  constructor(ctx) {
    super(ctx, 'gwbShell')   // ← 就这一句。内核看的是「谁 provide 了它」
  }
}
```

**不绑包名**：外壳件叫什么都行，provide 这个名字的就是。

内核认识 `gwbShell` 这一个名字——那免不了，它总得挑一个件把 `#root` 交出去。但**声明这件事
走运行时而不是包清单**，白得三样：

- **「多于一条外壳」这种局面不存在了**。cordis 的 `provide` 撞名**直接抛**，第二个 provide
  `gwbShell` 的件根本挂不上，日志里还明说撞的是谁
- **半死的外壳挑不出来**。内核只认真的挂起来了的（fiber 是 `ACTIVE`）。一个 `inject` 还没
  满足的外壳（比如它等的命令总线没装）从此报不出来，而不是让渲染层去 boot 一个跑不起来的
- 内核不用为这件事去读每个包的清单

外壳的 `client.js` 要导出 **`bootShell`**：

```js
export function bootShell(args, root) {
  root.textContent = '我拿到整页了'
  args.host.call('kernel.info').then((res) => {
    // args.host.call 是命令通道:走到宿主,分发给插件,原路回
  })
  return { dispose() { /* 这个件被卸载时,把这棵树拆干净 */ } }
}
```

`args` 里有三样：

| | 是什么 |
| --- | --- |
| `host.call(command, args?)` | 命令通道，走到宿主分发再原路回 |
| `home` | home 目录的绝对路径 |
| `entries` | 条目表，每条 `{ id, ok, pkg, disabled }`。`ok` 判的是 fiber 真的 **ACTIVE** 了，不是「fiber 建出来了」 |

加东西往 `args` 里加，签名不动。

**回一个 `{ dispose }`**：件被卸载时页面上那棵树得有人拆。眼下渲染层还不会调它（它不感知
条目变化），但契约先立着——将来要热换外壳时不必回头改所有外壳件。

### 为什么不叫 `mount`

因为**「占整页的根」和「占井里的一格」是两种件**，args 形状本来就不同：外壳拿 `entries`
（它要据此排出可开窗格表）、拿不到 `shell` 与 `pane`；窗格反过来。

共用一个动词会让人以为它俩是同一件事的两个变体，而形状对不上**只有运行时才发现**——
误读 `args.pane` 得到 `undefined`，不报错、只是行为不对。所以两个角色各用各的动词：
外壳 `bootShell`、窗格 **`mountPane`**。**你导出哪个名字，就声明了自己是哪种件。**

### 窗格那半的形状不在这儿定

`mountPane` 的 `args` 里有什么，**是外壳件说了算的**——内核只定 `bootShell`，它连「窗格」
这个概念都没有。所以那份契约的正本住**件仓的 `gwb-shell` 那页**，不在这个站上。

大意是这样，细节以那边为准：

```js
export function mountPane({ host, shell, pane }, container) {
  // host 跟外壳拿到的是同一个命令通道
  // shell 能开本件的另一格、能往格间总线发消息
  // pane.id 说这是本件的哪一格，pane.instance 说这是那一格的第几份
  return { dispose() {} }
}
```

窗格清单也归外壳：件在 `apply` 里调 `ctx.gwbShell.registerPane(…)` 注册，**不写进包清单**
（判据见[窗格清单动态注册](/docs/trajectory/2026-09-07-panes-runtime-registry)）。

渲染层启动时问内核要 `kernel.info`，里头的 `shellPkg` 就是答案——挑的活全在宿主那边，
它扫服务表找「谁 provide 了 `gwbShell` 且真的挂起来了」。

**一个都没有就是留白**：原因进 console，不在页面上解释（见[刻意不做什么](/docs/not-doing)）。
那句话会分开说两种成因——一个件都没 provide，还是有件在等它的依赖。

**「不止一条」不用处理**：那种局面到不了渲染层，cordis 的 `provide` 撞名时第二个件就挂
不上了。

## 页面的公共面：`window.gwb`

preload 在页面上挂了一个 `window.gwb`，**谁在这页上跑都够得着**——外壳、窗格件、随手在控制台
里敲的一句，都一样：

| | 是什么 |
| --- | --- |
| `command(name, args?)` | 命令通道。外壳与窗格拿到的 `args.host.call` 就是它包了一层 |
| `onEvent(cb)` | 件经 `gwbKernel.emit` 推上来的事件 |
| `logs.backlog()` | 开机到此刻的日志条目（主进程那圈环形缓冲） |
| `logs.on(cb)` | 之后的日志，**按批**推，回一个注销函数 |

`args` 里给的那几样是**外壳给窗格的额外便利**（它替你绑好了身份），不是「唯一入口」。日志
这类页面级的东西直接用 `window.gwb`——**外壳不该转发它**，它凭什么认识「日志」。

### 日志那两条为什么不走命令通道

缓冲住在主进程，而命令要从缓冲旁边路过、绕到宿主再原路背回来。更要命的是**宿主一挂命令全废**
——那恰恰是最需要看日志的时候。判据全文见[日志走 preload](/docs/trajectory/2026-09-07-logs-preload-api)。

### 条目的形状

```ts
{ seq, ts, source, level, name, msg }
```

- **`seq`** 主进程发号的单调计数，也是**唯一键**。**去重和排序都用它，别拿 `ts` 拼字符串**
  ——同一毫秒里两句一模一样的话是常事，字符串键会静默吃掉第二句
- **`source`** 是 `plugin` / `host` / `main` / `renderer` 四路之一
- **`level`** 是 `error`/`warn`/`info`/`debug`，四路给的都是真级别，没有猜出来的

**没有类型包**——按形状收，写个判形函数当运行期守卫，认不出的条目丢掉、不崩。为什么不进
词汇表包，见[条目不进词汇表](/docs/trajectory/2026-09-07-log-shape-not-in-vocab)。

### 取日志的那段舞蹈：先订阅，后取历史

```js
const off = window.gwb.logs.on((batch) => { /* 一批一批地追上去 */ })
const history = await window.gwb.logs.backlog()
// 两段按 seq 合并，交叠的那一瞬靠 seq 去重挡住
```

**顺序不能反。** 缓冲里是开机以来的整段，窗格挂载那一刻之前推的全在里面；先取历史再订阅的话，
中间那一瞬的条目会漏掉。

### 两条硬纪律

**一、件别自己挂 cordis exporter。** 日志出口归内核——件挂一个就是同一句话走两条通道，日志页里
两行一模一样。件要打日志就正常用 `ctx.logger`，四路汇总会收到。

**二、日志窗格在收条目的路径上一个 `console` 都不许打。** 渲染层的 console 是四路之一：窗格打
一句 → 主进程收走 → 进缓冲 → 推回窗格 → 那条路上如果又打了一句，就是一变二、二变四，**界面
当场冻死**。取表失败那种非循环路径上的可以留。

## 服务命名：一律 `gwb` 开头

cordis 的 `ctx` 是一个共享命名空间，所有件的服务都挂在上面。规则很短：

- 件提供的服务一律 `gwb` 开头的小驼峰，默认跟件名对应（`gwb-commands` 件 → `ctx.gwbCommands`）
- 消费方 `inject: ['gwbCommands']`
- **例外：cordis 官方件的服务照它自己的**（`timer`、`loader`）——那不是这个生态的东西

为什么全加而不是「通用名才加」：代价不对称。该加没加、将来撞了要改名，所有消费方的
`inject` 与 `ctx.xxx` 跟着改，那是破坏性变更；不该加而加了，只是名字长几个字符。

顺带白得一条反向信息：**看到 `ctx.foo` 没前缀，就知道它不是这个生态的**——外部件，行为
不归我们管。

## 内核自己的一条命令

除这一条外，内核不认识任何命令名——其余一律交给 `ctx.gwbCommands`（由某个件提供的服务）。

| 命令 | 干什么 |
| --- | --- |
| `kernel.info` | 自省口：pid、node 版本、home 路径、**日志目录**、条目表与每条的挂载结果、谁是外壳 |

装机口不在这儿：内核连 pnpm 都不碰，装包是**件的事**——`gwb-plugins` 件的
`plugins.install` 命令干这个。早先的文档写过一条 `kernel.install`，那是装机口还没
搬去件那边的旧形状，看到就当过时处理。

**路径一律从这儿取，别自己拼。** `logDir` 就是个例子：它是 `<home>/logs`，件照着拼也拼得对
——但那样目录名就有了第二处真源，哪天内核换个名字，件不会报错，只会**静默显示一条错路径**。

「本体不认识任何插件的命令名」是有意的纪律。内核要用某个件的能力时，正确的做法是让那个
件把能力送上来，而不是内核去点名调它。

## 内核信息怎么拿

**两条路，不能混：**

- **这次运行的状态**（home 在哪、版本是多少、装机怎么调）→ **cordis 服务**。宿主起步时
  往 `ctx` 上挂一个键，插件从 `ctx` 读
- **说这些话用的词**（类型、零依赖纯函数）→ **词汇表包**，`import` 进来

第一样不可能靠 `import` 拿到：`dataDir` 是宿主启动时从环境变量算出来的运行时值。插件
import 一份内核代码，拿到的是代码不是那次运行的结果。

内核的 `src/` 也不该整个发成包给插件用——插件用不着主进程与宿主入口，而发出去就成了
要维护的契约。

两样都在了：宿主在挂 loader 之前 `provide('gwbKernel', …)`，词汇表包是
`@godcreator02/gwb-plugin-api`。取内核服务用它的 `requireKernel(ctx)`，**别写进 `inject`**
——那个服务在根上下文 provide、永不撤销，写进 `inject` 只会多一处挂不上的可能。

## 契约按最小重定

母仓那批件准备废弃、插件全部重做，所以契约不受「11 件不改一行」的约束。

有份实测数据说明契约面该多大：把母仓 11 件源码全扫一遍，从平台包根出口一共只取了 12 个
名字，其中 11 件全用的只有 1 个（`GwbContext`），7 件用的 1 个（`requireKernel`），6 件
用的 1 个（`isRecord`）。剩下 9 个里，4 个其实是**插件之间**的契约（http 件对 mcp 件的
承诺那种，该住提供方自己的包里），5 个是各 1 件在用的实现细节漏出。

所以内核词汇表应该只有个位数个名字，而不是母仓那 600 行。
