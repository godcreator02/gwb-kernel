# 写一个件

内核认的东西非常少。下面这些就是全部。

## 最小的一个件

一个件就是一个普通的 npm 包，装在 `<home>/node_modules` 下：

```json
{
  "name": "@you/thing",
  "version": "0.0.1",
  "type": "module",
  "exports": { ".": "./index.js" }
}
```

```js
export const name = 'thing'

export function apply(ctx) {
  // ctx 是 cordis 的 Context。你在这里注册服务、挂监听、开东西
}
```

`apply` 的签名与语义全归 cordis，不归这个内核——内核只负责把模块 `import` 进来交给
`ctx.plugin`。

## 让它被挂上

`<home>/cordis.yml` 是条目表，顶层是一个数组：

```yaml
- id: thing
  name: "@you/thing"
  config:
    port: 2870
- id: 先关着的
  name: "@you/other"
  disabled: true
```

`name` 要写**完整包名**。`id` 不写就用 `name`。`config` 原样交给 `apply` 的第二个参数。
`disabled: true` 的条目不挂。

文件不存在就是一个件都没装，内核不会替你写模板。

## 界面那半

件要在窗口里画东西，就多导出一个 `./client` 子路径：

```json
{
  "exports": {
    ".": "./index.js",
    "./client": "./client.js"
  }
}
```

`client.js` 由浏览器**直接加载**，不经过打包器，所以它不能有裸名 `import`——写成自包含的
一个文件。页面通过这条 URL 拿到它：

```
gwb://asset/plugins/@you/thing/client.js
```

## 外壳

窗口里的那个界面根只交给一个件，叫**外壳**。件在包清单里这样声明自己是外壳：

```json
{
  "gwb": { "shell": true }
}
```

外壳的 `client.js` 要导出 `mountShell`：

```js
export function mountShell(args, root) {
  root.textContent = '我拿到整页了'
  args.host.call('kernel.info').then((res) => {
    // args.host.call 是命令通道:走到宿主,分发给插件,原路回
  })
}
```

渲染层启动时问内核要条目表，挑出「挂上了 且 `gwb.shell` 为 true」的那一条。

**一条都没有，或者不止一条，都是留白**：一扇窗只交得出一个界面根，同时有几条时挑谁都是
碰运气，所以不挑。原因进 console，不在页面上解释——见[刻意不做什么](/docs/not-doing)。

## 内核自己的两条命令

除这两条外，内核不认识任何命令名——其余一律交给 `ctx.cli`（由某个件提供的服务）。

| 命令 | 干什么 |
| --- | --- |
| `kernel.info` | 自省口：pid、node 版本、home 路径、条目表与每条的挂载结果 |
| `kernel.install` | 装机口：`{ specs: string[] }`，转发 pnpm 装进 home。装完不重挂，重启生效 |

「本体不认识任何插件的命令名」是有意的纪律。内核要用某个件的能力时，正确的做法是让那个
件把能力送上来，而不是内核去点名调它。

## 内核信息怎么拿

**两条路，不能混：**

- **这次运行的状态**（home 在哪、版本是多少、装机怎么调）→ **cordis 服务**。宿主起步时
  往 `ctx` 上挂一个键，插件从 `ctx` 读
- **说这些话用的词**（类型、零依赖纯函数）→ **词汇表包**，`import` 进来

第一样不可能靠 `import` 拿到：`dataDir` 是宿主启动时从环境变量算出来的运行时值。插件
import 一份内核代码，拿到的是代码不是那次运行的结果。

内核的 `src/` 也不该整个发成包给插件用——插件用不着主进程与宿主入口，而发出去就成了
要维护的契约。

**这两样眼下都还没有**：`ctx.provide` 一次都没调过，词汇表包也还没建。这是下一刀要做的。

## 契约按最小重定

母仓那批件准备废弃、插件全部重做，所以契约不受「11 件不改一行」的约束。

有份实测数据说明契约面该多大：把母仓 11 件源码全扫一遍，从平台包根出口一共只取了 12 个
名字，其中 11 件全用的只有 1 个（`GwbContext`），7 件用的 1 个（`requireKernel`），6 件
用的 1 个（`isRecord`）。剩下 9 个里，4 个其实是**插件之间**的契约（http 件对 mcp 件的
承诺那种，该住提供方自己的包里），5 个是各 1 件在用的实现细节漏出。

所以内核词汇表应该只有个位数个名字，而不是母仓那 600 行。
