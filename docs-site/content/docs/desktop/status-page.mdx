**本页回答**：只读状态页什么时候出现、显示什么；它的数据从哪来、条目状态怎么说成一句话；什么时候重新推送；为什么只做到这一步。页面怎么在外壳与状态页之间切换，见接缝页[外壳接管](/docs/seams/shell)。

## 是什么

没有插件调用 `setShell`、或外壳启动失败（import 失败、默认导出不是函数）时，页面显示一份只读状态页。它显示三样内核手上已有的数据：

- home 的路径
- loader 里每个条目一行：id、包名、加载到哪一步
- 最近 20 行错误与警告日志（全文在 `gwb.log`）

全部是纯文本，没有按钮；页首一句话说明是没有外壳，还是外壳启动失败、原因是什么。

## 数据从哪来

数据由 `main.ts` 的 `report()` 在每次推送时重新计算：条目取自 loader 的条目树，错误行从 cordis logger 自带的环形缓冲里筛出 error 与 warn 级别的最后 20 条。loader 还没加载时条目表是空的。

{/* ref file="../apps/desktop/src/main.ts" lines="173-195" */}

它随每一条 `gwb:shell` 一起推给页面（推送的整份形状见 [IPC 通道](/docs/seams/ipc)）；页面上有外壳时不看它。

## 条目状态怎么说

`entry-state.ts` 的 `describeEntry` 把一个条目说成一句话。状态名照 cordis 的 fiber 状态原名；fiber 之外还有停用和「没有 fiber」（import 失败）两种。等待中的带上还缺哪个服务，失败的带上错误的第一行。

{/* ref file="../apps/desktop/src/entry-state.ts" lines="29-40" */}

cordis 的 fiber 状态是 `const enum`，在本仓的编译设置下引用不到，所以按它的定义照抄了一份名字表。本仓没有测试核对这张表，升级 cordis 时要对照它的 `FiberState` 声明看一遍；插件管理 `@godcreator/gwb-plugin-manager` 自己也抄了一份，由它自己的测试对照 cordis 的声明核对。

{/* ref file="../apps/desktop/src/entry-state.ts" lines="18-20" */}

## 什么时候重新推送

条目状态变化（cordis 的 `internal/status` 事件）、每来一行 error 或 warn 日志，都会触发重新推送，200 毫秒内的多次合并成一次；每次推送的都是整份当前状态。页面订阅时还会主动请求一次当前值（`gwb:hello`），所以页面比插件晚就位也不会错过。

## 为什么只做到这一步

状态页只显示内核已经有的数据，不分析失败原因、不重试、不放按钮：那些需要认识具体的插件，是外壳和插件管理窗格的事。它存在只为一件事——外壳没有就位或启动失败时页面不是一片空白，人能看到卡在哪个条目、最近报了什么错（[外壳未就位时的阶段页](/trajectory/2026-09-08-stage-page)）。
