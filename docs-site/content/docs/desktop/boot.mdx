**本页回答**：内核是怎么被启动器加载起来的；内核从入口模块求值到外壳显示出来依次做了什么，哪几处顺序是约束、为什么；启动失败和插件出错时内核怎么办；退出时怎么清理。

<Diagram name="kernel-boot" title="一次启动：内核准备好 home 和 cordis，插件从 cordis.yml 进来，页面最后交给外壳">
- 整个应用只有两个进程：主进程里是内核和 cordis 实例，所有插件都运行在 cordis 里；渲染进程是唯一的窗口。home 是磁盘上的一个目录
- 第 1 步：按 `GWB_HOME` 选定 home，缺 `package.json` 或 `cordis.yml` 就补一份最小的，已有的不动
- 第 2 步：打开 `gwb.log`；同一个 home 已有实例在运行就退出；把本次运行的 pid、版本写进 `runtime.json`
- 第 3 步：创建 cordis 实例，根上下文指向 home，并提供 `gwbKernel`——早于任何插件
- 第 4 步：创建窗口；这时还没有外壳，页面显示只读状态页
- 第 5 步：注册 loader，设好按 home 解析包名的 import，根层只放一条 include 条目 `home`，它读 `cordis.yml`；loader 按条目从 home 的 `node_modules` 找到插件包并加载
- 第 6 步：外壳插件调用 `setShell`，页面注入 importmap、把 `#root` 交给外壳
</Diagram>

## 在这之前：启动器找到内核

从安装包启动时，Electron 先运行的是启动器：启动器选定 home、把绝对路径写回 `GWB_HOME`，读 home 里内核包清单的 `engines.electron` 与 `main`，当前 Electron 在范围里才 import 内核入口；home 里没有内核包、版本不满足时，弹框说明原因、退出码 1，内核一行都不运行（[启动器加载内核](/docs/seams/launcher)）。从仓里 `pnpm start` 时没有这一步，Electron 直接运行内核。下面从内核入口模块开始求值算起。

## 两段：模块求值时与 ready 之后

**模块求值时**做完不需要窗口的部分：选定 home、设置 userData、补齐最小形态，打开日志文件，检查单实例锁，写 `runtime.json`，创建 cordis 实例、接上日志、提供 `gwbKernel`、注册 IPC 通道（home、单实例锁与日志文件的规则见[内核应用](/docs/desktop)）。**Electron ready 之后**才去掉默认菜单、创建窗口并加载页面、注册 loader、加载全部条目。

入口不能顶层 `await app.whenReady()`：Electron 要等入口模块求值完才触发 ready，顶层等待会互相等待、静默卡死。ready 之后的部分放在 `whenReady()` 返回的 promise 的 `then` 里执行，启动失败也在这条链上处理：

启动失败时先写一行日志，再弹错误框（Electron 保证 ready 之前也能弹出，窗口可能还没有），框里带着 `gwb.log` 的路径，退出码 1。

## 顺序是约束

ready 之后这一段的顺序本身就是约束：

{/* ref file="../apps/desktop/src/main.ts" lines="275-292" */}

- **`gwbKernel` 在注册 loader 之前提供**：它在模块求值时就已提供，任何插件加载时都已经在了（[`gwbKernel` 要在注册 loader 之前提供](/trajectory/2026-09-07-wall-gwbkernel-provide-early)）
- **窗口先于 loader**：页面在插件加载的过程中就显示只读状态页，页面的 console 也从一开始就进日志
- **`loader.internal` 在加载条目之前设好**：不设的话 loader 按自己的位置解析包名，插件静默加载失败。内核给它的 import 按 home 里的真实路径解析包名（[插件加载](/docs/seams/loading)）
- **等 loader 加载完**才写「up」那行日志并推送一次页面状态：那时各条目都已走到各自的终态

窗口创建时不显示，第一帧画好才显示；窗口底色 `#151518` 与页面入口 `index.html` 的 html 背景、安装包图标的底色是同一个值，窗口创建到第一帧之间、最小化后还原、整页重新加载的第一帧露出来的都是这个颜色，不闪白。改底色时三处一起改。

## 插件出错不带走内核

插件和内核在同一个进程里，插件的错误就是这个进程的错误。内核对未捕获的异常和没人处理的 rejection 只写一行 error 日志、不退出——一个坏插件不该让整个工作台退出。插件自己的失败由 cordis 记在它的条目上，只读状态页上看得到。

## 退出

所有窗口关闭就退出。退出前内核卸载 loader，整棵插件树的清理逐层执行；插件启动的长期子进程靠这一步结束，否则主进程一退它们就成了孤儿进程。谁创建了 cordis 实例，谁负责卸载它。

- 第一次进入 `will-quit` 时阻止退出，开始清理；清理完再退出，第二次进入时直接放行。loader 还没加载（刚启动就退出）时没有可卸载的，同样放行
- **等清理结束要内核和插件都做到**：内核 `dispose()` 之后还要 `await()` 才等得到嵌套的异步清理；插件要把清理的 promise 从 effect 的清理函数里**返回**出来。少做一方，退出时就等不到插件的清理（[退出收尾：内核等、插件返回](/trajectory/2026-09-12-quit-dispose-two-halves)）
- **最多等 5 秒**：某个插件的清理卡住时，到 5 秒就不再等它、照常退出，工作台不能一直不退；清理中抛出的错误只写一行 warn
