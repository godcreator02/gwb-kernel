插件与页面代码用到内核的地方，类型都从内核包的包根取，正本是 `apps/desktop/src/api.ts`。这些类型随内核包发布，版本号就是内核包的版本号（[词汇表包并进内核包](/trajectory/2026-09-24-vocab-into-kernel-package)）：

```ts
import type { GwbContext } from '@godcreator/gwb-kernel-desktop'
```

插件的 peer 里本来就写着内核包，pnpm 把它装进插件仓的 `node_modules`，不用另加依赖。只写 `import type`，编译后不留 import，运行时不会加载内核入口。

## 有哪些类型

| 类型 | 是什么 | 谁用 |
| --- | --- | --- |
| `GwbKernelApi` | 内核服务 `ctx.gwbKernel` 的形状：`dataDir`、`version`、`emit`、`handleRequest`、`registerImports`、`setShell` | 插件；内核的 `main.ts` 把服务对象标成这个类型 |
| `GwbRequestHandler` | 请求通道的处理器：收一个未知的载荷，返回值可以是 Promise；抛错时页面的请求拒绝 | 调 `handleRequest` 的插件 |
| `GwbContext` | 插件 `apply` 拿到的上下文：cordis 的 `Context` 加 `gwbKernel` | 插件 |
| `GwbWindowApi` 与 `Window.gwb` 的全局声明 | 页面上 `window.gwb` 的形状：`request`、`prepareImports`、`on`、`onShell` | 外壳与窗格插件的页面代码 |
| `ShellBoot` | 外壳模块默认导出的形状：拿 `#root`，回一个可选的 `dispose` | 外壳插件 |

每个成员做什么、细节在哪一页，见[内核应用](/docs/desktop)的「接口」。整个 `src/api.ts` 就是这张表的定义：

代码里只要 import 了内核包的类型（哪怕只是 `import type {}`），TypeScript 就认得 `window.gwb`。`GwbRequestHandler` 的载荷与返回值都是 `unknown`：内核不定义业务回执，回执的形状由登记通道的插件自己导出。

## 包根怎么导出

内核包的包根有两个条件：`types` 指向 `dist/api.d.ts`，给 TypeScript 用；`default` 指向 `dist/main.js`，是内核入口。包根的运行时入口一加载就启动 Electron 应用，所以包根对外只给类型：

{/* ref file="../apps/desktop/package.json" lines="8-15" hash="4f8340723bcf" blob="df73ceac0ed7" */}

清单顶层不写 `types`，类型只经 `exports` 给出：插件的 TypeScript 要用认 `exports` 的模块解析方式（`bundler`，或 `node16` 起）。这几条由测试核对：

`dist/api.d.ts` 由单独一份 tsc 配置生成：只编译 `src/api.ts`、只出声明文件，内核内部实现的类型不跟着发出去。

## 兼容约束

这些类型是插件与内核之间的约定。插件在 peer 里写它兼容的内核范围，下限是验证时那个内核的版本号：

```json
{ "peerDependencies": { "@godcreator/gwb-kernel-desktop": "^<验证时那个内核的版本号>" } }
```

pnpm 装插件时拿它和 home 里的内核包比，不满足只警告；插件管理拿它和运行中内核的 `gwbKernel.version` 比，范围不包含的插件在回执里标出来，只标不拦；devkit 的 `devkit.release` 发插件前检查它。内核自己不读这个字段。这个比较要靠得住，内核的版本号就得反映已有的插件会不会被弄坏：

- **会弄坏插件的改动**：删掉一个类型或成员；改参数、返回值的类型；改调用方依赖的语义（比如 `setShell` 的撤销在什么时候清空、`request` 在什么情况下拒绝、`handleRequest` 同名时怎么办）
- **类型之外的约定同样算**：内核与插件、页面、home 之间任何一条接缝上已有的东西，包括升级 `cordis`、loader、include 的版本，改 home 的布局
- **不会弄坏插件的改动**：加一个类型；给已有类型加可选成员；只改注释

哪种改动升版本号的哪一位、发破坏性版本前后要多做哪几步，见[开发](/docs/develop)。

形状对不上时谁先发现：内核自己的 `main.ts` 从同一个文件取 `GwbKernelApi`，内核服务对象的形状对不上时本仓的类型检查当场失败；`preload.cjs` 是 CJS、不经类型检查，`window.gwb` 上有哪几个成员由 `preload.test.ts` 核对；仓外的插件与页面代码要等新内核包发到团队包源、装上之后，才在各自仓的类型检查里发现。

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| cordis 的 `Context` 类型（内核包的 peer） | `GwbContext` 在它上面加 `gwbKernel` | 使用方没装 cordis，`GwbContext` 里 cordis 那部分就拿不到类型；插件自己也在 peer 里写 `cordis`，插件仓与 home 里都有（[cordis 写在 peer 里](/trajectory/2026-09-07-wall-cordis-peer)） |
| TypeScript 的 DOM 类型（`HTMLElement`、`Window`） | `ShellBoot` 的参数、`window.gwb` 的全局声明 | 不会缺：`src/api.ts` 第一行的 `/// <reference lib="dom" preserve="true" />` 保留到 `dist/api.d.ts`，使用方 tsconfig 的 `lib` 不带 `DOM`、又关掉 `skipLibCheck` 时也能通过类型检查。代价是 import 了这些类型的主进程代码也看得到 DOM 的全局类型（[类型声明里写明要 DOM 类型](/trajectory/2026-09-24-vocab-declares-dom)） |

## 不在这里的

- **实现**：`gwbKernel` 由 `main.ts` 提供，`window.gwb` 由 `preload.cjs` 注入；`src/api.ts` 只写形状
- **命令与回执的类型**：请求载荷、命令的登记形状与回执 `GwbResult` 由命令插件 `@godcreator/gwb-commands` 自己导出，调用方从它那里 `import type`（[不保留命令兼容层](/trajectory/2026-09-27-request-without-compat)）
- **插件管理的回执类型**：由插件管理 `@godcreator/gwb-plugin-manager` 自己导出
- **运行时的值**：`dataDir` 这类值是那一次运行算出来的，插件只能从 `ctx.gwbKernel` 取
- **IPC 通道名与日志行的格式**：`gwb:request` 这类通道名只在内核包里，页面代码只经 `window.gwb` 调用（[页面与主进程之间的通道](/docs/desktop/ipc)）；`gwb.log` 一行的格式见[日志](/docs/desktop/log)
- **只读状态页的数据形状**：`gwb:shell` 里还有一个 `report` 字段，只给内核自己的页面入口用，`onShell` 的参数类型只写了 `url`
