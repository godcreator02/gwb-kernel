**本页回答**：插件和页面代码从哪里 `import type` 内核的接口；有哪些类型、各属于哪条接缝；包根为什么只导出类型、怎么构建出来；它们依赖什么；改这些类型时内核版本号怎么升；哪些类型不在这里。

这些类型随内核包发布，版本号就是内核包的版本号。它们自己不算一条接缝：接缝 2、3、4 交换的东西的形状写在这里（[词汇表包并进内核包](/trajectory/2026-09-24-vocab-into-kernel-package)）。插件和页面代码这样写：

```ts
import type { GwbContext } from '@godcreator/gwb-kernel-desktop'
```

插件的 peer 里本来就写着内核包（[插件在 peer 里写兼容哪个内核](/docs/design#插件在-peer-里写兼容哪个内核)），pnpm 把它装进插件仓的 `node_modules`，不用另加依赖。只写 `import type`，编译后不留 import，运行时不会加载内核入口。

## 有哪些类型

| 类型 | 是什么 | 接缝 |
| --- | --- | --- |
| `GwbResult` | 已弃用的兼容导出；命令回执正本从 `@godcreator/gwb-commands` 取 | [3 IPC 通道](/docs/seams/ipc)、[10 命令转交](/docs/seams/commands) |
| `GwbKernelApi` | 内核服务 `gwbKernel`：`dataDir`、`version`、`emit`、`handleRequest`、`registerImports`、`setShell` | [2 内核服务](/docs/seams/kernel) |
| `GwbContext` | 插件 `apply` 拿到的上下文：cordis 的 `Context` 加 `gwbKernel` | [2 内核服务](/docs/seams/kernel) |
| `GwbWindowApi`，以及 `Window.gwb` 的全局声明 | 页面上的 `window.gwb`：`request`、`on`、`onShell`、`prepareImports`，以及已弃用的 `command` | [3 IPC 通道](/docs/seams/ipc) |
| `ShellBoot` | 外壳模块默认导出的形状 | [4 外壳接管](/docs/seams/shell) |

`GwbRequestHandler` 是通道处理器类型，接受未知载荷，返回值可以是 Promise；内核不定义业务回执。整个 `src/api.ts` 就是这张表的定义：

代码里只要 import 了内核包的类型（哪怕只是 `import type {}`），TypeScript 就认得 `window.gwb`。内核自己的 `main.ts` 从同一个文件取 `GwbKernelApi`、把内核服务对象标成这个类型，形状对不上时本仓 `pnpm check` 当场失败；仓外的插件与页面代码要等新内核包发到团队包源、装上之后，才在各自仓的类型检查里发现。

## 包根怎么导出

内核包的包根有两个条件：`types` 指向 `dist/api.d.ts`，给 TypeScript 用；`default` 指向 `dist/main.js`，是内核入口。包根的运行时入口一加载就启动 Electron 应用，所以包根对外只给类型：

{/* ref file="../apps/desktop/package.json" lines="8-15" */}

清单顶层不写 `types`，类型只经 `exports` 给出：插件的 TypeScript 要用认 `exports` 的模块解析方式（`bundler`，或 `node16` 起）。这几条由 `apps/desktop/tests/importmap.test.ts` 核对：

`dist/api.d.ts` 由单独一份 tsc 配置生成：只编译 `src/api.ts`、只出声明文件，内核内部实现的类型不跟着发出去。构建时在编译内核之后运行它（构建步骤见[开发](/docs/develop#从源码启动)）：

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| cordis 的 `Context` 类型（内核包的 peer） | `GwbContext` 在它上面加 `gwbKernel` | 使用方没装 cordis，`GwbContext` 里 cordis 那部分就拿不到类型；插件自己也在 peer 里写 `cordis`，插件仓与 home 里都有（[cordis 写在 peer 里](/trajectory/2026-09-07-wall-cordis-peer)） |
| TypeScript 的 DOM 类型（`HTMLElement`、`Window`） | `ShellBoot` 的参数、`window.gwb` 的全局声明 | 不会缺：`src/api.ts` 第一行的 `/// <reference lib="dom" preserve="true" />` 保留到 `dist/api.d.ts`，使用方 tsconfig 的 `lib` 不带 `DOM`、又关掉 `skipLibCheck` 时也能通过类型检查。代价是 import 了这些类型的主进程代码也看得到 DOM 的全局类型（[类型声明里写明要 DOM 类型](/trajectory/2026-09-24-vocab-declares-dom)） |

## 改这些类型的规则

这些类型是插件与内核之间的约定，**对插件只增不减**：加一个类型、给已有类型加可选字段升 y；删名字、改形状（参数、返回值、回执字段的类型或含义）、改调用方依赖的语义升 x，并先照说明书 `gwb-release` 的「发破坏性版本多做的两步」通知下游。完整规则见[开发](/docs/develop#发版)。

## 不在这里的

- **实现**：`gwbKernel` 由内核应用的 `main.ts` 提供，`window.gwb` 由 `preload.cjs` 注入；`src/api.ts` 只写形状
- **命令插件的类型**：`gwbCommands` 服务、命令的登记形状由命令插件 `@godcreator/gwb-commands` 自己导出，调用方从它那里 `import type`
- **插件管理的回执类型**：由插件管理 `@godcreator/gwb-plugin-manager` 自己导出
- **运行时的值**：`dataDir` 这类值是那一次运行算出来的，插件只能从 `ctx.gwbKernel` 取
- **日志行的格式与 IPC 通道名**：日志行格式归[日志](/docs/seams/log)接缝；`gwb:command` 这类通道名在内核应用里，页面代码只经 `window.gwb` 调用
- **只读状态页的数据形状**：`gwb:shell` 里还有一个 `report` 字段，只给内核自己的页面入口用，`onShell` 的参数只写了 `url`
