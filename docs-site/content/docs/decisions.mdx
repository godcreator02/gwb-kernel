# 定过的事

**这一页是事前的选择**，[撞过的墙](/docs/walls)是事后的教训。一个选择后来撞了墙，
两边各记各的。

每条固定六段。「代价」那段最要紧——将来后悔时，得认得出是不是这一条在疼。

### 另起一条线，而不是在母仓上做减法

**问题**：母仓约 5100 行，其中约 3600 行服务于「让失败变得体面」。想要一个只做必需事情的
内核，是改它还是重来。

**候选**：① 在母仓上砍掉那 3600 行 ② 另起一个仓从头推

**判据**：砍掉等于扔掉那些行背后的教训（每一条都对应一次真翻车）；而重来可以**移除产生
那些教训的功能本身**——不自动升级，四路判定连同它制造的全部麻烦一起消失。两者性质不同：
前者是删代码，后者是删需求。

**定了**：另起 `gwb-kernel`。后续进一步定为**正线**，母仓与件仓准备废弃、只作参考，
插件全部重做。

**代价**：两条线并存期间要维护两套；母仓那些坑要重新撞一遍（已经撞了好几个）。
另外「查母仓」有个反向风险——去看一个坑怎么解的，顺手把解法连同周围那圈机制一起搬回来
是最自然的动作。

**日期**：2026-09-07

### 打包器到期再选，现在不换 Electron Forge

**问题**：构建用 electron-vite、打包用 electron-builder（母仓那套），要不要换成官方的 Forge。

**候选**：① 现在换 Forge ② 保持现状，打包到期再选

**判据**：查到的事实——Forge 的 `plugin-vite` 自 v7.5.0 起标为 **experimental**，至今仍是；
而 electron-vite 是它的**上游**（官方 FAQ 写着「功能稳定后会 port 到 plugin-vite」）。
更关键的是时机：换 Forge 动的是**打包层与编排层**，而前四刀根本不碰打包——现在换等于在
主线上插一条支线，两者失败症状还长得像。

**定了**：不换。打包到期时（要出安装包）再拿两个各试一次，那时手上有一个确定的问题：
pnpm 怎么进产物。

**代价**：以后真要换，接线要重做一遍。为把这个代价压住，同时定了一条零成本的约束：
**别让打包器的形状渗进源码**——主进程走正常的包解析，不依赖「依赖被内联进束」。

**日期**：2026-09-07

### 取址交给 cordis 官方 loader，内核自己不做

**问题**：第二刀自己写了 87 行取址（读 yml → 拼路径 → import）。cordis 有官方的
`plugin-loader` 与 `plugin-include`，要不要用。

**候选**：① 保持自己写 ② 挂 loader + include

**判据**：`EntryTree` 的 API 是现成的（`create`/`remove`/`update`/`store`/`await`），
**热挂卸是白得的**——直接消掉了「设置件改完要重启」那个取舍。而母仓不用 include、自己写
了 500 行做同一件事。

**定了**：内核只挂 loader，再往它的树上放一条 `cordis:include` 条目，其余全归这两个。
内核连 yml 都不认识。

**代价**：多两个依赖；引导链有四条判据要记住（都住应用依赖树、include 走 `builtins`、
做成条目而非 `ctx.plugin`、承载 yml 那条 id 写死）。这些连同踩到的坑记在 walls。

**日期**：2026-09-07

### cordis 官方件开四个，不开六个

**问题**：官方件有十来个，开哪些。

**候选**：逐个判。

**判据**：「真遇到需求才加」。

**定了**：开 `plugin-loader`、`plugin-include`（内核挂）、`plugin-timer`、
`plugin-logger-console`（装进 home）。不开 `plugin-hmr`（**在这个架构下不起作用**：跑的是
home 里那份产物，盯仓内源码盯到变化也没有对应模块可换）、`plugin-http`/`plugin-server`
（**内核**没有外部访问需求；另订正一处措辞：`plugin-http` 其实是 HTTP **客户端**
`ctx.http`，本来就不是这一侧的候选，当时把两个写在一起是没查过）、
`plugin-config`/`plugin-webui`、`plugin-database`、`@cordisjs/schema`。

**代价**：没有 hmr，改件要重新构建发版装进 home。timer 与 logger-console 是普通件，
**可以被停掉**——停掉 logger-console，件的日志就静默消失（内核自己的日志不受影响，
另有保底 error 出口）。

**`logger-console` 后来撤掉了，开着的从四个变三个**（下面「出口收归内核」那条）。上面那句
代价正是撤它的理由之一：做日志窗格时要把四路日志汇成一条流水，内核为此必须有一个全量
exporter，**而这条决定当初的前提是「内核没有全量出口，logger-console 是唯一出口」**——前提
一没，「件的日志有没有出口取决于某个件装没装」就从可接受的代价变成了不可接受的。
留着这一条是因为它记着那个前提；理由换了，结论也换了。

**这一条里有两处判错了**，是做 `gwb-settings` 时重新过准入判据第二关翻出来的。结论都没变，
但理由得换——**留着错的理由比没有理由更坏，下次照它推会推歪**：

- **`plugin-config` 不是 Koishi 生态的**。它是 cordis 官方 webui 仓（`cordiverse/webui`）的件，
  依赖里没有任何 koishi 包，而且**已改名**为 `@cordisjs/plugin-loader-webui`：peer 吃
  `cordis ^4.0.0-rc.6` ＋ `plugin-loader ^1.0.0-rc.4`，对这儿的 rc.9 / rc.6 **是匹配的、
  装得进来**。不用它的真实理由有三条，每条都比原来那句硬：它硬 peer 一个
  `@cordisjs/plugin-webui`（**没标 optional**），而 webui `@Inject('server')`——为一个条目
  编辑器要拖进 HTTP＋WebSocket 服务器；它自己**不存任何东西**，`createConfig`/`updateConfig`
  就是转手调 `ctx.loader` 的那几个；另一半体量是 node_modules 与 Yarn PnP 的包扫描
  （插件市场那半），这条线明确不要
- **`@cordisjs/schema` 是 cordis 3 遗物，已从官方仓删除**。原来的理由「配置校验现在不需要」
  也不对——**cordis 4 本体自带**：`plugin.Config` 走 `@standard-schema/spec`，挂载时
  `resolveConfig` 同步校验、不过就抛 `ValidationError`（async schema 直接拒）。schemastery
  3.18 自己实现了 `~standard`，中间那层 service 包装因此没有存在意义。zod / valibot /
  arktype 任何实现 Standard Schema 的都能直接当 `Config` 用

**日期**：2026-09-07（两处理由订正于同日）

### 组件复用分三层，不照搬母仓那套

**问题**：shadcn/tailwind 组件在多个件之间怎么复用。

**候选**：① 共享一个组件库 + importmap（母仓做法）② 每个件全自带 ③ 分层处理

**判据**：实测数据——母仓那套里 **CSS 一分没省**（8 个件 8 张 62.8–66.5KB 的表，彼此差不到
6%），省下的只有 JS，而代价是 3 个平台包严格同号 + 每件 4 处版本钉死 + 3 份 tsconfig +
6 个产物守卫 + 7 处分散真源 + **8 类静默失败**。这个比例不成立。

另外这三样性质不同：React 是**运行时环境**（多份是多个世界），组件源码是**代码**（多份
只是体积与漂移），CSS 工具类是**样式规则**（多份会因属性顺序互相污染）。

**定了**：**样式共享、组件各拉各的**——这正是 shadcn 的原教旨。件持有的是结构与语义类名，
主题是语义名背后的值，两层正交（Obsidian 400+ 变量、插件只准写 `var(--x)`，同一个机制）。

- **design token 共享一份**，独立成 `@godcreator02/gwb-tokens` 包，跟件平级装进 home，
  由外壳件注 `<link>` 引进页面
- **组件每个件自己从 shadcn 官方拉**（件里放一份 `components.json`，`shadcn add <名>`）。
  **仓里没有任何「组件源」，也不建 registry**
- **React 共享**，机制上内核零 UI 知识

**代价**：各件的组件版本会漂移（A 件三月拉的，B 件九月拉的）。**而这正是要的** ——
件独立发版，各自决定什么时候跟进；统一风格由令牌保证，不由组件源码一致保证。
CSS scope 围栏与 Portal 逃逸这两件事仍然躲不掉。

**日期**：2026-09-07（同日落地，形状有三处细化：`gwb.shared` 由**提供方**声明「我提供
这几个裸名」而不是消费方声明要什么；内核扫 home 清单的 `dependencies` 收集，不扫条目表；
`gwb://` 没有多开 `/shared/` 路径——子路径通用化之后共享包跟件走同一条 URL）

**上面那条 CSS 判据要读准**：「8 个件 8 张 63KB 的表、彼此差不到 6%」**不是「共享 CSS
无效」的证据，是「母仓没共享 CSS」的证据**——它只共享了 JS。反过来读才对：8 张表高度重复，
说明每张里绝大部分是同一套东西。而各拉各的之后每个件只扫自己真用到的类，实测验收件那张
**16.9KB**，比母仓那种扫整个共享组件库的 63KB 小得多。

**这条改过一次**：起初写的是「组件源码每个件复制一份，同源先靠手工，撞疼了再建 registry」。
那句话隐含着「件之间的组件该保持一致，所以需要一个源来维护」——**那个前提不成立**，是母仓
`gwb-ui` 共享组件包留下的思维惯性。shadcn 的组件本来就是给你改的，A 件的 button 跟 B 件的
不必一样。取消那个前提之后，registry、复制源、手工同步全都不需要了，而 shadcn CLI 在
monorepo 下本来就是「每个 workspace 各有一份 `components.json`」。

### 服务名一律 `gwb` 开头，不做「通用名才加」

**问题**：cordis 的 `ctx` 是共享命名空间，件的服务名要不要统一加前缀。

**候选**：① 全加 ② 只有通用名（`cli`、`http`）才加

**判据**：**代价不对称**。该加没加、将来撞了要改名，所有消费方的 `inject` 与 `ctx.xxx`
跟着改，那是破坏性变更；不该加而加了，只是名字长几个字符。一边破坏性变更一边审美，
那道「够不够通用」的主观题不值得天天做一遍。撞名风险也不是假想：home 里已装着官方件，
`timer`/`loader`/`logger` 被占着。

**定了**：一律 `gwb` 开头小驼峰，默认跟件名对应。cordis 官方件的服务照它自己的。

**代价**：「宿主给的 vs 件给的」这个区分不再由命名承担，改由契约说清（内核提供的只有
`gwbKernel` 一个）。白得一条反向信息：看到 `ctx.foo` 没前缀就知道它不是这个生态的。

**日期**：2026-09-07

### 件的包名加 `gwb-` 前缀，scope 不换

**问题**：新做的件要跟废弃那批错开，而 `@godcreator02/cli`、`/shell` 等已被占着。

**候选**：① 换 scope（另建 npm organization）② 加 `gwb-` 前缀

**判据**：scope 绑定 npm 账号（注册的就是 `godcreator02`），换要另建 org；而本机 Verdaccio
上 scope 本来就随便定。加前缀成本为零，且实测 `gwb-shell` 这些名字全空着。

**定了**：`@godcreator02/gwb-<件名>`。

**代价**：包名比原来长；两批件在同一个 registry 上并存一段时间。

### 依赖写 peer 还是 dev：三档，不是两档

**问题**：母仓的判据是「运行时真 import 了才写 peer，只 `import type` 写 dev」。按它写，
两次都错。

**候选**：沿用两档 / 补一档中间的。

**判据**：**发布出去的包不带 devDependencies**。词汇表包的 `GwbContext extends Context` 把
cordis 写成 dev，消费方那边 `ctx.logger`/`effect`/`provide` 全报「不存在」；`gwb-cli` 的
`GwbCli.run` 回 `GwbResult` 是同一回事。

**定了**：三档——运行时真 import → peer；**只 import type 但出现在导出的类型里 → 也要
peer**；只在实现内部用、不出现在导出面 → dev。

**代价**：判断时要多看一眼「它出现在导出面吗」。白得一条：peer 声明之后 pnpm 会把它自动
装进 home，消费方不用手动装。

**日期**：2026-09-07

### 引入 oxlint（含 type-aware），但不抄母仓那份白名单

**问题**：正线两个仓的门禁只有 `typecheck + test`，一条 lint 都没有。而代码里有三条纪律完全靠
人记住：promise 一律 `void` 前缀、`JSON.parse` 先落 `unknown` 再 `as` 到具名形状、`catch (err: unknown)`。

**候选**：① 什么都不做 ② 引 oxlint，照抄母仓那份配置 ③ 引 oxlint，规则集重新定
④ 顺带把格式化（oxfmt）、CI、git hooks 一起补上

**判据**：先说为什么过得了准入判据第二关——**这不是「将来可能要」**，那三条纪律现在没有任何东西
守着，而 type-aware 的 `no-floating-promises`、`no-unsafe-*` 恰好就是守它们的。（顺带把一件事
落成先例：**两道关的第一关对工具链不适用**——它问的是「进内核还是做插件」，lint 两者都不是；
第二关适用，而且要照常回答「现场是什么」。）

排除②的理由是实测。先看清一件容易看错的事：**母仓那 18 条并不是默认那批的子集**——18 条里
10 条本来就默认开着，另外 8 条是从 pedantic / suspicious 额外捞的 `no-unsafe-*` 一族。所以那份
配置的净效果是**「砍掉 101 条 correctness，换来 8 条 `no-unsafe-*`」**，而那 8 条是为母仓
`GwbContext` 的 `[key: string]: any` 索引签名服务的。

同一份代码上跑三个口径：**只开默认（111 条）零诊断；母仓 18 条报 1 条；并集 119 条也是 1 条**。
那 1 条是 `host/main.ts` 的 `no-unsafe-argument`，出在 `...message.args`——**是 cordis 自己把
`logger.args` 声明成 `any[]`**，不是本仓的 any。

正线仓没有 any 索引签名，那 8 条在这里的全部收获就是这条第三方带进来的、实际无害的报警；
而白名单的真代价是**新规则永远进不来**——oxlint 升级新增的 correctness 规则，白名单口径下得有人
手工去追。**前提要记住**：将来真出现 any 扩散，那 8 条的价值就回来了。

母仓文档站那张工具链表里，**oxlint 是唯一一件没写选型理由的工具**——这一条正好补上那处空白。

**定了**：`oxlint 1.81.0` + `oxlint-tsgolint 7.0.2001`，两个都**精确钉版**，`pnpm lint` 串进
`pnpm check`（typecheck → lint → test）。**配置只做三件事：指 schema、开 type-aware、排掉不该扫
的目录——一条 `rules`、一条 `plugins` 都不写。** 五件实测撞出来的细节：

- **`plugins` 不写**：这字段是**覆盖不是追加**（只写 `["typescript"]` 时规则数从 111 掉到 84），
  而写全默认那三个等于没写（规则数一样是 111），却多一份会跟默认漂移的手工名单
- **`no-unused-vars` 的 ignorePattern 不写**：oxlint 这条规则**默认就认 `^_`**，文档特意注明这跟
  ESLint 与 typescript-eslint 不同——那两个从不提供默认 pattern。母仓那三行是 ESLint 时代的遗产
- **`--deny-warnings` 不能省**：不带它，4 条诊断照样 `exit 0`——屏幕上有红字而门禁放行
- **`ignorePatterns` 相对配置文件所在目录解析**（拿临时配置做反向探针时，`docs-site/**` 因此没
  匹配上，文件数从 17 变 28）
- **排产物那条当时得锚定写**：`packages/gwb-plugin-api/lib/**`，图省事写 `**/lib` 会连
  `src/lib/` 这种真源码目录一起罩住。跟 `.gitignore` 里踩过的是同一个形状，而且**在 lint 这边更
  隐蔽**：少扫一个文件是没有症状的。（**后来产物目录整体改成 `dist`**，这条锚定连同 `.gitignore`
  里那行注释一起删掉了——`**/dist` 可以放心裸写。见「产物目录一律 dist」那条）

`docs-site` 排除是**硬理由不是抄母仓**：它钉 `typescript ^6.0.3`，而 type-aware 要 TS 7+。

串进 `check` 而不是像 `pnpm doc` 那样单开：那条先例的实际内容是「要起文档站的解析链、太慢」，
在这儿没被触发——**实测 lint 单跑 293ms，整条 check 3.1s**。将来真超过 5 秒再考虑拆，而且那时
正确的拆法是「不带 type-aware 的进门禁 + `lint:types` 单开」，不是整条拿出去。

**代价**：

- 精确钉版意味着**升级要人工做**。换来的是门禁口径不会因为一次 `pnpm install` 悄悄漂移——
  这条线刻意不做 CI，门禁只在人手跑 `pnpm check` 时才跑，一次漂移可能几天后才被发现
- **`--type-check` 明确不用**（它能替代 `tsc --noEmit`，但这里有三份不同口径的 tsconfig，替不掉
  这个结构；换掉 tsc 是另一个数量级的决定）
- **oxfmt 明确不引入**（还在 0.66.0 没到 1.0；母仓也完全没有格式化工具）。**CI、git hooks、
  `--fix` 同样不做**——门禁靠 `pnpm check` 加纪律。写下来是因为下次一定会有人拿「oxlint 都有了
  顺手加 oxfmt」来推
- **lint 面靠纪律不靠机制**：当前是 17 个 `.ts`（`apps/desktop/src` 11 + `tests` 3 + 两份 config
  + 词汇表包 1）。将来加了新包忘了它在不在某份 tsconfig 里，它会静默留在 lint 面外——**记下这个
  数就是唯一的守卫**，下次数不上就有人会发现

**日期**：2026-09-07

### 文档三层分流，检查单独成命令

**问题**：`CLAUDE.md` 涨到 147 行 14 节，什么都往里塞。

**候选**：① 继续塞 ② 分层

**判据**：`CLAUDE.md` **每次会话都进上下文**，塞多了每次都在付；而「为什么」和「怎么做」
是需要时才查的。三层各有各的判据（不知道就做错 / 需要时查 / 读不懂这一行）。

**定了**：`CLAUDE.md` 只装硬约束（147 → 82 行）；为什么与踩坑进文档站并用 livedoc **钉在
代码上**；注释只写现状。**注释里不写文档站的页名或锚点**——livedoc 只钉「文档 → 代码」，
反向没守卫，写死位置必然腐烂。

### 窗格清单动态注册，不做静态声明

### 词汇表是独立包、与内核同仓——不是件，也不走服务

**问题**：内核与件之间的契约（三个类型加两个纯函数）以什么形态存在、住哪个仓。被连挑五问：
必须是个包吗 / 不能全走 cordis 服务吗 / 为什么内核里只有它是包 / 为什么不做成件住件仓 /
内核一定要配几个包。

**候选**：① 独立包住内核仓（现状） ② 砍掉全走 cordis 服务（弱类型约定） ③ 做成件住件仓
④ 件仓手写类型（消费方持有契约）

**判据**：两条。一、**类型是编译期的东西，跨仓就得有可 install 的载体**——cordis 服务递

②④ 的下场是各件手写 declare 或 any，写错运行时才知道，内核实现也失去「被发出去的契约

之前就要 provide），靠 home 里装好的件提供类型是鸡生蛋。件形态多出来的（apply 生命周期、

内核 `src/` 的一部分）。总图：包给类型、服务给运行时值；件是干活的包，词汇表是只命名的包，
内核是不被安装的安装者。「内核配几个包」等于落进「类型跨仓」格子的东西数，现为 1——
第二个要正经过准入判据两道关。

**代价**：多一个要构建（tsc 出 `dist/`）、要发版的小包；依赖档位已撞过两次（见 walls）。

**代价**：一次跨两仓的机械重命名（5 个包的 `package.json` / `tsconfig` / 构建脚本 / 产物测试

缺文件的包，那个是静默的。

**判据**：先确认可行——cordis 4.0.0-rc.9 **有反查提供者的公开面**：`ctx.reflect.store`
（`Dict<Impl, symbol>`）的 `Impl` 带 `fiber`，loader 用 `declare module` 给 `Fiber` 加了
`entry?: Entry`，两处都有类型声明。时序上也没有窗口：主进程**先起宿主、等它
`loader.await()` 收敛发 `ready`，才开窗**，所以渲染层问的时候件早挂完了。

③ 是 ② 的严格劣化：认领必须能撤，件得自己 `ctx.effect` 包住、忘了包就是「件卸了外壳还
占着」；而 ② 里 cordis 的 `provide` 本来就走 `fiber.effect`，收尾是白得的。而且它的调用方
身份还是得从 fiber 反推——反查照做不误。

④ 把耦合挪到了**更差的位置**：渲染层得硬编码那个命令名，等于内核仍然认识外壳、只是从
「字段名」换成「命令名」，而渲染层是最没资格持有约定的那层；诊断也更远（`gwbCli` 缺席时
说的是「认不出 shell.boot」）。

**定了**：② 。内核认 `gwbShell` 这个**服务名**（不绑包名，外壳件叫什么都行）。

**白得三样**——这也是选它而不是 ① 的真正理由：

1. **「多于一条外壳」这种局面不存在了**。cordis 的 `provide` 撞名直接抛，第二个件根本
   挂不上，日志里明说撞的是谁。渲染层那条留白分支删掉了
2. **半死的外壳挑不出来**。反查只认 `fiber.state === ACTIVE`。这顺手暴露并修掉了一个真
   bug：`walkEntries` 原来判 `fiber !== undefined`，而 `registry.plugin()` **同步建 fiber、
   跟 inject 无关**，所以 inject 永远等不到的件也报 `ok: true`
3. `kernel.info` 不用再把每个包的 `package.json` 重读一遍

**代价**：内核仍然认识一个名字（从字段名变成服务名），耦合度没变——它总得挑一个件把
`#root` 交出去。另外「装了但还没挂上的外壳」从此在条目表里只是一条 `ok: false`，认不出
它本来想当外壳；那个信息现在只在宿主日志里。真需要「装了但没启用的件」那种界面时另想
办法（同 `describeSelf` 那条的代价）。

**`gwb.shared` 不跟着搬**：共享包**不是件**——在 home 的 `dependencies` 里但不在
`cordis.yml` 里，没有 `apply`、没有 fiber、没有 ctx，压根没有运行时可言。而且 importmap
必须赶在第一句动态 import 之前注入，比任何运行时都早（共享包的运行时只能靠 import 它自己
跑起来，那一句就已经晚了）。它跟 `gwb.shell` 并列过一阵，但**并列的理由只是碰巧都还在
清单里**：一个是必须在，一个是还没搬。

### 日志四路汇在主进程，件不再自己挂 exporter

**问题**：要在窗格里看见「一切」日志。而日志实际有四路来源，散在三个进程里：件与 loader 的
cordis 日志（宿主）、宿主自己的话（`[host] up`、`[install]`、`[stdin]` 坏行）、主进程自己的话、
渲染层的 console。谁把它们汇成一条流水、汇在哪。

**候选**：① 各汇各的，窗格去四个地方取 ② 汇在宿主 ③ 汇在主进程 ④ 汇在日志件里（母仓做法：
件自己挂 cordis exporter，经内核的 `emit` 推给页面）

**判据**：**位置由「谁够得着」决定，不由「谁该负责」决定。**

主进程够得着三路——它自己的话、宿主 pipe 过来的那条流、渲染层的 `console-message`；宿主够不着
渲染层；件够不着的更多，它跑在宿主子进程里，主进程与渲染层那两路一个字都看不见。

第二条判据是**生存期**，它单独就足以否掉②：缓冲放宿主里，宿主一崩缓冲跟着没——**而那正是要看
历史段的头号场景**。`proc.on('exit')` 是主进程才有的观测点，「宿主退出（code=1）」这句话本身就是
最要紧的一条日志，宿主里的任何东西都记不到它。

④ 另有两条硬伤。**时序**：件是 `cordis.yml` 里一条并发挂载的普通件，它注册 exporter 之前那一段
全丢——而[那个现场](/docs/walls)（`gwb-cli` 相对 import 少 `.js`、件静默挂不上）恰好就发生在
那一段。**历史段里最值钱的就是启动那几百毫秒，而件自己挂正好看不到它。** 其二是**绕一圈**：
缓冲在主进程，件挂了 exporter 还得推回主进程，等于「内核收到 → 交给件 → 件送回内核」，而中间
那一跳可以被 yml 里一行 `disabled: true` 掀掉。

**定了**：**汇在主进程**，环形缓冲与落盘都在那儿。cordis 那一路由**宿主自己挂一个全量 exporter**、
经 fd3 上行（行协议加一条 `{ t: 'log', … }`），不经过任何件。宿主自己那几处裸 `console.error`
一并改走 `ctx.logger('host')` 等，归进同一路。

`gwb-logger` 件不挂 exporter、不落盘、不碰通道——**它只出一格窗格**。

**代价**：内核从此认识「日志条目」这个形状，比现在那条「一条 stderr 流」宽。将来窗格想多一个
字段，改的是内核，而且是跨仓的破坏性变更。

第二笔：宿主那个 exporter 从「只管 error」扩成全量之后，**fd3 上的流量跟着涨**，跟命令回执挤在
同一条管子里。真出现命令被日志挤住的现场，那时再谈分管子——不要现在就分。

**日期**：2026-09-07

### 缓冲里存结构化条目，不存原始行

**问题**：主进程那圈环形缓冲存什么——`process.stderr` 上流过的原始文本行，还是解析好的条目。
这道题在路线页上挂了一阵，写的是「得看窗格怎么解析」。

**候选**：① 存原始行，窗格自己解析 ② 存结构化条目 ③ 两样都存

**判据**：窗格形状定下来之后这道题的答案是唯一的。**窗格要按级别与来源筛，就得要结构**；而
原始行里那两样根本不存在——`source` 靠猜前缀猜不回来，级别更是无从谈起。让窗格去解析等于把一个
做不到的任务推给它。

③ 的毛病是**两份真相**：同一句话在缓冲里有两种形态，「显示哪一份、按哪一份筛」会成为一个永远要
回答的问题。

而且**文件那条线已经存原始行了**（劫持 stderr 那一处），两条线各存各的形态，不重叠、不互为替身。

**定了**：`{ seq, ts, source, level, name, msg }`，主进程、**2000 条**。

- **`seq`** 是主进程发号的单调计数，**唯一键**，去重与排序都用它。母仓拿 `ts|name|msg` 拼字符串
  ——同一毫秒里两句一模一样的话会被静默吃掉一句，四路合流之后那不是假想。名字用 `seq` 不用 `sn`，
  跟 cordis 自己的 `Message.sn` 错开：**发号的是主进程，而 cordis 那个只在宿主那一路里有序**
- **`source`** 是 `plugin` / `host` / `main` / `renderer` 四个字面量。**闭集**——所以窗格的路筛选
  做得成多选
- **`level`** 是 `error`/`warn`/`info`/`debug`。**四路全都有真级别**：宿主那几处改走 `ctx.logger`、
  主进程走一个带级别的 `mainLog`、渲染层用 `console-message` 给的 `level`（只有 `warning → warn`
  一条要转）。**「裸行猜级别」这个问题因此不存在**——治在源头，不治在解析
- **`msg`** 是宿主侧已经 `Logger.format` 渲染好的字符串。跨 fd3 的 JSON 因此一定序列化得动，
  顺带解决了「`args` 里有 Error 对象或循环引用」

**debug 也收**（exporter 设 `levels: { default: 3 }`），跟 info 一样对待，筛不筛归窗格。
**收得到才筛得掉，反过来不行。**

**代价**：2000 条是内存里的天花板，一条按 200 字节估约 400 KB。收了 debug 之后冲得更快——真觉得
翻不回去，改的是这个常量，不是形状。

第二笔：形状定死之后加字段就是跨仓的破坏性变更，而**两仓之间没有任何编译期守卫**（见下面那条）。

**日期**：2026-09-07

### 出口收归内核，`plugin-logger-console` 不再开

**问题**：宿主的 exporter 扩成全量之后，`@cordisjs/plugin-logger-console` 还开不开。两个都在的话，
同一句 cordis 日志在终端里打两遍。

**候选**：① 继续开，内核的 exporter 只送 fd3、绝不投 stderr ② 继续开，主进程按内容去重
③ 不开，内核的 exporter 一手包办（送 fd3 + 投一行 stderr）

**判据**：② 先出局——「两条通道进来的同一句话认成一句」要靠内容比对，那正是 `seq` 这条判据要
消掉的东西。

①③ 之间看的是**「件的日志有没有出口」该不该取决于某个件装没装**。

①之下会出现一个方向反了的局面：件的一条 `info` 出现在**窗格里、却不在文件里**。而文件的存在
理由是「脱离终端起的时候出了事还有地方查」——一个比界面还窄的文件没有意义。补这个洞要求
`logger-console` 必须装着，可它**现在根本没装**：`RECOMMENDED` 是空表，装机一个包都不装。也就是
说文档写着「开着」而盘上是关着的，cordis 的 info/warn 至今一个字都不出。

还有一处不对称：选③、将来嫌前缀丑，是在那一行渲染上加几行，便宜可逆；选①、将来有人漏装或者
在 yml 里注掉那条，是「所有报错都记录下来」当场违约，**而且是静默的**——没人会发现，直到真出事
去翻文件才发现是空的。

格式几乎白得：`Logger.format` 是静态方法，取 `ctx.logger('x').constructor` 就能调（母仓那个件正是
这么避开 `import cordis` 的），`exporter.colors = 3` 就有全色。

**定了**：不开 `logger-console`。开着的 cordis 官方件从四个变**三个**——`plugin-loader`、
`plugin-include`、`plugin-timer`。内核那个 exporter **正文渲染一次、投两处**：
`process.stderr.write`（→ 终端 + 文件）与 fd3（→ 窗格）。

可验收的性质是：**正文一字不差**。终端那行在正文前面多一段 `HH:mm:ss.SSS 级别 名字`，
窗格不要那段——它有结构化字段，时间、级别、来源自己画。

**落地时才想清楚的一处**：那段前缀**四路必须共用一处**（`formatLogLine`）。各写各的话，同一份
日志文件里就是宿主那路带时间与级别、主进程那路只有个方括号前缀，两种格式混着读。第一次实机
起来看文件就撞见了，见[撞过的墙](/docs/walls)。

**代价**：`Logger.format` 只渲染正文，**不带级别、不带 name、不带时间戳、不带 `+耗时`**——那些是
`logger-console` 自己拼的。所以那段前缀要自己写，约六到十行，**从此归内核维护**。

第二笔：**这条推翻了「cordis 官方件开四个」那条的一部分**。那条的代价段写着「停掉 logger-console，
件的日志就静默消失」——如今静默消失这件事没有了，换来的是格式归自己维护。两条都留着，那条的
前提（当时内核没有全量出口，logger-console 是唯一出口）今天已经不成立。

第三笔，也是最要紧的一条防回头的话：**将来想要颜色、对齐、`+耗时`，加在内核那一行渲染上，
不要回头去装 `logger-console`**——装了就是两行重复。

顺带白得一样：`RECOMMENDED` **仍然是空表**，装机那条线一个字不动，首启不连 registry、不装任何包。

### 日志的历史段与实时走 preload 新开的口，不走命令通道

**问题**：日志窗格要取「开机到现在」那一段，还要订阅之后的实时。走已有的 `host.call(命令)`，
还是在 preload 上另开口。

**候选**：① 走命令通道（内核加一条 `kernel.logs` 自省命令）② `kernel.info` 顺手带上
③ preload 上新开两条口

**判据**：**缓冲住在主进程，而命令通道是「渲染层 → 主进程 → fd3 → 宿主 → 件 → 原路回」。**
走①等于让请求从缓冲旁边路过、绕到另一个进程、再把数据原路背回来。

更要命的是**宿主一挂命令全废**（`hostCommand` 直接回「宿主已退出」），**而宿主刚死正是最需要
翻历史的时刻**。这一条单独就足以定案。

①还有一笔账在别处：主进程现在**一个命令名都不认识**，`ipcMain.handle('gwb:command')` 是一条纯
管道。为一条自省数据在它前面插一个「有些 `kernel.*` 会被主进程截住」的分支，代价不对称——破坏
之后每一条命令的路由都多一个问句。② 则是把一张会长到两千条的表塞进自省口，而那个口每次启动都
被渲染层调一次。

实时那一半**也不复用 `gwb:event`**：日志不是件发的事件（四路里三路根本不来自任何件）；复用要给
payload 加一个判别键，等于在件之间的事件总线上划走一个保留字段；而且每个挂了 `onEvent` 的件都会
被日志洪水冲一遍。

**定了**：preload 的面从两样变四样，日志那两条收在一个键下：

```ts
window.gwb = {
  command(name, args?),
  onEvent(cb),
  logs: {
    backlog(): Promise<LogEntry[]>,                     // 开机到此刻
    on(cb: (batch: LogEntry[]) => void): () => void,    // 之后的，按批推
  },
}
```

**实时按批推不按条推**（主进程攒约 100ms 一发）：一条一次 IPC 的话，崩溃循环刷屏时光是 IPC 就能
把渲染层压住。

**「窗口就绪之前的条目一条不丢」靠三件事落实，缺一条就不成立**：入缓冲那一步**绝不看窗口在不在**
（推窗的 sink 为空时照常入缓冲）；窗格**先订阅、后取 backlog**，两段按 `seq` 合并；`seq` 真唯一。

**历史段只覆盖本次启动**。跨启动要再写一份结构化的 JSONL，那是净新增的第二份日志文件，两份内容
不一致时没人说得清该信哪一份——真要，重新过一遍准入判据。

**代价**：**窗格件从此有一样东西不从 `args` 来。** `mountPane` 只给 `{ host, shell, pane }`，而日志
窗格要伸手去够 `window.gwb`——这是个先例，将来会有人照着办。所以话要说死：`window.gwb` 是**页面的
公共面**（谁在这页上跑都够得着），`args` 是**外壳给窗格的额外便利**，两者不是替代关系。
**外壳不该转发日志**——它凭什么认识「日志」。

第二笔：preload 多两个口，将来打包与沙箱那边多两处要顾。

### 日志文件按字节轮转，不按天也不按启动

**问题**：整条 stderr 追加进 `<home>/gwb-kernel.log`，一次启动写一条分隔线，**永远长**。

**候选**：① 保持单文件不轮转 ② 按天一份 ③ 每次启动一份 ④ 超过字节上限就切段，超过份数删最旧

**判据**：**封不封得住顶。** ② 封不住——一次崩溃循环几分钟能刷几十 MB，而那一天就是一个文件。
③ 反过来：开发期一天起停几十次，目录里躺着几十个几 KB 的碎片，而「刚才那一趟」正是最常要找的
东西，碎片一多反而认不出来。④ 两头都封得住。

**按字节不按行数**，两条理由：行长差异巨大（一条 stack 三千字、一条「挂上」三十字），行数切不出
可预期的文件大小；而且**字节数是唯一 O(1) 判得出的**——轮转判断跑在**每一次 `write` 上**，它必须
是常数时间，`chunk.length` 白得，数 `\n` 要扫一遍缓冲区。

要剔掉一个假理由：**「防磁盘涨满」不能拿来当依据**——那属于「让失败变得体面」，正是这条线在砍的
东西。真理由只有两条：无限长的文件读不动；将来若要从文件翻更早的历史，几百 MB 没法翻。

**定了**：`<home>/logs/`，现役那份叫 `gwb.log`，写满 **2 MB** 就切、归档成 `gwb-<切段时刻>.log`，
目录里**保留 20 份**，超出的删最旧。每次启动仍写一条分隔线——同一份里可能跨好几次启动，没有它
认不出边界。

三处实现上定死的：

- **记账不 `fstat`**：`written += chunk.length`，启动时一次 `statSync` 取初值。每行一次 fstat 等于
  把落盘成本翻倍
- **切的三步全同步**（`closeSync` → rename → `openSync`），保住[现在那个「同步写」的性质](/docs/walls)。
  先关再 rename 是 Windows 要求的——rename 一个自己正开着的文件会 `EPERM`
- **两个 latch 不共用**：`dead`（写失败 → 此后不写）与 `rotateDead`（切失败 → **不再切，但照常写**）。
  「只说一次、此后不再试」那条理由（每行重试把每行输出变成一次失败的系统调用）在轮转上**不成立**，
  共用会把「一次 rename 撞占用」放大成「整条落盘线掐死」——而 Windows 上拿编辑器开着归档文件就够
  触发一次

**代价**：`log-file.ts` 从 38 行涨到约 95，**是这一轮里增幅最大的一个文件**。能砍掉的只有它——
回退成无限 append，其余都是「四路进窗格」的最小集。

第二笔：只留最近 20 份，**再往前就是没有了**。想留全的人自己搬走。

第三笔：删最旧要扫一遍目录再排序（时刻命名的代价；序号命名只需一条 rename 链）。换来的是归档名
自己说得出「这段是什么时候的」。

旧的 `<home>/gwb-kernel.log` **不搬、不迁移、不删**，留在原地不再被写——日志不是数据，写一段搬运
是纯粹的体面；而删用户的东西比留一个孤儿文件严重得多。

**日期**：2026-09-07

### 日志条目的形状不进词汇表包

**问题**：`{ seq, ts, source, level, name, msg }` 是内核与件之间的契约面。要不要给
`@godcreator02/gwb-plugin-api` 加上它。

**候选**：① 加进词汇表包 ② 不加，正本写进文档，件那边手写一份并配判形函数

**判据**：三条，第二条是决定性的。

一、**它不是「内核与所有件」的契约，是「内核与日志窗格件」的契约**，全部件里只有一个消费方。
词汇表的收进判据是「多数件都要」——[实测支持](/docs/walls)：母仓 11 件全扫，从平台包只取了 12 个
名字，11 件全用的只有 1 个。

二、**它走的是渲染层那条路，不是 cordis 服务那条路。** 窗格的 `client.js` 跑在浏览器里，而词汇表
包的入口是 node 半的（`import type { Context } from 'cordis'`）。要给它加一个 `./client` 子出口
——那是**给这个包加第二类东西**，而「内核配几个包」那条定过：第二个要正经过准入判据两道关。
第一关就否了：内核自己不需要这个类型，需要它的是一个件。

三、`bootShell` 的 args 形状、`mountPane` 的 args 形状**都没进词汇表包**，正本都在文档里。日志条目
跟它们是同一类东西。而且跨 IPC 来的东西本来就得当 `unknown` 收窄一次，有没有类型包都得写那个
判形函数。

**定了**：不加。正本写进「写一个件」那页新增的一节，件那边五行 `interface` 加一个判形函数当运行期
守卫，认不出的条目丢掉、不崩。

**代价**：件那边手写一份类型，**内核改形状时没人拦**——跟 `bootShell` 的 args 同一笔账。词汇表包
维持在一个包、五个名字。

**将来真出现「第二个消费日志的件」，或者「形状改过一次而件没跟上、运行时才发现」的现场，那时再
讨论进不进词汇表包，并且要连着「它拦住了什么」一起记。**

### 设置件：一包全部，值分两份落盘

**问题**：件要有地方放凭据和偏好。`gwbData` 是「每个件自己的地盘」（身份自动绑定、读不到
别人的），而一个 API key 三个件都要用——结构上放不下。另外「设置」这个名字底下压着两件
不相干的事：一份全局 JSON 的读写，和「插件启停/卸载」（那半操作 `ctx.loader`）。

**候选**：① 边界——只做键值存储 / 一包全部 / 先不划 ② 存储——一个文件扁平表 / 按件嵌套 /
两层 ③ 落点——`<home>/settings.json` / 走 `gwbData` 的 `<home>/data/<包名>/` ④ 作用域——
只做 home 级 / 加机器级 ⑤ 官方件——用 `plugin-loader-webui` / 自己调 `ctx.loader`

**判据**：几条各管一段——

- **凭据不能跟着 home 走**。home 分格的目的是「验收有干净场子」，隔离的是「装哪些件、件
  怎么配」；凭据是「我是谁」，跟开哪个场子正交。复制一份的代价是轮换时必然漏一处，而漏掉
  那份的症状是「这个件能用、那个件 401」，排查时根本不会想到设置有好几份
- **`cordis.yml` 的 `config` 当不了设置**。它是「件怎么挂起来」不是「件跑起来用什么」：
  按条目存放不下跨件共享的凭据，天生 home 级、跨不了 home，改一项要整个重挂而且
  `inject` 它的件跟着抖，写回还会把用户手写的注释全丢掉（见 walls）
- **两份文件的键必然不同**。`entryId` 是 home 局部的概念，机器级跨 home 只能用包名；而
  home 级要能分开「同一个包挂的两条条目」，只有 `entryId` 做得到
- **元信息落盘，因为这个件还管启停**。停掉一个件它的设置就从界面上消失、连「先配好 key
  再启用」都做不了，那很怪
- **官方件版本上装得进来，但要拖 webui＋server**（上面「官方件开几个」那条已订正）

**定了**：`@godcreator02/gwb-settings`，提供 `ctx.gwbSettings`（`define`/`get`/`set`/`delete`）。

- 值落**两份**：`<home>/settings.json` 跟 `cordis.yml` 并排、键是 `entryId`；
  `<userData>/machine.json` 跟 `homes/` 并列、键是**包名**。两份同一个结构：按件嵌套，
  外加一格 `"*"` 公共区
- 件用短 key，落哪由 `scope: 'home' | 'machine'` ＋ `shared` 两个声明算出来。**这两个维度
  正交，合起来是四格**——但实践中只有两种写法（普通项、凭据项），而且每一格都是被具体
  需求逼出来的，不是预先设计的
- **元信息件注册＋落盘留一份**：件挂着时代码是权威、覆盖盘上那份；件停了用盘上那份显示
  （`all()` 的 `live` 字段标着）
- `all()` **只做命令不进服务面**：界面要看全部，而服务面受身份约束，两者矛盾
- 命令面走**嵌套注入**不硬 `inject`——没有命令总线时服务面照样完整。这一条跟 `gwb-shell`
  判得不一样，它没有 cli 就是个开不出任何东西的空井
- 插件启停/卸载是**第二版**，自己调 `ctx.loader`，不用官方件

**代价**：

1. **凭据明文**（个人应用，拍过板的）。三笔账记在这儿，将来疼的时候认得出：`settings.all`
   把凭据交给渲染层——眼下同机、件都是自己写的，但 roadmap 里「MCP / 外部访问」一旦到期，
   **第一个要重看的就是这条命令**；`machine.json` 跨所有 home，一处泄露就是全部；它跟
   `homes/` 并列，备份整个 userData 时跟着走
2. **开了一个口子**：件可以自己往 home 根、甚至 userData 根写文件。settings 是**特例**——
   它代管的是归用户的文件，跟 `cordis.yml` 同性质。**别让它变成惯例**
3. **`machine.json` 跨 home 共享 = 两个实例可能同写**。原子 rename 保证不写坏，但会丢更新，
   而且完全静默。眼下靠「写前重读合并」把窗口缩到毫秒级，不是根治
4. **依赖条目 id 是手写的**。随机 id 下 home 级设置每次启动对不上，只能 warn 一声（见 walls）
