# 定过的事

**这一页是事前的选择**，[撞过的墙](/docs/walls)是事后的教训。一个选择后来撞了墙，
两边各记各的。

每条固定六段。「代价」那段最要紧——将来后悔时，得认得出是不是这一条在疼。

---

### 另起一条线，而不是在母仓上做减法

**问题**：母仓约 5100 行，其中约 3600 行服务于「让失败变得体面」。想要一个只做必需事情的
内核，是改它还是重来。

**候选**：① 在母仓上砍掉那 3600 行 ② 另起一个仓从头推

**判据**：砍掉等于扔掉那些行背后的教训（每一条都对应一次真翻车）；而重来可以**移除产生
那些教训的功能本身**——不自动升级，四路判定连同它制造的全部麻烦一起消失。两者性质不同：
前者是删代码，后者是删需求。

**定了**：另起 `gwb-kernel`。后续进一步定为**正线**，母仓与件仓准备废弃、只作参考，
插件全部重做。

**代价**：两条线并存期间要维护两套；母仓那些坑要重新撞一遍（已经撞了好几个）。
另外「查母仓」有个反向风险——去看一个坑怎么解的，顺手把解法连同周围那圈机制一起搬回来
是最自然的动作。

**日期**：2026-09-07

### 打包器到期再选，现在不换 Electron Forge

**问题**：构建用 electron-vite、打包用 electron-builder（母仓那套），要不要换成官方的 Forge。

**候选**：① 现在换 Forge ② 保持现状，打包到期再选

**判据**：查到的事实——Forge 的 `plugin-vite` 自 v7.5.0 起标为 **experimental**，至今仍是；
而 electron-vite 是它的**上游**（官方 FAQ 写着「功能稳定后会 port 到 plugin-vite」）。
更关键的是时机：换 Forge 动的是**打包层与编排层**，而前四刀根本不碰打包——现在换等于在
主线上插一条支线，两者失败症状还长得像。

**定了**：不换。打包到期时（要出安装包）再拿两个各试一次，那时手上有一个确定的问题：
pnpm 怎么进产物。

**代价**：以后真要换，接线要重做一遍。为把这个代价压住，同时定了一条零成本的约束：
**别让打包器的形状渗进源码**——主进程走正常的包解析，不依赖「依赖被内联进束」。

**日期**：2026-09-07

### 取址交给 cordis 官方 loader，内核自己不做

**问题**：第二刀自己写了 87 行取址（读 yml → 拼路径 → import）。cordis 有官方的
`plugin-loader` 与 `plugin-include`，要不要用。

**候选**：① 保持自己写 ② 挂 loader + include

**判据**：`EntryTree` 的 API 是现成的（`create`/`remove`/`update`/`store`/`await`），
**热挂卸是白得的**——直接消掉了「设置件改完要重启」那个取舍。而母仓不用 include、自己写
了 500 行做同一件事。

**定了**：内核只挂 loader，再往它的树上放一条 `cordis:include` 条目，其余全归这两个。
内核连 yml 都不认识。

**代价**：多两个依赖；引导链有四条判据要记住（都住应用依赖树、include 走 `builtins`、
做成条目而非 `ctx.plugin`、承载 yml 那条 id 写死）。这些连同踩到的坑记在 walls。

**日期**：2026-09-07

### cordis 官方件开四个，不开六个

**问题**：官方件有十来个，开哪些。

**候选**：逐个判。

**判据**：「真遇到需求才加」。

**定了**：开 `plugin-loader`、`plugin-include`（内核挂）、`plugin-timer`、
`plugin-logger-console`（装进 home）。不开 `plugin-hmr`（**在这个架构下不起作用**：跑的是
home 里那份产物，盯仓内源码盯到变化也没有对应模块可换）、`plugin-http`/`plugin-server`
（没有外部访问需求）、`plugin-config`/`plugin-webui`（Koishi 生态的）、`plugin-database`、
`@cordisjs/schema`。

**代价**：没有 hmr，改件要重新构建发版装进 home。timer 与 logger-console 是普通件，
**可以被停掉**——停掉 logger-console，件的日志就静默消失（内核自己的日志不受影响，
另有保底 error 出口）。

**日期**：2026-09-07

### 组件复用分三层，不照搬母仓那套

**问题**：shadcn/tailwind 组件在多个件之间怎么复用。

**候选**：① 共享一个组件库 + importmap（母仓做法）② 每个件全自带 ③ 分层处理

**判据**：实测数据——母仓那套里 **CSS 一分没省**（8 个件 8 张 62.8–66.5KB 的表，彼此差不到
6%），省下的只有 JS，而代价是 3 个平台包严格同号 + 每件 4 处版本钉死 + 3 份 tsconfig +
6 个产物守卫 + 7 处分散真源 + **8 类静默失败**。这个比例不成立。

另外这三样性质不同：React 是**运行时环境**（多份是多个世界），组件源码是**代码**（多份
只是体积与漂移），CSS 工具类是**样式规则**（多份会因属性顺序互相污染）。

**定了**：
- **design token（CSS 变量）共享一份**，由外壳件提供——这是统一风格的真正机制，也是
  shadcn 官方的做法
- **组件源码每个件复制一份**，配一个自建 shadcn registry 保持同源
- **React 共享**，但机制上内核零 UI 知识：件在 `package.json` 里声明 `gwb.shared`，
  内核收集所有条目的声明拼 importmap，`gwb://` 多认一条 `/shared/` 路径

**代价**：组件改一处要改 N 个件（靠 registry 重拉 + 纪律）；CSS scope 围栏与 Portal 逃逸
这两件事躲不掉，仍要做。React 共享那条**还没实现**——等外壳件真要用时再做。

**日期**：2026-09-07

### 服务名一律 `gwb` 开头，不做「通用名才加」

**问题**：cordis 的 `ctx` 是共享命名空间，件的服务名要不要统一加前缀。

**候选**：① 全加 ② 只有通用名（`cli`、`http`）才加

**判据**：**代价不对称**。该加没加、将来撞了要改名，所有消费方的 `inject` 与 `ctx.xxx`
跟着改，那是破坏性变更；不该加而加了，只是名字长几个字符。一边破坏性变更一边审美，
那道「够不够通用」的主观题不值得天天做一遍。撞名风险也不是假想：home 里已装着官方件，
`timer`/`loader`/`logger` 被占着。

**定了**：一律 `gwb` 开头小驼峰，默认跟件名对应。cordis 官方件的服务照它自己的。

**代价**：「宿主给的 vs 件给的」这个区分不再由命名承担，改由契约说清（内核提供的只有
`gwbKernel` 一个）。白得一条反向信息：看到 `ctx.foo` 没前缀就知道它不是这个生态的。

**日期**：2026-09-07

### 件的包名加 `gwb-` 前缀，scope 不换

**问题**：新做的件要跟废弃那批错开，而 `@godcreator02/cli`、`/shell` 等已被占着。

**候选**：① 换 scope（另建 npm organization）② 加 `gwb-` 前缀

**判据**：scope 绑定 npm 账号（注册的就是 `godcreator02`），换要另建 org；而本机 Verdaccio
上 scope 本来就随便定。加前缀成本为零，且实测 `gwb-shell` 这些名字全空着。

**定了**：`@godcreator02/gwb-<件名>`。

**代价**：包名比原来长；两批件在同一个 registry 上并存一段时间。

**日期**：2026-09-07

### 依赖写 peer 还是 dev：三档，不是两档

**问题**：母仓的判据是「运行时真 import 了才写 peer，只 `import type` 写 dev」。按它写，
两次都错。

**候选**：沿用两档 / 补一档中间的。

**判据**：**发布出去的包不带 devDependencies**。词汇表包的 `GwbContext extends Context` 把
cordis 写成 dev，消费方那边 `ctx.logger`/`effect`/`provide` 全报「不存在」；`gwb-cli` 的
`GwbCli.run` 回 `GwbResult` 是同一回事。

**定了**：三档——运行时真 import → peer；**只 import type 但出现在导出的类型里 → 也要
peer**；只在实现内部用、不出现在导出面 → dev。

**代价**：判断时要多看一眼「它出现在导出面吗」。白得一条：peer 声明之后 pnpm 会把它自动
装进 home，消费方不用手动装。

**日期**：2026-09-07

### 文档三层分流，检查单独成命令

**问题**：`CLAUDE.md` 涨到 147 行 14 节，什么都往里塞。

**候选**：① 继续塞 ② 分层

**判据**：`CLAUDE.md` **每次会话都进上下文**，塞多了每次都在付；而「为什么」和「怎么做」
是需要时才查的。三层各有各的判据（不知道就做错 / 需要时查 / 读不懂这一行）。

**定了**：`CLAUDE.md` 只装硬约束（147 → 82 行）；为什么与踩坑进文档站并用 livedoc **钉在
代码上**；注释只写现状。**注释里不写文档站的页名或锚点**——livedoc 只钉「文档 → 代码」，
反向没守卫，写死位置必然腐烂。

`livedoc check` **不进 `pnpm check`**：它要起文档站的解析链，每次跑测试都带上太慢。
单独两条 `pnpm doc` / `pnpm doc:confirm`。

**代价**：钉住的代码一改要跑一次 `pnpm doc` 再复核——多一道确认。而检查不在门禁里，
意味着**靠人的纪律**：提交前跑一次。

**日期**：2026-09-07
