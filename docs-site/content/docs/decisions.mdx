# 定过的事

**这一页是事前的选择**，[撞过的墙](/docs/walls)是事后的教训。一个选择后来撞了墙，
两边各记各的。

每条固定六段。「代价」那段最要紧——将来后悔时，得认得出是不是这一条在疼。

---

### 另起一条线，而不是在母仓上做减法

**问题**：母仓约 5100 行，其中约 3600 行服务于「让失败变得体面」。想要一个只做必需事情的
内核，是改它还是重来。

**候选**：① 在母仓上砍掉那 3600 行 ② 另起一个仓从头推

**判据**：砍掉等于扔掉那些行背后的教训（每一条都对应一次真翻车）；而重来可以**移除产生
那些教训的功能本身**——不自动升级，四路判定连同它制造的全部麻烦一起消失。两者性质不同：
前者是删代码，后者是删需求。

**定了**：另起 `gwb-kernel`。后续进一步定为**正线**，母仓与件仓准备废弃、只作参考，
插件全部重做。

**代价**：两条线并存期间要维护两套；母仓那些坑要重新撞一遍（已经撞了好几个）。
另外「查母仓」有个反向风险——去看一个坑怎么解的，顺手把解法连同周围那圈机制一起搬回来
是最自然的动作。

**日期**：2026-09-07

### 打包器到期再选，现在不换 Electron Forge

**问题**：构建用 electron-vite、打包用 electron-builder（母仓那套），要不要换成官方的 Forge。

**候选**：① 现在换 Forge ② 保持现状，打包到期再选

**判据**：查到的事实——Forge 的 `plugin-vite` 自 v7.5.0 起标为 **experimental**，至今仍是；
而 electron-vite 是它的**上游**（官方 FAQ 写着「功能稳定后会 port 到 plugin-vite」）。
更关键的是时机：换 Forge 动的是**打包层与编排层**，而前四刀根本不碰打包——现在换等于在
主线上插一条支线，两者失败症状还长得像。

**定了**：不换。打包到期时（要出安装包）再拿两个各试一次，那时手上有一个确定的问题：
pnpm 怎么进产物。

**代价**：以后真要换，接线要重做一遍。为把这个代价压住，同时定了一条零成本的约束：
**别让打包器的形状渗进源码**——主进程走正常的包解析，不依赖「依赖被内联进束」。

**日期**：2026-09-07

### 取址交给 cordis 官方 loader，内核自己不做

**问题**：第二刀自己写了 87 行取址（读 yml → 拼路径 → import）。cordis 有官方的
`plugin-loader` 与 `plugin-include`，要不要用。

**候选**：① 保持自己写 ② 挂 loader + include

**判据**：`EntryTree` 的 API 是现成的（`create`/`remove`/`update`/`store`/`await`），
**热挂卸是白得的**——直接消掉了「设置件改完要重启」那个取舍。而母仓不用 include、自己写
了 500 行做同一件事。

**定了**：内核只挂 loader，再往它的树上放一条 `cordis:include` 条目，其余全归这两个。
内核连 yml 都不认识。

**代价**：多两个依赖；引导链有四条判据要记住（都住应用依赖树、include 走 `builtins`、
做成条目而非 `ctx.plugin`、承载 yml 那条 id 写死）。这些连同踩到的坑记在 walls。

**日期**：2026-09-07

### cordis 官方件开四个，不开六个

**问题**：官方件有十来个，开哪些。

**候选**：逐个判。

**判据**：「真遇到需求才加」。

**定了**：开 `plugin-loader`、`plugin-include`（内核挂）、`plugin-timer`、
`plugin-logger-console`（装进 home）。不开 `plugin-hmr`（**在这个架构下不起作用**：跑的是
home 里那份产物，盯仓内源码盯到变化也没有对应模块可换）、`plugin-http`/`plugin-server`
（没有外部访问需求）、`plugin-config`/`plugin-webui`（Koishi 生态的）、`plugin-database`、
`@cordisjs/schema`。

**代价**：没有 hmr，改件要重新构建发版装进 home。timer 与 logger-console 是普通件，
**可以被停掉**——停掉 logger-console，件的日志就静默消失（内核自己的日志不受影响，
另有保底 error 出口）。

**日期**：2026-09-07

### 组件复用分三层，不照搬母仓那套

**问题**：shadcn/tailwind 组件在多个件之间怎么复用。

**候选**：① 共享一个组件库 + importmap（母仓做法）② 每个件全自带 ③ 分层处理

**判据**：实测数据——母仓那套里 **CSS 一分没省**（8 个件 8 张 62.8–66.5KB 的表，彼此差不到
6%），省下的只有 JS，而代价是 3 个平台包严格同号 + 每件 4 处版本钉死 + 3 份 tsconfig +
6 个产物守卫 + 7 处分散真源 + **8 类静默失败**。这个比例不成立。

另外这三样性质不同：React 是**运行时环境**（多份是多个世界），组件源码是**代码**（多份
只是体积与漂移），CSS 工具类是**样式规则**（多份会因属性顺序互相污染）。

**定了**：**样式共享、组件各拉各的**——这正是 shadcn 的原教旨。件持有的是结构与语义类名，
主题是语义名背后的值，两层正交（Obsidian 400+ 变量、插件只准写 `var(--x)`，同一个机制）。

- **design token 共享一份**，独立成 `@godcreator02/gwb-tokens` 包，跟件平级装进 home，
  由外壳件注 `<link>` 引进页面
- **组件每个件自己从 shadcn 官方拉**（件里放一份 `components.json`，`shadcn add <名>`）。
  **仓里没有任何「组件源」，也不建 registry**
- **React 共享**，机制上内核零 UI 知识

**代价**：各件的组件版本会漂移（A 件三月拉的，B 件九月拉的）。**而这正是要的** ——
件独立发版，各自决定什么时候跟进；统一风格由令牌保证，不由组件源码一致保证。
CSS scope 围栏与 Portal 逃逸这两件事仍然躲不掉。

**日期**：2026-09-07（同日落地，形状有三处细化：`gwb.shared` 由**提供方**声明「我提供
这几个裸名」而不是消费方声明要什么；内核扫 home 清单的 `dependencies` 收集，不扫条目表；
`gwb://` 没有多开 `/shared/` 路径——子路径通用化之后共享包跟件走同一条 URL）

**上面那条 CSS 判据要读准**：「8 个件 8 张 63KB 的表、彼此差不到 6%」**不是「共享 CSS
无效」的证据，是「母仓没共享 CSS」的证据**——它只共享了 JS。反过来读才对：8 张表高度重复，
说明每张里绝大部分是同一套东西。而各拉各的之后每个件只扫自己真用到的类，实测验收件那张
**16.9KB**，比母仓那种扫整个共享组件库的 63KB 小得多。

**这条改过一次**：起初写的是「组件源码每个件复制一份，同源先靠手工，撞疼了再建 registry」。
那句话隐含着「件之间的组件该保持一致，所以需要一个源来维护」——**那个前提不成立**，是母仓
`gwb-ui` 共享组件包留下的思维惯性。shadcn 的组件本来就是给你改的，A 件的 button 跟 B 件的
不必一样。取消那个前提之后，registry、复制源、手工同步全都不需要了，而 shadcn CLI 在
monorepo 下本来就是「每个 workspace 各有一份 `components.json`」。

### 服务名一律 `gwb` 开头，不做「通用名才加」

**问题**：cordis 的 `ctx` 是共享命名空间，件的服务名要不要统一加前缀。

**候选**：① 全加 ② 只有通用名（`cli`、`http`）才加

**判据**：**代价不对称**。该加没加、将来撞了要改名，所有消费方的 `inject` 与 `ctx.xxx`
跟着改，那是破坏性变更；不该加而加了，只是名字长几个字符。一边破坏性变更一边审美，
那道「够不够通用」的主观题不值得天天做一遍。撞名风险也不是假想：home 里已装着官方件，
`timer`/`loader`/`logger` 被占着。

**定了**：一律 `gwb` 开头小驼峰，默认跟件名对应。cordis 官方件的服务照它自己的。

**代价**：「宿主给的 vs 件给的」这个区分不再由命名承担，改由契约说清（内核提供的只有
`gwbKernel` 一个）。白得一条反向信息：看到 `ctx.foo` 没前缀就知道它不是这个生态的。

**日期**：2026-09-07

### 件的包名加 `gwb-` 前缀，scope 不换

**问题**：新做的件要跟废弃那批错开，而 `@godcreator02/cli`、`/shell` 等已被占着。

**候选**：① 换 scope（另建 npm organization）② 加 `gwb-` 前缀

**判据**：scope 绑定 npm 账号（注册的就是 `godcreator02`），换要另建 org；而本机 Verdaccio
上 scope 本来就随便定。加前缀成本为零，且实测 `gwb-shell` 这些名字全空着。

**定了**：`@godcreator02/gwb-<件名>`。

**代价**：包名比原来长；两批件在同一个 registry 上并存一段时间。

**日期**：2026-09-07

### 依赖写 peer 还是 dev：三档，不是两档

**问题**：母仓的判据是「运行时真 import 了才写 peer，只 `import type` 写 dev」。按它写，
两次都错。

**候选**：沿用两档 / 补一档中间的。

**判据**：**发布出去的包不带 devDependencies**。词汇表包的 `GwbContext extends Context` 把
cordis 写成 dev，消费方那边 `ctx.logger`/`effect`/`provide` 全报「不存在」；`gwb-cli` 的
`GwbCli.run` 回 `GwbResult` 是同一回事。

**定了**：三档——运行时真 import → peer；**只 import type 但出现在导出的类型里 → 也要
peer**；只在实现内部用、不出现在导出面 → dev。

**代价**：判断时要多看一眼「它出现在导出面吗」。白得一条：peer 声明之后 pnpm 会把它自动
装进 home，消费方不用手动装。

**日期**：2026-09-07

### 引入 oxlint（含 type-aware），但不抄母仓那份白名单

**问题**：正线两个仓的门禁只有 `typecheck + test`，一条 lint 都没有。而代码里有三条纪律完全靠
人记住：promise 一律 `void` 前缀、`JSON.parse` 先落 `unknown` 再 `as` 到具名形状、`catch (err: unknown)`。

**候选**：① 什么都不做 ② 引 oxlint，照抄母仓那份配置 ③ 引 oxlint，规则集重新定
④ 顺带把格式化（oxfmt）、CI、git hooks 一起补上

**判据**：先说为什么过得了准入判据第二关——**这不是「将来可能要」**，那三条纪律现在没有任何东西
守着，而 type-aware 的 `no-floating-promises`、`no-unsafe-*` 恰好就是守它们的。（顺带把一件事
落成先例：**两道关的第一关对工具链不适用**——它问的是「进内核还是做插件」，lint 两者都不是；
第二关适用，而且要照常回答「现场是什么」。）

排除②的理由是实测。先看清一件容易看错的事：**母仓那 18 条并不是默认那批的子集**——18 条里
10 条本来就默认开着，另外 8 条是从 pedantic / suspicious 额外捞的 `no-unsafe-*` 一族。所以那份
配置的净效果是**「砍掉 101 条 correctness，换来 8 条 `no-unsafe-*`」**，而那 8 条是为母仓
`GwbContext` 的 `[key: string]: any` 索引签名服务的。

同一份代码上跑三个口径：**只开默认（111 条）零诊断；母仓 18 条报 1 条；并集 119 条也是 1 条**。
那 1 条是 `host/main.ts` 的 `no-unsafe-argument`，出在 `...message.args`——**是 cordis 自己把
`logger.args` 声明成 `any[]`**，不是本仓的 any。

正线仓没有 any 索引签名，那 8 条在这里的全部收获就是这条第三方带进来的、实际无害的报警；
而白名单的真代价是**新规则永远进不来**——oxlint 升级新增的 correctness 规则，白名单口径下得有人
手工去追。**前提要记住**：将来真出现 any 扩散，那 8 条的价值就回来了。

母仓文档站那张工具链表里，**oxlint 是唯一一件没写选型理由的工具**——这一条正好补上那处空白。

**定了**：`oxlint 1.81.0` + `oxlint-tsgolint 7.0.2001`，两个都**精确钉版**，`pnpm lint` 串进
`pnpm check`（typecheck → lint → test）。**配置只做三件事：指 schema、开 type-aware、排掉不该扫
的目录——一条 `rules`、一条 `plugins` 都不写。** 五件实测撞出来的细节：

- **`plugins` 不写**：这字段是**覆盖不是追加**（只写 `["typescript"]` 时规则数从 111 掉到 84），
  而写全默认那三个等于没写（规则数一样是 111），却多一份会跟默认漂移的手工名单
- **`no-unused-vars` 的 ignorePattern 不写**：oxlint 这条规则**默认就认 `^_`**，文档特意注明这跟
  ESLint 与 typescript-eslint 不同——那两个从不提供默认 pattern。母仓那三行是 ESLint 时代的遗产
- **`--deny-warnings` 不能省**：不带它，4 条诊断照样 `exit 0`——屏幕上有红字而门禁放行
- **`ignorePatterns` 相对配置文件所在目录解析**（拿临时配置做反向探针时，`docs-site/**` 因此没
  匹配上，文件数从 17 变 28）
- **排产物那条当时得锚定写**：`packages/gwb-plugin-api/lib/**`，图省事写 `**/lib` 会连
  `src/lib/` 这种真源码目录一起罩住。跟 `.gitignore` 里踩过的是同一个形状，而且**在 lint 这边更
  隐蔽**：少扫一个文件是没有症状的。（**后来产物目录整体改成 `dist`**，这条锚定连同 `.gitignore`
  里那行注释一起删掉了——`**/dist` 可以放心裸写。见「产物目录一律 dist」那条）

`docs-site` 排除是**硬理由不是抄母仓**：它钉 `typescript ^6.0.3`，而 type-aware 要 TS 7+。

串进 `check` 而不是像 `pnpm doc` 那样单开：那条先例的实际内容是「要起文档站的解析链、太慢」，
在这儿没被触发——**实测 lint 单跑 293ms，整条 check 3.1s**。将来真超过 5 秒再考虑拆，而且那时
正确的拆法是「不带 type-aware 的进门禁 + `lint:types` 单开」，不是整条拿出去。

**代价**：

- 精确钉版意味着**升级要人工做**。换来的是门禁口径不会因为一次 `pnpm install` 悄悄漂移——
  这条线刻意不做 CI，门禁只在人手跑 `pnpm check` 时才跑，一次漂移可能几天后才被发现
- **`--type-check` 明确不用**（它能替代 `tsc --noEmit`，但这里有三份不同口径的 tsconfig，替不掉
  这个结构；换掉 tsc 是另一个数量级的决定）
- **oxfmt 明确不引入**（还在 0.66.0 没到 1.0；母仓也完全没有格式化工具）。**CI、git hooks、
  `--fix` 同样不做**——门禁靠 `pnpm check` 加纪律。写下来是因为下次一定会有人拿「oxlint 都有了
  顺手加 oxfmt」来推
- **lint 面靠纪律不靠机制**：当前是 17 个 `.ts`（`apps/desktop/src` 11 + `tests` 3 + 两份 config
  + 词汇表包 1）。将来加了新包忘了它在不在某份 tsconfig 里，它会静默留在 lint 面外——**记下这个
  数就是唯一的守卫**，下次数不上就有人会发现

### 文档三层分流，检查单独成命令

**问题**：`CLAUDE.md` 涨到 147 行 14 节，什么都往里塞。

**候选**：① 继续塞 ② 分层

**判据**：`CLAUDE.md` **每次会话都进上下文**，塞多了每次都在付；而「为什么」和「怎么做」
是需要时才查的。三层各有各的判据（不知道就做错 / 需要时查 / 读不懂这一行）。

**定了**：`CLAUDE.md` 只装硬约束（147 → 82 行）；为什么与踩坑进文档站并用 livedoc **钉在
代码上**；注释只写现状。**注释里不写文档站的页名或锚点**——livedoc 只钉「文档 → 代码」，
反向没守卫，写死位置必然腐烂。

`livedoc check` **不进 `pnpm check`**：它要起文档站的解析链，每次跑测试都带上太慢。
单独两条 `pnpm doc` / `pnpm doc:confirm`。

**代价**：钉住的代码一改要跑一次 `pnpm doc` 再复核——多一道确认。而检查不在门禁里，
意味着**靠人的纪律**：提交前跑一次。

### 窗格清单动态注册，不做静态声明

**问题**：外壳要排出「可开窗格」表。清单是件在 `package.json` 里静态声明（母仓做法），
还是件挂上之后调 API 注册。

**候选**：① 静态 `gwb.panes` ② 运行时注册

**判据**：母仓那条注释给的理由是「外壳排表时 client 束还没加载」——**那个前提在这条线上
不成立**。cordis 架构下「件挂上」与「件的浏览器束加载」是两件事：件挂上时它的 node 半
就在跑了，而 `client.js` 仍然是点了才动态 import。所以注册可以发生在 `apply` 里，
**动态注册根本不牺牲懒加载**。

**定了**：运行时注册。窗格清单不是「第一个插件存在之前必须发生的事」，内核一行不加，
服务由外壳件提供。

**代价**：件没挂上时就说不出它有什么窗格（要列「可用但未启用」的界面得自己去读包清单）。
白得三样：热挂卸跟着 loader 走、件能按配置决定开几格、不用写母仓那 25 行「防盘上清单被
手改」的宽容校验——注册来的东西不用防。

**日期**：2026-09-07

### 运行时环境由内核拼，件只声明自己提供什么

**问题**：浏览器里的裸名 `import 'react'` 要有 importmap 才解析得了。这张表谁拼、谁注入。

**候选**：① 内核 ② 外壳件 ③ 内核产物自带 react（母仓做法）

**判据**：提供运行时环境是**通用能力**，不是某个件的职责——要 React 的不会只有外壳。
主流做法也在这一边：Module Federation 是宿主声明 shared 做版本协商，single-spa 是容器
注入 importmap，没有谁把它交给业务插件。③ 则让内核认识了 `react` 这个词。

而母仓为「importmap 必须在文档开头注入」付过一笔代价（`sharedBase` 得在 preload 就位，
缺了整页重载补救）——**实测这笔不用付了**：本机 Chromium 152 上，页面跑过 module 脚本
之后再注入照样解析，多张表可以追加新键。

**定了**：内核拼、内核注，注入点在「拿到条目表之后、第一句动态 import 之前」。件在包清单
里声明 `gwb.shared`，内核只搬运声明，全程不认识 `react` 这个词。

**代价**：内核多一块收集与注入的机制（约 30 行）。三条约束跟着来：一个裸名只许一个提供方
（撞了报错，因为浏览器那边已解析过的键本来也覆盖不掉）；提供运行时的包必须装在 home
**顶层**（内核按包名拼路径，不走 node 解析）；npm 上的 react 不能直接用——它至今没有
ESM 出口，得有人打一份 ESM 包发出来。

**日期**：2026-09-07

### 词汇表是独立包、与内核同仓——不是件，也不走服务

**问题**：内核与件之间的契约（三个类型加两个纯函数）以什么形态存在、住哪个仓。被连挑五问：
必须是个包吗 / 不能全走 cordis 服务吗 / 为什么内核里只有它是包 / 为什么不做成件住件仓 /
内核一定要配几个包。

**候选**：① 独立包住内核仓（现状） ② 砍掉全走 cordis 服务（弱类型约定） ③ 做成件住件仓
④ 件仓手写类型（消费方持有契约）

**判据**：两条。一、**类型是编译期的东西，跨仓就得有可 install 的载体**——cordis 服务递
运行时值、递不了类型：件在 install 后、tsc 跑的那一刻就要解析到契约，那一刻内核不在场。
②④ 的下场是各件手写 declare 或 any，写错运行时才知道，内核实现也失去「被发出去的契约
钉着」的约束。二、**契约跟定义方走**——`gwbKernel` 是内核 provide 的，词得住提供方这边；
住件仓等于消费方持有契约，内核改实现没人拦。内核自己还是它的第一个消费方（挂 loader
之前就要 provide），靠 home 里装好的件提供类型是鸡生蛋。件形态多出来的（apply 生命周期、
可被禁用、可挂不上）它一样用不上——契约恰恰不能「挂不上」。

**定了**：维持 `@godcreator02/gwb-plugin-api` 独立包、与内核同仓平级（`packages/` 不是
内核 `src/` 的一部分）。总图：包给类型、服务给运行时值；件是干活的包，词汇表是只命名的包，
内核是不被安装的安装者。「内核配几个包」等于落进「类型跨仓」格子的东西数，现为 1——
第二个要正经过准入判据两道关。

**代价**：多一个要构建（tsc 出 `dist/`）、要发版的小包；依赖档位已撞过两次（见 walls）。
方向不对称：砍了再改回来等于所有已 import 的件重发；留着再砍，代价轻得多——留是轻的这边。

**日期**：2026-09-07

### 产物目录一律 `dist`，把 `lib` 让出去

**问题**：包的构建产物落在 `lib/`。而 `lib` 在 JS 生态里普遍是**源码**里放工具代码的目录名
（shadcn 的 `@/lib/utils`、fumadocs 的 `src/lib/source`、Next 社区的 `lib/`），两边在争同一个名字。

**候选**：① 保持 `lib`，每撞一次锚定一次路径 ② 产物改 `dist`，把 `lib` 让给源码

**判据**：**同一个坑撞了三次，前两次的修法都是在治症状**——

1. `.gitignore` 裸写 `lib/` 把 `docs-site/src/lib/source.ts` 罩住了。内核仓改成锚定
   `/packages/gwb-plugin-api/lib/`，**而件仓当时漏了**：那个文件一直没进 git，等于件仓的
   文档站克隆下来是跑不起来的（这次才发现）
2. oxlint 的 `**/lib` 会连 `src/lib/` 一起罩住，同样靠锚定绕过。**在 lint 这边更隐蔽**：
   少扫一个文件没有任何症状
3. shadcn CLI 的 `@/lib` 别名——第三次

三次都在给同一个名字冲突打补丁。而**产物目录本来就已经有两个不叫 lib 的**：`out/`
（electron-vite）与 `dist/`（electron）。它俩在 `.gitignore` 里一直是裸写的、从来不用锚定，
因为**没人拿这两个名字当源码目录**。所以改 `dist` 不是引入新约定，是向仓里已有的约定收敛。

**定了**：所有包的构建产物落 `dist/`。两个仓的 `.gitignore` 简化成裸写 `dist/`，oxlint 的排除
并进已有的 `**/dist`，那条锚定连同解释它的注释一起删掉。

**代价**：一次跨两仓的机械重命名（5 个包的 `package.json` / `tsconfig` / 构建脚本 / 产物测试
约 25 处），所有包重发一轮。漏改会在构建期炸，**唯一要盯的是 `files` 字段**——漏了会发出一个
缺文件的包，那个是静默的。

选在这时候改是因为**成本最低**：5 个包、全是 0.0.x、没有外部消费方。件多起来之后代价线性增长。

**日期**：2026-09-07

### 数据落盘做成件，不进内核

**问题**：件要记住东西（外壳的窗格布局、设置件的选项）。落到哪、怎么落得有个规矩，否则
每个件自己找地方扔。内核现在只有 `gwbKernel.dataDir`，再没有别的。

**候选**：① 进内核，照母仓的 `gwbKernel.store(名)` ② 做成一个件 ③ 什么都不做，各件自己
拿 `dataDir` 拼路径

**判据**：**准入判据第一关直接否掉①**——落盘不是「第一个插件存在之前必须发生的事」
（`gwb-cli` 就不落盘）。而 CLAUDE.md 写着「加功能的默认形态是加一个插件，往内核里加之前
先问：这件事能不能由某个件提供、由 cordis 的服务注入送到用得着的地方去」——**它能**，
基座只需要一个 `dataDir`。③ 则会长出五种路径写法，而那正是这套约定要防的。

**定了**：`@godcreator02/gwb-store` 件，提供 `ctx.gwbStore`，内核一行不动。

面**只有三样**（`dir` / `readDoc` / `writeDoc`），不抄母仓那五个：母仓多出的三个是给
「集合」用的（一条记录一个文件、读时逐条宽容、坏记录留底），而眼下唯一的消费方 shell
只存**一份**布局。等真有件要存一堆同类东西再加。

两条实现上定死的：**原子落盘**（先写同目录临时文件再 rename，否则写一半崩了会毁掉上一份）、
**数据目录用完整包名**（`<home>/data/@godcreator02/gwb-shell/`，短名不保证跨件唯一，而数据
撞了是互相覆盖，比样式撞了严重）。

**代价**：件多一层 `inject: ['gwbStore']` 依赖——store 件没挂上，依赖它的件也不挂。这是
cordis 的正常语义，但它确实是内核方案没有的一种失败形态。**将来真出现「store 没挂导致
一片件全废」的现场，那时再讨论进不进内核，并且要连着「它拦住了什么」一起记。**

**日期**：2026-09-07
