**本页回答**：内核给插件提供了哪些接入面（上下文上的服务、类型、IPC 通道、页面侧接口、home 布局）；内核自己直接用了哪个插件、怎么用的。

内核不是插件：它不在 `cordis.yml` 里，不登记命令，插件从内核拿到的一切都在下面几张表里。本页是总表，每行只写是什么、在哪取；两边各保证什么、边界在哪，写在行末链接的接缝页。

## 内核提供

### 服务与类型

| 名字 | 怎么取 | 说明 |
| --- | --- | --- |
| `ctx.gwbKernel` | 直接取，不写进 `inject`：内核在根上下文上提供，插件的上下文沿父上下文取到 | 成员 `dataDir`、`version`、`emit`、`setShell`；在注册 loader 之前提供，永不撤销（[内核服务](/docs/seams/kernel)） |
| `ctx.baseUrl` | cordis 上下文的属性，从根上下文继承 | home 目录的 `file:` 地址；loader 与 include 从它出发找 `cordis.yml` |
| `ctx.loader` | loader 提供的服务；内核在根上下文上注册 loader | 条目树（`create`、`update`、`remove`、`resolve`、`root`）。根层只有一条 id 为 `home` 的 include 条目，由它读 `cordis.yml`，所以 `cordis.yml` 里的条目 id 都是 `home:<手写 id>`；包名一律按 home 的 `node_modules` 里的真实路径解析。形状由 loader 与 include 的版本决定，不在内核包导出的类型里（[插件加载](/docs/seams/loading)、[home 布局与条目树](/docs/seams/home)） |
| `ctx.logger` | cordis 自带 | 插件写日志、注册自己的 exporter 都经它；内核注册的 exporter 把每一行写进 stderr 与 `gwb.log`，error 行还会进只读状态页（[日志](/docs/seams/log)） |
| `ctx.fiber.entry` | 插件自己上下文上的 fiber，loader 在上面加了 `entry` | 这个插件对应的条目：`id`、`options.name`（包名）、`parent`。不在 cordis 的类型里，也不在内核包导出的类型里，用它的插件按运行时的形状取（见下面「约定通道」） |
| `GwbResult` | 从内核包的包根 `import type` | 命令回执 `{ ok, data, error }` |
| `GwbKernelApi` | 同上 | `ctx.gwbKernel` 的形状 |
| `GwbContext` | 同上 | 插件 `apply` 拿到的上下文：cordis 的 `Context` 加 `gwbKernel` |
| `GwbWindowApi` 与全局 `Window.gwb` | 同上；import 了内核包的任何类型，TypeScript 就认得 `window.gwb` | 页面上 `window.gwb` 的形状 |
| `ShellBoot` | 同上 | 外壳模块默认导出的形状 |

五个类型各属于哪条接缝、改它们时版本号怎么升，见[包根导出的接口类型](/docs/desktop/api)。

`GwbWindowApi` 里 `onShell` 的参数类型只写了 `{ url }`，内核实际推送的是 `{ url, report }`：`report` 是只读状态页的数据（home 路径、各条目的状态、最近的错误行），只给内核自己的页面入口用，不在契约里。

### IPC 与页面接口

四个 IPC 通道的两端都在内核包里（页面一侧是 `preload.cjs`，主进程一侧是 `main.ts`）：外壳与插件的页面代码只经 `window.gwb` 用它们，列出通道名是为了排查时认得出来（[IPC 通道](/docs/seams/ipc)）。

| 名字 | 方向 | 说明 |
| --- | --- | --- |
| `gwb:command` | 页面 → 主进程，回执原路返回 | 只接收顶层框架的调用；交给 `ctx.gwbCommands.run(命令名, 参数, { via: 'ui' })`，回执原样交回（[命令转交](/docs/seams/commands)） |
| `gwb:event` | 主进程 → 页面 | `gwbKernel.emit(payload)` 的 payload，原样；窗口不在时丢弃 |
| `gwb:shell` | 主进程 → 页面 | 整份外壳状态 `{ url, report }` |
| `gwb:hello` | 页面 → 主进程 | 不带内容；主进程向发来的页面回一条 `gwb:shell` |
| `window.gwb.command(命令名, 参数)` | 页面调用 | 经 `gwb:command` 调命令，拿到 `GwbResult` |
| `window.gwb.on(回调)` | 页面订阅 | 收 `gwb:event`，返回取消订阅的函数 |
| `window.gwb.onShell(回调)` | 页面订阅 | 收 `gwb:shell`，订阅时发一次 `gwb:hello` 取当前值；只有内核的页面入口用 |
| importmap | 页面入口里固定写好 | `react`、`react/jsx-runtime`、`react-dom`、`react-dom/client` 指向内核包 `dist/react/` 里的文件；页面代码构建时外置这四个名字（[页面上的 react](/docs/seams/page-react)） |
| 外壳模块的默认导出 | 页面入口调用 | 外壳插件经 `setShell(url)` 交出地址，页面入口 import 它，把 `#root` 交给它的默认导出（`ShellBoot`），拿回可选的 `dispose`（[外壳接管](/docs/seams/shell)） |
| 主框架与 `window.open` | 主进程拦下 | 主框架只能是内核包里的 `index.html`，只放行整页重新加载；`window.open` 与 `target="_blank"` 不开新窗口，`http:`、`https:` 地址交给系统默认浏览器（[页面边界](/docs/seams/ipc#页面边界)） |
| 页面上的 console | 页面 → 日志 | 转成名字为 `renderer` 的 cordis 日志，级别照搬 |

### home 布局与文件

home 里每个文件谁写、谁读，全站只在这里列一份。

| 路径 | 谁写 | 谁读 | 说明 |
| --- | --- | --- | --- |
| home 目录本身 | 内核（不存在就创建） | 所有插件经 `gwbKernel.dataDir` | 环境变量 `GWB_HOME` 只写名字时是 `%APPDATA%\gwb-kernel\homes\<名字>`，带路径分隔符时就是那个目录，不设时是 `default`；路径统一成磁盘上的真实路径。同一个 home 只运行一个实例 |
| `package.json` | 创建 home 的一方（`INSTALL.md` 或 `devkit.home.new`）；之后只由插件管理运行的 pnpm 改 | 内核（启动时只看在不在）、pnpm | 包清单。缺了内核启动失败、不补（[home 布局与条目树](/docs/seams/home)） |
| `cordis.yml` | 创建 home 的一方；之后由 include 经条目树写回 | include（内核放在根层的那条 `home` 条目） | 条目清单。缺了内核启动失败、不补 |
| `node_modules/` | pnpm，由插件管理调用 | 内核按真实路径解析包名；启动器从这里加载内核包 | |
| `gwb.log`、`gwb.log.1` | 内核（注册在 cordis 日志流上的 exporter） | 人与 agent；日志插件的 `logger.where` 报告它的路径 | 写到 128 MB 轮转，只留一份旧的（[日志](/docs/seams/log)） |
| `runtime.json` | 内核每次启动整份重写 `pid`、`startedAt`、`version`、`cdp`；MCP 入口插件 `@godcreator/gwb-mcp` 读出、补上 `mcp` 字段再写回 | devkit、安装工作台的 agent | 退出时不删（[runtime.json](/docs/seams/runtime)） |
| `electron/` | Electron（Chromium 的 userData） | Electron | 单实例锁按它区分 home |
| `settings.json` | 设置插件 `@godcreator/gwb-settings` | 设置插件 | 与 `cordis.yml` 并排，按条目 id 的末段分区；内核不知道它 |
| `data/<条目 id 末段>/` | 数据插件 `@godcreator/gwb-data` | 数据插件 | 每条条目一个目录 |
| 其余目录 | 各插件自己（例如 MCP 入口插件的 `mcp/`） | 写它的插件 | 内核不分配、不检查 |

## 内核用到的插件

只有一处：转交页面发来的命令时读命令插件的服务。

| 服务 | 怎么取 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- | --- |
| `gwbCommands`，由命令插件 `@godcreator/gwb-commands`（基础插件仓 `gwb-base-plugins`）提供 | 每条命令转交的那一刻按服务名读 `ctx.gwbCommands`，不写 `inject` | 调 `run(命令名, 参数, { via: 'ui' })`，把页面经 `gwb:command` 发来的命令交给它，返回值原样交回页面 | 内核照常运行；这条命令回 `{ ok: false, error: '没有命令服务（ctx.gwbCommands），无法执行 <命令名>' }` |

内核用的类型是 `main.ts` 里自己声明的一份：只有 `run` 一个方法，返回 `Promise<unknown>`。命令插件在自己的包里另声明了完整的 `gwbCommands?: GwbCommands`，两份声明从不在同一次编译里出现，**两者之间没有类型检查**：命令插件改了 `run` 的参数或来源的取值，本仓 `pnpm check` 不会失败；`apps/desktop/tests/main.test.ts` 用的是一个手写的假命令插件，也发现不了。只有在隔离 home 里装上真的命令插件实机验证才能发现（[命令转交](/docs/seams/commands)）。

## 约定通道

下面几样没有类型、也不经内核包导出：对方在自己的代码里直接写着这些名字或形状，内核这边改了，对方的类型检查发现不了。

| 通道 | 对方 | 名字 | 说明 |
| --- | --- | --- | --- |
| 日志的 logger 名 | 日志插件 `@godcreator/gwb-logger` | `kernel`、`loader`、`renderer` | 日志插件按 logger 名判断来源：`kernel`、`loader` 算内核，`renderer` 算页面，其余算插件。`kernel` 是内核自己的日志名，`renderer` 是内核转页面 console 用的名字，`loader` 是内核包依赖的 loader 自己用的名字。内核改了名字，这些日志在日志插件里就被当成插件的日志，不报错 |
| 日志文件名 | 日志插件 | `gwb.log` | 日志插件的 `logger.where` 自己拼出 `<home>/gwb.log` 报告出去，不问内核 |
| `runtime.json` 与其中的 `mcp` 字段 | MCP 入口插件 `@godcreator/gwb-mcp` | `runtime.json`、`mcp` | 内核每次启动整份重写这个文件，MCP 入口在端口开好后读出、补上 `mcp` 再写回；内核不认识 `mcp` 字段（[runtime.json](/docs/seams/runtime)） |
| 条目 id 的形状 | 数据插件、设置插件 | `home:<手写 id>` | 两者从 `ctx.fiber.entry.id` 取末段当数据目录名、设置分区名，超过两段就报错。内核改掉根层那条 `home` 条目、或再嵌一层 include，这两个插件就算不出目录与分区 |
| `ctx.fiber.entry` | 命令插件、说明书插件 `@godcreator/gwb-skills`、`@godcreator/gwb-node-cli`、`@godcreator/gwb-py-cli`、数据插件、设置插件、插件管理 | `id`、`options.name`、`parent.tree` | 靠 loader 加在 fiber 上的条目认出调用方：命令插件取包名，记下每条登记的命令属于哪个插件；数据与设置插件取 id 与包名；插件管理从自己的条目找到条目树。这些字段是 loader 的内部结构，内核只决定用哪个版本的 loader，换版本就是改接缝（[home 布局与条目树](/docs/seams/home)） |
