# gwb-kernel 是什么

god 工作台的**正线**：最小的、能正常运行插件的那个版本。一个只做四件事的 Electron
应用，其余一切皆插件。

目标不是「内核行数最少」，是**「能把插件正常跑起来」所需的最小集**。这两者不一样：
前者容易滑向什么都不做，后者带着一条验收标准——插件得真能干活。

母仓 `god-workbench` 与它的件仓 `gwb-plugins` **准备废弃**，此后只作参考。插件全部
重做一份。

## 为什么另起一条

母仓走到今天大约 5100 行：`apps/desktop` 约 1500 行是执行壳，`packages/gwb-platform`
约 3600 行是判据。把这 5100 行逐块过一遍会发现，其中约 3600 行服务的是同一件事——
**让失败变得体面**：

- 自动升级的四路判定（首启 / 升级 / 补标记 / 已是最新）与 base 快照账本
- 装完之后数一遍盘核对清单、装失败时把 `package.json` 还原回去
- 图形界面上的阶段页与兜底页（正在装、装不上、外壳没生效、多条外壳）
- `cordis.yml` 读不动时备份原件、回写模板

这些不是超前设计，是被真实翻车逼出来的，代码注释里留着当时的现场（「上次多半装到
一半进程没了」）。但它们有一个共同的前提：**存在一个会自动升级、会自我修复的装机**。

这条线的选择是把那个前提拿掉。不自动升级，四路判定连同它制造的全部麻烦一起消失。
这不是假装问题不存在，是移除产生问题的那台机器。

目标是约 1500 行。

## 内核只做四件事

推导的起点是一句话：**让 cordis 插件跑起来，并且有界面**。从它出发，三条不可谈判的
事实决定了剩下的一切——插件是 JS 模块，要被 `import` 才会运行；插件是「后来才有的」，
所以不能自己把自己带来；界面在浏览器环境而插件逻辑在 node 环境，这是两个执行世界。

| | 是什么 | 为什么不可消去 |
| --- | --- | --- |
| **载体** | 起一个 node 进程挂 cordis，开一扇窗 | 模块要有运行时才跑得起来；界面得有地方待着 |
| **取址** | 读 yml 知道装了哪些，找到文件在哪，挂上 | 没有取址，`import` 这个词都写不出来 |
| **装机** | 把包名转发给 pnpm，装进 home | 「用户可以装插件」是工作台的定义 |
| **桥** | 命令与事件双向，`gwb://` 交出插件的浏览器那半 | 两个执行世界必须能对话 |

外加一份**词汇表**——它不做事，只命名。取址要说得出「条目」，桥要说得出「命令」
「事件」，这些名词的定义就是它。它不是第五件事，是前四件赖以表达的语言。

详见[内核四件事](/docs/four-things)。

## 准入判据：两道关，都得过

**一、凡是「第一个插件存在之前必须发生的事」，才进内核。其余一律皆插件。**

**二、真遇到需求才加。** 不是「将来可能要」「顺手做了吧」「母仓有这个」——是某件事
**此刻就干不成**，而且干不成的现场说得出来：谁、在做什么、卡在哪。

加功能的默认形态是**加一个插件**，不是往内核里加一段。往内核里加之前先问：这件事能不能
由某个件提供、由 cordis 的服务注入送到用得着的地方去？能，就该是插件。

这两句是这个仓存在的全部理由。它们一旦松动，仓就会慢慢长回母仓的样子——每一条「顺手
加上」的自动化都有它自己的道理，加够二十条就又是 5100 行。

拿不准的时候按「不进」处理：加回来永远比拿掉容易。

已经明确不做的那些，连同各自的理由，见[刻意不做什么](/docs/not-doing)。

## 插件契约：按最小重定

插件全部重做，所以契约不受「母仓那 11 件不改一行」的约束——按第一性原理定，不照抄。

有一份实测数据支持这个决定。把母仓 11 件源码全扫一遍，它们从平台包根出口一共只取了
12 个名字，按使用面分三档：

| 档 | 名字 | 判断 |
| --- | --- | --- |
| 11 件全用 / 7 件 / 6 件 | `GwbContext`、`requireKernel`、`isRecord` | **真属于内核词汇表** |
| 各 2 件（一个提供、一个消费） | `GwbHttpApi`、`GwbSkill`、`GwbSkillsApi`、`GwbCli` | **插件之间的契约，不是内核契约**——该住提供方那个件自己的包里。内核根本不知道 http 是什么 |
| 各 1 件 | `nodeChildEnv`、`readYamlDoc`、`PLATFORM_RUNTIME_VERSIONS`、`noHandlerError`、`PluginStore` | 实现细节漏出来的（devkit 一家占 3 个）。**包里放了实现，就一定会有人引到实现** |

所以内核的词汇表应该只有个位数个名字，而不是母仓那 600 行。

**内核信息怎么给插件：运行时状态走 cordis 服务，类型走词汇表包。** 这是两条路，不能混——
`dataDir` 是宿主启动时算出来的运行时值，插件 import 一份内核代码拿不到它。把内核的
`src/` 整个发成包给插件用是错的：插件用不着主进程与宿主入口，而发出去就成了要维护的契约。
