# 刻意不做什么

下面每一条母仓都有。这里没有，不是排期没排到，是**决定不做**。要做，得先推翻
[准入判据](/docs/overview#准入判据)那一句。

写下来是为了防一件事：一年之后有人看到某处「缺了个自动化」，顺手补上，理由充分，
然后再来十九次。

## 装机口

母仓有一台装机，这条线一度也有：`kernel.install` 命令转发 pnpm、首启装一份推荐列表。
2026-09-08 **整口拿掉**——内核不碰 pnpm（判据见[装机口移除](/docs/trajectory/2026-09-08-no-install-port)）。

为什么：装机这台机器的价值在「自动地装」，而自动装的头两件事——判该不该装、装失败怎么
办——正是自动升级那套麻烦的入口，这两条上面已经判了不做。剩下「手动装」根本不需要内核：
进 home、`pnpm add`、`cordis.yml` 写条目，home 里那份 README 写着全流程；图形界面的装件
面归件——件仓的 `gwb-plugins` 件，`plugins.install` 命令干这个，件在自己的进程里有完整
的 node，不必经内核转发。

内核为「装」保留的只有[安家](/docs/kernel/home)：home 是个 pnpm 认得的普通 npm 项目根。

## 自动升级

母仓会在每次启动时判断 home 里的件该不该顶到新版本：首启、升级、补版本标记、已是最新
四路，配一份 base 快照账本记住「上次装的时候推荐值是多少」，据此区分「这个版本是我们
装的」和「这个版本是用户自己钉的」。

这里没有。**装过了就不再动它**。首启装一遍推荐列表，之后 home 归用户。

为什么：那套判定的复杂度全部来自一个需求——自动顶版本的同时不能覆盖用户的选择。不自动
顶，判定就没有存在的必要。母仓约 1200 行服务于此。

## 盘上对账与失败还原

母仓装完会数一遍 `node_modules` 核对清单说的件是不是真在（pnpm 报成功不等于东西都在），
装失败会把 `package.json` 原文还原回去（写清单等于盖了「装过了」的章，失败却留着章，
下次会当成已装好）。

这里没有。**装不上就是装不上**，回一句 pnpm 的原话。

为什么：这两条都是自动升级的配套。没有那台机器反复改写清单，也就没有「章盖了一半」
这种局面。

## 图形界面上的失败兜底页

母仓在窗口里画「正在装底座件」「装不上，点这里重试」「外壳插件未生效，去终端跑
`gwb entry enable shell`」「多条外壳同时启用」。

这里没有。窗口起不来、装不上、插件挂了，一律 `console` 说清（主进程把渲染层的
console 转到终端），页面不替失败解释。

为什么：出路本来就在命令行——那条路不经 GUI 也不经宿主，界面点不动时照样使得上。
在图形界面上把失败再解释一遍是体验优化，不是逻辑必须项。

**这一条原本连「阶段页」一起否着，2026-09-08 推翻了半边**：外壳还没上来时，窗口摆一份
已装清单而不是留白（阶段页，现场与界线见
[那次推翻](/docs/trajectory/2026-09-08-stage-page)）。划出去的界线：界面只陈述
「还没到」的事实，不解释失败；失败兜底页这半条继续不做。

**同一天，「已经没了」那半个时态也划出去了**：宿主崩了窗口停在最后一帧装活，讣告只在
日志窗格里一条 main 的 error，没人会想到去翻。渲染层收到主进程捎的 `gwb:host-exit`
就把整页换成崩溃页——退出码、临终日志尾巴的原文、日志文件在哪（现场与界线见
[崩溃页](/docs/trajectory/2026-09-08-crash-page)）。现在的完整界线：**界面陈述「还没到」
与「已经没了」两种时态的事实，仍然不解释失败、不摆重试、不自动恢复**；哪天它长出
「点击重试」或第一句归因，线就是那时候破的。

## 插件之间的准入核对

母仓（计划中）会在挂载时读件的 `peerDependencies`，核对平台包版本全等、插件 peer 的
semver 范围、拒绝环依赖，并在 `gwb plugin add A` 时自动补装 A 缺的 peer。

这里没有。插件之间的依赖关系是插件自己的事。

为什么：准入核对的价值是把「装了但跑不起来」提前到「装的时候就拦住」。而这条线的装机
本来就是「管他装不装得上」——拦不拦在同一个位置，收益抵消掉了。

## `cordis.yml` 的模板与自愈

母仓在文件不存在时写一份默认模板（十来条底座件），在文件读不动时把原件备份成 `.bad`
再回写模板。

这里没有。文件不存在就**建一份空表 `[]`**——那既是「一个件都没装」的正当表达，也是 home
起得来的最小形态（读不到这个文件的话 `include` 会抛，而那个错落在 loader 的挂载链上，
**宿主整个退出**，见[新 home 起不来那面墙](/docs/trajectory/2026-09-07-wall-fresh-home-no-yml)）。除此之外一条都不写：不写模板，不写任何条目。
读不动就报错说清是哪一句坏了。

为什么：那个文件归用户。首次写模板是一次性的便利，但「读不动就回模板」等于在用户的
配置坏掉时替他做决定，而那份配置可能只是少个引号。

## 不属于「不做」，属于「到期再选」

有一条容易混进来：**打包器**。这条线用 electron-vite 构建，但打包（出安装包）到第四刀
之后才到期，到时候手上会有一个确定的问题——pnpm 怎么进产物——那时再拿两个工具各试一次。

现在唯一做的准备是零成本的那条：**别让打包器的形状渗进源码**。主进程走正常的包解析，
不依赖任何依赖被内联进束。母仓有一句反面教材，源码的 `import` 写法被 asar 的行为反向
决定了；这里不这么写，将来换任何打包器都不疼。
