# K8 版本升哪一位

## 规则

**0.x 版本里只在破坏契约（对外承诺的接口）时升 x，其余一律升 y。**

## 怎么判

哪些算契约、依赖范围怎么写、发布破坏性版本时要多做的两步，正本在 devkit 的说明书（skill）`gwb-release` 里，这里不复述。本页只补两条：
- 共享库的导出子路径、接口定义包的导出，也算契约
- **宿主（内核）换 cordis 大版本，是内核的破坏性版本**：每个插件都依赖 cordis 的协议，不管它的构建产物里有没有 import cordis。先装新内核，所有插件在隔离 home 里同一次全部重新验证，不靠 peer 来提示（[K2](/docs/criteria/k2) 只让按值 import cordis 的插件写 peer）

## 标准例子

- react 升大版本是 shell 的破坏性版本：[E2 shell](/docs/criteria/examples/e2-shell#对外接口)
- 接口定义包改了命令的参数或返回值结构，要改 `contract` 与 `minCompatible`：[E4 块笔记](/docs/criteria/examples/e4-block-note)

## 反例

删了运行时导出只升 y；加功能、加可选参数顺手升 x。

## 为什么

依赖范围管不到运行时实际解析到哪个版本：词汇表包从 0.1 到 0.2 撤掉了运行时导出，下游的范围还写着 `^0.1.2`，home 里照样解析到 0.2.7，三个插件加载失败。真正起保证作用的是发版前的检查，加上 [K4](/docs/criteria/k4) 的契约版本比对。

## 执行

`devkit.release` 的发版前检查自动执行其中一部分。
