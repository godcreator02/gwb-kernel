# K3 什么能进 importmap

## 规则

**importmap 只放整个页面必须只有一份的运行时代码**，目前就是 react 的那四个包名；提供方只能是有条目（在 `cordis.yml` 里配置了加载）的插件。

## 怎么判

同一个模块在页面上出现两份就会出错（全局单例、hooks、跨组件树的 context 这类），才进。只是体积大、或者好几个插件都用，不进，各自打包进构建产物——页面从本机 `file://` 加载，重复几百 KB 可以接受。

进了 importmap 之后的规矩：
- 提供方只能是有条目的插件，在自己清单的 `gwb.shared` 里声明；库不声明
- 一个包名只有一个提供方，名字冲突时全部拒绝（见[页面上的包名](/docs/seams/shared)）
- 插件的外置名单（构建时不打包、留给 importmap 提供的包名清单）只从提供方读（提供方导出一个构建时用的 helper），不手工复制
- 共享的运行时升大版本，就是提供方的破坏性版本（见 [K8](/docs/criteria/k8)）
- 插件之间共享 React context，只能通过 importmap 的提供方，或者通过 props 传递；各插件自带的库里的 context 在插件之间不通

## 标准例子

- 唯一的提供方：[E2 shell](/docs/criteria/examples/e2-shell#对外接口)
- 使用方怎么外置：[E3 unit-folder](/docs/criteria/examples/e3-unit-folder#构建产物里的包名-import)
- 体积大但不是单例、各插件自带：[E4 块笔记](/docs/criteria/examples/e4-block-note#构建产物里的包名-import)

## 反例

库自己声明 `gwb.shared`（它没有条目，能进 importmap 只是因为它被装成了 home 的直接依赖）；为了省体积把工具库放进 importmap；在各插件的构建脚本里手工复制外置名单。

## 为什么

[importmap 由内核管，不归外壳](/trajectory/2026-09-09-importmap-in-kernel)：它是页面级的运行时服务，放什么由提供方声明。提供方限定为插件，提供方就一定是 home 的直接依赖、有人管它的升级。

## 执行

名字冲突时全部拒绝，这一条已有自动检查。库声明共享、手工复制外置名单，还在迁移中。插件管理安装时「库不加条目」的判断，是因为库（`block-note`）还要装进 home；库不再声明 `gwb.shared` 之后删（见[插件管理](/docs/plugin-manager#对照关键判据)）。
