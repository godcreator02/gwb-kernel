# K6 契约住哪

## 规则

**谁提供，谁定义。** 内核提供的接口，类型放在词汇表包里，只增不减；插件提供的服务类型、命令参数与返回值类型，放在那个插件自己的包里（或者它发布的接口定义包里）。

## 怎么判

- 内核的接口：`gwbKernel`、`window.gwb` 的 `command` / `on`、外壳的默认导出——类型在词汇表包 `@godcreator/gwb-plugin-api` 里，纯类型
- 插件的接口：服务接口、命令的参数和返回值类型都由提供方导出；命令返回值的外层结构 `{ ok, data, error }` 属于命令总线插件
- 调用方取类型只用 `import type` 引提供方的包；有意不引提供方类型的调用方（对方是可选的插件），对返回值做防御式的类型收窄，不算违反
- 不用 `as` 把东西强制转换成提供方的类型；要收窄接口，就通过赋值让类型检查来验证

## 标准例子

- 命令返回值的外层结构放在命令总线插件里：[E1 commands](/docs/criteria/examples/e1-commands#契约)
- 导出命令的返回值类型：[E3 unit-folder](/docs/criteria/examples/e3-unit-folder#契约)
- 接口定义包：[E4 块笔记](/docs/criteria/examples/e4-block-note#契约)

## 反例

把插件之间的契约塞进词汇表包；使用方手写提供方的类型；`ctx as unknown as SomeShape`；返回值结构只写在命令描述里、没有导出类型。

## 为什么

[词汇表是独立的包](/trajectory/2026-09-07-vocab-package-standalone)、[词汇表包就这么大](/trajectory/2026-09-07-wall-vocab-just-size)：契约应该放在定义方那边；放在使用方那边，就等于使用方持有契约，提供方改了实现也没人拦得住。

## 执行

词汇表包已经是纯类型；命令返回值的外层结构还放在词汇表包里，迁移中；「只增不减」靠发版纪律保证。
