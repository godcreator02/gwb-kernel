# K4 件与件怎么交互

## 规则

**件与件只经 cordis 服务与命令交互，不 import 别的件。** 要共享代码，提供方另发一个无状态的契约包；要共享盘上格式，按区间比对契约版本。

## 怎么判

- **「import 别的件」**指 import 带 `apply` 或模块状态的件包入口与子路径。import 一个库或契约包不算——契约包只有类型、常量与纯函数，没有模块状态，消费方写 dev、打进自己的产物
- **跨边界只传**纯数据、函数与 `{ ok, data, error }` 信封；不对来自别件所带库里的类做 `instanceof`（各件带的是不同的拷贝）。`Error`、`URL` 这类平台全局对象不受限
- **在场与联动**交给 cordis 的 inject：提供方重挂，依赖它的件被自动拆掉再挂回
- **契约版本**：几个件读写同一份盘上格式、或依赖同一组命令的形状时，提供方给出 `contract` 与 `minCompatible` 两个数，消费方把自己期望的版本**写死在自己代码里**，落在区间外就拒绝挂载，不只警告
- **数据目录归主人**：件的数据目录只由它自己读写；别的件要那份数据，走它的命令。生态公约的文件（比如单元的 `unit.json`）归定义它的那个件，读的一方照它发布的契约

## 标准例子

- 契约包、提供方、消费方与版本区间：[E4 块笔记](/docs/criteria/examples/e4-block-note)

## 反例

import 别的件的包或子路径来拿运行时函数；靠模块单例跨件共享状态；契约版本要求完全相等（加一个可选字段就判不合）、或只警告；消费方从共享库里取期望版本（比对恒等、形同虚设）；自己拼路径去读别件的数据目录。

## 为什么

各件带的库是各自的拷贝，模块单例与 `instanceof` 跨件不成立；块笔记两个仓里所有 `instanceof CommandError` 接住的都是本件自己造的对象、命令总线只传信封，所以各件私有一份不出错，真正的风险是版本漂开导致盘上格式对不上。
