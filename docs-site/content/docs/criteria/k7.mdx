# K7 状态与卸载清理

## 规则

**插件自己启动的进程、定时器、监听，以及尚未完成的写盘和网络请求，卸载时都要清理掉，并返回 promise。** 每次重新加载都该清掉的状态放在 `apply` 里。

## 怎么判

- **返回到哪里**：从 `ctx.effect` 的清理函数里返回 promise（在 `Service` 上就是由 dispose 返回它）；注册类 API 返回的注销函数也包进 `ctx.effect`。用 `.catch(() => {})` 把 promise 吞掉、或者 `void` 掉不返回，都算没有返回
- **清理什么**：子进程要杀掉整棵进程树、等它真正退出；定时器清掉；尚未完成的写盘要写完再 resolve（不是丢掉待写的数据）；进行中的网络请求要能中止
- **状态放哪**：模块顶层的状态在同一版本重新加载时不会重置，只放真正需要跨越重新加载保留下来的东西。数据写盘通过数据插件，配置通过设置插件，home 下的路径只从 `gwbKernel.dataDir` 取
- **例外，都要在代码里写明**：
  - 有意比宿主（内核）活得更久的进程（测试 home、外部编辑器），要 detached 加 `unref`，并且插件下次加载时（包括工作台重启之后）能找到它、重新接管
  - 插件对自己发起的重新加载任务，天然会在自己卸载之后继续运行，只允许持有条目树（loader 按 `cordis.yml` 建起来的全部条目）与 logger
  - 位置由外部固定的文件（`runtime.json` 里 MCP 入口那一项、`~/.npmrc`）和用户指定的数据根目录（论文库这类），不通过数据插件
  - 中途结束会让共享的磁盘状态只改了一半的子进程（插件管理正在改 home 的 pnpm），卸载时让它跑完，不结束

## 反例

卸载时清掉等待写盘的定时器，等于丢掉这次写盘；关闭数据库之前不等进行中的写入完成；启动了子进程，只靠超时来结束它；`server.close()` 不等它真正关闭。

## 为什么

内核退出时只等插件返回的 promise，超过 5 秒就强制退出：[退出时的卸载清理由内核负责，分两半](/trajectory/2026-09-12-quit-dispose-two-halves)。[数据写盘做成插件，不进内核](/trajectory/2026-09-07-gwb-data-plugin)。
