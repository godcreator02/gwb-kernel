# K2 依赖怎么写（peer 怎么用）

## 规则

**peer 只写由宿主（内核）提供、插件按值 import（import 的是运行时的值，不只是类型）的 `cordis`；其余一律写 dev。** 构建产物里剩下的包名 import（bare specifier，直接写包名、不带相对路径的 import，比如 `from 'cordis'`）只能是：node 内置模块、`electron`、`cordis`（在 node 端代码里），以及 importmap 里的名字（在浏览器端代码里）。

## 怎么判

按运行时这份代码由谁提供来决定：

| 运行时由谁提供 | 写法 |
| --- | --- |
| 宿主提供、插件按值 import（`extends Service` 这类） | peer：`cordis` |
| 运行环境自带（node 内置模块、`electron`） | 不声明 |
| 页面通过 importmap 提供（react 的四个包名，见 [K3](/docs/criteria/k3)） | dev；浏览器端代码构建时外置（不打包，运行时由 importmap 提供） |
| 另一个插件 | dev（只取类型）；运行时通过 inject 和命令使用（见 [K4](/docs/criteria/k4)） |
| 本插件运行时自己用的库、接口定义包 | dev；构建产物里不留它的包名 import |
| 构建时才用到的输入（shell 的样式映射文件 `theme.reference.css`、tailwind 之类） | dev |
| 外部程序、python 环境 | 不声明；用的时候检测它在不在 |

「按值 import」和「只 import 类型」的区别，看编译后留不留下东西：

```ts
// 按值 import：Service 是一个类，运行时要用到它——构建产物里原样留下这一句，要写 peer cordis
import { Service } from 'cordis'
export default class MyPlugin extends Service { /* … */ }

// 只 import 类型：编译后整句消失，构建产物里没有 cordis——不写 peer，cordis 写 dev
import type { Context } from 'cordis'
export function apply(ctx: Context) {
  ctx.provide('myService', { /* … */ })   // ctx 是 cordis 交给插件的，不用 import
}
```

真实插件的对照见 [E1 commands](/docs/criteria/examples/e1-commands#清单)（不写 peer）和 [E2 shell](/docs/criteria/examples/e2-shell#清单)（写 peer）。

判据只看构建产物，不管用什么方式构建：用 tsc 直接输出也好、用 esbuild 打包也好，构建产物里多出一个包名 import 就是违反。

**peer 的意思是「运行时要从 home 里解析到这个包」**，所以只看构建产物里有没有这个包名 import：构建产物里有 `import … from 'cordis'`（比如 `extends Service`）才写 peer `cordis`；没有就不写——**哪怕 d.ts 里有 `declare module 'cordis'`**，那只是类型，使用这些类型的一方自己在 dev 里列 cordis。插件照样依赖 cordis 的协议，但这份兼容性不靠 peer 表达：宿主换 cordis 大版本就是内核的破坏性版本，所有插件在同一次里全部重新验证（见 [K8](/docs/criteria/k8)）。这条可以自动检查：构建产物里出现 `cordis` 的包名 import 却没写 peer，或者写了 peer 构建产物里却没有，都拒绝。

**类型引用到的包由使用方自己列全**：本插件做类型检查时引用到的别的包的类型（包括上游 d.ts 里又引用到的包），这些包都写进本插件的 dev；检查流程里关掉 `skipLibCheck` 跑一遍类型检查——缺哪个包它会点名报「找不到模块」，否则那段类型会不报错地变成 any。**只引类型时必须写 `import type`**，`import { type X }` 在 `verbatimModuleSyntax` 下会在构建产物里留下一句空 import。

插件需要另一个插件已经安装（比如块笔记的各个插件需要 bn-core），这一点不写进清单（package.json）；没装时它停在「等待缺少的某个服务」的状态，在[只读状态页](/docs/kernel/bridge)和 `plugin-manager.list` 里都看得到。

## 标准例子

- 不按值 import cordis 就不写 peer：[E1 commands](/docs/criteria/examples/e1-commands#清单)
- 因为 `extends Service`，所以 peer 只有 cordis：[E2 shell](/docs/criteria/examples/e2-shell#清单)、[E5 node-cli](/docs/criteria/examples/e5-node-cli#清单)
- 别的插件、接口定义包、构建时输入全都写 dev：[E3 unit-folder](/docs/criteria/examples/e3-unit-folder#清单)、[E4 块笔记](/docs/criteria/examples/e4-block-note#清单)

## 反例

用 peer 声明别的插件、库、react、已经停止发布的共享包、词汇表包；按值 import 词汇表包（它是纯类型包，没有运行时导出，插件会加载失败）；自己用的库写进 `dependencies`，构建产物里却留着它的包名 import；写 `instanceof Service`——插件和宿主用的 cordis 可能是两份不同的拷贝，跨拷贝判断结果为 false。

## 为什么

- cordis 靠 `Symbol.for` 协议键在多份拷贝之间工作，插件自带一份也好、home 里另有一份也好，provide / inject / 跟着依赖一起重新加载都正常，只有跨拷贝的 `instanceof` 为 false：仓根 `probes/2609231600_cordis-multi-copy/`；[cordis 写成 peer 而不是 dev](/trajectory/2026-09-07-wall-cordis-peer)
- 只写 dev 时，类型引用到的包靠 pnpm 默认的隐藏提升（hoist）来解析，少列一个就悄悄变成 any，关掉 `skipLibCheck` 就会报出来：`probes/2609231600_types-without-peer/`（情形 01、04）
- peer 从来只警告、不拦截，而且管不到运行时实际解析到哪个版本（见 [K8](/docs/criteria/k8)）；把它收窄成「宿主提供」这一种含义，依赖就只剩两种写法
