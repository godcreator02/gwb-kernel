**本页回答**：什么时候才进这个仓；第一次怎么准备；怎么从源码启动内核、隔离 home 里的插件从哪来、构建时做了什么；提交前跑哪些检查；每个测试文件证明什么、哪些只能实机验证；怎么在隔离 home 里验证；内核包怎么把 react 打成页面能用的文件；怎么打安装包、打包脚本一步步做了什么、哪几道检查不能删、打完怎么验证；发版按什么顺序做、版本号升哪一位、包根导出的接口类型改动的规则、怎么发布到 gitea releases。

## 什么时候进这个仓

**日常从安装版启动，不进这个仓**（开始菜单「gwb-kernel」）；新机器安装照仓根 `INSTALL.md`。**改内核本身才进这个仓**，改动只在隔离 home 里实际运行验证，不碰日常用的 `default`。写 `cordis.yml` 里的插件不在这里——命令插件 `@godcreator/gwb-commands` 在基础插件仓 `gwb-base-plugins`，插件管理 `@godcreator/gwb-plugin-manager` 在 devkit 仓 `gwb-devkit`。

## 第一次准备

在仓根：

```powershell
pnpm install
cd apps\desktop; pnpm setup:electron
```

electron 这个包没有安装脚本，二进制要显式运行一次它的 `install.js` 才会下载下来；不运行的话启动失败，pnpm 也不提示（[electron 不带安装脚本](/trajectory/2026-09-07-wall-electron-postinstall)）。

## 从源码启动

```powershell
$env:GWB_HOME = '<这次验什么>-<yyMMddHHmm>'
cd apps\desktop; pnpm start
```

`GWB_HOME` 每次验证给一个新名字，home 会建在 `%APPDATA%\gwb-kernel\homes\<名字>`；**不设就是 `default`**，同一个 home 已有实例在运行时这次启动会直接退出（[内核应用](/docs/desktop)）。

### 隔离 home 里的插件从哪来

内核不带插件，全新的 home 里 `cordis.yml` 是空表：启动后页面只显示[只读状态页](/docs/desktop)，页面发来的命令都回「没有命令服务」。要验证命令、外壳、插件管理这些，先往这个 home 里装上命令插件等插件，两种做法：

- **用 devkit**：`devkit.home.new {"short":"<这次验什么>"}` 新建一个隔离 home，装好内核包（运行这条命令的内核那个版本）、内核要的 `cordis`，以及命令插件、外壳、数据、设置、说明书、插件管理、基础窗格这一套基础插件，并用安装版的启动器打开它。关掉那个窗口，再把 `GWB_HOME` 设成它返回的 home 名，从源码启动
- **照 `INSTALL.md` 手动装**：在 home 目录里写 `cordis.yml` 的条目、用机器上的 pnpm `pnpm add` 对应的包，步骤与仓根 `INSTALL.md` 第 3 步相同，只把 home 目录换成这个隔离 home

### 构建做了什么

`pnpm start` 先构建再启动 electron。构建依次是：先整个删掉 `dist/`——清单的 `files` 只列 `dist`，旧版本留下的目录不删就会被一起发出去；内核 `tsc`；再用 `tsconfig.api.json` 只为 `src/api.ts` 生成包根导出的类型声明 `dist/api.d.ts`（[包根导出的接口类型](/docs/desktop/api)）；把页面的两个文件 `index.html`、`preload.cjs` 从 `src/` 复制进 `dist/`，最后运行 `scripts/build-react.ts`，用 esbuild 把 react 的四个包名打进 `dist/react/`，页面的 importmap 用的就是它们（见下面[内核包怎么打包 react](#内核包怎么打包-react)）：

## 在隔离 home 里验证

两条路，都不碰 `default`。

**发内核开发版进隔离 home**：验证的是安装版的样子——启动器从 home 里加载内核包。先用 `devkit.home.new` 开一个隔离 home，再从另一个 home 调：

```
devkit.dev {"home":"<隔离 home 名>","dir":"<本仓根>","packages":["apps/desktop"]}
```

本仓要发的 npm 包只有内核包，所以 `packages` 只写 `apps/desktop`。目标 home 的插件管理要 0.12.0 起。主进程里的内核换不掉，装完它会停掉那个 home 再启动，直到页面上 `shell.env` 报出的内核版本就是这次打包的版本号；回执的 `kernel.version` 就是它。不用重打安装包。

**从源码启动**：改一次就想看一次、不想每次发开发版时用。

1. 照上面「隔离 home 里的插件从哪来」准备好 home，构建后带调试端口启动，端口别和其他会话重复：

   ```powershell
   $env:GWB_HOME = '<这次验什么>-<yyMMddHHmm>'
   cd apps\desktop; pnpm build
   pnpm exec electron . --remote-debugging-port=<端口> --disable-backgrounding-occluded-windows
   ```

   内核把调试端口写进 home 的 `runtime.json`（[runtime.json](/docs/seams/runtime)），`devkit.cdp` 从那里找到它；后一个开关让窗口被遮住时页面照常刷新，截图不会拿到旧画面
2. 用 `devkit.cdp` 在这个 home 的页面上调命令、截图、读页面状态
3. 看结果：home 里的 `gwb.log`；没有外壳或外壳启动失败时，页面上的[只读状态页](/docs/desktop)列出每个条目加载到哪一步

## 内核包怎么打包 react

页面上的 react 由内核包提供（[页面上的 react](/docs/seams/page-react)）。构建的最后一步 `scripts/build-react.ts` 用 esbuild 把 react 与 react-dom 打成浏览器能直接 import 的 ESM，写进 `dist/react/` 的四个文件：`react.js`、`react-jsx-runtime.js`、`react-dom.js`、`react-dom-client.js`，页面入口 `index.html` 里写死的 importmap 指向它们。react 与 react-dom 是内核包的开发依赖，升级 react 就是发一版内核。

- **为什么要打包**：react 19 的清单 `exports` 只有 `react-server` 与 `default` 两个条件，`default` 指向 CJS 的 `index.js`，浏览器不能直接 import
- **为什么用 esbuild**：rolldown 在 browser 平台对「CJS 里 require 一个外置的包」保留 `require`，浏览器里没有 `require`，产物一加载就报错；esbuild 会把它提升成顶层 `import`
- **react-dom 的两个文件把 `react` 外置**：四个包名共用同一个 react 实例，页面的 importmap 把 `react` 指到 `react.js`
- **替换 `__require` 探针**：react-dom 在工厂函数内部调 `require('react')`，esbuild 提不到顶层，产物里留一个 `__require` 探针，在浏览器里一运行就报错。构建脚本在这两个文件头加一句 `import * as __gwb_react from "react"`，再把探针换成只认 `react` 的同步解析器：返回 `__gwb_react.default`（react-dom 要用 React 的内部成员，要的是 CJS 的 `module.exports` 原对象），遇到别的名字就抛错。脚本按 esbuild 生成代码的样子认这个探针，产物里有 `__require` 却认不出来时构建失败，不把带探针的产物发出去
- **入口文件逐个列出具名导出**：`src/react/` 下四个入口各自 import 对应的包，再一个一个 `export const`。esbuild 从 react 的 CJS 转发链上推不出具名成员，直接打只有一个 `default`。名单对齐 `@types/react` 19 的稳定 API，react 加了新 API 就补一行；少一个的话，用到它的窗格加载时报「does not provide an export named …」、整个窗格空白，构建与类型检查都发现不了

{/* ref file="../apps/desktop/scripts/build-react.ts" lines="22-43" */}

**测试**：`apps/desktop/tests/react-bundles.test.ts` 读真实的产物（仓根 `pnpm check` 先构建内核包），查三件事：四个文件里都没有 `typeof require` 探针；react-dom 的两个文件以那句 import 开头、带着修补后的 `__require`；`react.js` 的具名导出里有 `default`、`useState`、`useEffect`、`createElement`、`useEffectEvent`。`importmap.test.ts` 另外查 `index.html` 里 importmap 的四个地址指到打包脚本产出的文件。

## 打安装包

```powershell
pwsh installer\scripts\build.ps1
```

在仓根运行，产物在 `installer\build\dist\`。安装包产出什么、装好之后是什么样见[安装包](/docs/installer)。安装包只带启动器与 Electron，输入全部来自本仓的 `apps/launcher`；内核不打进安装包，装在 home 里。只有 Electron 版本或启动器本身变了才需要重新打。

**1. 检查工作区**：已跟踪的文件有未提交的改动就停下——打包用的是仓里的代码，有改动时打出来的 exe 说不清装了什么。未跟踪的新文件不算。

{/* ref file="../installer/scripts/build.ps1" lines="15-16" */}

**2. 构建启动器**：`apps/launcher` 里 `pnpm build`。

{/* ref file="../installer/scripts/build.ps1" lines="18-22" */}

**3. 读版本号**：启动器版本与 electron 版本都从 `apps/launcher/package.json` 读；安装包的版本号就是启动器的版本号。electron 的版本只写在它的 `devDependencies.electron` 这一处，经命令行传给 electron-builder——electron-builder 只在项目根找 electron 版本、不看 `directories.app`，所以 `electron-builder.yml` 里不写。内核要的 Electron 范围写在内核包的 `engines.electron`，启动器的测试检查两边对得上。

### 不能删的检查

- **每条 npm / pnpm 之后检查退出码**：pwsh 对原生命令的非零退出码默认不停，不检查的话前一步失败（比如组装目录是空的）也会照样打出安装包（[打包脚本静默出错的两处](/trajectory/2026-09-15-wall-installer-silent-failures)）

### 验证

打包脚本 `build.ps1` 没有单元测试，它自己在每一步检查退出码和产物，打完之后这样验证：

- **打包形态能启动**：准备一个临时 home（`GWB_HOME` 给路径），`package.json` 里列内核包（本仓 `apps/desktop` 用 `pnpm pack` 打出的 tarball，以 `file:` 写进去）与内核要的 `cordis`，`pnpm install`；运行 `installer\build\dist\win-unpacked\` 里的 exe，启动器从 home import 内核，`gwb.log` 里有「up」那一行、没有 error。不设 `GWB_HOME` 运行它会打开真正的 default home
- **缺内核包时启动器拒绝启动**：把那个 home 里的内核包删掉再启动，弹框说明缺内核包、退出码 1
- **单实例锁**：同一个 home 再启动一次，退出码 1、`runtime.json` 不变
- **安装说明**：派一个没有上下文的子代理，只给它 `INSTALL.md`，让它往一个临时 home（`GWB_HOME` 给路径）里照做一遍、启动 `win-unpacked` 的内核，MCP 入口能调通、条目全部 ACTIVE 才算通过；它不得不问的每个问题都是说明的漏洞

## 发版

通用的发版步骤在说明书 `gwb-release`，这里只写内核包自己的：

1. **升版本号**：改 `apps/desktop/package.json` 的 `version`，包根导出的接口类型跟内核包用同一个版本号。升哪一位按改没改接缝判断：
   - **改了接缝上已有的东西就升 x**（`0.x.y` 里的 x）：十条接缝上已有的任何一样被改名、删除、改了形状或含义——包根导出的接口类型（`src/api.ts`）、IPC 通道、页面 importmap 里已有的包名、home 布局、`runtime.json` 的字段、日志行格式、内核包清单的 `engines.electron`——以及升级 `@cordisjs/plugin-loader`、`@cordisjs/plugin-include`、`cordis` 的版本（拿不准会不会弄坏插件管理，一律按会弄坏算）。插件在 peer 里写内核包的 `^` 范围，插件管理拿它和运行中的内核比（[插件在 peer 里写兼容哪个内核](/docs/design#插件在-peer-里写兼容哪个内核)）；升了 x，所有插件的范围都不再包含新内核，要先照 `gwb-release` 通知下游
   - **只给接缝加东西（加类型、加可选字段）、只改内核内部或修 bug，升 y**：插件的 `^` 范围仍然包含新内核
   - **包根导出的接口类型对插件只增不减**：能加一个可选字段、一个类型解决的，不删名字、不改形状（参数、返回值、回执字段的类型或含义）、不改调用方依赖的语义；非改不可时，照 `gwb-release` 的「发破坏性版本多做的两步」先通知下游。契约之外的东西（日志行的格式、命令插件与插件管理的类型）不放进 `src/api.ts`。内核的 `main.ts` 自己用这些类型，本仓 `pnpm check` 当场发现内核这一侧形状不对；仓外的插件与页面代码要等新内核包发到团队包源、装上之后，才在各自仓的类型检查里发现（[包根导出的接口类型](/docs/desktop/api)）
2. **发内核包到团队包源**：`devkit.release` 的 `packages` 只写 `["apps/desktop"]`
3. **启动器或 Electron 变了才打安装包、发布到 gitea releases**：打包见上面[打安装包](#打安装包)。发布仓 `godcreator/gwb-kernel` 公开，源码在同一个仓（只有 main 分支），release 附带 Windows 安装包；push 用 git 凭据管理器里的凭据，API 用 gwb-gitea 插件的 `gitea.http`（用法在它的说明书）
   - tag 跟安装包（启动器）的版本走（`v<版>`），与 release 一一对应；release 说明指向仓根 `INSTALL.md`
   - **推送 tag 会让同名的草稿 release 自动公开**：要先存草稿、人工确认后再公开，就最后推 tag
4. **本机升级**：先在隔离 home 里装新内核包验证，再升 default home 里的内核包并重启工作台；启动器变了才重新运行新版安装包。改了契约时先装新内核，再发用到新契约的插件：插件先到、内核还是旧的，插件拿到的 `gwbKernel` 就缺它要的东西。升了 x 时，再在新内核上测插件、把它们 peer 里内核包的范围改到新内核并发版
