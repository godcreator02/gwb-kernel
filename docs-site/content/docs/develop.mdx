**本页回答**：什么时候才进这个仓；第一次怎么准备；怎么从源码启动、构建时做了什么、隔离 home 里的插件从哪来；提交前跑哪些检查；怎么在隔离 home 里验证改动；什么时候要打安装包；发版按什么顺序做、内核包的版本号升哪一位。每个测试文件证明什么写在各模块页的「怎么单独测」：[内核应用](/docs/desktop#怎么单独测)、[安装包与启动器](/docs/installer#怎么单独测)。

## 什么时候进这个仓

**日常从安装版启动，不进这个仓**（开始菜单「gwb-kernel」）；新机器安装照仓根 `INSTALL.md`。**改内核本身才进这个仓**，改动只在隔离 home 里实际运行验证，不碰日常用的 `default`。写 `cordis.yml` 里的插件不在这里——命令插件 `@godcreator/gwb-commands` 在基础插件仓 `gwb-base-plugins`，插件管理 `@godcreator/gwb-plugin-manager` 在 devkit 仓 `gwb-devkit`。

## 第一次准备

在仓根：

```powershell
pnpm install
cd apps\desktop; pnpm setup:electron
```

electron 这个包没有安装脚本，二进制要显式运行一次它的 `install.js` 才会下载下来（仓根 `.npmrc` 让它走 npmmirror 镜像）；不运行的话启动失败，pnpm 也不提示（[electron 不带安装脚本](/trajectory/2026-09-07-wall-electron-postinstall)）。

## 从源码启动

```powershell
$env:GWB_HOME = '<这次验什么>-<yyMMddHHmm>'
cd apps\desktop; pnpm start
```

`GWB_HOME` 每次验证给一个新名字，home 建在 `%APPDATA%\gwb-kernel\homes\<名字>`；**不设就是日常用的 `default`**。同一个 home 已有实例在运行时，这次启动写一行 error 后直接退出。

`pnpm start` 先构建再启动 electron。构建依次是：整个删掉 `dist/`（清单的 `files` 只列 `dist`，上一次构建留下的文件不删就会被一起发出去）；`tsc` 编译内核；用 `tsconfig.api.json` 只为 `src/api.ts` 生成包根导出的类型声明 `dist/api.d.ts`；把页面的 `index.html`、`preload.cjs` 复制进 `dist/`；最后运行 `scripts/build-react.ts` 把 react 打进 `dist/react/`（[页面上的 react 怎么打包](/docs/desktop#页面上的-react-怎么打包)）：

### 隔离 home 里的插件从哪来

内核不带插件。全新的 home 里 `cordis.yml` 是空表，启动后页面只显示只读状态页，页面发来的命令都回「没有命令服务」。要验证命令、外壳、插件管理这些，先往这个 home 里装上插件，两种做法：

- **用 devkit**：`devkit.home.new {"short":"<这次验什么>"}` 新建一个隔离 home，装好内核包（运行这条命令的那个内核的版本）、内核要的 `cordis` 与一套基础插件，并用安装版打开它。要从源码启动它时，先关掉那个窗口，再把 `GWB_HOME` 设成回执里的 home 名
- **照 `INSTALL.md` 手动装**：步骤与仓根 `INSTALL.md` 第 3 步相同，只把 home 目录换成这个隔离 home

## 提交前的检查

{/* ref file="../package.json" lines="5-14" */}

- **`pnpm check`**（仓根）：先构建内核包（连同 react 的打包产物与包根的类型声明，测试要读真实的构建产物），再对全仓做类型检查、lint 和测试。测试是 `apps/*/tests/` 下的 vitest 测试；`src/api.ts` 里的类型写坏了，内核的类型检查跟着失败
- **`pnpm doc`**（仓根）：文档站的检查，不在 `pnpm check` 里。确认用仓根的 `pnpm doc:confirm <页的路径…>`，路径相对 `docs-site/`，只点名自己改的页

## 在隔离 home 里验证

两条路，都不碰 `default`。

**发内核开发版进隔离 home**：验证的是安装版的样子——启动器从 home 里加载内核包。先用 `devkit.home.new` 开一个隔离 home，再从另一个 home 调：

```
devkit.dev {"home":"<隔离 home 名>","dir":"<本仓根>","packages":["apps/desktop"]}
```

本仓要发的 npm 包只有内核包，所以 `packages` 只写 `apps/desktop`。devkit 把它打成开发版号的包文件，经目标 home 的插件管理 `plugin-manager.update {"specs":{…}}` 装进去；`specs` 里只有内核包，`cordis` 由插件管理照新内核包 peer 里的版本自己对齐，所以**目标 home 的插件管理要 0.13.0 起**。主进程里的内核换不掉，装完 devkit 停掉那个 home 再启动，等到页面上 `shell.env` 报出的内核版本就是这次打包的版本号；回执的 `kernel.version` 就是它。不用重打安装包。

**从源码启动**：改一次就想看一次时用。

1. 照上面「隔离 home 里的插件从哪来」准备好 home，构建后带调试端口启动，端口别和别的会话重复：

   ```powershell
   $env:GWB_HOME = '<这次验什么>-<yyMMddHHmm>'
   cd apps\desktop; pnpm build
   pnpm exec electron . --remote-debugging-port=<端口> --disable-backgrounding-occluded-windows
   ```

   内核把调试端口写进 home 的 `runtime.json`（[runtime.json](/docs/seams/runtime)），`devkit.cdp` 从那里找到它；后一个开关让窗口被遮住时页面照常刷新，截图不会拿到旧画面
2. 用 `devkit.cdp` 在这个 home 的页面上调命令、截图、读页面状态
3. 看结果：home 里的 `gwb.log`；没有外壳或外壳启动失败时，页面上的[只读状态页](/docs/desktop#只读状态页)列出每个条目加载到哪一步

## 打安装包

```powershell
pwsh installer\scripts\build.ps1
```

在仓根运行，产物在 `installer\build\dist\`。安装包只带启动器与 Electron，内核不打进去；**只有 Electron 版本或启动器本身变了才需要重新打**。打包脚本一步步做什么、哪几道检查不能删、打完怎么验证，见[安装包与启动器](/docs/installer)。

## 发版

通用的发版步骤在说明书 `gwb-release`，这里只写内核包自己的：

1. **升版本号**：改 `apps/desktop/package.json` 的 `version`，包根导出的接口类型跟内核包用同一个版本号。升哪一位按改没改接缝判断：
   - **改了接缝上已有的东西就升 x**（`0.x.y` 里的 x）：十条接缝上已有的任何一样被改名、删除、改了形状或含义——包根导出的接口类型（`src/api.ts`）、IPC 通道、页面 importmap 里已有的包名、home 布局、`runtime.json` 的字段、日志行格式、内核包清单的 `engines.electron`——以及升级 `@cordisjs/plugin-loader`、`@cordisjs/plugin-include`、`cordis` 的版本（拿不准会不会弄坏插件管理，一律按会弄坏算）。插件在 peer 里写内核包的 `^` 范围，升了 x 之后所有插件的范围都不再包含新内核，要先照 `gwb-release` 的「发破坏性版本多做的两步」通知下游（[插件在 peer 里写兼容哪个内核](/docs/design#插件在-peer-里写兼容哪个内核)）
   - **只给接缝加东西（加类型、加可选字段）、只改内核内部或修 bug，升 y**：插件的 `^` 范围仍然包含新内核
   - **包根导出的接口类型对插件只增不减**：能加一个可选字段、一个类型解决的，不删名字、不改形状、不改调用方依赖的语义。契约之外的东西（日志行格式、命令插件与插件管理的类型）不放进 `src/api.ts`（[包根导出的接口类型](/docs/desktop/api)）
2. **发内核包到团队包源**：`devkit.release {"dir":"<本仓根>","packages":["apps/desktop"]}`；发到哪由内核包清单的 `publishConfig.registry` 决定，没写 `devkit.release` 就拒发
3. **启动器或 Electron 变了才打安装包、发布到 gitea releases**：发布仓是 gitea 上的 `godcreator/gwb-kernel`（本仓的 git 远端 `gitea`），release 附带 Windows 安装程序；push 用 git 凭据管理器里的凭据，API 用 gwb-gitea 插件的 `gitea.http`（用法在它的说明书）
   - tag 跟安装包（启动器）的版本走（`v<版>`），与 release 一一对应；release 说明指向仓根 `INSTALL.md`
   - **推送 tag 会让同名的草稿 release 自动公开**：要先存草稿、人工确认后再公开，就最后推 tag
4. **本机升级**：先在隔离 home 里装新内核包验证，再在 default 上调 `plugin-manager.update {"specs":{"@godcreator/gwb-kernel-desktop":"<版本>"}}`（插件管理把 `cordis` 一起对齐，`specs` 里不写它）；回执 `restartRequired` 为 `true` 时重启工作台，`pluginsOutsideRange` 列出 peer 范围不包含新内核的插件。改了契约时先装新内核、再发用到新契约的插件：插件先到、内核还是旧的，插件拿到的 `gwbKernel` 就缺它要的东西。升了 x 时，再在新内核上测插件、把它们 peer 里内核包的范围改到新内核并发版
