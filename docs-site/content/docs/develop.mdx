**日常从安装版启动，不进这个仓**（开始菜单「gwb-kernel」）；新机器安装照仓根 `INSTALL.md`。**改内核本身才进这个仓**，改动只在隔离 home 里实际运行验证，
不碰日常用的 `default`。`cordis.yml` 里的插件不在这里写：命令插件 `@godcreator/gwb-commands` 在基础插件仓 `gwb-base-plugins`，
插件管理 `@godcreator/gwb-plugin-manager` 在生命周期插件仓 `gwb-lifecycle-plugins`。

## 怎么跑

### 第一次准备

在仓根：

```powershell
pnpm install
cd apps\desktop; pnpm setup:electron
```

**`setup:electron` 必须显式运行一次**：electron 这个包没有安装脚本，二进制要运行它的 `install.js` 才会下载下来，仓根 `.npmrc` 让它走 npmmirror 镜像。
不运行的话启动失败，pnpm 也不提示（[electron 不带安装脚本](/trajectory/2026-09-07-wall-electron-postinstall)）。

{/* ref file="../.npmrc" lines="3-3" hash="a8b8a37fe3b5" blob="1418d8b82153" */}

仓根是 pnpm 工作区，收 `apps/*` 与文档站。**工作区链接会替包源满足 peer**：装包出问题先读当前的 `pnpm-workspace.yaml` 与 `pnpm-lock.yaml` 里的 `settings`，别照旧配置办。

### 从源码启动

```powershell
$env:GWB_HOME = '<这次验什么>-<yyMMddHHmm>'
cd apps\desktop; pnpm start
```

`GWB_HOME` 每次验证给一个新名字，home 建在 `%APPDATA%\gwb-kernel\homes\<名字>`；**不设就是日常用的 `default`**。同一个 home 已有实例在运行时，
这次启动在 `gwb.log` 写一行 error 后退出，退出码 1。

`pnpm start` 先构建再启动 electron。构建依次是：整个删掉 `dist/`；`tsc` 编译内核；用 `tsconfig.api.json` 只为 `src/api.ts` 生成包根导出的类型声明；
把页面的 `index.html`、`preload.cjs` 复制进 `dist/`：

{/* ref file="../apps/desktop/package.json" lines="29-29" hash="0105543ddee3" blob="df73ceac0ed7" */}

**第一步必须删掉 `dist/`**：内核包清单的 `files` 只列 `dist`，上一次构建留下的文件不删，就会跟着发到每个 home（[残留 dist](/trajectory/2026-09-25-stale-dist-shipped)）。

{/* ref file="../apps/desktop/package.json" lines="17-19" hash="8e3ed34eac97" blob="df73ceac0ed7" */}

### 隔离 home 里的插件从哪来

内核不带插件，也不补 home 里的文件：home 里缺 `package.json` 或 `cordis.yml` 时内核启动失败（见[启动与退出](/docs/desktop/boot)）。要验证命令、外壳、插件管理这些，先把插件装进这个 home：

- **用 devkit**：`devkit.home.new {"short":"<这次验什么>"}` 新建一个隔离 home，装好内核包（运行这条命令的那个内核的版本）、内核要的 `cordis` 与基础插件，并用安装版打开它。
  要从源码启动它，先关掉那个窗口，再把 `GWB_HOME` 设成回执里的 home 名
- **照 `INSTALL.md` 手动装**：步骤与仓根 `INSTALL.md` 第 3 步相同，只把 home 目录换成这个隔离 home

## 怎么检查

提交前两样都要绿：

- **`pnpm check`**（仓根）：先构建内核包，再对全仓做类型检查、`oxlint --type-aware --deny-warnings` 和测试。测试是 `apps/*/tests/` 下的 vitest 测试；
  `src/api.ts` 里的类型写坏了，构建与类型检查跟着失败
- **`pnpm doc`**（仓根）：文档站的检查，不在 `pnpm check` 里。改了被钉住的代码，同一个提交里运行 `pnpm doc:confirm`，
  剩下的黄灯逐条复核后 `pnpm doc:confirm <页的路径…> --accept`，路径相对 `docs-site/`，只点名自己改的页

{/* ref file="../package.json" lines="5-14" hash="47313b192440" blob="d702649f0e7f" */}

{/* ref file="../vitest.config.ts" lines="5-5" hash="1988100f1c27" blob="3cef56ce7fa9" */}

仓根的 `README.md`、`AGENTS.md`、`INSTALL.md`、`CLAUDE.md` 是生成物：正本在 `docs-site/content/docs/outputs/` 下的同名 mdx，映射写在 `docs-site/docfirst.config.mjs` 的 `outputs`。
改正本后在 `docs-site` 运行 `pnpm doc:render`，正本与生成物放进同一个提交；直接改生成物，下次渲染就被覆盖。

## 在隔离 home 里验证

两条路，都不碰 `default`。

**发内核开发版进隔离 home**：验证的是安装版的样子，启动器从 home 里加载内核包。先用 `devkit.home.new` 开一个隔离 home，再从另一个 home 调：

```
devkit.dev {"home":"<隔离 home 名>","dir":"<本仓根>","packages":["apps/desktop"]}
```

本仓要发的 npm 包只有内核包，所以 `packages` 只写 `apps/desktop`。devkit 把它打成开发版号的包文件，经目标 home 的插件管理
`plugin-manager.update {"specs":{…}}` 装进去；`specs` 里只有内核包，`cordis` 由插件管理照新内核包 peer 里的版本自己对齐。
主进程里的内核换不掉，装完 devkit 停掉那个 home 再启动，等到 `shell.env` 报出的内核版本就是这次打包的版本号。不用重打安装包。

**从源码启动**：改一次就想看一次时用。

1. 照上面「隔离 home 里的插件从哪来」准备好 home，构建后带调试端口启动，端口别和别的会话重复：

   ```powershell
   $env:GWB_HOME = '<这次验什么>-<yyMMddHHmm>'
   cd apps\desktop; pnpm build
   pnpm exec electron . --remote-debugging-port=<端口> --disable-backgrounding-occluded-windows
   ```

   内核把调试端口写进 home 的 `runtime.json` 的 `cdp`，`devkit.cdp` 从那里找到它；不带 `--remote-debugging-port` 启动的 home，`devkit.cdp` 连不上。
   后一个开关让窗口被遮住时页面照常刷新，不带的话截图拿到的是旧画面
2. 用 `devkit.cdp` 在这个 home 的页面上调命令、截图、读页面状态
3. 看结果：home 里的 `gwb.log`（一行一个 JSON，见[日志](/docs/desktop/log)）；没有外壳或外壳启动失败时，页面上的只读状态页列出每个条目加载到哪一步（见[页面入口](/docs/desktop/page)）

测试覆盖不到、只能这样实机验证的：真实窗口里画出来的样子；单实例锁本身（同一个 `GWB_HOME` 启动两次，第二次退出码 1、`runtime.json` 仍是第一个实例的 pid）；
插件清理超过 5 秒时照常退出；页面登记浏览器模块后能加载提供方的模块（React 的打包、版本和测试归外壳，内核只验登记与准备机制；
隔离 preload 注入的映射对页面生效，另有独立实验 `probes/2609271940_preload-importmap/`，它不替代完整 home 验证）；启动器的弹框与从 home 真的加载起内核。

另外一处测试核对不到：只读状态页的条目状态名是照 cordis 的 `FiberState` 抄的一份数字顺序（它是 `const enum`，本仓的编译设置下引用不到），**升级 cordis 时对照它的声明看一遍**，
否则状态页上会把一种状态报成另一种。

## 打安装包

```powershell
pwsh installer\scripts\build.ps1
```

在仓根运行，产物在 `installer\build\dist\`。安装包只带启动器与 Electron，输入全部来自本仓的 `apps/launcher`，内核装在 home 里，
所以**只有 Electron 版本或启动器本身变了才需要重新打**。安装包产出什么见[安装包](/docs/installer)。

### 打包的步骤

**1. 检查工作区**：内核仓里已跟踪的文件有未提交的改动就停下，未跟踪的新文件不算。打包用的是仓里的代码，有改动时打出来的 exe 说不清装了什么。

{/* ref file="../installer/scripts/build.ps1" lines="15-16" hash="0c908c861c86" blob="d883fc0fa1c8" */}

**2. 构建启动器**：`apps/launcher` 里 `pnpm build`。

{/* ref file="../installer/scripts/build.ps1" lines="18-22" hash="f4b3cf8c5180" blob="d883fc0fa1c8" */}

**3. 读版本号**：启动器版本与 electron 版本都从 `apps/launcher/package.json` 读，安装包的版本号就是启动器的版本号。electron 的版本只写在它的
`devDependencies.electron` 一处，经命令行传给 electron-builder：electron-builder 只在项目根找 electron 版本、不看应用目录，所以 `electron-builder.yml` 里不写。
内核要的 Electron 范围写在内核包的 `engines.electron`，启动器的测试检查两边对得上。

{/* ref file="../installer/scripts/build.ps1" lines="24-26" hash="0ded539efcf4" blob="d883fc0fa1c8" */}

**4. 组装应用目录**：把启动器的构建产物复制到 `installer\build\app`，按启动器的清单写一份只留运行字段的 `package.json`（入口 `main.js`、依赖照抄），再 `npm install`。

{/* ref file="../installer/scripts/build.ps1" lines="28-48" hash="93e409b2a06f" blob="d883fc0fa1c8" */}

**5. electron-builder**：`installer/node_modules` 里没有 electron-builder 就先 `npm install`，再按下面的配置打出 `gwb-setup-<版>.exe`，最后列出产物和大小。

### 不能删的检查

- **每条 npm / pnpm 之后检查退出码**（`Assert-LastExit`）：pwsh 对原生命令的非零退出码默认不停，不检查的话前一步失败（比如组装目录是空的）也会照样打出安装包
  （[打包静默出错](/trajectory/2026-09-15-wall-installer-silent-failures)）
- **启动器的依赖写进应用目录的清单再 `npm install`**：electron-builder 按清单收集 `node_modules`，用 `--no-save` 装进去的包它不收，打出来的 `app.asar` 里就没有 `semver`

{/* ref file="../installer/scripts/build.ps1" lines="10-13" hash="eb90509ef873" blob="d883fc0fa1c8" */}

### 打完怎么验证

打包脚本没有单元测试，它自己在每一步检查退出码，打完之后这样验证：

- **打包形态能启动**：准备一个临时 home（`GWB_HOME` 给路径），`package.json` 里列内核包（本仓 `apps/desktop` 用 `pnpm pack` 打出的包文件，以 `file:` 写进去）与内核要的 `cordis`，
  写好 `cordis.yml`，`pnpm install`；运行 `installer\build\dist\win-unpacked\` 里的 exe，启动器从 home import 内核，`gwb.log` 里有内核的 up 那一条、没有 error。
  **不设 `GWB_HOME` 运行它会打开真正的 default**
- **缺内核包时启动器拒绝启动**：把那个 home 里的内核包删掉再启动，弹框说明缺内核包、退出码 1
- **单实例锁**：同一个 home 再启动一次，退出码 1、`runtime.json` 不变
- **安装说明**：派一个没有上下文的子代理，只给它 `INSTALL.md`，让它往一个临时 home（`GWB_HOME` 给路径）里照做一遍、启动 `win-unpacked` 的 exe，
  MCP 入口能调通、条目全部 ACTIVE 才算通过；它不得不问的每个问题都是说明的漏洞

**别日常直接运行 `win-unpacked\`**：每次打包整个重新生成，会和运行中的 exe 冲突。

## 发版

升哪一位以 devkit 的说明书 `gwb-release` 为准（`run skill.read {"name":"gwb-release"}`），通用的发版步骤在说明书 `gwb-devkit`。这里只写内核包自己的。

### 内核包什么改动升 x、什么升 y

内核包的版本号就是包根导出接口类型的版本号，改 `apps/desktop/package.json` 的 `version`：

- **包根导出的接口类型**（`src/api.ts`，插件 `import type` 取）：加类型、给已有类型加可选字段，升 y；删掉、改名、改形状、改调用方依赖的语义，升 x
- **接缝上已有的东西**：改了就升 x，只加东西升 y。已有的东西包括 IPC 通道与请求通道、浏览器模块登记与准备接口的语义、home 的布局、`runtime.json` 的字段、
  `gwb.log` 的格式、内核包清单的 `engines.electron`，以及 `@cordisjs/plugin-loader`、`@cordisjs/plugin-include`、`cordis` 的版本（拿不准会不会弄坏插件管理，一律按会弄坏算）
- **只改内核内部或修 bug**，升 y

{/* ref file="../apps/desktop/package.json" lines="37-43" hash="9afff01b3cb1" blob="df73ceac0ed7" */}

插件在 peer 里写内核包的 `^` 范围（`^0.x.y` 只包含同一个 x），**升了 x 之后所有插件的范围都不再包含新内核**：发之前照 `gwb-release` 的「发破坏性版本多做的两步」给下游仓投反馈；
能加一个可选字段、一个类型解决的，就不删名字、不改形状。契约之外的东西不放进 `src/api.ts`（见[包根导出的接口类型](/docs/desktop/api)）。

### 发版顺序

1. **升版本号并提交**，同一个版本号永不重发
2. **发内核包到团队包源**：`devkit.release {"dir":"<本仓根>","packages":["apps/desktop"]}`。发到哪由内核包清单的 `publishConfig.registry` 决定，没写 `devkit.release` 就拒发
3. **启动器或 Electron 变了才打安装包、发布到 gitea releases**：发布仓是 gitea 上的 `godcreator/gwb-kernel`（本仓的 git 远端 `gitea`），release 附带安装程序；
   push 用 git 凭据管理器里的凭据，API 用 gwb-gitea 插件的 `gitea.http`（用法在它的说明书）
   - tag 跟安装包（启动器）的版本走（`v<版>`），与 release 一一对应；release 说明指向仓根 `INSTALL.md`
   - **推送 tag 会让同名的草稿 release 自动公开**：要先存草稿、人工确认后再公开，就最后推 tag
4. **本机升级**：先在隔离 home 里装新内核包验证，再在 default 上调 `plugin-manager.update {"specs":{"@godcreator/gwb-kernel-desktop":"<版本>"}}`（插件管理把 `cordis` 一起对齐，
   `specs` 里不写它）；回执 `restartRequired` 为 `true` 时重启工作台，`pluginsOutsideRange` 列出 peer 范围不包含新内核的插件。
   改了契约时先装新内核、再发用到新契约的插件：插件先到、内核还是旧的，插件拿到的 `gwbKernel` 就缺它要的东西。升了 x 时，再在新内核上测插件、把它们 peer 里内核包的范围改到新内核并发版
