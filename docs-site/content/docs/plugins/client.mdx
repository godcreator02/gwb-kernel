# 浏览器那半

读完这页你能回答：件的浏览器那半怎么被加载；页面上能碰到什么；外壳和窗格两种角色差在哪；
样式与组件从哪来。

## 地址：自己算，自己报

件的浏览器那半是一份普通的 ESM 产物，浏览器直接从 `file://` 加载——没有协议、没有定址表。
地址的算法只有一句：

```ts
const CLIENT_URL = new URL('./client.js', import.meta.url).href
```

dist 下的产物互为邻居，从自己的模块地址出发一步就到。这个地址**件自己消费**：注册窗格时
报 `client`（与可选 `style`）两个字段；外壳件则把 `./client.js` 交给 `setShell`（见
[服务与命令](/docs/plugins/services)）。内核全程不认识你的包名、角色名、导出名。

打包纪律一条：**只把 importmap 里有的裸名外置**（react 那几个），其余依赖全部打进自己这份
束——外置错了不在构建期报，运行期一句 `Failed to resolve module specifier`。

## `window.gwb`：页面的公共面

{/* ref file="../apps/desktop/src/preload.cjs" lines="4-19" */}

| | 是什么 |
| --- | --- |
| `command(name, args?)` | 命令通道：`gwb:command` → 命令总线 → `GwbResult` |
| `on(cb)` | 件经 `gwbKernel.emit` 推上来的消息，回注销函数 |
| `onShell(cb)` | 外壳地址与 importmap，回注销函数；**订上先收当前值** |

只有这三个。旧线上还有 `onHostExit` 与 `logs.backlog`/`logs.on`——宿主没了、日志归
`gwb-logger` 件走 `on` 推，那几个口随两进程线退役。

谁在这页上跑都够得着——外壳、窗格件、随手在控制台敲的一句，都一样。外壳给窗格的便利层
**不是唯一入口**；日志这类页面级的东西窗格直接订 `window.gwb.on`——**外壳不该转发它**，
它凭什么认识「日志」。

四步，每步都有理由：

1. **先注 importmap，再 import 外壳**——注过就盖不掉已解析过的裸名，次序反了第一句裸名
   import 就炸（见[取址](/docs/kernel/loading#浏览器半的取址-importmap-是内核拼的)）；
   空表不注，注一张空表没有意义还占坑
2. **拆旧外壳**——`dispose()` 失败只 `console.error`，不阻新的上
3. **url 是 null 就画只读现状**——一句「没有外壳件」，下面是内核推来的条目清单与错误行
   （见下一节）。没有轮询：单进程后不存在「外壳还没轮到」的中间态，条目换态是内核推过来的
4. **校验默认导出是函数再调**——`mod.default(root)`，返回的 `dispose` 记下来给下一轮拆
   （形状就是词汇表的 `ShellBoot`，见[词汇表](/docs/plugins/vocab)）；失败 `console.error`
   加同一份只读现状，头一句换成「外壳起不来：原话」

## 两种角色，两个动词

**「占整页的根」和「占井里的一格」是两种件**，导出的动词必须不同——**你导出哪个名字，
就声明了自己是哪种件**：外壳导出 `mountShell`，窗格导出 `mountPane`。共用一个动词会让人
以为它俩是同一件事的两个变体，而形状对不上**只有运行时才发现**。

### 外壳：谁调 `setShell`，谁就是外壳

内核不挑外壳、也不认识「外壳」这个词——**件的 node 半自己交页面根**：

```ts
export function apply(ctx: GwbContext) {
  const kernel = requireKernel(ctx)
  ctx.effect(() => kernel.setShell(new URL('./client.js', import.meta.url).href))
}
```

包在 `effect` 里：件卸载、撤销函数跑、页面收回那句话——外壳身份是运行时一通电话，不是
清单声明（旧线「谁 provide `gwbShell` 谁是外壳」的判法随两进程退役了，
了断见[轨迹](/docs/trajectory/2026-09-09-single-process)）。开机要的 home 与三张样式
表地址，外壳的浏览器半开机问一次 `shell.env` 命令再起——命令契约正本在件仓。

默认导出的形状：

```js
export default function mountShell(root) {
  // 把界面装进 root
  return { dispose() { /* 件被卸载时，把这棵树拆干净 */ } }
}
```

**回一个 `{ dispose }`**：件被卸载时页面上那棵树得有人拆——内核那页 html 会调它（见上面
第 2 步）。

### 窗格：`mountPane` 的契约正本住件仓

`mountPane` 的 `args` 里有什么，**是外壳件说了算的**——内核只定 `ShellBoot`，它连「窗格」
这个概念都没有。窗格清单是运行时注册：件在 `apply` 里调 `ctx.gwbShell.registerPane(…)`，
报 `client`/`style` 地址，不写进包清单（判据见
[窗格动态注册](/docs/trajectory/2026-09-07-panes-runtime-registry)与
[args 归外壳](/docs/trajectory/2026-09-07-pane-args-shell-owned)）。大意是这样，细节以
件仓 `gwb-shell` 那页为准：

```js
export function mountPane(args, container) {
  // args 里有 pane.id（这是本件的哪一格）等；client/style 地址注册时报过了
  return { dispose() {} }
}
```

**必须同步返回一个 `{ dispose }` 对象**——async 函数、返回 Promise、返回别的，都会被外壳
当契约违规报出来。

## 样式

样式表跟 client 一条路：地址自己算（`new URL('./style.css', import.meta.url)`）、注册时
报 `style` 字段，外壳开格时注 `<link>`。

**注了不等于到位**：`<link>` 是异步取的，束里第一帧 DOM 完全可能落在表到位之前，那一瞬间
是一堆没有样式的裸元素。等 `link.onload` 再渲染。

件的样式整张 scope 在 `[data-gwb-plugin="<完整包名>"]` 之下，容器上不挂这个属性，一个类名
都不生效。设计令牌（颜色、圆角那些 CSS 变量）全生态共享一份，件的表里只有
`var(--background)` 这样的引用——**换主题＝换那一份值，所有件当场跟着变，一个都不用重新
构建**。字体也是令牌：改全局字体＝覆盖 `--gwb-font-sans` / `--gwb-font-mono` 两个变量，
一处值，全场生效。

用户侧的现成入口是 gwb-theme 件（件仓）：「外观」格里收两项字体加一段自定义 CSS，输入即
预览、保存落盘；重启后外壳 boot 经 `theme.startupCss` 把整段取走、注在令牌表**之后**——
同特异性下靠文档序取胜。这条命令是**软契约**：theme 没装时总线回「没有这条命令」，外壳
跳过，谁也不欠谁。

## 组件

**每个件自己从 shadcn 官方拉**（`pnpm dlx shadcn@latest add button`）。**没有「工作台的
组件库」这种东西，也不建 registry**——shadcn 的组件源码本来就是给你改的，A 件的 button 跟
B 件的不一样完全没关系。**统一风格由令牌保证，不由组件源码一致保证**，这两层正交。

配置三处对齐，`@/` 一律指向 `src/client`：`components.json` 的 `aliases`、两份 `tsconfig`
的 `paths`、打包器的 esbuild `alias`。两个容易撞的点：

- **别写 `baseUrl`**——TS 7 把它移除了（`TS5102`），shadcn 文档给的还是老写法；`paths`
  直接相对 tsconfig 所在目录解析
- `components.json` 的 **`tailwind.css` 必须指一个真实存在的文件**（`tailwind` 对象整个
  必填）。件因此有一个 `src/client/styles.css`——它同时也是件写自己 CSS 规则的地方

## 两条纪律

**收日志的路径上一个 `console` 都不许打**——页面窗格的 console 是日志三路之一，回环起来
界面当场冻死（见[日志](/docs/kernel/logs)末尾）。**样式与令牌的细节正本在件仓**——这页
只记内核侧认得到的形状，跨仓钉不了码。
