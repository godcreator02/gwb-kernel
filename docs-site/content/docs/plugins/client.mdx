# 浏览器那半

读完这页你能回答：页面上能碰到什么；外壳和窗格两种角色差在哪；样式与组件从哪来。

## `./client` 与打包纪律

件要在窗口里画东西，多导出一个 `./client` 子路径。它由浏览器经 `gwb://` 直接加载、不经过打包器。裸名 `import` 只有一种情况能用：**那个名字在页面的 importmap 里**。所以打包纪律是一条：**只把 importmap 里有的裸名外置**（react 那几个），其余依赖全部打进自己这份束——外置错了不在构建期报，运行期一句 `Failed to resolve module specifier`。

## `window.gwb`：页面的公共面

{/* ref file="../apps/desktop/src/preload/index.ts" lines="10-28" */}

| | 是什么 |
| --- | --- |
| `command(name, args?)` | 命令通道，走到宿主分发再原路回 |
| `onEvent(cb)` | 件经 `gwbKernel.emit` 推上来的事件，回注销函数 |
| `logs.backlog()` | 开机到此刻的日志条目（主进程那圈环形缓冲） |
| `logs.on(cb)` | 之后的日志，**按批**推，回注销函数 |

谁在这页上跑都够得着——外壳、窗格件、随手在控制台敲的一句，都一样。外壳给窗格的 `args.host.call` 是它替你绑好身份的一层便利，**不是唯一入口**；日志这类页面级的东西直接用 `window.gwb`——**外壳不该转发它**，它凭什么认识「日志」。

## 两种角色，两个动词

**「占整页的根」和「占井里的一格」是两种件**，args 形状本来就不同：外壳拿 `entries`（它要据此排出可开窗格表）、拿不到 `shell` 与 `pane`；窗格反过来。共用一个动词会让人以为它俩是同一件事的两个变体，而形状对不上**只有运行时才发现**。所以：外壳 **`bootShell`**，窗格 **`mountPane`**——**你导出哪个名字，就声明了自己是哪种件。**

### 外壳：谁 provide `gwbShell`，谁就是外壳

```ts
export default class MyShell extends Service {
  constructor(ctx) {
    super(ctx, 'gwbShell')   // ← 就这一句。内核看的是「谁 provide 了它」
  }
}
```

**不绑包名**：外壳件叫什么都行，provide 这个名字的就是。内核认识 `gwbShell` 这一个名字——那免不了，它总得挑一个件把 `#root` 交出去。声明走运行时而不是清单，白得三样：「多于一条外壳」的局面不存在（provide 撞名直接抛）；半死的外壳挑不出来（内核只认 fiber ACTIVE 的提供者）；内核不用为这件事去读每个包的清单（判据见[外壳身份运行时](/docs/trajectory/2026-09-07-shell-identity-service)）。

外壳的 client 导出 **`bootShell`**：

```js
export function bootShell(args, root) {
  // args.host.call(command, args?) —— 命令通道
  // args.home —— home 目录绝对路径
  // args.entries —— 条目表，每条 { id, ok, pkg, disabled }
  return { dispose() { /* 件被卸载时，把这棵树拆干净 */ } }
}
```

**回一个 `{ dispose }`**：件被卸载时页面上那棵树得有人拆。眼下渲染层还不会调它（它不感知条目变化），但契约先立着——将来要热换外壳时不必回头改所有外壳件。

渲染层启动时问内核要 `kernel.info`，里头的 `shellPkg` 就是答案；**一个都没有就是留白**，原因进 console 分开说两种成因（一个件都没 provide，还是有件在等它的依赖）。

### 窗格：`mountPane` 的契约正本住件仓

`mountPane` 的 `args` 里有什么，**是外壳件说了算的**——内核只定 `bootShell`，它连「窗格」这个概念都没有。大意是这样，细节以件仓 `gwb-shell` 那页为准：

```js
export function mountPane({ host, shell, pane }, container) {
  // host 跟外壳拿到的是同一个命令通道
  // shell 能开本件的另一格、能往格间总线发消息
  // pane.id 说这是本件的哪一格，pane.instance 说这是那一格的第几份
  return { dispose() {} }
}
```

**必须同步返回一个 `{ dispose }` 对象**——async 函数、返回 Promise、返回别的，都会被外壳当契约违规报出来。窗格清单也是运行时注册：件在 `apply` 里调 `ctx.gwbShell.registerPane(…)`，不写进包清单（判据见[窗格动态注册](/docs/trajectory/2026-09-07-panes-runtime-registry)与[args 归外壳](/docs/trajectory/2026-09-07-pane-args-shell-owned)）。

## 样式

样式表跟 client 走同一条路：列进 `exports`（比如 `./style.css`），件自己注 `<link>`。

**注了不等于到位**：`<link>` 是异步取的，束里第一帧 DOM 完全可能落在表到位之前，那一瞬间是一堆没有样式的裸元素。等 `link.onload` 再渲染。

件的样式整张 scope 在 `[data-gwb-plugin="<完整包名>"]` 之下，容器上不挂这个属性，一个类名都不生效。设计令牌（颜色、圆角那些 CSS 变量）全生态共享一份，件的表里只有 `var(--background)` 这样的引用——**换主题＝换那一份值，所有件当场跟着变，一个都不用重新构建**。

## 组件

**每个件自己从 shadcn 官方拉**（`pnpm dlx shadcn@latest add button`）。**没有「工作台的组件库」这种东西，也不建 registry**——shadcn 的组件源码本来就是给你改的，A 件的 button 跟 B 件的不一样完全没关系。**统一风格由令牌保证，不由组件源码一致保证**，这两层正交。

配置三处对齐，`@/` 一律指向 `src/client`：`components.json` 的 `aliases`、两份 `tsconfig` 的 `paths`、打包器的 esbuild `alias`。两个容易撞的点：

- **别写 `baseUrl`**——TS 7 把它移除了（`TS5102`），shadcn 文档给的还是老写法；`paths` 直接相对 tsconfig 所在目录解析
- `components.json` 的 **`tailwind.css` 必须指一个真实存在的文件**（`tailwind` 对象整个必填）。件因此有一个 `src/client/styles.css`——它同时也是件写自己 CSS 规则的地方

## 两条纪律

收日志的路径上一个 `console` 都不许打；件不自己挂 cordis exporter——理由与后果见[日志](/docs/kernel/logs)末尾。
