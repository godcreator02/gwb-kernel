# 内核四件事

这四件事是从「让 cordis 插件跑起来，并且有界面」这一句推出来的，不是分模块分出来的。
每一件都要能回答同一个问题：**为什么它不能是插件**。答案永远是同一句——它必须在第一个
插件存在之前就位。

## 一、载体

**做什么**：GUI 主进程起一扇窗；宿主子进程起一个 cordis `Context`。

宿主是纯 node 进程，由主进程用 `spawn(process.execPath, ['--expose-internals', host.mjs])`
拉起，靠 `ELECTRON_RUN_AS_NODE=1` 把 electron 当 node 使。之所以要这个绕法：`--expose-internals`
是 cordis 加载模块用得上的，而主进程的 `NODE_OPTIONS` 白名单拒绝它。

**为什么不能是插件**：模块要有运行时才跑得起来，窗口要有进程才开得出来。这两样都发生在
第一个插件之前。

**窗口必须由内核开**，不能交给插件——这条有个不显然的推论：即使将来把窗口的尺寸、标题、
关窗语义都交出去，`BrowserWindow` 这个动作本身仍留在内核，因为在插件挂上之前就得有一扇窗
让页面加载。

**几个进程的输出也归载体接住**。主进程自己的、宿主 pipe 过来的、渲染层 `console-message`
转来的，三处最后都汇在 `process.stderr` 上——劫持这一处就全在，这条流进 `<home>/logs/`
（2 MB 切一段、留 20 份）。

而**界面要的是另一回事**：日志窗格得按级别与来源筛，文本行给不了这个。所以四路日志各自在
**源头**结构化成条目，进主进程的一圈环形缓冲，窗格从 preload 上取历史段、订阅实时。

**缓冲与汇总在主进程**，不在宿主、也不在任何件：够得着四路的只有它，而且宿主崩了之后它还在
——那正是最需要翻历史的时刻。判据见[定过的事](/docs/decisions)。

## 二、取址

**内核自己不做这件事**，它只挂两样，其余全归它们：

- `@cordisjs/plugin-loader` —— 条目树与模块加载
- 一条 `cordis:include` 条目 —— 读 `<home>/cordis.yml`

**内核连 yml 都不认识。**

关键是 `baseUrl` 指向 home 那个目录：loader 的模块解析从这儿起步，`<home>/node_modules`
里的件因此按裸名就找得到。母仓把 baseUrl 设成应用目录，所以它必须自己把每个条目名算成
绝对 file URL——那句「裸名包只在 home 位时 loader 会静默挂不上」的血泪注释，根因就在这里。

四条引导链上的判据：

- loader 与 include **都住应用依赖树**：它们要在读 yml 之前就位，写进 yml 是鸡生蛋
- include 走 loader 的 `builtins`——`cordis:` 前缀的名字直接从内建表取、不经模块解析
  （baseUrl 指着 home，按裸名找不到住在应用依赖树里的它）
- 做成**条目**而不是 `ctx.plugin(Include)`：它的子树因此挂在 loader 树上，条目表、fiber
  状态、热挂卸全在一棵树里，外面只认 `ctx.loader` 一个入口
- 承载 yml 那条条目的 id **写死为 `home`**：条目 id 有层级（`<父>:<子>`），父 id 一变，
  所有件的 id 跟着变，外壳按 panel id 存的布局就全对不上

**热挂载的形态**：include 没有文件监听，`refresh()` 要外部调。所以不是「改文件自动生效」，
而是**「调条目树的 API，树自己写回 yml」**——设置件将来走这条，比编辑文件等监听合理。

**为什么它仍然是内核的一件事**：取址必须在第一个业务插件之前发生。内核把它交给一个官方
引导插件，不等于这件事不存在——只是实现从「自己写」变成「挂一个官方件」。

### 开着的 cordis 官方件

| 包 | 住哪 | 为什么 |
| --- | --- | --- |
| `@cordisjs/plugin-loader` | 应用依赖树，内核挂 | 条目树与模块加载。热挂卸是白得的 |
| `@cordisjs/plugin-include` | 应用依赖树，内核挂 | 读 yml 成条目。有了它内核连 yml 都不必认识 |
| `@cordisjs/plugin-timer` | home，走 yml 条目 | `ctx.setTimeout` 随件卸载自动收——原生的会在插件已卸载后触发 |

**不开的七个，各有理由**：

- `plugin-logger-console` —— **出口归内核自己那个全量 exporter**。做日志窗格时内核为了汇四路
  必须挂一个全量出口，它跟这个件直接冲突：两个都在，同一句 cordis 日志打两遍。而且
  「件的日志有没有出口」不该取决于某个件装没装——它曾经开着，也曾经**只是文档里开着**
  （`RECOMMENDED` 一直是空表）

- `plugin-hmr` —— **在这个架构下不起作用**：跑的是 home 里那份产物，盯仓内源码盯到变化
  也没有对应模块可换。除非哪天做「源码映射进 home」的开发模式
- `plugin-http` / `plugin-server` —— **内核**没有外部访问需求。MCP 那条线后来真长出来了，
  但它是**件**（`@godcreator02/gwb-mcp`），而那个件自己起 `node:http`、这两个官方件也没装。
  顺带记一处订正：`plugin-http` 其实是 **HTTP 客户端**（`ctx.http`），本来就收不了请求
- `plugin-config` / `plugin-webui` —— **不是 Koishi 的**（那句判错了，见 decisions）。
  `plugin-config` 已改名 `plugin-loader-webui`、版本上装得进来，但它硬 peer 一个 webui，
  而 webui 要 `server`——为一个条目编辑器拖进 HTTP＋WebSocket
- `plugin-database` —— 没有超出「件自己写文件」的需求
- `@cordisjs/logger` —— 旧版，cordis 4.x 本体已自带
- `@cordisjs/schema` —— cordis 3 遗物、已从官方仓删除；**配置校验 cordis 4 本体自带**
  （`plugin.Config` 走 Standard Schema）

**内核留下的那半**：`resolvePlugin` / `entryFile` 还在，但不管挂载了。它们是**主进程**的
`gwb://` 在用——把插件的 `client.js` 交给页面时要知道包在哪，而 loader 跑在宿主子进程里，
主进程够不着。入口只认四档写法（`exports` 对应子路径 → 条件对象的 `import`/`module`/`default`
→ `main` → `index.js`），外加一条越界检查：入口指到包目录外一律不认，认了它一个包就能让
内核读任意文件。

## 三、装机

**做什么**：把包名转发给 pnpm（`pnpm add <spec>`，cwd 是 home 目录）。registry 归 pnpm 按
`.npmrc` 决定——本地还是远端不是内核该管的事。pnpm 随应用自带，不看 PATH 上有没有。

两个调用点：

- `kernel.install` 命令，插件与界面都能调
- 首启——home 还不是个包就建出 `package.json`，再按推荐列表装一遍

**装过了一概不碰。** 不判四路、不存快照、不猜哪条是用户钉的版本。装不上就回一句原因
（pnpm 输出的尾巴），不还原、不对账、不重试。装完不重挂，重启就好。

**为什么不能是插件**：它是装插件的那台机器，同上的循环。

**为什么它必须存在**：插件从哪来，逻辑上只有两条路——随本体交付（那它就不是「后来的」了，
插件集合在发版那一刻冻结），或者事后装进来。选后者，就必须有装机。这不是技术决定，是
「这是一个工作台」这句话的推论。

## 四、桥

桥有两个方向的活，第二个最容易被漏掉。

**传消息**：渲染层经 IPC 到主进程，主进程经 fd3 到宿主，宿主分发给插件，原路回。协议是
一行一条 JSON：命令下行走 stdin，宿主上行走 fd3（fd1 留给宿主自己的日志，混在一起就没法读）。

**日志不走这条通道**：缓冲住在主进程，preload 上另有两条口直接拿（历史段与实时）。走命令
的话请求要从缓冲旁边路过、绕到宿主再原路背回来，而**宿主一挂命令全废**——那恰恰是最需要看
日志的时候。日志上行倒是走 fd3（宿主那一路的条目），跟命令回执共用一条管子。

**传代码**：插件的浏览器那半住在 node 那边的 `node_modules` 里，页面得有一条取货通道。
约定只一条 URL：

```
gwb://asset/plugins/<包名>/client.js
```

包名带 scope 自然是两段，所以规则是「最后一段是资源名、前面全是包名」。目前只交出
`client.js`，样式与图标要用时再加，不预留。

**为什么不能是插件**：两个执行世界之间的通道，得在任何一边有插件之前就存在。

## 词汇表

它归不进上面任何一件事，因为它不做事——它只命名。取址要能说出「条目」，桥要能说出
「命令」「事件」，这些名词的定义就是它。

这也顺带解释了它为什么该是零依赖、零 node 引用的：一个只命名不做事的东西，本来就不该
依赖任何执行环境。

## 眼下做到哪一步

四刀都已经跑通，每一刀都有实机验收，不是桩：

| | 断言 | 怎么证明的 |
| --- | --- | --- |
| 一 | 两个世界通上了 | 页面调一条命令，穿过 IPC → fd3 → cordis 宿主再原路回；宿主 pid 独立、`node` 版本对得上 |
| 二 | 能挂插件 | 三条条目分别是「挂上」「位里没有」「被禁用」，逐条对上；界面调到了那个件注册的服务 |
| 三 | 看得见 | 外壳件的 `client.js` 经 `gwb://` 到了页面，`bootShell` 被调，外壳自己经 bridge 调命令走通 |
| 四 | 能从零装出一套 | 删净 home 起一次建出 home；外壳调 `kernel.install` 从本机 registry 装下一个真包；重启后取址找到它、cordis 接受、挂上 |
| 五 | **热挂载生效**、内核给得出信息 | 取址换成 loader + include；一个测试件在运行中 `create` 一条条目——那个件当场挂上，`remove` 之后当场卸载、清理 effect 真跑了，yml 自动写回；`ctx.gwbKernel` 四样对上；`emit` 的事件穿过 fd3 到了外壳 |

第四步串起了全部四件事：**装 → 取址 → 挂载**，用的是真实插件。第五步之后，改配置不必重启。
