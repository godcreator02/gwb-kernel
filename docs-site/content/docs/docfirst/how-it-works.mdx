# 账本与钉码

读完这页你能回答：docfirst 的五类引用怎么写；账本里存的是什么；check 的四种颜色分别要你做什么；为什么它不在 `pnpm check` 里。

## 文档钉代码

正式记号是一条 MDX 注释，构建时被换成带状态点的代码块：

```mdx
{/* ref file="../apps/desktop/src/host/home.ts" lines="32-37" */}
```

五类引用：`ref`（行段/整文件）、`tree`（目录树，可带 depth）、`exists`/`absent`（断言在/不在）、`has`（文件里有这个字面量）。**引用路径相对文档站目录**（`../apps/...`）。**跨仓钉不了**——件仓的代码只能在件仓自己的站上钉。

草稿写 `@@docfirst ref ../x.ts:12-20 @@`，confirm 时转正。

## 账本：`.ledger.json`

confirm 给每条引用记四样：git blob、commit、行段、64 位内容段哈希。行号记的是**当时那个 blob 里的位置**；核对时拿 `git diff` 的 hunk 表把旧行段映射到今天。**绿只认段哈希**——内容没变，挪了位置也算新鲜。

## check 四色

| 色 | 意思 | 你要做什么 |
| --- | --- | --- |
| 🟢 fresh | 段哈希没变 | 什么都不用 |
| 🟡 changed | 钉住的代码变了，附 diff | **人看一眼**：这页说的还是不是这件事 |
| 🔴 missing | 指向空气（文件没了、行段映射不到） | 改钉或删引用 |
| ⚪ unconfirmed | 还没入账 | 跑 confirm |

check 还会报：孤儿记录、已删文档的残留记录、名册外组件、README 生成物与正本不一致。有红就退出码 1。

## confirm：先提交，再确认

顺序是铁的：**改代码 → 提交 → 写文档 → confirm**。git 比较器拒钉未提交、未跟踪、被 ignore 的文件。confirm 做三件事：快照入账、草稿记号转正、清孤儿记录。

**行号不用人维护**——代码挪了位置，下次 confirm 把记号改写成今天的位置。**但内容变了要人看一眼**——那正是报黄的意义，别闭着眼 confirm 过去。

## 生成物：README 与 `.ai.md`

`docfirst.config.mjs` 的 `outputs` 把正本摆出去：`readme.mdx` → 仓根 `README.md`。`render --target ai` 把每页渲染成无 JSX、锚点齐全、引用展开成真代码的 `.ai.md`——给不带浏览器的读者（比如 agent）直接读的那份。

**README 别手改**，改正本、跑 render、一起提交。

## 为什么不在 `pnpm check` 里

它要起文档站的解析链，太慢，每次跑测试都带上不值。单独两条：

```powershell
pnpm doc          # docfirst check：钉住的代码变了报黄，指向空气报红
pnpm doc:confirm  # 看过之后确认；草稿记号也在这一步转正
```

改了被钉住的代码就跑一次，多次攒着一起跑也行。**提交前跑一次**是个好习惯。

## 反向没有守卫

docfirst 只钉「文档 → 代码」。代码里想指文档？没有任何机制保证那个页面还在——所以**注释里不写文档站的页名或锚点**，要指路就写「见文档站」四个字。
