**本页回答**：词汇表包管什么、不知道什么；它导出哪些名字、每个名字属于哪条接缝；插件怎么用它；改它的规则——什么算补丁、什么算破坏；它和内核的版本号怎么走、怎么发版；它依赖什么、怎么测、代码从哪读。

## 管什么

`packages/gwb-plugin-api`，包名 `@godcreator/gwb-plugin-api`。内核与插件、页面之间的全部契约都写在这一个文件里：主进程一侧是 `gwbKernel` 与命令总线 `gwbCommands`，页面一侧是 `window.gwb` 的三个函数，外壳是一个默认导出的形状。每个名字是什么、属于哪条接缝，见下面的「提供的接口」。

在[接缝图](/docs#接缝图)上它是「词汇表包」那个框：接缝 2、3、4、5 两侧共用的类型，它自己不算一条接缝。

**它是独立的包、和内核放在同一个仓**：类型只在编译时存在，cordis 服务只能传递运行时的值，插件在别的仓里编译时要能装到一个带类型的包；契约由提供服务的一方定义，放在插件仓里就等于调用方持有契约，内核改实现时没有任何检查能发现契约被改坏了（[词汇表是独立包、与内核同仓](/trajectory/2026-09-07-vocab-package-standalone)、[它就这么大](/trajectory/2026-09-07-wall-vocab-just-size)）。

## 不知道什么

- **没有运行时代码**：包里只有类型，也没有一条运行时依赖，构建出的 `dist/index.js` 是空模块。类型给的是形状，拿不到值：`dataDir` 这类值是内核那一次运行算出来的，只能从 `ctx.gwbKernel` 取
- **不知道谁实现这些类型**：`gwbKernel` 由内核应用的 `main.ts` 提供，`gwbCommands` 由内置的命令插件提供，`window.gwb` 由页面一侧的 `preload.cjs` 注入；包里只写形状
- **契约之外的东西不放进来**：日志行的格式、插件管理的回执类型都不在这里——前者见[日志](/docs/seams/log)，后者由插件管理自己导出

## 数据结构

全部内容就是下面这一个文件：五个接口、一个函数类型，加上页面上 `window.gwb` 的全局声明。`import` 本包（哪怕只是 `import type {}`），TypeScript 就认得 `window.gwb`。

## 提供的接口

它不是任何一条接缝的一侧，而是接缝两侧共用的类型：两侧都从这里 `import type`，形状对不上，类型检查就失败。每个名字属于哪条接缝，两边各保证什么写在接缝页：

| 名字 | 是什么 | 接缝 |
| --- | --- | --- |
| `GwbResult` | 命令的回执形状 | [命令总线](/docs/seams/command-bus) |
| `GwbKernelApi` | 内核服务 `gwbKernel` | [内核服务](/docs/seams/kernel) |
| `GwbCommandDef`、`GwbCommands` | 一条命令的说明、命令总线 | [命令总线](/docs/seams/command-bus) |
| `GwbContext` | 插件 `apply` 拿到的上下文：cordis 的 `Context` 加上面两个服务 | [内核服务](/docs/seams/kernel) |
| `GwbWindowApi`，以及 `Window.gwb` 的全局声明 | 页面上的 `window.gwb` | [IPC 通道](/docs/seams/ipc) |
| `ShellBoot` | 外壳模块默认导出的形状 | [外壳接管](/docs/seams/shell) |

**使用方**：本仓的[内核应用](/docs/desktop)、[命令插件](/docs/commands)、[插件管理](/docs/plugin-manager)经工作区链接用它；`cordis.yml` 里的插件和页面代码从团队包源装它。插件在 devDependencies 里列它，只用 `import type`。内核自己也只 import 它的类型。

### 改它的规则

- **对插件只增不减**：加一个可选字段、加一个方法、加一个类型，是补丁版本。删名字、改形状（参数、返回值、回执字段的类型或含义）、改调用方依赖的语义，是破坏，升次版本号，并照 devkit 说明书 `gwb-release` 的「发破坏版多做两步」先通知下游
- **契约之外的东西不放进来**：见上面「不知道什么」
- **改完先让内核通过类型检查**：本仓 `pnpm check` 先构建它，再对内核和两个内置插件做类型检查（见下面「怎么单独测」）

### 版本号与发版

**与内核同版本号**：`packages/gwb-plugin-api/package.json` 和 `apps/desktop/package.json` 的 `version` 一起升、写同一个号。升哪一位照 devkit 的说明书 `gwb-release`，每次升之前都读。

两者发到不同的地方：

- **词汇表包发到团队包源**，插件从那里装：

  ```
  devkit.release {"dir":"<本仓>","packages":["packages/gwb-plugin-api"]}
  ```

  别在包目录手动 `pnpm publish`：那会跳过 git 工作区干净检查与构建产物白名单检查
- **内核发 exe**，见[安装包](/docs/installer)

内核包 `apps/desktop` 把词汇表包写在 `dependencies` 里（`workspace:*`，`pnpm pack` 时换成实际版本号），打安装包时 npm 从团队包源装同一个版本的词汇表包，所以要先发词汇表包、再打安装包。

改了契约时先装新内核，再发用到新契约的插件：插件先到、内核还是旧的，插件拿到的 `gwbKernel` 就缺它要的东西。完整步骤见[开发](/docs/develop#发版)。

| 接口 | 用来做什么 | 生产实现 | 测试实现 |

| cordis 的 `Context` 类型 | `GwbContext` 在它上面加 `gwbKernel`、`gwbCommands` | 使用方自己装的 `cordis`，peer 范围 `^4.0.0-rc.9` | 本包开发依赖里固定版本的 `cordis`，`typecheck` 用它 |

## 怎么单独测

包里没有逻辑，也没有测试文件；守住它的是类型检查：

- **本包自己**：`pnpm typecheck`（在包目录）检查 `src/index.ts` 能编译
- **两侧对得上**：仓根 `pnpm check` 先构建词汇表包与两个内置插件，再对全仓做类型检查、lint 和测试。内核 `main.ts` 的 `kernel` 对象标成 `GwbKernelApi`，命令插件的 `createRegistry` 返回 `GwbCommands`，形状改坏了，它们的类型检查一定跟着失败（见[开发](/docs/develop#提交前的检查)）

仓外的插件与页面代码要等它发到团队包源、装上新版之后，才在各自仓里的类型检查中暴露不兼容，所以破坏性改动要先照 `gwb-release` 通知下游。
