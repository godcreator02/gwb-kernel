**本页回答**：内核为什么这么小、为什么是现在这个形状；往内核里加东西要满足什么；它刻意不做哪些事；内核仓里放什么，插件怎么标明自己兼容哪个内核、内核的版本号什么时候升 x。

## 内核只做第一个插件运行之前必须做的事

内核存在的理由是一条验收标准：用尽可能小的内核让插件正常运行，而且插件要真能完成实际工作。所以内核只做插件替代不了的那几件：

- 选定 home、创建 cordis 实例、加载 `cordis.yml` 里的插件，退出时卸载整棵插件树——[插件加载](/docs/seams/loading)、[内核应用](/docs/desktop/boot)
- 把页面交给外壳，没有外壳时显示只读状态页——[外壳接管](/docs/seams/shell)
- 页面上的包名解析——[页面上的包名](/docs/seams/shared)
- 页面和插件之间转交命令、推送事件——[IPC 通道](/docs/seams/ipc)
- 内核自己出错时人能看到：唯一的日志输出，启动失败时弹错误框——[日志](/docs/seams/log)

### 准入判据

往内核里加东西要同时满足两条：

1. **第一个插件运行之前必须完成。** 先问这件事能不能由某个插件提供、通过服务交给需要它的地方——能，就做成插件。插件运行在主进程里、能拿到 `electron`，开窗口、菜单、托盘、对话框、子进程都由插件来做；命令总线、插件管理也是插件
2. **此刻确实需要**：说不出此刻是谁、在做什么、因为缺了它卡在哪一步，就不加

判断不了就按「不进内核」处理：以后再加进来，永远比加进来之后再拿掉容易。不算理由的：「将来可能要」「顺手做了」「旧版工作台仓 god-workbench 里有这个」；为了方便某个插件，往内核里加只有它用的逻辑。改内核由人来决定（[这个内核的起点](/trajectory/2026-09-07-gwb-kernel)、[另起一个新仓，而不是在旧仓上删减](/trajectory/2026-09-07-fresh-line-over-subtraction)）。

**刻意不做**（要做得先推翻上面的条件）：

- 给插件提供「安装」接口——装插件只经插件管理 `@godcreator/gwb-plugin-manager` 的 `plugin-manager.*` 命令（[移除内核的安装接口](/trajectory/2026-09-08-no-install-port)）；插件之间的依赖齐不齐也不核对
- 往新 home 里装插件——由创建这个 home 的一方装，见下面「内核仓只放内核，插件自己写明测过哪个内核」
- `cordis.yml` 的模板与自动修复——文件缺了只补一个空表（[全新 home 没有 `cordis.yml` 时启动失败](/trajectory/2026-09-07-wall-fresh-home-no-yml)）
- 界面上的失败处理——除了只读状态页，不分析原因、不重试，也没有按钮（[外壳未就位时的阶段页](/trajectory/2026-09-08-stage-page)）
- 写数据——内核只提供 `dataDir`，写数据由数据插件负责（[数据写盘做成插件](/trajectory/2026-09-07-gwb-data-plugin)）
- 打包器——用 `tsc` 直接输出，主进程按正常的包解析加载模块（[打包器以后再选](/trajectory/2026-09-07-bundler-deferred)）

还没决定、在等前提条件的事在[路线](/future/roadmap)。

## 插件和内核跑在同一个进程里

所有插件都运行在 Electron 主进程的 cordis 实例里，`import('electron')` 就能直接创建窗口、菜单、托盘、对话框和子进程——这些内核一概不代劳。没有宿主子进程、没有自定义资源协议，页面直接加载 `file://` 地址（[两个进程合并为一个](/trajectory/2026-09-09-single-process)）。

代价：一个插件出错就是这个进程出错。所以内核对未捕获的异常和没人处理的 rejection 只记录、不退出——一个坏插件不该让整个工作台退出。

## 每个 home 相互独立

home 是磁盘上的一个目录，也是一个普通的 npm 项目根：内核包自己、装了哪些插件、加载哪些条目、各插件的数据、日志、本次运行的记录，全在里面。`GWB_HOME` 选定用哪个 home，不设时是 `default`。

- 不同的 home 可以同时运行，插件、端口、数据互不影响；开发和验证用单独创建的隔离 home，不碰日常用的 `default`
- 内核装在 home 里，和插件在同一个 `node_modules`：插件写 peer 的 `cordis` 与内核用的是同一份；各个 home 的内核版本可以不同，新内核先装进隔离 home 验证（[内核装进 home](/trajectory/2026-09-24-kernel-in-home)）
- 同一个 home 只能运行一个实例：第二次启动拿不到锁就退出（[同一 home 只允许一个实例](/trajectory/2026-09-12-one-home-one-instance)）
- 插件要 home 路径只从 `ctx.gwbKernel.dataDir` 取

## 包名一律按 home 解析

插件的包名 import（直接写包名、不带相对路径的 import，比如 `from 'cordis'`）一律到 home 的 `node_modules` 里找，主进程和页面用同一个解析函数：先把 `<home>/node_modules/<包名>` 解析成磁盘上的真实路径，再按包的 `exports` 找到文件。

从真实路径开始，是为了运行中换了版本能拿到新版本：pnpm 布局里真实路径带版本号，不会命中 Node 为上一版记下的解析缓存（[Node 的 CJS 解析缓存会返回旧版本](/trajectory/2026-09-09-wall-resolver-cache)）。主进程怎么用见[插件加载](/docs/seams/loading)，页面怎么用见[页面上的包名](/docs/seams/shared)。

## 页面整页交给外壳

内核在页面上只提供三样东西：一个空的 `#root`、一张 importmap、一个 `window.gwb`。页面显示什么全部由外壳决定——谁调用 `setShell`，谁就是外壳，后调用的替换先调用的。没有外壳、或外壳启动失败时，页面显示只读状态页：各条目加载到哪一步、最近的错误日志，没有按钮。见[外壳接管](/docs/seams/shell)。

## 内核不认识 cordis.yml 里任何插件、服务、命令的名字

- 加载哪些插件，由 `cordis.yml` 决定，内核用 cordis 官方的 include 去读
- 页面发来的命令，内核原样转交给命令总线 `ctx.gwbCommands`（[IPC 通道](/docs/seams/ipc)）
- 包清单里内核只读一个字段 `gwb.shared`（[页面上的包名](/docs/seams/shared)）
- 插件之间怎么交互——服务、命令、契约版本——内核不参与

内核认识的服务名只有两个：自己提供的 `gwbKernel`，和转交页面命令时要找的 `gwbCommands`。`gwbCommands` 由 `cordis.yml` 里的命令插件提供，home 里没有它时，页面发来的每条命令都回失败回执。换掉 `cordis.yml` 里的任何一个插件（包括外壳、命令插件）都不用改内核。

## 内核仓只放内核，插件自己写明测过哪个内核

内核仓只放三样：内核应用 `apps/desktop`（[内核应用](/docs/desktop)）、词汇表包 `packages/gwb-plugin-api`（[词汇表包](/docs/vocab)）、安装包——启动器 `apps/launcher` 与打包脚本 `installer/`（[安装包](/docs/installer)）。准入判据只有一句：**只有第一个插件运行之前必须完成的事才进内核。**

插件一个也不放。命令插件 `@godcreator/gwb-commands` 在基础插件仓 `gwb-base-plugins`；插件管理 `@godcreator/gwb-plugin-manager` 在 devkit 仓 `gwb-devkit`，和 devkit 一起开发。两者都是 `cordis.yml` 里的普通插件，和别的插件一样装在 home 里、经插件管理升级、可以停用和卸载。

新 home 里的内核包与插件由创建这个 home 的一方安装：日常用的 `default` 由装机的 agent 照仓根 `INSTALL.md` 用 pnpm 安装；测试用的隔离 home 由 devkit 的 `devkit.home.new` 安装。安装包只带启动器与 Electron，不带内核、插件，也不带 pnpm。

### 插件写明在哪个内核版本上测过

内核和插件各自发版，一个插件在哪个内核上测过，由插件自己写在 `package.json` 的 `gwb.testedKernel` 里：

```json
{ "gwb": { "testedKernel": "0.2.7" } }
```

插件管理的 `plugin-manager.list` 拿它和运行中内核的 `gwbKernel.version` 比：在同一条版本线上就算测过——主版本号是 0 时前两位相同（`0.2.1` 与 `0.2.7`），主版本号不是 0 时主版本号相同；不在同一条版本线上、没写、写的不是合法版本号，回执里这个包就标出来。只标出来，不拦加载：内核不读这个字段。devkit 的 `devkit.release` 发插件之前检查这个字段。

这个比较要靠得住，内核的版本号就得反映已有的插件会不会被弄坏：**改了接缝上已有的东西就升 x**（`0.x.y` 里的 x）——改名或删除、改形状或含义，以及升级 `@cordisjs/plugin-loader`、`@cordisjs/plugin-include` 的版本、改 home 布局（插件按内核的 loader 加载，插件管理按 loader 的条目树和 home 布局改条目、装包，这两样拿不准会不会弄坏，一律按会弄坏算）。只给接缝加东西（加类型、加可选字段）、只改内核内部或修 bug，升 y，测过的插件仍算测过。这和 devkit 的说明书 `gwb-release` 的规矩一致。八条接缝见[接缝图](/docs#接缝图)，发版步骤见[开发](/docs/develop#发版)。
