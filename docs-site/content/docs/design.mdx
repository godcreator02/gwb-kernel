**本页回答**：内核为什么这么小、为什么是现在这个形状；往内核里加东西要满足什么、它刻意不做哪些事；每一条设计推出了什么、代价是什么。每条只写此刻的边界，怎么走到今天的写在所链的轨迹卡里。

## 内核提供主进程启动与页面模块解析环境

内核存在的理由是一条验收标准：用尽可能小的内核让插件正常运行，而且插件要真能完成实际工作（[这个内核的起点](/trajectory/2026-09-07-gwb-kernel)）。所以内核只做插件替代不了的那几件事：

- 选定 home、创建 cordis 实例、加载 `cordis.yml` 里的插件，退出时卸载整棵插件树——[插件加载](/docs/seams/loading)、[启动与退出](/docs/desktop/boot)
- 把页面交给外壳，没有外壳时显示只读状态页——[外壳接管](/docs/seams/shell)
- 页面模块解析环境：登记模块、校验冲突、在加载前准备 importmap；React 的版本和文件由 shell 提供——[浏览器模块](/docs/seams/page-react)
- 页面和插件之间传递消息：页面发来的命令转交给命令插件，插件发出的事件推给页面——[IPC 通道](/docs/seams/ipc)、[命令转交](/docs/seams/commands)
- 内核自己出错时人能看到：唯一的日志输出，启动失败时弹错误框——[日志](/docs/seams/log)

### 准入判据

往内核里加东西要同时满足两条：

1. **主进程插件启动所需的基础能力，或页面模块加载前必须建立的解析环境。** 先问这件事能不能由某个插件提供、通过服务交给需要它的地方——能，就做成插件。插件运行在主进程里、能拿到 `electron`，开窗口、菜单、托盘、对话框、子进程都由插件来做；命令总线、插件管理也是插件
2. **此刻确实需要**：说不出此刻是谁、在做什么、因为缺了它卡在哪一步，就不加

判断不了就按「不进内核」处理：以后再加进来，永远比加进来之后再拿掉容易。不算理由的：「将来可能要」「顺手做了」「旧版工作台仓 god-workbench 里有这个」，以及为了方便某个插件往内核里加只有它用的逻辑。改内核由人来决定（[另起一个新仓，而不是在旧仓上删减](/trajectory/2026-09-07-fresh-line-over-subtraction)）。

**刻意不做**（要做得先推翻上面的判据）：

- 给插件提供「安装」接口：装插件只经插件管理的 `plugin-manager.*` 命令；插件之间的依赖齐不齐也不核对（[移除内核的安装接口](/trajectory/2026-09-08-no-install-port)）
- 往新 home 里装内核包与插件：由创建这个 home 的一方装，见下面「内核仓只放内核」
- `cordis.yml` 的模板与自动修复：`package.json` 与 `cordis.yml` 缺了也不补，启动失败并写明缺哪个，由创建 home 的一方准备（[内核删掉四处兜底](/trajectory/2026-09-25-kernel-drop-fallbacks)）
- 界面上的失败处理：除了只读状态页，不分析原因、不重试，也没有按钮（[外壳未就位时的阶段页](/trajectory/2026-09-08-stage-page)）
- 写数据：内核只提供 `dataDir`，写数据由数据插件负责（[数据写盘做成插件](/trajectory/2026-09-07-gwb-data-plugin)）
- 打包器：内核用 `tsc` 直接输出，主进程按正常的包解析加载模块；页面运行时的打包由提供方插件负责（[打包器以后再选](/trajectory/2026-09-07-bundler-deferred)）

还没发生、在等前提条件的事在[路线](/future/roadmap)。

## 插件和内核运行在同一个进程里

所有插件都运行在 Electron 主进程的 cordis 实例里，`import('electron')` 就能直接创建窗口、菜单、托盘、对话框和子进程，内核一概不代劳。没有宿主子进程、没有自定义资源协议，页面直接加载 `file://` 地址（[两个进程合并为一个](/trajectory/2026-09-09-single-process)）。

代价：一个插件出错就是这个进程出错。所以内核对未捕获的异常和没人处理的 rejection 只记录、不退出——一个坏插件不该让整个工作台退出。

## 每个 home 相互独立

home 是磁盘上的一个目录，也是一个普通的 npm 项目根：内核包、装了哪些插件、加载哪些条目、各插件的数据、日志、本次运行的记录，全在里面。`GWB_HOME` 选定用哪个 home，不设时是 `default`。

- 不同的 home 可以同时运行，插件、端口、数据互不影响；开发和验证用单独创建的隔离 home，不碰日常用的 `default`
- 各个 home 的内核版本也可以不同，见下一节
- 同一个 home 只能运行一个实例：第二次启动拿不到锁就退出（[同一 home 只允许一个实例](/trajectory/2026-09-12-one-home-one-instance)）
- 插件要 home 路径只从 `ctx.gwbKernel.dataDir` 取

## 内核和插件一样装在 home 里

内核应用是 npm 包 `@godcreator/gwb-kernel-desktop`，和 `cordis`、各插件一起装在每个 home 的 `node_modules` 里；安装包只带启动器与 Electron。启动器选定 home，读 home 里内核包清单的 `engines.electron` 与 `main`，Electron 版本在范围内才 import 内核（[启动器加载内核](/docs/seams/launcher)）。

理由：宿主和插件装在同一个 `node_modules` 里，Node 生态的标准做法就都成立。内核放在安装包里时 pnpm 看不见它：插件写的 peer `cordis` 被另装一份，内核与插件运行在两份版本不同的 cordis 上；兼容哪个内核也只能另造字段声明（[内核装进 home](/trajectory/2026-09-24-kernel-in-home)）。

推出了：

- **cordis 只有一份**：内核包把 `cordis` 写成 peer，home 根上列一份，内核、loader、include 与插件都解析到它（[home 布局与条目树](/docs/seams/home)）
- **插件用 peer 声明兼容哪个内核**，见本页最后一节
- **新内核先在隔离 home 里验证**：装进那个 home 就行，不用重打安装包，也不碰 `default`
- **升级内核是装进 home 再重启**：主进程里的内核换不掉。插件管理升级全部插件时不动内核包与 `cordis`；点名换内核包时把 `cordis` 一起对齐到新内核包 peer 里的版本，重启由人决定（命令见[开发](/docs/develop#发版)）

代价：发版物是内核包与安装包两样；启动器与内核之间多一条 Electron 版本兼容，靠 `engines.electron` 对上；home 里没装内核包就起不来，建 home 时要把内核包与 `cordis` 一起装上。

## 包名一律按 home 解析

插件的包名 import（直接写包名、不带相对路径的 import，比如 `from 'cordis'`）一律到 home 的 `node_modules` 里找：先把 `<home>/node_modules/<包名>` 解析成磁盘上的真实路径，再从那里解析出入口文件。从真实路径开始，是为了运行中换了版本能拿到新版本：pnpm 布局里真实路径带版本号，不会命中 Node 为上一版记下的解析缓存（[Node 的 CJS 解析缓存会返回旧版本](/trajectory/2026-09-09-wall-resolver-cache)）。做法见[插件加载](/docs/seams/loading)。

页面上的包名不走这套解析：插件用 registerImports 登记，页面 prepareImports 后才 import（[浏览器模块](/docs/seams/page-react)）。

## 页面整页交给外壳，内核只保证页面边界

内核在页面上只提供三样东西：一个空的 `#root`、一套 importmap 登记与准备机制、一个 `window.gwb`。页面显示什么全部由外壳决定——谁调用 `setShell` 谁就是外壳，后调用的替换先调用的；没有外壳、或外壳启动失败时，页面显示只读状态页（[外壳接管](/docs/seams/shell)）。

页面能调用整条命令总线，所以内核不给命令分权限，只保证页面边界：主框架只可能是内核包里的 `index.html`，跳到别的地址、重定向一律拒绝，只放行整页重新加载；`window.open` 从不打开新窗口，`http:`、`https:` 地址交给系统默认浏览器，别的协议拒绝；`gwb:request` 只接收顶层框架的调用。只保证这一处比给每条命令分等级便宜得多（[页面边界](/trajectory/2026-09-25-page-navigation-lock)、[网页链接交给系统浏览器](/trajectory/2026-09-25-open-external-links)，做法见 [IPC 通道](/docs/seams/ipc#页面边界)）。

## 内核不认识 cordis.yml 里的插件与命令

- 加载哪些插件由 `cordis.yml` 决定，内核用 cordis 官方的 include 去读
- 页面请求交给插件经 `handleRequest` 登记的处理器，内核不解释业务载荷（[请求通道](/docs/seams/requests)）
- 内核不看插件包清单里的任何字段
- 插件之间怎么交互——服务、命令、契约版本——内核不参与

请求通道不查找插件服务名；内核只提供自己的 `gwbKernel`。业务插件通过代码登记通道、管理载荷与结果，替换插件不要求内核认识新的服务或回执。

## 内核仓只放内核

内核仓只放两样：内核应用 `apps/desktop`，它的包根同时导出内核给插件与页面的接口类型；安装包——启动器 `apps/launcher` 与打包脚本 `installer/`。插件一个也不放：命令插件 `@godcreator/gwb-commands` 在基础插件仓 `gwb-base-plugins`；插件管理 `@godcreator/gwb-plugin-manager` 在生命周期插件仓 `gwb-lifecycle-plugins`，和 devkit 一起开发（[内核仓只放内核](/trajectory/2026-09-24-kernel-repo-only-kernel)）。两者都是 `cordis.yml` 里的普通插件，和别的插件一样装在 home 里、经插件管理升级、可以停用和卸载。

新 home 里的内核包与插件由创建这个 home 的一方安装：日常用的 `default` 由装机的 agent 照仓根 `INSTALL.md` 用 pnpm 安装；测试用的隔离 home 由 devkit 的 `devkit.home.new` 安装。安装包只带启动器与 Electron，不带内核、插件，也不带 pnpm。

## 插件在 peer 里写兼容哪个内核

内核和插件各自发版。插件兼容哪些内核，写在自己 `package.json` 的 `peerDependencies` 里，范围的下限是验证时那个内核的版本号：

```json
{ "peerDependencies": { "@godcreator/gwb-kernel-desktop": "^<验证时那个内核的版本号>" } }
```

内核装在 home 里，这就是 Node 生态里插件声明宿主版本的标准写法：pnpm 装插件时拿它和 home 里的内核包比，不满足只警告、照装。插件管理拿它和运行中内核的 `gwbKernel.version` 比，范围不包含（或没写、写的不是 `^x.y.z`）的插件在回执里标出来，只标不拦；devkit 的 `devkit.release` 发插件之前检查它。内核不读这个字段。比对规则在 `gwb-lifecycle-plugins` 仓的文档站。

这个比较要靠得住，内核的版本号就得反映已有的插件会不会被弄坏。插件按内核的 loader 加载，插件管理按 loader 的条目树和 home 布局改条目、装包，所以升级 loader、include、`cordis` 的版本或改 home 布局也算改了接缝。哪些改动升 x、哪些升 y，见[开发](/docs/develop#发版)；十条接缝见[接缝图](/docs#接缝图)。
