**本页回答**：怎么查出哪些包有新版本；`update` 和 `update-all` 差在哪；一键热升级按什么计划走、为什么升级与重新加载必须在同一条命令里、为什么插件管理自己排最后；重新加载一条条目为什么要等旧的卸载完。

## 查新版本

`outdated` 运行一次 `pnpm outdated --json`，返回「包名 → `{ current, latest }`」，空对象表示全都最新。

- 退出码 1 表示「有过期包」，是结果不是失败
- 找不到 pnpm、输出解析不了都转成 `ok: false` 的回执：界面上它只显示一句提示
- 它只读不写，也排进 pnpm 的串行队列：排队等一下没关系，省得另外处理并发

## update：只升包，不重新加载

`update` 运行 `pnpm add <包>@latest`，不建条目、不动条目——条目引用的是包名，换了版本照样有效。正在运行的插件还是旧代码，重启内核后才换成新版本；要不重启就生效，用 `update-all`。

## 一键热升级

- `outdated` 查出过期包，一次 `pnpm add` 把它们都升到精确版本；旧版本目录随即被 pnpm 删除
- 同一条命令里，升级了的每条条目停用再启用。真实路径带版本号，内核重新解析就拿到新版本；插件管理自己排最后、回执发出之后才动
- 调用命令 `shell.reload`，页面整页重新加载，窗格拿到新版本的页面代码

- **精确版本**：用 `outdated` 查到的版本号，不用 `@latest` 标签——两次查询之间又发了一版，也不会装成回执上没写的那个
- **每条条目各自重新加载**：被别的插件 inject 的插件重新加载时，cordis 会把依赖它的插件停用再启动，但那是重跑内存里的旧代码，磁盘上的新版本没有加载
- 本来就停用的条目保持停用，记为 `skipped`
- 插件管理自己那条排在它的包里最后，它的包排在所有包最后
- 给了 `only` 就只升点名的几个；点了名却不在过期清单里的，回执里列出来

### 升级与重新加载在同一条命令里

pnpm 装新版本时会删掉旧版本目录。升级之后、重新加载之前只要隔着一条命令，旧版插件去读磁盘上自己的文件就读不到。所以 `update-all` 一条命令做完：一次 `pnpm add` → 查 peer 版本 → 逐条重新加载 → 整页重新加载。`pnpm add` 失败时一条条目都不动。

### 重新加载一条条目

{/* ref file="../plugins/plugin-manager/src/remount.ts" lines="52-60" */}

- 启用时 loader 重新 import 包名，内核按真实路径解析，版本换了路径就换了，拿到的就是新版本；条目在 `cordis.yml` 里的位置与 id 都不变
- **等旧的卸载完再启用**：loader 停用条目时调 `fiber.dispose()` 但不等它结束，而服务是在卸载过程中撤销的。不等就启用，新实例启动时旧服务可能还在，cordis 报「service has been registered」
- 每一步最多等 5 秒，超时就继续，读到什么状态报什么（`ACTIVE` 才算加载成功）
- `remount` 命令用的是同一套时序，目标是命令插件（`gwb-commands`）时也在这一条命令里做完

### 插件管理自己排最后

在命令处理函数里停用插件管理自己，这条 `await` 链会跟着一起卸载，回执永远到不了调用方。所以回执先发出（`selfDeferred: true`、`reload: 'deferred'`），下一个宏任务再重新加载自己，重新加载完再调 `shell.reload`。这时插件管理原来的实例已经卸载，ctx 上什么都不能用，那段代码只持有条目树、id、命令插件的引用与 logger——这是[关键判据 K7](/docs/criteria/k7) 写明的例外。

### 整页重新加载

经命令插件调用外壳的 `shell.reload`，按命令名查找，不 import 外壳。回执的 `reload`：`done` 已经重新加载；`deferred` 等插件管理自己重新加载完再做；`unavailable` 命令表里没有它或它失败了，界面要手动刷新，原因在 `note` 里。

## 怎么单独测

- `tests/outdated.test.ts`：`pnpm outdated` 输出的解析，空输出、格式变了、单条缺字段
- `tests/update-all.test.ts`：计划——精确版本、自己最后、停用的保持停用、分组条目不算、`only` 的过滤
- `tests/remount.test.ts`：停用再启用的时序（假的条目树）；自己那条推迟到下一个宏任务
- `tests/loader.test.ts`：用真实的 loader 停用再启用一条条目，回到 `ACTIVE`
- 整条热升级只能实机验证：在隔离 home 里先装某个包的旧版本，再调 `plugin-manager.update-all`
