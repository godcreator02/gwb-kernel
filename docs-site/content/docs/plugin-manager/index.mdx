## 管什么

一个按 cordis 插件写法写的插件，源码在内核仓 `plugins/plugin-manager/`，包 `@godcreator/gwb-plugin-manager` 不单独发布，**内置在内核里**：内核把它作为 loader 根层的条目、排在承载 `cordis.yml` 的 include 条目之前加载，经 config 告诉它那条 include 条目的 id 与 pnpm 的路径；它用到条目树时，从自己条目所在的那一层取出承载 `cordis.yml` 的那棵。它不是 `cordis.yml` 里的条目、不在 home 里，所以不出现在 `list` 里，`update-all` 不升级它，也不能停用、卸载、重新加载，随内核一起升级（为什么内置见轨迹卡[核心插件内置](/trajectory/2026-09-23-core-plugins-built-in)）。

它管 home 里的两层东西：pnpm 装进来的**包**，和 `cordis.yml` 里指向包的**条目**——只装包、不加条目，插件不会运行。具体是：

- 装包并加一条条目、卸载包连同它的全部条目、给已装的包加删条目
- 启用、停用、重新加载一条条目
- 查已装的包哪些有新版本，一键热升级并逐条重新加载，不重启
- 选条目 id、改显示名、把一个 id 的数据与设置的归属转给另一个包
- 同一时刻只允许一个改动；所有 pnpm 调用排进同一个串行队列

它依赖内核没写进文档的内部结构（loader 条目树、home 的布局、包名的解析规则），见[条目树与 home 布局](/docs/seams/home)。

### 靠哪几个机制工作

| --- | --- | --- |
| home 的两层与唯一写入者 | 包与条目两层；包只经一个串行队列改，条目只经 loader 的条目树改；同一时刻只允许一个改动 | [home 的两层与唯一写入者](/docs/plugin-manager/home) |

| 安装与卸载 | 装包与加条目在一条命令里做完、不等加载；home 里只有插件；卸载先删条目后卸包 | [安装与卸载](/docs/plugin-manager/install) |
| 重新加载一条条目 | 停用 → 等旧的卸载完 → 启用，一条命令做完 | [重新加载一条条目](/docs/plugin-manager/remount) |

| 找 pnpm 与运行 pnpm | 用内核交来的那份固定版本的 pnpm；直接启动、不设超时；卸载时不结束 pnpm | [pnpm](/docs/seams/pnpm) |

## 不知道什么

- **不知道包源上有什么可装**，也不配第三方包源：那是基础插件仓的 `gwb-plugin-sources`
- **不画界面**：插件管理窗格在界面平台仓的 `gwb-baseui`，它经命令调用插件管理
- **不管插件之间的依赖齐不齐**：缺了就停在「等待缺少的服务」，`plugin-manager.list` 里看得到
- **不替插件装 peer、库、页面上的共享包名**：插件管理只装包、加条目，理由见[安装与卸载](/docs/plugin-manager/install#home-里只有插件)
- **不管条目加载成没成功**：建条目只等写入、不等加载，成没成功看 `list` 的 `active`，原因在日志里
- **不知道调用方是谁**：命令只收参数对象，页面、agent、别的插件调的是同一条命令
- **不猜 include 条目叫什么**：它的 id 由内核经 config 给出；完整 entryId 从条目对象上读，不自己拼
- **不管数据与设置的内容**：卸载、删条目都不删它们，留在磁盘上；插件管理只读、只转它们的归属记录
- **不管自己和命令插件**：两者不在 home 里，不在它安装、卸载、升级、重新加载的范围内
- **这些命令怎么调用不写在这里**：说明书 [gwb-plugin-manager](/outputs/skills/gwb-plugin-manager)，生成到包里的 `SKILL.md`，agent 经 MCP 入口读它

**12 条命令**，都登记在命令插件上，名字是 `plugin-manager.<命令>`：

| --- | --- |
| 查看 | `list` |
| 安装与卸载 | `install`、`uninstall`、`add-entry`、`remove-entry` |

## 怎么单独测

每个机制由哪几条测试守着，写在各机制页的「守住它的测试」里。这里只讲测试放在哪、怎么跑。

{/* tree dir="../plugins/plugin-manager/tests" depth="1" */}

- 在仓根运行 `pnpm check`：构建词汇表包与两个内置插件，再对全仓做类型检查、lint 和测试。插件管理的测试和内核的一起跑
- 除 `index.ts`、`vocab.ts` 外，每个源码文件都有同名的测试文件，传入构造的数据或临时目录，不需要 electron；`config.test.ts` 测 `index.ts` 里核对 config 的那一个函数
- `loader.test.ts` 用内核实际使用的 loader 与 include 版本、照内核的加载顺序搭一个 home（内置插件作为根层条目排在 include 条目之前），用到时再取条目树，内核升级这两个包时它先失败；`fiber-state.test.ts` 核对条目状态名和内核的一致
- `artifact.test.ts` 核对构建产物除 node 内置模块外没有包名 import；`self-report.test.ts` 核对 `package.json` 里的自我描述与文档一致
- 串行队列、建条目不等加载、卸载顺序、转归属、真正启动 pnpm 这些没有单元测试，只能从源码启动内核、在隔离 home 里验证（仓根 AGENTS 的「怎么跑」），再用 `devkit.cdp` 调命令
