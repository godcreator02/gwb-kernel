**本页回答**：插件管理是什么、不管什么；它靠哪几个机制工作，各在哪一页；源码怎么分块；有哪些命令；怎么测。它和内核之间交换什么、各保证什么，在接缝页[home 与插件管理](/docs/seams/home)。

## 是什么

一个按 cordis 插件写法写的插件，源码在内核仓 `plugins/plugin-manager/`，**内置在内核里**：内核在加载 `cordis.yml` 之前直接加载它，经 config 交来承载 `cordis.yml` 的条目树与 pnpm 的路径。它不是 `cordis.yml` 的条目、不在 home 里，所以不出现在 `list` 里，`update-all` 不升级它，也不能停用、卸载、重新加载，随内核一起升级（为什么内置见轨迹卡[核心插件内置](/trajectory/2026-09-23-core-plugins-built-in)）。

它管 home 里的两层东西：pnpm 装进来的**包**，和 `cordis.yml` 里指向包的**条目**——只装包、不加条目，插件不会运行。它依赖内核没写进文档的内部结构（loader 条目树、home 的布局、包名的解析规则），见[home 与插件管理](/docs/seams/home)。

## 靠哪几个机制工作

每页讲一个机制：它是什么、为什么这么做、怎么做的，需要时配图。

| 机制 | 一句话 | 页 |
| --- | --- | --- |
| home 的两层与唯一写入者 | 包与条目两层；包只经一个串行队列改，条目只经 loader 的条目树改；同一时刻只允许一个改动 | [home 的两层与唯一写入者](/docs/plugin-manager/home) |
| 对外只有命令 | 12 条命令是唯一的调用方式；服务只表示「装了」；回执类型由插件管理导出 | [对外只有命令](/docs/plugin-manager/commands) |
| 安装与卸载 | 装包与加条目在一条命令里做完、不等加载；home 里只有插件；卸载先删条目后卸包 | [安装与卸载](/docs/plugin-manager/install) |
| 重新加载一条条目 | 停用 → 等旧的卸载完 → 启用，一条命令做完 | [重新加载一条条目](/docs/plugin-manager/remount) |
| 热升级 | 升级与重新加载在同一条命令里；精确版本、每条条目各自重新加载 | [热升级](/docs/plugin-manager/upgrade) |
| id 与归属 | id 是身份不能改；选 id 时看磁盘上的归属记录，不读到别的包的数据 | [id 与归属](/docs/plugin-manager/ids) |
| 找 pnpm 与运行 pnpm | 用内核交来的那份固定版本的 pnpm；直接启动、不设超时；卸载时不结束 pnpm | [找 pnpm 与运行 pnpm](/docs/plugin-manager/pnpm) |

## 不管什么

- 查包源上有什么可装、配第三方包源：基础插件仓的 `gwb-plugin-sources`
- 插件管理窗格的界面：界面平台仓的 `gwb-baseui`
- 插件之间的依赖齐不齐：缺了就停在「等待缺少的服务」，`plugin-manager.list` 里看得到
- 插件的 peer、库、页面上的共享包名：插件管理只装包、加条目，理由见[安装与卸载](/docs/plugin-manager/install#home-里只有插件)
- 这些命令怎么调用：说明书 [gwb-plugin-manager](/outputs/skills/gwb-plugin-manager)，生成到包里的 `SKILL.md`，agent 经 MCP 入口读它

## 源码分块

十三个文件。读磁盘与启动进程只在 `home.ts` 与 `pnpm.ts`，其余的纯逻辑文件不 import `node:fs`，单元测试传入构造的数据就能跑；`index.ts` 把它们组装起来，依赖其余所有文件。

<Diagram name="pm-modules" title="源码分三层：组装、纯逻辑、读磁盘与启动进程">
- 顶层 `index.ts`：12 条命令与只表示「装了」的服务，按顺序调用下面各块，依赖其余所有文件
- 中间十个纯逻辑文件，不读磁盘、不启动进程
- 底层两个：`home.ts` 读 home 的 `package.json`，`pnpm.ts` 找 pnpm、启动进程
- 插件管理外面：home 目录、内核经 config 交来的条目树、内核内置的命令插件、三个可选插件（data、settings、skills）
</Diagram>

## 命令一览

| 分组 | 命令 |
| --- | --- |
| 查看 | `list` |
| 安装与卸载 | `install`、`uninstall`、`add-entry`、`remove-entry` |

## 怎么测

每个机制由哪几条测试守着，写在各机制页的「守住它的测试」里。这里只讲测试放在哪、怎么跑。

{/* tree dir="../plugins/plugin-manager/tests" depth="1" */}

- 在仓根运行 `pnpm check`：构建词汇表包，再对全仓做类型检查、lint 和测试。插件管理的测试和内核的一起跑
- 除 `index.ts`、`vocab.ts` 外，每个源码文件都有同名的测试文件，传入构造的数据或临时目录，不需要 electron
- `loader.test.ts` 用内核实际使用的 loader 与 include 版本、照内核的加载顺序搭一个 home，取条目树交给直接加载的插件，内核升级这两个包时它先失败；`fiber-state.test.ts` 核对条目状态名和内核的一致
- 串行队列、建条目不等加载、卸载顺序、转归属、真正启动 pnpm 这些没有单元测试，只能实机验证：从源码启动内核、用隔离 home（仓根 AGENTS 的「怎么跑」），再用 `devkit.cdp` 调命令
