**本页回答**：插件管理是什么、不管什么；它靠哪几个机制工作，各在哪一页；源码怎么分块；有哪些命令；怎么测。它和内核之间交换什么、各保证什么，在接缝页[home 与插件管理](/docs/seams/home)。

## 是什么

一个插件，源码在内核仓 `plugins/plugin-manager/`，由 `cordis.yml` 的条目加载、版本号独立于内核。它管 home 里的两层东西：pnpm 装进来的**包**，和 `cordis.yml` 里指向包的**条目**——只装包、不加条目，插件不会运行。放在内核仓，是因为它依赖内核没写进文档的内部结构（loader 条目树、home 的布局、包名的解析规则），理由见[home 与插件管理](/docs/seams/home)。

## 靠哪几个机制工作

每页讲一个机制：它是什么、为什么这么做、怎么做的，需要时配图。

| 机制 | 一句话 | 页 |
| --- | --- | --- |
| home 的两层与唯一写入者 | 包与条目两层；包只经一个串行队列改，条目只经 loader 的条目树改；同一时刻只允许一个改动 | [home 的两层与唯一写入者](/docs/plugin-manager/home) |
| 对外只有命令 | 12 条命令是唯一的调用方式；服务只表示「装了」；回执类型由插件管理导出 | [对外只有命令](/docs/plugin-manager/commands) |
| 安装与卸载 | 装包与加条目在一条命令里做完、不等加载；home 里只有插件；卸载先删条目后卸包 | [安装与卸载](/docs/plugin-manager/install) |
| 重新加载一条条目 | 停用 → 等旧的卸载完 → 启用；插件管理自己排到回执之后 | [重新加载一条条目](/docs/plugin-manager/remount) |
| 热升级 | 升级与重新加载在同一条命令里；精确版本、每条条目各自重新加载、自己最后 | [热升级](/docs/plugin-manager/upgrade) |
| id 与归属 | id 是身份不能改；选 id 时看磁盘上的归属记录，不读到别的包的数据 | [id 与归属](/docs/plugin-manager/ids) |
| 找 pnpm 与运行 pnpm | 只用原生可执行文件、设置项优先；直接启动、不设超时；卸载时不结束 pnpm | [找 pnpm 与运行 pnpm](/docs/plugin-manager/pnpm) |

## 不管什么

- 查包源上有什么可装、配第三方包源：基础插件仓的 `gwb-plugin-sources`
- 插件管理窗格的界面：界面平台仓的 `gwb-baseui`
- 插件之间的依赖齐不齐：缺了就停在「等待缺少的服务」，`plugin-manager.list` 里看得到
- 插件的 peer、库、页面上的共享包名：插件管理只装包、加条目，理由见[安装与卸载](/docs/plugin-manager/install#home-里只有插件)
- 这些命令怎么调用：说明书 [gwb-plugin-manager](/outputs/skills/gwb-plugin-manager)，生成到包里的 `SKILL.md`，agent 经 MCP 入口读它

## 源码分块

十三个文件。读磁盘与启动进程只在 `home.ts` 与 `pnpm.ts`，其余的纯逻辑文件不 import `node:fs`，单元测试传入构造的数据就能跑；`index.ts` 把它们组装起来，依赖其余所有文件。

<Diagram name="pm-modules" title="源码分三层：组装、纯逻辑、读磁盘与启动进程">
- 顶层 `index.ts`：12 条命令与只表示「装了」的服务，按顺序调用下面各块，依赖其余所有文件
- 中间十个纯逻辑文件，不读磁盘、不启动进程
- 底层两个：`home.ts` 读 home 的 `package.json`，`pnpm.ts` 找 pnpm、启动进程
- 插件管理外面：home 目录、loader 提供的条目树、四个可选插件（commands、data、settings、skills）
</Diagram>

| 文件 | 管什么 | 在哪一页讲 |
| --- | --- | --- |
| `index.ts` | 12 条命令与服务，按顺序调用下面各块 | [对外只有命令](/docs/plugin-manager/commands) |
| `tree.ts` | 从插件自己的条目上取条目树与自己的 entryId | [home 的两层](/docs/plugin-manager/home) |
| `inventory.ts` | 条目树与 home 清单对照成 `list` 的结果 | [home 的两层](/docs/plugin-manager/home) |
| `home.ts` | 读 home 的 `package.json`（读磁盘） | [home 的两层](/docs/plugin-manager/home) |
| `busy.ts` | 同一时刻只允许一个改动，重入返回 BUSY | [home 的两层](/docs/plugin-manager/home) |
| `uninstall.ts` | 卸载要删哪些条目 | [安装与卸载](/docs/plugin-manager/install) |
| `remount.ts` | 停用再启用的时序；自己那条推迟到回执之后 | [重新加载](/docs/plugin-manager/remount) |
| `outdated.ts` | 解析 `pnpm outdated` 的输出 | [热升级](/docs/plugin-manager/upgrade) |
| `update-all.ts` | 一键热升级的计划；条目状态名 | [热升级](/docs/plugin-manager/upgrade) |
| `ids.ts` | id 规则、默认 id、选 id；包名与版本范围的校验 | [id 与归属](/docs/plugin-manager/ids) |
| `pnpm-path.ts` | 找 pnpm（磁盘信息由调用方传入） | [pnpm](/docs/plugin-manager/pnpm) |
| `pnpm.ts` | 查磁盘、启动 pnpm、收集输出（启动进程） | [pnpm](/docs/plugin-manager/pnpm) |
| `vocab.ts` | 取内核服务、判断是不是对象 | — |

## 命令一览

| 分组 | 命令 |
| --- | --- |
| 查看 | `list` |
| 安装与卸载 | `install`、`uninstall`、`add-entry`、`remove-entry` |
| 启用与重新加载 | `enable`、`disable`、`remount` |
| 升级 | `outdated`、`update-all` |
| id 与显示名 | `transfer-owner`、`set-label` |

参数与回执见[对外只有命令](/docs/plugin-manager/commands)。

## 怎么测

- 单元测试：除 `index.ts`、`vocab.ts` 外，每个文件都有同名的 `tests/<文件名>.test.ts`，传入构造的数据或临时目录
- `tests/loader.test.ts`：用内核实际使用的 loader 与 include 版本搭一个 home，跑取条目树、`create` / `update` / `remove` 写回 `cordis.yml`、停用再启用后 `ACTIVE`；另断言这几个版本和 `apps/desktop` 一致
- `tests/fiber-state.test.ts`：条目状态名和内核只读状态页用的那份一致
- `tests/self-report.test.ts`、`tests/artifact.test.ts`：清单自述与构建产物的检查
- 安装、热升级的整条路径只能实机验证：`devkit.dev` 把开发版装进隔离 home，再调命令
