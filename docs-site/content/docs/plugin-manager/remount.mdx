**本页回答**：重新加载一条条目按什么顺序做、为什么要等旧的卸载完；目标是插件管理自己时为什么要推迟到回执之后；为什么要用 `remount` 一条命令，而不是 `disable` 加 `enable`。热升级重新加载每条条目用的也是这一套。

## 停用 → 等旧的卸载完 → 启用

**是什么**：重新加载一条条目 = 停用 → 等旧实例卸载完 → 启用 → 等新实例加载完，返回新实例的状态。启用时 loader 重新 import 包名，内核按真实路径解析——包换了版本，路径就换了，拿到的就是新版本；条目在 `cordis.yml` 里的位置与 id 都不变。原本停用的条目，重新加载后是启用的。

**为什么要等**：loader 停用条目时调 `fiber.dispose()` 但不等它结束，而插件提供的服务是在卸载过程中才撤销的。停用后马上启用，新实例启动时旧实例的服务可能还在，cordis 报「service has been registered」：

<Diagram name="pm-remount" title="停用后马上启用会撞上还没撤销的旧服务；等旧的卸载完再启用就正常">
- 上：停用后马上启用。旧实例还在卸载、服务还没撤销，新实例启动时提供同名服务，cordis 报 service has been registered
- 下：等旧实例卸载完再启用。新实例启动时同名服务已经撤销，正常加载到 `ACTIVE`
</Diagram>

**怎么做**：每一步用 cordis 的 `fiber.await()` 等它把手头的事做完，最多等 5 秒，超时就继续，读到什么状态报什么（`ACTIVE` 才算加载成功）。修改条目树时抛错，回执的 `action` 是 `failed`，`state` 里是那句错误。

## 目标是插件管理自己：回执之后再动

**是什么**：`remount` 的目标是插件管理自己时，先返回回执（`action: 'deferred'`，`state` 是动手前的状态），下一个宏任务才重新加载；热升级里升到了插件管理自己，也是这样排在最后。

**为什么**：在命令处理函数里停用插件管理自己，这条 `await` 链会跟着一起卸载，回执永远到不了调用方。

**怎么做**：把重新加载排到下一个宏任务，那时命令的应答早已发出。这段代码运行时插件管理原来的实例已经卸载，ctx 上什么都不能用（取服务会报 inactive context），所以它只持有事先拿到的条目树、id 与 logger；热升级那次另外持有命令插件的引用，重新加载完调用 `shell.reload`。之后用 `plugin-manager.list` 核对 `active`，不会有第二份回执。

{/* ref file="../plugins/plugin-manager/src/remount.ts" lines="74-96" */}

**例外**：插件卸载时要清理掉自己启动的一切，内核退出时等的就是这些清理。这段在插件自己卸载之后才运行的代码是允许的例外，条件就是上面这条：只持有条目树与 logger，不碰 ctx。

## 用 remount 一条命令，不拼 disable 加 enable

**是什么**：要让一条条目重新 import（比如装了新版本之后），调 `remount`。目标是别的条目（包括命令插件）时，在这一条命令里做完；是插件管理自己时，按上一节推迟。

**为什么**：停用和启用之间不能隔着第二条命令。目标是命令插件时，`disable` 一返回，命令表就没了，`enable` 调不进去；目标是插件管理自己时，`disable` 之后就没有谁来处理 `enable` 了。重新加载由不会被这次重新加载卸掉的代码一次做完：别的条目在调用方的 `await` 链里做完，这条链只持有条目树与 logger，不经过命令插件，命令插件被卸载也不影响它继续执行。

<Callout type="warn" title="别用 disable 加 enable 两条命令拼出重新加载">
目标是命令插件或插件管理自己时，条目会停在停用状态，没有命令能把它启用回来，只能手工改 `cordis.yml` 再重启。
</Callout>
