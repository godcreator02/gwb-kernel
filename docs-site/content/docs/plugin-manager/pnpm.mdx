**本页回答**：插件管理用的是哪个 pnpm、怎么找到它；怎么启动它、输出怎么收；卸载时正在运行的 pnpm 为什么不结束。pnpm 什么时候运行、为什么排队，见[唯一写入者](/docs/plugin-manager/home#包只经-applytohome排进一个串行队列)。

## 只用自己依赖里的那份 pnpm

**是什么**：插件管理的 `dependencies` 写固定版本的 `@pnpm/exe.win32-x64`，随插件管理一起装进 home。运行时从插件管理自己的位置解析这个包，启动里面的 `pnpm.exe`。不读设置、不找 PATH，机器上装没装 pnpm、装的哪个版本，都和插件管理无关。

**为什么**：
- 各人机器上装的 pnpm 版本不同，出过兼容问题。固定一份，所有 home 改动时用的都是同一个版本
- 依赖的是可执行文件包，不是 `pnpm` 包：`pnpm` 包带安装脚本，pnpm 默认不运行依赖的安装脚本，每次改 home 都会以 `ERR_PNPM_IGNORED_BUILDS` 退出码 1 结束；`@pnpm/exe.win32-x64` 的包里只有一个 `pnpm.exe`（实验见[pnpm.exe 装新 home](/trajectory/2026-09-23-pnpm-exe-home-install-probe)）
- 原生可执行文件可以直接启动，不用开 shell，也就没有参数引号转义的问题

**怎么做**：

<Diagram name="pm-pnpm-lookup" title="插件管理从自己的依赖里找到 pnpm">
- home 按 pnpm 的布局存放：插件管理和它依赖的 `@pnpm/exe.win32-x64` 在 `node_modules/.pnpm/` 下同一个目录里
- 插件管理从自己的位置按 node 的规则解析 `@pnpm/exe.win32-x64/package.json`，旁边的 `pnpm.exe` 就是要启动的文件，工作目录是 home
- 包或文件找不到：报错，让人重装插件管理
- 插件管理升级时 pnpm 版本可能跟着变。pnpm 只把链接换到新版本目录，旧目录和正在运行的那个文件留在原处，不会因为文件被占用而失败

## 直接启动、不设超时

**是什么**：直接启动找到的那个文件，环境变量原样传下去，不设超时。

**为什么**：
- 环境原样传下去，用户的 `~/.npmrc`、pnpm 配置（`@godcreator` 的包源、包龄豁免）照常读到；只去掉 `ELECTRON_RUN_AS_NODE`——它只对 electron 有意义，留着会传给 pnpm 启动的依赖构建脚本
- 装一个大包本来就可能要几分钟，定一个时限只会在慢网络上误杀正常的安装；网络层的超时 pnpm 自己有。真卡住了，由人去结束进程

**怎么做**：改 home 的那几次（`add` / `remove`）成功时不保留输出（几十行进度没人看），失败时回执带 stdout 与 stderr 合起来的最后 12 行——pnpm 把原因写在最后。`outdated` 要读 stdout 上的 JSON，用另一个函数完整保留 stdout；两边对输出的取舍相反，所以不合成一个。

**守住它的测试**：启动参数与环境、输出只留最后几行有单元测试；真正启动进程、收集输出只能实机验证（`devkit.dev` 装进隔离 home 后调 `plugin-manager.install` / `outdated`）。

## 卸载时不结束 pnpm

**是什么**：插件管理卸载时（包括内核退出），正在运行的 pnpm 不结束，让它跑完。

**为什么**：pnpm 正在改 home 的 `package.json` 与 `node_modules`，中途结束会留下装了一半的 home，比让它跑完更难收拾；它跑完之后回执没人接，改动照样生效。

**例外**：插件启动的子进程，卸载时本该杀掉整棵进程树、等它真正退出。这是允许的例外，理由写在 `runPnpm` 的注释里——例外都要在代码里写明。
