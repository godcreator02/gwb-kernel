# 安家：home 两件套

读完这页你能回答：home 在哪、里面有什么；为什么每次启动都要铺一遍；那份**每次开机整份重写**的
运行时身份为什么跟别的反着来；同一 home 为什么开不出第二份；装机去哪了。

## home 在哪

{/* ref file="../apps/desktop/src/main.ts" lines="30-44" */}

不设 `GWB_HOME` 落 `%APPDATA%\gwb-kernel\homes\default`。`GWB_HOME` 给**纯名字**落
`homes\<名>`；给**含 `\` 或 `/` 的路径**就把那个目录本身当 home——验收要干净场子时指一个
scratchpad 下的目录就行，名字与路径两种写法没有第三种语义。

选出来的路径先 `realpath` 归一（大小写、junction、斜杠写法都钉到磁盘真实路径）：同一 home
的两种给法必须归成同一个串，下面的单开锁才认得出「同一个 home」。

**Chromium 的 userData 拆成每 home 一份**（`<home>/electron`）：一是多个 home 并跑不再共享
同一份 Local Storage 互相串味（隔离 home 的页面看不见 default 的 UI 状态）；二是单开锁的
钥匙就是 userData，拆了它锁才按 home 生效。homes 的根从 `appData` 推、不从 userData
推——userData 已经按 home 拆了，再从它推就成了递归。

## 同一 home 只许一个实例

{/* ref file="../apps/desktop/src/main.ts" lines="65-76" */}

Electron 的平台锁，钥匙是上面拆出来的那份 userData：同一 home 的第二份拿不到锁，stderr
报一句、退出码 1、`runtime.json` 不动（在跑那份的身份不被盖掉）；第一个实例把已在跑的窗
抬到前面。不同 home 钥匙不同，随便并跑。不手搓锁文件——那得判 pid 活没活，平台锁在进程
死时由操作系统放掉，没有陈锁这回事。判据与否掉的候选见
[单开锁](/docs/trajectory/2026-09-12-one-home-one-instance)。

## 每次启动铺两件套

{/* ref file="../apps/desktop/src/main.ts" lines="45-53" */}

这段每次启动都跑，幂等，差什么补什么、**在的一律不覆盖**：

| 文件 | 是什么 |
| --- | --- |
| `package.json` | `{"name":"gwb-home","private":true}`——件的 dependencies 住这儿；内核扫它收集 `gwb.shared` 拼 importmap（见[取址](/docs/kernel/loading#浏览器半的取址-importmap-是内核拼的)） |
| `cordis.yml` | 空表 `[]`。那是「一个件都没装」的正当表达，也是 home 起得来的最小形态——读不到它整趟起不来（见[那面墙](/docs/trajectory/2026-09-07-wall-fresh-home-no-yml)） |

旧线还有第三件：铺一份 README 进 home 写装件流程。**随两进程线退役了**——home 归用户，
说明文档归文档站（[跑起来](/docs/getting-started/first-run)），不往用户的盘上复制一份会
过期的。

**为什么不是只在首启**：有人手工删掉 `cordis.yml` 之后，只在首启补的话就再也起不来了，而
那个失败同样是整趟退出。

`dataDir` 是单源：`ctx.baseUrl`、`gwb.log` 的路径都从它推出来。件要路径走
`gwbKernel.dataDir` 拿（见[服务与命令](/docs/plugins/services)），**别自己拼**——home 的
选法哪天变了，自己拼的不报错，只会静默写错地方。

铺家是安家，不是装机——它只保证 home **起得来**，不保证里面有什么。

## 还有一份运行时身份

{/* ref file="../apps/desktop/src/main.ts" lines="78-109" */}

`runtime.json` 不属于上面那两件套，**规矩正好相反：每次开机整份重写**。两件套是 home 的家当，
谁也不该替用户覆盖；这一份是**此刻这个进程**的身份，上一轮留下的每一格都该被盖掉。

里面是 pid、起的时刻、版本、应用目录，外加 Chromium 调试口。版本是 `app.getVersion()`——
从内核包自己的清单读，装在仓里还是安装位都报得出自己是哪一版；mcp 件绑上口之后补它的
`mcp` 格，读改写、保留不认得的字段，这一格活得下来。调试口是这份记录存在的理由：它是命令行
上的开关，**只有起进程的这只手知道**——内核不认识它、页面也读不到，而外面的工具（比如要换一版
件再看一眼的那条链）得先够得着这个 home 才谈得上别的。没开这道口就**没有那一格**，不写 0 也不
写 null：写了的话读的人还得再判一次「这个数算不算数」。

两条给读的人的规矩：

**进程退出不删。** 崩溃与被 kill 是常态，而「退出时删」那条路在这两种情况下本来就不会跑；留着
的记录是「上一次它在哪儿」的唯一线索。

**所以读的人负责验活**：pid 还活着，而且那个 pid **真的持着记录里那个端口**。pid 会被复用、端口
会被下一个进程占走，只认文件就会静默连到别人身上。内核这边不做对账、不扫别的 home、不清理——
那不是内核的活。

写不动只报一句 warn 就往下走：这一格是给工具用的方便，不是启动的前置。

## 装机去哪了

曾经有第四件事叫装机：`kernel.install` 命令转发 pnpm、首启装一份推荐列表。2026-09-08
**整口拿掉**，词汇表包里的 `install()` 一并删了。**内核不碰 pnpm。**

判据收在[装机口移除](/docs/trajectory/2026-09-08-no-install-port)那张卡里，一句话版：
「用户可以装件」不再要求内核是那台机器——home 是个**普通的 npm 项目根**，装包就是进
home、`pnpm add`、`cordis.yml` 写条目的手工活（全流程见[跑起来](/docs/getting-started/first-run)）；
图形界面的装件面归件——件仓的 `gwb-plugins` 件，`plugins.install` 命令干这个。

内核为「装」保持的就一样：**home 的形状 pnpm 认得**。这就够了。
