# importmap

**本页回答**：插件在页面里运行的代码写 `import 'react'` 时，页面凭什么能解析到文件；这张表由谁拼、从哪里读、什么时候计算、名字冲突时怎么办。

## 管什么

把「哪个包给页面提供哪几个包名 import（bare specifier，直接写包名、不带相对路径的 import，比如 `from 'cordis'`）」的声明收集齐，解析成 `包名 → file:// 地址` 的 importmap（每个包名对应一个文件地址），随外壳地址一起推送给页面（推送以及页面怎么注入这张表见[页面与 IPC](/docs/kernel/bridge)）。理由见[importmap 归内核](/trajectory/2026-09-09-importmap-in-kernel)：它是页面级的运行时服务，没有外壳时其他插件在页面里运行的代码也得能解析；声明由提供包的一方来写。

## 不知道什么

不认识 react 或任何包名，只转交提供方的声明。不查版本、不比较两个提供方谁更新。不扫描传递依赖——只看 home 清单里的直接依赖。不知道页面有没有真的 import 某个名字。

## 数据结构

- **声明**：包清单里的 `gwb.shared`，`包名 → exports 子路径`，即每个包名对应包里的一个导出子路径。这是内核读包清单时唯一认识的 `gwb` 字段
- **表**：`Record<包名, file:// 地址>`，键是包名、值是文件地址，每次调用都重新计算，不缓存

## 提供的接口

`collectImports({ dataDir, warn })`：读取 `<home>/package.json` 的 dependencies，逐个读取每个包自己的清单，把 `gwb.shared` 里的每一条经 [`resolveFromHome`](/docs/kernel/loading)（与主进程一侧用的是同一个解析函数）解析成真实文件的 `file://` 地址。

两条规则都在这段代码里：**名字冲突时全部拒绝**——同一个包名有两个提供方，这个名字就不进表，后出现的每个提供方各报一句 warn，页面 import 它时直接报解析错误；**解析不到只报 warn**——一个提供方出了问题，只损失它自己提供的那几个名字。形状不对的声明（不是对象、名字为空、子路径不是非空字符串）直接忽略，不报错。

因为从真实路径开始解析、每次都重新计算，共享包升级版本之后**整页重新加载**就能拿到新版本（[importmap 也会遇到 Node 解析缓存](/trajectory/2026-09-17-wall-importmap-resolver-cache)）；不重新加载页面就看不到——页面上的 importmap 只注入一次。

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `resolveFromHome` | 把子路径解析成真实文件 | `bare-import.ts` | 同一个函数，传入手工构造的临时 home |
| `warn` | 名字冲突与解析失败时报一句 | `ctx.logger('kernel').warn` | 收集进数组后断言 |
| 磁盘 | 读取 home 清单与各包清单 | 文件系统 | 临时目录 |

## 怎么单独测

`imports.ts` 不依赖 electron 与 cordis，warn 由调用方传入：传入手工构造的临时 home，证明没有清单或没有依赖时得到空表、正常的声明解析到真实文件、子路径写法等价、名字冲突时全部拒绝且后出现的提供方各报 warn、解析不到只报 warn、junction 改指向后重新计算能拿到新版本、形状不对的声明被忽略（`tests/imports.test.ts`）。
