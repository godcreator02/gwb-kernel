# 内核接口

**本页回答**：内核给插件、给页面分别提供哪些接口；这些接口的类型定义在哪里；内核唯一会校验的形状是什么。

## 管什么

`@godcreator/gwb-plugin-api` 这个包：给内核与插件之间的契约（对外承诺的接口）起名字，只定义名字、不含任何逻辑，没有运行时导出。它与内核在同一个仓里（`packages/gwb-plugin-api`），版本号与内核保持一致、一起发布。内核自己也是它的第一个使用方（`main.ts` 从它取 `GwbKernelApi` 的类型）。理由见[词汇表是独立包、与内核同仓](/trajectory/2026-09-07-vocab-package-standalone)。

## 不知道什么

不知道任何插件的服务、命令、窗格——那些类型定义在提供它们的插件里。没有运行时代码：`requireKernel`、`isRecord` 这类很小的辅助函数由各插件自己带。不约束插件在主进程运行的部分和在页面运行的部分怎么组织，`ShellBoot` 是内核唯一会校验的形状。

## 数据结构

{/* ref file="../packages/gwb-plugin-api/src/index.ts" */}

整个文件就是契约：
- **`GwbKernelApi`**（主进程一侧，`ctx.gwbKernel`）：`dataDir`、`version`、`emit(payload)`、`setShell(url) → 撤销函数`。在根上下文 provide、永不撤销，插件直接取用，不需要写进 `inject`
- **`GwbContext`**：cordis 的 `Context` 加上 `gwbKernel`
- **`GwbWindowApi`**（页面一侧，`window.gwb`，通过全局类型声明加到 `window` 上）：`command`、`on`、`onShell`
- **`ShellBoot`**：外壳模块的默认导出，`(root) => { dispose? } | void`
- **`GwbResult`**：命令回执 `{ ok, data?, error? }`

## 提供的接口

**给插件**：`dataDir` 是 home 的绝对路径（见[home](/docs/kernel/home)）；`version` 是内核自己的版本号，读取内核的包清单，与 `runtime.json` 里的 `version` 是同一个值（[内核报告自己的版本](/trajectory/2026-09-18-kernel-reports-version)）；`emit` 与 `setShell` 的行为见[页面与 IPC](/docs/kernel/bridge)。

{/* ref file="../apps/desktop/src/main.ts" lines="223-237" */}

**给页面**：`window.gwb` 的三个函数，在这个页面上运行的任何代码都能直接调用，没有第二个入口（见[页面与 IPC](/docs/kernel/bridge)）。

**校验**：页面入口（`index.html`）只校验一件事——外壳模块的默认导出是函数，否则显示只读状态页并写明原因。

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| cordis 的 `Context` 类型 | `GwbContext` 在它上面扩展 | `cordis`（出现在导出的类型声明里，所以是 peer） | — |
| DOM 的 `HTMLElement` 类型 | `ShellBoot` 的参数 | 使用方的 lib 配置 | — |

## 怎么单独测

没有运行时代码可测。它的正确性靠仓根的 `pnpm check`：先构建它，再对全仓做 typecheck——内核从它取类型，契约写坏了，内核的 typecheck 一定跟着失败。
