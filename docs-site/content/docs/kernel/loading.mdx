# 挂载

**本页回答**：cordis 怎么在主进程里起来、件怎么从 home 被找到并挂上、启动与退出各自为什么是这个形状。

## 管什么

主进程里一个 cordis `Context`，件全挂在它身上。内核只挂两样官方件——`@cordisjs/plugin-loader`（条目树与模块加载）和一条 `cordis:include` 条目（读 `<home>/cordis.yml`），再替 loader 补上 node 半的裸名解析；其余的挂载、热挂卸、条目写回全归这两个官方件。退出时由内核把整棵件树拆完。

## 不知道什么

不认识 `cordis.yml` 的格式（归 include），不认识任何件的包名、服务名、命令名。不监听文件——改 yml 不热生效，热挂卸走 loader 的条目树 API（`create` / `update` / `remove`，归 plugin-manager 这类件去调）。不判断件「挂没挂上」，那是 fiber 的状态（`ACTIVE` 才算，[那面墙](/trajectory/2026-09-07-wall-fiber-not-active)）。

## 数据结构

- **条目树**：根下一条 id 固定为 `home` 的 include 条目，`cordis.yml` 里的每一条是它的子条目，完整 id 是 `home:<id>`。`home` 这个 id 一变，所有件的 id 跟着变（[那面墙](/trajectory/2026-09-07-wall-home-entry-id-fixed)）
- **`loaderFiber`**：挂上的 loader 的 fiber，退出时拆它；`main()` 走到挂载之前是 `undefined`

## 提供的接口

**根上下文与 baseUrl**：`ctx.baseUrl` 是 home 的 file URL，设在**根**上下文——include 挂在根、拿根的 `baseUrl` 解析 `cordis.yml`（[那面墙](/trajectory/2026-09-07-wall-baseurl-on-root-ctx)）。

**引导链**：顺序本身就是判据——`gwbKernel` 在模块顶层就已 provide（先于一切挂载，[那面墙](/trajectory/2026-09-07-wall-gwbkernel-provide-early)）；`await ctx.plugin(Loader)` 必须 await（[那面墙](/trajectory/2026-09-07-wall-ctx-plugin-thenable)）；给 `loader.internal` 塞裸名解析（主进程没有 `--expose-internals`，不塞的话件**静默**挂不上）；include 从 loader 的 builtins 取（它住应用依赖树，按 home 解析找不到，[那面墙](/trajectory/2026-09-07-wall-include-via-builtins)）；最后 `loader.await()` 等整棵树收敛。

{/* ref file="../apps/desktop/src/main.ts" lines="275-284" */}

**node 半的裸名解析**：两步——先 `realpathSync.native` 把 `<home>/node_modules/<包名>` 解成真实目录（pnpm 布局里带版本号的那一处），再从那儿起 `createRequire` 按 `exports` 解析到入口文件、按 ESM import 进来。第一步是热重挂的要害：Node 的 CJS 解析缓存按「请求名 + 起点」记，包换了版本、逻辑路径没变时会回旧版本，真实路径天然不跟上一版撞（[那面墙](/trajectory/2026-09-09-wall-resolver-cache)）。浏览器半拼 importmap 用的也是这同一条 `resolveFromHome`。

{/* ref file="../apps/desktop/src/bare-import.ts" lines="17-29" */}

**启动的形状**：入口模块里不能顶层 `await app.whenReady()`——`ready` 要等入口模块求值完才发，互相等死、静默挂住（[那面墙](/trajectory/2026-09-09-wall-esm-await-whenready)）。启动体挂在 `.then(main)` 上；`main()` 里抛出的一切走 `.catch`：写日志、弹错误框、`app.exit(1)`。所有窗关掉即退出。

{/* ref file="../apps/desktop/src/main.ts" lines="287-297" */}

**退出的形状**：`will-quit` 里拦下这一趟，`dispose()` loader 的 fiber 再 `await()` 等整棵树拆完，然后再 `app.quit()`。件起的长命子进程靠这条路被带走。两半缺一不可：`dispose()` 只**启动**拆卸，要补 `await()` 才等得到嵌套的异步收尾；件那半得把真收尾**返回**成 promise，不然等到的是空盒（[退出收尾两半](/trajectory/2026-09-12-quit-dispose-two-halves)）。某个件的收尾挂死时 5 秒超时硬退；收尾出错只记不拦。

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| cordis `Context` | 件的运行时 | `cordis`（应用依赖树） | — |
| `@cordisjs/plugin-loader` | 条目树、模块加载、热挂卸 | 应用依赖树 | — |
| `@cordisjs/plugin-include` | 读写 `cordis.yml` | 应用依赖树，经 builtins 取 | — |
| 磁盘上的 pnpm 布局 | 裸名解析 | `<home>/node_modules` | 测试里手造的临时 home（含 junction） |

## 怎么单独测

`bare-import.ts` 不碰 electron 与 cordis，副作用只有磁盘读：喂一个手造的临时 home，证明主入口与 scoped 包解析得到、子路径写法等价、junction 换指向后拿到新版本、包不在时 ENOENT 带完整路径（`tests/bare-import.test.ts`）。引导链、热挂卸与退出收尾只在隔离 home 里实机验。
