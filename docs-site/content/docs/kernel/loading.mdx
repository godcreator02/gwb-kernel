# 取址：loader、include 与 importmap

读完这页你能回答：内核自己认识 yml 吗；引导链那几步为什么是这个顺序；node 半与浏览器半
的裸名分别怎么解析；热挂载到底由什么触发；「fiber 建出来了」和「挂上了」差在哪。

**为什么不能是插件**：取址必须在第一个业务插件之前发生。内核把它交给官方插件，不等于这件事
不存在——只是实现从「自己写」变成「挂一个官方插件」。

> cordis 本体的能力地图与文档链接，见[底座：cordis](/docs/kernel/cordis)；这页只讲本仓怎么组装它。

## 内核挂两样，其余全归它们

- `@cordisjs/plugin-loader` —— 条目树与模块加载
- 一条 `cordis:include` 条目 —— 读 `<home>/cordis.yml`

**内核连 yml 都不认识。**

## baseUrl 指向 home，而且设在根上下文

{/* ref file="../apps/desktop/src/main.ts" lines="104-106" */}

`ctx.baseUrl` = home 目录的 file URL，loader 的模块解析从这儿起步，`<home>/node_modules` 里的插件因此按裸名就找得到。母仓把 baseUrl 设成应用目录，所以它必须自己把每个条目名算成绝对 file URL——那句「裸名包只在 home 位时 loader 会静默挂不上」的血泪注释，根因就在这里。

「设在根上下文」是硬的：loader 只把 `config.baseUrl` 应用到自己那个扩展 ctx 上，而 include 挂在根、拿**根的** `baseUrl` 解析 `cordis.yml` 的路径。设错位置，include 拿到 undefined，报 `Invalid URL`（见[那面墙](/trajectory/2026-09-07-wall-baseurl-on-root-ctx)）。

## 引导链：顺序全是判据

{/* ref file="../apps/desktop/src/main.ts" lines="254-260" */}

1. **先 provide `gwbKernel`，再动 loader**。这个服务挂在根 fiber 上（根 fiber 生来 ACTIVE）、
   永不撤销，而且 provide 发生在模块顶层（`ctx.provide('gwbKernel', kernel)`）、结构上先于
   `main()` 里的一切；晚一步，第一批插件读到 `undefined`（见[那面墙](/trajectory/2026-09-07-wall-gwbkernel-provide-early)）。
2. **`await ctx.plugin(Loader)`**。`ctx.plugin()` 返回的是 thenable（包着 fiber 的就位等待），不 await，下一行 `ctx.loader` 就是 `undefined`（见[那面墙](/trajectory/2026-09-07-wall-ctx-plugin-thenable)）。
3. **替 loader 塞一个 `internal.import`**。主进程没有 `--expose-internals`，loader 拿不到 node
   内部的 ESM loader，`ctx.loader.internal` 是 `undefined`——那时它按 loader 自己的位置解析裸名，
   插件**静默**挂不上。内核塞的这个 import 分两步走：先 `fs.realpathSync.native` 把
   `<home>/node_modules/<裸名>` 解成**真实目录**（pnpm 布局下那是 `.pnpm/<包>@<版本>/…` 里的
   一处），再从那个真实目录起 `createRequire` 按 CJS 条件解析到入口文件、按 ESM `import` 进来。
   `exports` 表照旧归 `createRequire`，内核自己不认识它。这段是独立的纯函数模块
   `src/bare-import.ts`（副作用只剩磁盘读），单测就在旁边 `tests/`——junction 换版那条把
   pnpm 布局原样造了一遍。

{/* ref file="../apps/desktop/src/bare-import.ts" lines="6-16" */}

   第一步不是绕路，是**热重挂**的全部要害：Node 的 CJS 解析带进程级缓存，`pnpm add 新版` 之后
   base 与裸名都没变，`createRequire(base).resolve(name)` 仍旧回**旧版本**的真实路径，条目停用
   再启用换不到新代码（见[那面墙](/trajectory/2026-09-09-wall-resolver-cache)）。
   `realpathSync.native` 走系统调用、不经那层缓存；从真实目录起的 `createRequire`，它缓存的键里
   含着版本号目录，天然不跟上一版撞。裸名找不到时 ENOENT 里带着 home ＋ 裸名那条完整路径。
4. **include 走 loader 的 builtins**。include 住在应用依赖树里，而 baseUrl 指着 home，按裸名
   找不到它；`cordis:` 前缀的名字直接从内建表取、不经模块解析。
5. **做成条目而不是 `ctx.plugin(Include)`，id 写死 `home`**。做成条目，它的子树就挂在 loader
   树上：条目表、fiber 状态、热挂卸全在一棵树里，外面只认 `ctx.loader` 一个入口。id 有层级
   （`<父>:<子>`），父 id 一变，所有插件的 id 跟着变，外壳按 panel id 存的布局就全对不上。

之后 `ctx.loader.await()`（286 行）等整棵树收敛，`main()` 才算走完。

## 浏览器半的取址：importmap 是内核拼的

插件有两半，浏览器那半也按裸名 import（react 那一族）。页面的裸名解析靠 importmap，而这张表
**由内核拼**：提供方在自己的 `package.json` 里声明 `gwb.shared`（裸名 → exports 子路径），
内核扫 home 清单收齐、用 `createRequire(ctx.baseUrl)` 解析成 `file://` 表，随外壳地址推给
页面。内核不认识 react 这个词，只搬运声明；共享包没有 node 半，清单是它唯一能说话的地方。
这段扫描是独立的纯函数模块 `src/imports.ts`（副作用只剩磁盘读，warn 由调用方注入），
单测就在旁边 `tests/`。

{/* ref file="../apps/desktop/src/imports.ts" lines="6-14" */}

两条规则都在这段扫描里：**先声明先得**——撞名只认先到的，后来者报一句警告、不算错；
**解析不到也是警告不是错**——某个共享包坏了只损失它自己那几个裸名，不连累别的插件。

拼好的表不单独发：`shellMessage()` 把 `{ url, imports }` 打成一份，`setShell`、撤销、
`gwb:hello` 应答三个时机推的都是它（见[桥](/docs/kernel/bridge)）。**每次现算**——所以共享包
装了要重启才看得见：就算表更新了，页面那张 importmap 只注一次、注过就盖不掉已解析过的名字
（见[内核契约面](/docs/plugins/contract)）。

## 热挂载：条目树的 API，不是文件监听

**include 没有文件监听。** 它读 `cordis.yml` 只有两处：挂载时，和 `refresh()`——而 `refresh()` 在这个仓里没有任何人调。所以不是「改文件自动生效」，而是：

- 挂一条：`await ctx.loader.create({ id, name, config }, 'home')`
- 改配置：`ctx.loader.update(id, options)` —— **整卸整重挂**，所有 effect 逆序跑完再重新 `apply`，不是原地补丁
- 卸一条：`ctx.loader.remove(id)`

树一变，yml 自动写回：include 把变更去抖后写临时文件再改名，原子落盘。设置插件将来走这条——**调条目树的 API，盘上的表自己跟上**，比「编辑文件等监听」合理。

**remove 的收尾顺序**：先 `fiber.dispose()`——所有 disposables 按注册的逆序跑，`provide` 的服务就地撤销、依赖它的插件被通知重估；然后才把条目从树里摘掉、写回 yml。**插件的清理函数是真的会跑的**，这是实机验收过的一条。

还有一条白得的行为：**自己把自己拆掉的插件会被写 `disabled`**。fiber 死了而条目还在时，loader 把那条标成禁用再写回——「人禁的」和「自己灭的」在盘上有区别。

## 「挂上了」是 fiber ACTIVE，不是 fiber 存在

cordis 建 fiber 是**同步**的、与 inject 满不满足无关——一个 `inject` 永远等不到的插件也有 fiber，只是到不了 `ACTIVE`（状态 2）。「挂上了」判的永远是 `fiber.state === ACTIVE`（见[那面墙](/trajectory/2026-09-07-wall-fiber-not-active)），外壳挑插件同样只认 ACTIVE 的提供者，不然渲染层会去 boot 一个跑不起来的外壳。

**一个包挂多条条目**是支持的：同一个模块一个 runtime，多条 fiber 各有各的配置。但 **provide 服务的插件挂不了第二条**——服务撞名当场抛，而且那个 rejection 落在挂载链上。内核对这类 rejection 的处理是：只记不退（见[日志](/docs/kernel/logs)）——一个坏插件不该带走工作台，条目表是真相，哪条挂上了哪条没挂它说了算。

## 失败模式

- **`cordis.yml` 不存在 = 整趟起不来**，不是「一个插件都没装」——include 读不到文件会抛，落进 `main()` 的 catch，写一句「起不来」然后 `app.exit(1)`。所以 `ensureHome` 每次启动幂等地铺一份空表 `[]`（见[安家](/docs/kernel/home)与[那面墙](/trajectory/2026-09-07-wall-fresh-home-no-yml)）
- **挂载错误要有人听才看得见**：loader 挂不上插件时只 `logger.error`，而 cordis 的日志在没有 exporter 时只缓冲不输出。内核的全量 exporter 在挂 loader **之前**注册，坏插件才报得出 `ERR_MODULE_NOT_FOUND` 带完整路径（见[日志](/docs/kernel/logs)）
- **不写 `id` 就发随机串，而且首次加载不写回 yml**——它会一直漂到某次写回才固化，在那之前每次启动都是新的。所以 id 一律手写（见[内核契约面](/docs/plugins/contract)）

## 官方插件：开着的与不开的

| 包 | 住哪 | 为什么 |
| --- | --- | --- |
| `@cordisjs/plugin-loader` | 应用依赖树，内核挂 | 条目树与模块加载。热挂卸是白得的 |
| `@cordisjs/plugin-include` | 应用依赖树，内核挂 | 读 yml 成条目。有了它内核连 yml 都不必认识 |
| `@cordisjs/plugin-timer` | home，走 yml 条目 | `ctx.setTimeout` 随插件卸载自动收——原生的会在插件已卸载后触发 |

**不开的，各有理由**：

- `plugin-logger-console` —— **出口归内核自己那个全量 exporter**。它跟全量出口直接冲突：两个都在，同一句 cordis 日志打两遍。页面上要看的日志归 `gwb-logger` 插件，它自己挂第二个 exporter（见[日志](/docs/kernel/logs)）
- `plugin-hmr` —— **在这个架构下不起作用**：跑的是 home 里那份产物，盯仓内源码盯到变化也没有对应模块可换
- `plugin-http` / `plugin-server` —— **内核**没有外部访问需求。给 agent 开门那条线真长出来了，但它是**插件**，自己起 `node:http`——先 mcp 后 command-http，内核全程不问门是什么协议。顺带一处订正：`plugin-http` 是 **HTTP 客户端**（`ctx.http`），本来就收不了请求
- `plugin-config` / `plugin-webui` —— 硬 peer 一个 webui，而 webui 要 `server`——为一个条目编辑器拖进 HTTP＋WebSocket
- `plugin-database` —— 没有超出「插件自己写文件」的需求
- `@cordisjs/logger` —— 旧版，cordis 4.x 本体已自带
- `@cordisjs/schema` —— cordis 3 遗物、已从官方仓删除；配置校验 cordis 4 本体自带（`plugin.Config` 走 Standard Schema）
