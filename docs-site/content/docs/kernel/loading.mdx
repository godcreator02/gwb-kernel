# 加载插件

**本页回答**：cordis 怎么在主进程里创建出来、插件怎么从 home 里被找到并加载、启动与退出流程为什么是现在这样。

## 管什么

主进程里有一个 cordis `Context`，所有插件都注册在它上面。内核只注册两个官方插件——`@cordisjs/plugin-loader`（条目树与模块加载）和一条 `cordis:include` 条目（读取 `<home>/cordis.yml`），再替 loader 补上主进程一侧的包名 import（bare specifier，直接写包名、不带相对路径的 import，比如 `from 'cordis'`）解析；其余的插件加载、运行中加载与卸载插件、把条目改动写回 `cordis.yml`，全部由这两个官方插件负责。退出时由内核卸载整棵插件树。

## 不知道什么

不认识 `cordis.yml` 的格式（由 include 负责），不认识任何插件的包名、服务名、命令名。不监听文件——改了 yml 不会立即生效，运行中加载与卸载插件要调用 loader 的条目树 API（`create` / `update` / `remove`，由 plugin-manager 这类插件去调用）。不判断插件是否加载成功，那由 fiber 的状态决定（`ACTIVE` 才算，见[「fiber 存在」不等于「加载成功」](/trajectory/2026-09-07-wall-fiber-not-active)）。

## 数据结构

- **条目树**：根下有一条 id 固定为 `home` 的 include 条目，`cordis.yml` 里的每一条都是它的子条目，完整 id 是 `home:<id>`。`home` 这个 id 一变，所有插件的 id 都跟着变（[承载 `cordis.yml` 的条目 id 固定为 `home`](/trajectory/2026-09-07-wall-home-entry-id-fixed)）
- **`loaderFiber`**：已注册的 loader 的 fiber，退出时卸载它；`main()` 执行到加载插件之前它是 `undefined`

## 提供的接口

**根上下文与 baseUrl**：`ctx.baseUrl` 是 home 的 file URL，设在**根**上下文上——include 注册在根上下文，用根上下文的 `baseUrl` 解析 `cordis.yml`（[`baseUrl` 要设在根上下文](/trajectory/2026-09-07-wall-baseurl-on-root-ctx)）。

**启动顺序**：这几步的顺序本身就是要求——`gwbKernel` 在模块顶层就已经 provide（早于任何插件加载，[`gwbKernel` 要在注册 loader 之前 provide](/trajectory/2026-09-07-wall-gwbkernel-provide-early)）；`await ctx.plugin(Loader)` 必须 await（[`ctx.plugin` 返回的是 thenable，不 await 服务就还没就绪](/trajectory/2026-09-07-wall-ctx-plugin-thenable)）；给 `loader.internal` 补上包名 import 解析（主进程没有 `--expose-internals`，不补的话插件会加载失败，而且**不报任何错**）；include 从 loader 的 builtins 取（它在应用自己的依赖树里，按 home 解析找不到，[include 要从 loader 的 builtins 取](/trajectory/2026-09-07-wall-include-via-builtins)）；最后 `loader.await()` 等整棵树的加载全部结束。

{/* ref file="../apps/desktop/src/main.ts" lines="275-284" */}

**主进程一侧的包名 import 解析**：分两步——先用 `realpathSync.native` 把 `<home>/node_modules/<包名>` 解析成真实目录（pnpm 布局里带版本号的那个目录），再从那里用 `createRequire` 按 `exports` 解析到入口文件，按 ESM import 进来。第一步是运行中重新加载插件时能拿到新版本的关键：Node 的 CJS 解析缓存按「请求的名字 + 起点目录」记录，包换了版本而逻辑路径没变时会返回旧版本，而真实路径天然与上一版不同（[Node 的 CJS 解析缓存会返回旧版本](/trajectory/2026-09-09-wall-resolver-cache)）。页面一侧拼 importmap 用的也是同一个 `resolveFromHome`。

{/* ref file="../apps/desktop/src/bare-import.ts" lines="17-29" */}

**启动流程**：入口模块里不能顶层 `await app.whenReady()`——`ready` 事件要等入口模块执行完才发出，两边互相等待，程序卡住且不报错（[Electron ESM 主进程不能顶层 await whenReady](/trajectory/2026-09-09-wall-esm-await-whenready)）。启动代码写在 `.then(main)` 里；`main()` 里抛出的任何错误都交给 `.catch`：写日志、弹错误框、`app.exit(1)`。所有窗口关闭即退出。

{/* ref file="../apps/desktop/src/main.ts" lines="287-297" */}

**退出流程**：在 `will-quit` 里拦下这一次退出，先对 loader 的 fiber 调用 `dispose()`，再 `await()` 等整棵树卸载完，然后才 `app.quit()`。插件启动的长期运行的子进程靠这条路径被一起结束。内核和插件两边缺一不可：`dispose()` 只是**开始**卸载，要再 `await()` 才能等到嵌套的异步清理；插件那边得把真正的清理**返回**成 promise，否则内核等到的是一个什么都不做的空 promise（[退出清理要内核与插件两边配合](/trajectory/2026-09-12-quit-dispose-two-halves)）。某个插件的清理卡住不结束时，5 秒超时后强制退出；清理出错只记录、不阻止退出。

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| cordis `Context` | 插件的运行时 | `cordis`（应用依赖树） | — |
| `@cordisjs/plugin-loader` | 条目树、模块加载、运行中加载与卸载 | 应用依赖树 | — |
| `@cordisjs/plugin-include` | 读写 `cordis.yml` | 应用依赖树，经 builtins 取 | — |
| 磁盘上的 pnpm 布局 | 包名 import 解析 | `<home>/node_modules` | 测试里手工构造的临时 home（含 junction） |

## 怎么单独测

`bare-import.ts` 不依赖 electron 与 cordis，副作用只有读磁盘：传入一个手工构造的临时 home，证明主入口与 scoped 包都能解析到、子路径写法等价、junction 改指向后拿到新版本、包不存在时报 ENOENT 并带完整路径（`tests/bare-import.test.ts`）。启动顺序、运行中加载与卸载、退出清理只能在隔离 home 里实机验证。
