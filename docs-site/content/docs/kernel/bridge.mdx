# 桥：命令、事件与 gwb://

读完这页你能回答：页面上一次点击到件的处理函数要经过几跳；importmap 是谁拼的、什么时候注入；`gwb://` 凭什么敢把 `node_modules` 里的文件交给页面。

**为什么不能是插件**：两个执行世界之间的通道，得在任何一边有件之前就存在。

## 传消息：命令的一跳不省

全链是这样：

```
页面 window.gwb.command(name, args)
→ preload ipcRenderer.invoke('gwb:command')
→ 主进程 hostCommand：发一个 randomUUID 当关联 id，一行 JSON 写进 stdin，上 120 秒定时
→ 宿主 readline → dispatch
→ ctx.gwbCommands.run(name, args)          # kernel.info 例外，见下
→ 回执 { t:'reply', id, result } 走 fd3
→ 主进程按 id 找回 pending 的 resolver → IPC promise 兑现 → 页面 await 到结果
```

**内核只原生命中一条命令**：`kernel.info`。其余一律转发给 `ctx.gwbCommands`——由某个件提供的命令总线，内核不认识任何具体命令名。「本体不认识件的命令名」是有意的纪律：内核要用某个件的能力，正确的做法是让那个件把服务送上来，而不是内核去点名调它。

超时与异常都有归属：

- 120 秒没回，就是 `{ ok: false, error: '命令超时' }`；日志说得出是哪条命令超的时
- 宿主死了，所有在途命令当场收到「宿主已退出」
- 晚到的回执静默丢弃——pending 表里那个 id 已经删了

## 事件：emit 的那一头是页面

件调 `ctx.gwbKernel.emit(payload)`，宿主包成 `{ t:'event', payload }` 走 fd3，主进程转 `webContents.send('gwb:event')`，页面的 `onEvent(cb)` 收到。**事件是火过就灭的**，没有历史段——要历史的是日志，那是另一条通道（见[日志](/docs/kernel/logs)）。

## 传代码：gwb:// 只认 exports 表

件的浏览器那半住在 node 那边的 `node_modules` 里，页面得有一条取货通道。约定只一条 URL：

```
gwb://asset/plugins/<包名>/<exports 子路径>
```

包名带 scope 自然是两段，所以规则是「`@` 开头吃两段、否则吃一段，剩下的全是子路径」。浏览器入口约定在 `./client`。

从 URL 到文件，四道关卡各有理由：

1. **scheme 特权注册**（`standard`/`secure`/`supportFetchAPI`/`corsEnabled`），时机在 app ready 之前——要当真的 URL 解析、要能被页面 fetch
2. **定址只认 exports 表**：入口四档写法（`exports` 对应子路径 → 条件对象的 `import`/`module`/`default` → `main` → `index.js`），外加一条越界检查：**入口指到包目录外一律不认**——认了它一个包就能让内核读任意文件
3. **MIME 白名单按真实文件判**：`.js`/`.mjs`/`.css` 之外一律 404。判的是解析出来的真文件的扩展名，不是 URL（`./client` 落在 `dist/client.js` 上）；`.css` 单列是因为 Chromium 对样式表的 content-type 查得严（见[那面墙](/docs/trajectory/2026-09-07-wall-css-content-type)）
4. **`no-store` + CORS `*`**：页面和 `gwb://asset` 是跨源的；文件随包更新，缓存只会撒谎

## importmap：内核拼，内核注

浏览器里 `import 'react'` 这种裸名，只有 importmap 说得出它在哪。分工是三段：

- **件（或共享包）在清单里声明** `gwb.shared`：「我给页面提供这几个裸名」，值是自己的 exports 子路径
- **宿主收齐**：扫 `<home>/package.json` 的 dependencies——**扫 home 清单不是条目表**，共享包不是件，不在 `cordis.yml` 上。**一个裸名只认先声明的那个**；撞名报进 `sharedConflicts`、不静默裁决——浏览器反正覆盖不了已解析的裸名，替它选一个赢家的结果是「页面上跑的到底是哪份说不清」
- **渲染层注入**：把每条裸名映射成 `gwb://asset/plugins/<包>/<子路径>`，写成 `<script type="importmap">` 挂上 head——**必须赶在第一句动态 import 之前**，已解析过的裸名再也改不了

npm 上的 `react` 至今没有 ESM 出口，直接用不了——要有人打成 ESM 再发一份（件仓的 `gwb-shared-react` 干的就是这个）。

**为什么这件事归内核**：importmap 必须比一切件的代码都早，而「哪些裸名映射到哪」的真相只在 home 的清单里——时机与信息，只有内核同时够得着。件的声明格式见[一件的解剖](/docs/plugins/anatomy)。

## preload 与窗的安全位

`contextIsolation: true`、`sandbox: false`（preload 是 ESM）。页面上内核只放一个 `window.gwb`——四个函数，面见[浏览器那半](/docs/plugins/client)。
