# 载体：两个进程、一扇窗

读完这页你能回答：为什么要用 `ELECTRON_RUN_AS_NODE` 把 electron 当 node 使；协议为什么只走 stdin 和 fd3；窗口为什么必须由内核开。

**做什么**：GUI 主进程起一扇窗；宿主子进程起一个 cordis `Context`。

**为什么不能是插件**：模块要有运行时才跑得起来，窗口要有进程才开得出来。这两样都发生在第一个件之前。

## 宿主是怎么被拉起来的

主进程先算出 home 目录，然后**先拉宿主、后开窗**——渲染层起步第一句话就是向内核要 `kernel.info`，宿主不在，那句话没人答。

{/* ref file="../apps/desktop/src/main/host-process.ts" lines="34-45" */}

`ELECTRON_RUN_AS_NODE=1` 把 electron 二进制当纯 node 使——宿主不需要 Chromium，要的是一个干净的 node。`--expose-internals` 不是装饰：cordis 的 loader 在有 node 内部 ESM loader 的场合会用它，而主进程的 `NODE_OPTIONS` 白名单拒绝这个 flag，所以只能挂在 spawn 参数上。

stdio 开四条管道，第四条（fd3）是协议上行的专用管。宿主退出时主进程在日志里补一条「宿主退出（code=…）」——**宿主没法报告自己的死亡**，那一行只能由活着的这边写。

## fd1 留给人看

四条 stdio 各有各的用途，关键的一条是**协议不占 fd1**：

| 管道 | 走什么 |
| --- | --- |
| stdin | 协议下行：命令，一行一条 JSON |
| fd3 | 协议上行：命令回执、事件、结构化日志 |
| fd1/fd2 | 人读的输出，原样转接到主进程自己的 stdout/stderr |

宿主里 `console.log` 被劫持成 `console.error`，落进 fd2 转出来。母仓试过把协议帧和人读的日志混进同一管——两边都没法读，这四条管的划分是那次的遗产。协议两端都对每行做形状检查，认不出的行丢弃并记一句警告，不猜。

## 窗口必须由内核开

即使将来把窗口的尺寸、标题、关窗语义都交出去，`BrowserWindow` 这个动作本身仍留在内核——**在件挂上之前就得有一扇窗让页面加载**。这条有个不显然的推论：「窗口里画什么」倒是完全归件的，内核自己一行界面代码都没有，所以「一个件都没装」的窗口就是白的（出路见[刻意不做什么](/docs/not-doing)）。

## 窗的安全位

`contextIsolation: true`、`sandbox: false`——后者是因为 preload 用的是 ESM。页面上内核只放一个 `window.gwb`（四个函数，见[浏览器那半](/docs/plugins/client)），其余什么都不注。
