# 撞过的墙

代码注释只写现状，**为什么、症状、当时怎么查的，全在这一页**。

每条都钉在具体代码上。代码改了这页报黄，得有人来复核——文档撒谎会被当场抓住，这是
这一页存在的全部意义。

## 宿主

### loader 挂不上一个件时，错误在启动期没有出口

内核在**任何件之前**就注册好日志出口——注册点紧挨着 `ctx` 造出来的地方：

{/* ref file="../apps/desktop/src/host/main.ts" lines="94-102" */}

**loader 没有吞错误**，它老老实实写着 `.catch(error => this.ctx.logger.error(error))`。问题
在下游：cordis 的 `LoggerService` 把消息存进 `buffer`，**没有 exporter 就没有出口**。而
`logger-console` 是 `cordis.yml` 里一条**并发挂载**的普通件——件挂载失败的那一刻，它可能
还没注册 exporter。

**症状**：件静默挂不上，日志一个字都没有，连「哪个件、为什么」都问不出来。第一个件
（`gwb-cli`）因为相对 import 少了 `.js` 撞上这个，查了几分钟。

补上之后同样的错当场是一行：

```
[loader] include: Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  '...\@test\broken\does-not-exist.js' imported from '...\@test\broken\index.js'
```

**后来这条保底线转正了**：做日志窗格时出口从「只管 error」扩成了全量，`logger-console`
也跟着撤掉——两个都在的话同一句话会打两遍。判据见[定过的事](/docs/decisions)。

当初「只管 error、`info`/`warn` 归 `logger-console`」那个取舍留在这儿，是因为**它解释了这个
exporter 为什么必须在挂 loader 之前注册**：那一刻还没有任何件，包括原来负责好格式的那个。
扩成全量之后这条要求只会更强——注册点还要再往前挪到 `ctx` 造出来的下一句，那样 cordis 自带
的那圈 buffer 里根本不会攒下东西，**用「提早注册」换掉了「事后补发」**。

### `ctx.plugin` 是 thenable，不 await 服务就还没就位

{/* ref file="../apps/desktop/src/host/main.ts" lines="347-353" */}

**症状**：`ctx.loader` 是 `undefined`，报 `Cannot read properties of undefined (reading 'await')`。

### `baseUrl` 要设在根上下文

{/* ref file="../apps/desktop/src/host/main.ts" lines="52-53" */}

`Loader` 只把 `config.baseUrl` 设在**它自己 `extend` 出来的 ctx** 上（`this.ctx = ctx.extend({ baseUrl })`），
而 `Include` 是挂在根上的。设在根上，两个都从那儿继承。

**症状**：`Invalid URL`——`include` 拿 `new URL(path, ctx.baseUrl)` 时 baseUrl 是 undefined。

顺带：这也是**母仓那句血泪的根因**。它那句注释说「裸名包只在 home 位时 loader 会静默
挂不上」，实际是因为它把 baseUrl 设成了应用目录，所以必须自己把每个条目名算成绝对
file URL。指向 home 之后 loader 自己就解析得到。

### `include` 的 `config.path` 是相对 baseUrl 的 URL，不是文件系统路径

它内部走的是 `fileURLToPath(new URL(config.path, ctx.baseUrl))`。

**症状**：传绝对路径时报 `ERR_INVALID_URL_SCHEME: The URL must be of scheme file`——Windows
的盘符 `C:` 被当成了 URL scheme。

### `include` 走 loader 的 `builtins`，而且做成条目

{/* ref file="../apps/desktop/src/host/main.ts" lines="349-352" */}

`include` 住应用依赖树，而 baseUrl 指着 home——按裸名找不到它。loader 的 `import()` 对
`cordis:` 前缀的名字直接从 `builtins` 表取、不经模块解析，所以挂 `builtins.include` 再用
`cordis:include` 引它。

**做成条目而不是 `ctx.plugin(Include)`**：这样它的子树挂在 loader 树上，条目表、fiber 状态、
热挂卸全在一棵树里，外面只认 `ctx.loader` 一个入口。直接 `ctx.plugin` 的话它是根上的一个
普通插件，`walkEntries` 走不到它读出来的条目。

### 承载 yml 那条条目的 id 写死为 `home`

{/* ref file="../apps/desktop/src/host/main.ts" lines="25-26" */}

条目 id 有层级（`<父>:<子>`）。不写死的话父 id 是随机的（`d9509601`），所有件的 id 跟着
变成 `d9509601:shell`，**每次启动都不一样**——外壳按 panel id 存的布局就全对不上。

另一条 API 细节：`create()` 回的是**全路径 id**，而 `remove()` / `resolve()` 只认树内的
**局部 id**。拿全路径去 remove 会报 `cannot resolve entry`。

### `gwbKernel` 要在挂 loader 之前 provide

{/* ref file="../apps/desktop/src/host/main.ts" lines="347-348" */}

件一挂上就要取得到。晚一步的症状是第一批件全都读到 `undefined`。

### 全新 home 起不来——`include` 读不到 `cordis.yml` 会把宿主整个搞挂

{/* ref file="../apps/desktop/src/host/install.ts" lines="13-30" */}

**症状**：一个全新的 home 首启，宿主 `exit 1`，日志里是一条未捕获的 promise rejection：

```
Error: config file not found: …\homes\boot-2609070610\cordis.yml
    at [cordis.init] (…/@cordisjs/plugin-include/lib/index.js:146:15)
[gwb] 宿主退出（code=1）
```

那个错落在 loader 的挂载链上，**不是「一个件都没装」，是整个进程没了**。

**为什么拖到现在才发现**：日常那个 home 早就有 `cordis.yml` 了，这条路径从来没人走过。
`homes/<名>` 一做出来、第一次开测试 home 就撞上了——**这正是「验从零装机要开新 home」
那条纪律要抓的东西**。而文档当时还写着「文件不存在就是一个件都没装」，跟实际行为对不上。

**修**：`ensureHome` 把 home 建成**起得来**的最小形态——包清单 + 一份空条目表 `[]`。
空表才是「一个件都没装」的正当表达。

**它每次启动都跑，不只首启**：两样各自判在不在、幂等。只在首启补的话，有人手工删掉
`cordis.yml` 之后就再也起不来了，而那个失败同样是宿主整个退出。

### 建 home 的 `package.json` 不由装机代劳

{/* ref file="../apps/desktop/src/host/main.ts" lines="332-343" */}

推荐列表是空表时装机会提前返回（`specs.length === 0`），`ensureHomeManifest` 轮不到，
于是 `package.json` 建不出来，「装过了」永远判不成立——**每次启动都当新 home**。

这个 bug 是实机验收抓到的：删净 home 起一次，日志说了「新 home」，但目录是空的。
**单测抓不着**，因为它是两个各自正确的函数组合顺序错了。

**后来从根上拆掉了这个组合**：`ensureHome` 挪到 `firstRun` 的第一行、无条件跑，跟装机再无
先后关系（见上一条）。当时那个修法是「建 home 不走装机那条路」，现在是「建 home 根本不跟
装机排队」。

## 主进程

### 三处输出汇在一处，劫持那一处就全在

{/* ref file="../apps/desktop/src/main/log-file.ts" lines="5-13" */}

主进程自己的、宿主 pipe 过来的、渲染层 `console-message` 转来的，最后都走
`process.stderr`。比母仓那份（只含宿主）更全，代码还少一半。

它只保证一件事：**脱离终端起的时候**（打包后双击，stderr 没人接），出了事还有地方查。
眼下每次都从终端起，所以这条现在用不上；等打包到期，它立刻从锦上添花变成不补就没法查。

**「全」有两种，别把这句读成「一条流覆盖全部」。** 做日志窗格之后有两条流并行，它们
**不是包含关系**：

| | 兜得住 | 兜不住 |
| --- | --- | --- |
| 这条（劫持 stderr → 文件） | **一切写进 stderr 的字节**——内核的话、pnpm 转发、第三方库直写、node 的 `emitWarning`、**未捕获异常的默认打印** | 级别与来源，它只有文本行 |
| 界面那条（四路结构化条目 → 缓冲 → 窗格） | `seq`/`source`/`level`，筛得动 | 没走结构化路径的任何东西，最要紧的是**未捕获异常** |

所以查崩溃的第一现场永远是文件，不是窗格。

### 日志写失败只说一次，此后不再试

{/* ref file="../apps/desktop/src/main/log-file.ts" lines="98-104" */}

静默停更会让人读到一段什么都没发生的时间；每行重试则把每行输出变成一次失败的系统调用。

**切段失败不共用这个 latch，也不该共用。** 上面那条理由（每行重试＝每行一次失败的系统调用）
在轮转上不成立：切不动只是文件长一点，照常写没有任何额外成本。共用一个 latch 的话，一次被
占用的 `rename`（Windows 上拿编辑器开着归档文件就够）会把整条落盘线判死——**把一个小故障
放大成「此后再也不落盘」**。所以是两个 latch：`dead` 管写、`rotateDead` 管切。

同一处还有一条更隐蔽的：`rotate` 里已经 `closeSync` 过了，**rename 抛出去的话就丢下一个关掉的
fd**，下一次写是 `EBADF`，照样把整条线判死。所以它无论成没成都要交回一个开着的 fd。这条有单测
钉着（`rename` 打桩抛 EPERM，然后断言交回的 fd 还写得进去）。

### 一处两投之后，终端里出现了两种格式

日志出口改成「四路各自结构化、正文投两处」之后，**第一次实机起来看日志文件就撞见了**：

```
18:36:32.897 I host up，dataDir=…，条目 1/1
[renderer] SHARED （空）
[renderer] [renderer] 没有件提供 gwbShell 服务,界面到此为止。…
```

**症状**：同一份文件里两种格式混着——宿主那路带时间与级别（它走 cordis 的 exporter，那儿拼了
前缀），主进程与渲染层那路只有个方括号名字（它们各自 `process.stderr.write` 时手拼的）。
外加**双前缀**：渲染层代码里本来就自己写着 `[renderer] `，而主进程收 `console-message` 时又
按来源加了一个。

**为什么**：「一行长什么样」被写在了三个地方。四路合流这件事天然会引出这个问题——每加一路，
就多一个人决定这一行怎么拼。

**修**：抽一个 `formatLogLine` 放进两头共用的协议文件，四路都走它；渲染层里那几处手写的
`[renderer] ` 前缀删掉——有了结构化的 `name` 字段之后，那是重复信息。

{/* ref file="../apps/desktop/src/shared/protocol.ts" lines="84-92" */}

### cordis 的 `Logger.format` 是静态方法，摘下来就丢了 `this`

取 `ctx.logger('x').constructor` 拿到 `Logger` 类是为了**不 import cordis 的内部**（母仓那个
日志件就是这么干的）。但

```ts
const format = factory('gwb').constructor.format   // ← 摘下来了
```

**症状**：不是运行时报错——是 `pnpm check` 里 oxlint 的 `typescript(unbound-method)` 拦下来的。
那份实现眼下确实没用 `this`（`format` 里全是参数与模块级的 `defaultFormatters`），所以**跑起来
一点事都没有**；等哪天 cordis 在里面加一句 `this.xxx`，才会炸在一个跟日志毫无关系的地方。

**修**：整个拿着那个类、调 `Logger.format(exporter, message)`，别把方法摘下来。

## 条目表

### 「fiber 在不在」不是「挂上了没有」

条目表的 `ok` 一开始判的是 `entry.fiber !== undefined`。看着天经地义，**是错的**：
cordis 的 `registry.plugin()` **同步就把 fiber 建出来并返回**，跟 `inject` 满不满足
完全无关。只有 `import` 那一步抛错才会让 `fiber` 留在 undefined。

所以一个 `inject` 永远等不到的件也报 `ok: true`——而那正是最该被看见的一种没挂上。

**这条不是推出来的，是撞出来的**：`gwb-shell` 硬 `inject: ['gwbCli']`，而
`gwb-cli` 没装进 home 时，它的 fiber 停在 `PENDING`、`ok` 仍报 true，于是渲染层照样把
`#root` 交给它、`import` 了它的 `client.js`、调了 `bootShell`——然后 `shell.panes` 这条
命令根本不存在。**井是空的，而 console 里只有一句「调不通」**，谁也看不出根因是另一个
件没装。

判据得是 `fiber?.state === FiberState.ACTIVE`。**那是个 `const enum`**，`isolatedModules`
下 import 不进来，只能照抄字面量 `2` 并在注释里说明。

{/* ref file="../apps/desktop/src/host/main.ts" lines="145-165" */}

修完之后启动日志会诚实一些：以前永远是 `条目 5/5`，现在有件在等依赖时会显示 `2/4`，
而且每条后面写着「挂上」还是「没挂」。

### 条目 `id` 不写，loader 发的是随机串

`EntryGroup.create` 走 `ensureId`，不写 `id` 就 `Math.random().toString(16).slice(2, 10)`
——**8 位随机十六进制，每次启动都不一样**。文档一度写着「`id` 不写就用 `name`」，那是错的，
两个包里没有任何一处拿 `name` 当 id。

更麻烦的是**初次加载不写回 yml**：`EntryGroup.update → create → ensureId` 这条路上没有
`write()`，只有 `EntryTree` 的 `create`/`remove`/`update` 才显式写。所以那个随机 id 会一直
漂到某次写回才固化。

**症状**：按条目身份存东西的件——外壳的窗格布局、设置件的 home 级设置——每次启动都对不上，
东西像是没存过。**没有报错**。

实机的 `cordis.yml` 一直是手写短名 id（`gwb-plugin-dev` 的规程就这么要求），所以这个坑
一次都没撞上；写下来是因为查 `gwb-settings` 该按什么做键时翻出来的。规程见
[写一个件](/docs/plugin)。

### 同一个包挂多条是支持的，但 provide 服务的件挂不了两条

`registry.plugin()` 每次都 `new Fiber`，只有 `runtime`（按 callback 去重）共享。两条条目
= 一个 Runtime ＋ 两个独立 fiber，`config` 与 `ctx` 各是各的。**实机验过三条**（同一个
探针包挂 writer / reader / commands 三种角色，各跑各的）。

但 `reflect.provide` 撞名当场抛：没有 `isolate` 时同一个域里第二条 provide 同名服务
直接 `service "x" has been registered`。所以能挂多条的只有不 provide 服务的件。

### 以下几条是**读源码得出的，没实机撞过**

第二版接「插件管理」（启停/卸载）时才会用到它们，真用之前建议各验一次：

- **`update` 改 `config` 是整个重挂**，不是原地更新：`Entry.update` → `_patchContext` →
  `fiber.update` → `restart()` → 完整 unload＋reload，`apply` 重跑、`provide` 全撤销再建。
  而 `provide` 一撤销就 `notify` 一圈，**`inject` 它的件跟着卸载再挂**——改一项配置抖一条
  依赖链。想不重挂得自己截 `internal/update` 且不调 `next()`（loader 自带的 Group 与
  Include 就是这么干的）
- **写回 yml 是全量 `yaml.dump(root.data)`**，源文本只用于「内容没变就不重读」的比对、
  不参与写。**注释、空行、引号风格全丢**，键序还被 `sortKeys` 重排成 id/name/其余字母序/config。
  而按[刻意不做什么](/docs/not-doing)的判断，那个文件**归用户**——第一次从界面改配置就把
  人写的注释清了，这件事得先想清楚
- **没有文件监听**。两个包里没有 `fs.watch` 也没有 chokidar，`Include.refresh()` 是个从未
  被调用的公开方法。外部手改 `cordis.yml` 不会被感知，要重启
- **`ctx.loader.remove('home:x')` 可能是静默 no-op**：`EntryTree.remove` 拿全路径 id 去调
  `EntryGroup.remove`，而后者拿它当短 id 查 `store`（键是 `x` 不是 `home:x`），查不到就
  直接 return——**条目没删，`write()` 还照写一遍**。`update` 没这问题（它先 resolve 成
  `Entry` 对象）
- **`ctx.loader.create(opts)` 不传 `parent` 落不了盘**：默认 `parent = null` 解析到 Loader
  自己的 root group，而 `Loader.write()` 是**空实现**。要写进 `cordis.yml` 得传
  `parent: 'home'`（那条 include 条目的 id）

## 取址

### 入口指到包目录外一律不认

{/* ref file="../apps/desktop/src/shared/entries.ts" lines="87-95" */}

认了它，**一个包就能让内核读任意文件**。这是这一层唯一的一条判断——其余的候选名补全、
位表、完整 exports 条件语义、realpath 实体化，母仓都有，这里都没有。

顺带说明这半为什么还留着：挂载归 loader 了，但**主进程**的 `gwb://` 要把件的 `client.js`
交给页面，得知道包在哪，而 loader 跑在宿主子进程里，主进程够不着。

### URL 里的点段轮不到自己判——`new URL` 已经吃掉了

{/* ref file="../apps/desktop/src/shared/asset-url.ts" lines="39-41" */}

子路径通用化之后第一反应是加一道「`.` 与 `..` 一律不认」。**那是死代码**：WHATWG 的
路径状态机会先百分号解码再判点段，`new URL` 出来的 `pathname` 里根本不会剩下它们。实测：

```
gwb://asset/plugins/@a/b/../escape.js    → pathname = /plugins/@a/escape.js
gwb://asset/plugins/@a/b/%2e%2e/escape.js → pathname = /plugins/@a/escape.js
```

两条都被规范化成了同一个东西，落到解析函数手上时形状是「只剩包名、没说要什么」，
自然不认。**留着那道检查比不写更糟**——读代码的人会以为这里挡住了越界，于是不再去问
真正的防线在哪。真正挡越界的只有 `resolvePlugin` 那句包目录前缀检查。

### 交样式表卡住的是 content-type，不是协议特权

{/* ref file="../apps/desktop/src/main/asset.ts" lines="8-17" */}

`registerSchemesAsPrivileged` 那四个特权（`standard` / `secure` / `supportFetchAPI` /
`corsEnabled`）早就配齐了，`gwb://` 加载模块脚本一直是好的。但 `<link rel=stylesheet>`
拿不到样式——**Chromium 对样式表做严格 MIME 检查，不是 `text/css` 一律拒**，而执行端把
content-type 写死成了 `text/javascript`。

**症状**：请求 200、内容也对，页面上就是没样式，控制台一句话都没有。

分派按**解析出的真实文件**判扩展名，不按 URL 判：`exports` 的 `./client` 落到的是
`dist/client.js`，URL 那一段压根没有扩展名。

## 构建

### 显式给 `rollupOptions` 会把 `externalizeDepsPlugin` 注入的 external 盖掉

{/* ref file="../apps/desktop/electron.vite.config.ts" lines="11-21" */}

而两个入口非得显式给 `input` 不可。所以不用那个插件，改成从 `package.json` 现读依赖表
自己判——加依赖不必回来改这里，也就不会漏。

**症状**：cordis 被整个内联进宿主束，`host.mjs` 从 2KB 涨到 51.6KB，而构建一声不吭。

### electron 这个包不带 postinstall

{/* has file="../apps/desktop/package.json" text="node node_modules/electron/install.js" */}

electron 44.1.1 的 `scripts` 字段是 `null`，二进制得显式跑一次 `install.js` 才落到 `dist/`。

里，也得 peer**——`GwbContext extends Context`，消费方必须解析得到，而**发布出去的包不带
devDependencies**。
