`gwb-kernel` 是 god 工作台的内核：一个 Electron 应用，cordis 运行在主进程里。内核只做两类事——主进程插件启动所需的基础能力，和页面模块加载前必须建立的解析环境：选定 home、建 cordis 实例并按 `cordis.yml` 加载插件、打开窗口并把页面交给外壳、在页面与插件之间传递消息、把日志写进 home。
命令总线、插件管理、界面、数据、设置、给 agent 用的 MCP 入口全是 `cordis.yml` 里的插件，各在自己的仓里；内核越小，换掉任何一个插件都越不用改内核（[这个内核的起点](/trajectory/2026-09-07-gwb-kernel)）。
本仓只有两个包：内核应用 `@godcreator/gwb-kernel-desktop`，和插件一样装在每个 home 里；安装包，只带启动器与 Electron。

## 准入判据与刻意不做的事

往内核里加东西要同时满足两条：

1. **是主进程插件启动所需的基础能力，或页面模块加载前必须建立的解析环境**；具体的运行时与版本由插件提供。先问这件事能不能由某个插件提供、经服务交给需要它的地方——能，就做成插件。插件就运行在主进程里、能直接 `import('electron')`，窗口、菜单、托盘、对话框、子进程都由插件来做
2. **此刻确实需要**：说得出是谁、在做什么、因为缺了它卡在哪一步

拿不准按「不进」处理：以后再加进来，永远比加进来之后再拿掉容易。「将来可能要」「顺手做了」「旧版工作台仓 god-workbench 里有」，以及为了方便某一个插件往内核里加只有它用的逻辑，都不算理由；改内核由人决定（[另起新仓，而不是在旧仓上删减](/trajectory/2026-09-07-fresh-line-over-subtraction)）。

**刻意不做**，要做得先推翻上面的判据：

- **不放插件**：命令插件 `@godcreator/gwb-commands` 在基础插件仓 `gwb-base-plugins`，插件管理 `@godcreator/gwb-plugin-manager` 在生命周期插件仓 `gwb-lifecycle-plugins`，都是 `cordis.yml` 里的普通插件，可以停用、卸载、单独升级（[内核仓只放内核](/trajectory/2026-09-24-kernel-repo-only-kernel)）
- **不给插件提供安装接口，也不带 pnpm**：装卸、升级只经插件管理的 `plugin-manager.*` 命令；插件之间的依赖齐不齐，内核不核对（[移除内核的安装接口](/trajectory/2026-09-08-no-install-port)）
- **不往新 home 里装东西**：内核包、`cordis` 与插件由创建 home 的一方安装——日常用的 `default` 由装机的 agent 照仓根 `INSTALL.md` 装，验证用的隔离 home 由 devkit 的 `devkit.home.new` 装；安装包不带内核、插件与 pnpm
- **不补、不修 home**：`package.json` 与 `cordis.yml` 缺了就启动失败并写明缺哪个，不生成模板（[缺文件改成启动失败](/trajectory/2026-09-25-kernel-drop-fallbacks)）
- **不认识插件与命令**：加载哪些插件由 `cordis.yml` 决定，页面请求交给插件登记的处理器，内核不看插件包清单里的任何字段，也不参与插件之间怎么交互
- **不写数据、不打包**：内核只提供 `dataDir`，写数据归数据插件（[数据写盘做成插件](/trajectory/2026-09-07-gwb-data-plugin)）；内核用 `tsc` 直接输出，页面运行时的打包归提供模块的插件（[打包器以后再选](/trajectory/2026-09-07-bundler-deferred)）

几条由判据推出、错了难改的边界：

- **插件和内核在同一个进程里**：所有插件运行在 Electron 主进程的 cordis 实例里，没有宿主子进程、没有自定义资源协议，页面直接加载 `file://` 地址。代价是一个插件出错就是这个进程出错，所以内核对插件里没被处理的异常只记日志、不退出（[两个进程合并为一个](/trajectory/2026-09-09-single-process)）
- **每个 home 相互独立**：`GWB_HOME` 选定 home，不设时是 `default`。不同的 home 可以同时运行，插件、端口、数据互不影响；同一个 home 只运行一个实例（[同一 home 只许一个实例](/trajectory/2026-09-12-one-home-one-instance)）
- **内核和插件一样装在 home 里**：宿主和插件在同一个 `node_modules` 里，`cordis` 只有一份，各个 home 可以装不同版本的内核，新内核装进隔离 home 就能验证，不用重打安装包。代价是发版物有内核包与安装包两样，启动器与内核之间多一条 Electron 版本约定（接缝 1），升级内核要装进 home 再重启（[内核装进 home](/trajectory/2026-09-24-kernel-in-home)）
- **插件在 peer 里写兼容哪个内核**：范围的下限是验证时那个内核的版本号。pnpm 装插件时拿它和 home 里的内核包比，不满足只警告；插件管理拿它和运行中的 `gwbKernel.version` 比，范围不包含的插件在回执里标出来，只标不拦；devkit 的 `devkit.release` 发插件前检查它。内核自己不读这个字段

```json
{ "peerDependencies": { "@godcreator/gwb-kernel-desktop": "^<验证时那个内核的版本号>" } }
```

这个比较要靠得住，内核的版本号就得反映已有的插件会不会被弄坏：改了下面任何一条接缝上已有的东西——包括升级 `cordis`、loader、include 的版本，改 home 的布局——都算破坏；版本号哪一位怎么升见[开发](/docs/develop)。

**约定**：

### 4 插件加载

**连接的模块**：`cordis.yml` 里的任何插件，与 loader 以及内核应用的启动与退出。

**接口**：插件包的入口导出 cordis 认识的形状，函数式写法如下，也可以默认导出一个继承 cordis `Service` 的类：

```ts
import type { GwbContext } from '@godcreator/gwb-kernel-desktop'

export const name = '@godcreator/gwb-demo'
export const inject = ['gwbData']           // 这些服务都在了，cordis 才调用 apply
export function apply(ctx: GwbContext): void { /* … */ }
```

**约定**：

- 插件：包清单的 `exports` 让 `require.resolve` 解析得到入口；依赖的服务写进 `inject`，缺一个就停在等待，补齐后 cordis 自动加载；卸载时清理自己创建的东西，异步的清理把 promise 从 effect 的清理函数里返回
- 内核应用：插件里没被处理的 rejection 与未捕获的异常只记一行名字为 `kernel` 的 error，不退出；退出时卸载整棵插件树，等各插件清理完，最多等 5 秒

{/* ref file="../apps/desktop/src/main.ts" lines="391-402" hash="8edc94e1bbea" blob="b613d37fa683" */}

**不负责的事**：内核不判断插件加载成功没有——以 cordis 给这个条目的 fiber 状态为准，`ACTIVE` 才算；插件之间的依赖齐不齐，内核不核对。

**连接的模块**：任何插件，与内核应用的内核服务、包根导出的接口类型。

**接口**：`ctx.gwbKernel` 的形状是包根导出的 `GwbKernelApi`，插件 `apply` 拿到的上下文类型是 `GwbContext`：

{/* ref file="../apps/desktop/src/api.ts" lines="9-31" hash="4d4da5ce95ba" blob="b2cf0ae6f72c" */}

**约定**：

- 内核应用：在根上下文上提供 `gwbKernel`，早于注册 loader、永不撤销；`dataDir` 是 home 在磁盘上的真实路径，`version` 是内核包清单里的版本号；`emit` 只转交给当前窗口，窗口不在就丢掉

### 6 请求通道

**连接的模块**：登记请求处理器的插件（例如命令插件 `@godcreator/gwb-commands`），与内核应用的请求分发；页面那一头经接缝 9。

**接口**：`gwbKernel.handleRequest(channel, handler)` 登记，页面 `window.gwb.request(channel, payload)` 调用：

{/* ref file="../apps/desktop/src/requests.ts" lines="10-31" hash="2c4f18e7d779" blob="2041dd1920e9" */}

{/* ref file="../apps/desktop/src/preload.cjs" lines="38-42" hash="acee284069bd" blob="97b2299ef0dc" */}

这两段说明：同名通道重复登记就抛错，注销函数幂等；找不到处理器时主进程回 `{ available: false }`，preload 以 `GWB_REQUEST_UNAVAILABLE: <channel>` 拒绝，找到了就把处理器的返回值原样交回页面。

**约定**：

- 登记方插件：注销函数交给 `ctx.effect`；解释载荷、返回能经结构化克隆的结果；载荷形状、回执类型和页面用的客户端由它自己定义、自己发布
- 内核应用：只接收顶层框架的请求；注销之后新请求拒绝，已经开始的请求照样完成；处理器抛错就让页面请求拒绝，不改写成任何业务回执

**不负责的事**：内核不认识命令名、来源标记与命令回执，不导入命令插件，也不重导出它的类型（[请求通道](/trajectory/2026-09-27-request-channel)、[不保留命令兼容层](/trajectory/2026-09-27-request-without-compat)）。一个请求在页面、preload、主进程之间怎么走见[页面与主进程之间的通道](/docs/desktop/ipc)。

### 7 浏览器模块

**连接的模块**：提供浏览器模块的插件（页面用的 React 由外壳 `@godcreator/gwb-shell` 提供），与内核应用的浏览器模块登记；页面上的准备经接缝 9。

**接口**：`gwbKernel.registerImports({ 包名: 地址 })` 返回撤销函数；页面动态 import 之前先 `await window.gwb.prepareImports(required?)`：

{/* ref file="../apps/desktop/src/browser-imports.ts" lines="8-35" hash="632127e56a4b" blob="a9ce57cbee25" */}

**约定**：

- 提供方插件：只登记精确的包名，地址是本地 `.js` / `.mjs` 文件的 `file:` 地址；撤销函数交给 `ctx.effect`
- 内核应用：一批先全部校验再登记，同名同地址按次数复用、最后一个撤销后才移除，同名不同地址抛错并列出两个地址；页面上已经注入的名字被撤销或换了地址，`prepareImports` 拒绝、要求整页重载

**不负责的事**：内核不带 React、不决定 React 的版本，也不扫描 home 或包清单找模块（[内核提供模块解析机制，外壳提供 React](/trajectory/2026-09-27-browser-imports-service)）；撤销登记不会卸载页面里已经解析的模块。importmap 怎么注入见[页面入口](/docs/desktop/page)。

**连接的模块**：外壳插件与它的页面模块，与内核服务的 `setShell`、内核包里的页面入口 `index.html`。

**连接的模块**：页面上的代码（外壳、窗格等），与内核包里 `preload.cjs` 注入的 `window.gwb`。

### 10 写日志

**连接的模块**：任何插件与页面上的代码，与内核应用的日志。

**接口**：插件写 `ctx.logger(名字).info / warn / error / debug`，进 cordis 的日志流；页面上的 console 输出由内核转成名字为 `renderer` 的日志；内核注册唯一的 exporter 收下每一条：

{/* ref file="../apps/desktop/src/main.ts" lines="340-342" hash="cb8cdc7db26f" blob="b613d37fa683" */}

{/* ref file="../apps/desktop/src/main.ts" lines="176-184" hash="02b49b6c7079" blob="b613d37fa683" */}

**约定**：

- 插件：日志一律经 `ctx.logger`，直接写 stderr 的内容不进文件；logger 名用自己能被认出的名字，不用 `kernel`、`loader`、`include`、`renderer`，这几个名字的日志算内核或页面的
- 内核应用：所有级别都写；cordis 格式化不了参数时退回逐个转成字符串，写日志的一方不抛；每个插件条目加载成功、加载失败各写一行 `loader` 日志，条目树安定之后写一行汇总；每条 error 在 200 毫秒内触发一次外壳状态推送，warn 不推

**不负责的事**：内核不给日志分级过滤、不按插件分文件，也不为页面建日志通道——要在页面上显示日志的插件自己读 `gwb.log`，再用自己的命令交给页面。挂载日志与汇总的规则见[日志](/docs/desktop/log)。

### 13 条目树与包

**连接的模块**：插件管理 `@godcreator/gwb-plugin-manager`（生命周期插件仓 `gwb-lifecycle-plugins`），与 loader 的条目树、home 里的 `package.json` 与 `node_modules/`。

**接口**：loader 服务 `ctx.loader` 上的 `create` / `update` / `remove` / `resolve` 与 `root`，以及条目带前缀的 id。它不在 `gwbKernel` 里，也不在内核包导出的类型里：形状就是内核包依赖里那两个版本的 loader 与 include 的内部结构（接缝 2 引的那几行清单）。

**约定**：

- 插件管理：改 `cordis.yml` 只经条目树——条目树把写回文件和当场加载、卸载一起做，绕过它直接写文件，下一次写回会把磁盘上的改动覆盖掉；只有它经 pnpm 改 `package.json` 与 `node_modules/`；点名换内核包时把 home 根上的 `cordis` 一起对齐到新内核包 peer 里的版本，装完要重启工作台才生效
- 内核应用：loader、include、`cordis` 的版本或 home 布局一变就是改了这条接缝；别的插件从 `ctx.fiber.entry` 读条目 id 与包名，这个字段同样是 loader 的内部结构，跟着 loader 的版本走

**不负责的事**：内核不知道插件管理存在，不带 pnpm；不读插件 peer 里的内核包范围，不兼容的插件照常加载。插件管理怎么装包、怎么比对 peer，写在 `gwb-lifecycle-plugins` 仓的文档站。

**测试**：本仓没有测试检查条目树的形状，它由插件管理所在的仓用同版本的 loader 与 include 测。

## 两个包

- [内核应用](/docs/desktop) `@godcreator/gwb-kernel-desktop`（`apps/desktop`）：主进程里建 cordis 实例、加载插件、提供 `gwbKernel`、写日志与 `runtime.json`，页面这边提供 `window.gwb` 与页面入口；包根只导出接口类型。发到团队包源，和插件一起装在每个 home 里
- [安装包](/docs/installer)（`apps/launcher` 与 `installer/`）：启动器加 Electron 打成的安装程序，不发 npm 包，不带内核、插件与 pnpm
