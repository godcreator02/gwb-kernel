# gwb-kernel 是什么

god 工作台的**正线**：最小的、能正常运行插件的那个版本。一个 Electron 应用，内核只做
六件事，其余一切皆件。

目标不是「内核行数最少」，是**「能把插件正常跑起来」所需的最小集**。这两者不一样：
前者容易滑向什么都不做，后者带着一条验收标准——插件得真能干活。

内核的全部本体是四个文件合计 512 行：`main.ts` 338、`imports.ts` 63、`index.html` 92、
`preload.cjs` 19，外加词汇表 62 行。`main.ts` 文件头一句注释是它的自我介绍，边界钉在
[系统地图](/docs/system-map)——未来区不钉活代码，钉码只在现状区。

这行注释说明的是边界，不是规模：六件事是「第一个件跑起来之前必须发生的事」，件真正
干活要的一切，内核一概不代办。

## 两步走到今天

**第一步（2026-09-07）：从母仓分出来。** 母仓 `god-workbench` 走到那天大约 5100 行：
`apps/desktop` 约 1500 行是执行壳，`packages/gwb-platform` 约 3600 行是判据。把这 5100 行
逐块过一遍会发现，其中约 3600 行服务的是同一件事——**让失败变得体面**：

- 自动升级的四路判定（首启 / 升级 / 补标记 / 已是最新）与 base 快照账本
- 装完之后数一遍盘核对清单、装失败时把 `package.json` 还原回去
- 图形界面上的阶段页与兜底页
- `cordis.yml` 读不动时备份原件、回写模板

这些不是超前设计，是被真实翻车逼出来的。但它们有一个共同的前提：**存在一个会自动升级、
会自我修复的装机**。这条线的选择是把那个前提拿掉：装包是「进 home、`pnpm add`、
`cordis.yml` 写条目」的手工活，内核不碰 pnpm。这不是假装问题不存在，是移除产生问题的
那台机器。了断见[装机口移除](/trajectory/2026-09-08-no-install-port)。

**第二步（2026-09-09）：从两进程并成一进程。** 第一版把 cordis 和所有件放进一个独立的
node 宿主子进程，跟 Electron 主进程隔开。本意是隔离，结果**隔开的那道墙上长出来的东西
全是绕墙用的**：fd3 协议、`gwb://` 资产协议、exports 解析、日志四路管道——每一件都是
为了让两个进程说话。而件真正要的恰恰是 Electron：开窗、菜单、托盘、子进程、`electron`
这个模块本身。于是墙拆掉，cordis 搬进 Electron 主进程，应用只剩主进程与渲染进程两个，
上面那一串跟着一起消失。了断与四个探针的读数见
[单进程重构](/trajectory/2026-09-09-single-process)。

## 内核只做六件事

推导的起点是一句话：**让 cordis 插件跑起来，并且有界面**。从它出发，几条不可谈判的
事实决定了剩下的一切——件是 JS 模块，要被 `import` 才会运行；件是「后来才有的」，所以
不能自己把自己带来；界面在浏览器环境而件的逻辑在 node 环境，这是两个执行世界。

| | 是什么 | 为什么不可消去 |
| --- | --- | --- |
| **铺 home** | 建目录、缺什么补什么（`package.json`、空 `cordis.yml`），不覆盖 | 件要有地方装，条目表要有地方待 |
| **起 cordis** | `Context` 的 `baseUrl` 指向 home，挂官方 loader 与 include | 没有底座，「件」这个词都不成立 |
| **解析裸名（node 半）** | 给 `loader.internal` 塞五行，按 home 解析裸包名 | 主进程没有 `--expose-internals`，不塞这五行件静默挂不上 |
| **解析裸名（浏览器半）** | 扫 home 清单里各包声明的 `gwb.shared`，解析成 `file://` importmap，随外壳地址推给页面 | 页面的裸名 `import` 之前必须有表；声明权在提供方，内核只搬运 |
| **开窗与桥** | 一扇窗；`gwb:command` 派给命令总线，`gwb:event` 推事件，`gwb:shell` 告诉页面外壳是谁 | 两个执行世界必须能对话 |
| **页面根 / 自己出错人看得见** | 页面听 `onShell` 去加载外壳，没有外壳时画一份只读现状；cordis 日志进 stderr 加 `<home>/gwb.log`，出错只记不退，起不来弹错误框 | 没有根界面没处画；错误没人看见等于没报错——而件没挂上这件事，件自己报不了 |

（表里六行，末行是两件事合写；「开窗与桥」和「页面根」也是同一件事的两头——主进程
推地址、页面加载，缺一半就什么都没有。四个文件合计 512 行：`main.ts` 338、`imports.ts` 63、
`index.html` 92、`preload.cjs` 19，外加词汇表 62 行。）

importmap 归内核是 2026-09-09 当天定的：上午试过归外壳，当天推翻——它是页面级的运行时
服务，没有外壳时别的浏览器半也得解析得到 react，而且共享包的声明权该在提供方不在消费方。
了断见 [importmap 归内核](/trajectory/2026-09-09-importmap-in-kernel)。

外加一份**词汇表**——它不做事，只命名。取址要说得出「条目」，桥要说得出「命令」
「事件」，外壳要说得出「默认导出」，这些名词的定义就是它。0.1 版**六个名字加一个形状、
62 行**，见[词汇表](/docs/plugins/vocab)。它不是第七件事，是前六件赖以表达的语言。

机制分五章，见[内核](/docs/kernel/processes)。

## 准入判据：两道关，都得过

**一、凡是「第一个插件存在之前必须发生的事」，才进内核。其余一律皆插件。**

**二、真遇到需求才加。** 不是「将来可能要」「顺手做了吧」「母仓有这个」——是某件事
**此刻就干不成**，而且干不成的现场说得出来：谁、在做什么、卡在哪。

加功能的默认形态是**加一个插件**，不是往内核里加一段。往内核里加之前先问：这件事能不能
由某个件提供、由 cordis 的服务注入送到用得着的地方去？能，就该是插件。

这两句是这个仓存在的全部理由。它们一旦松动，仓就会慢慢长回母仓的样子——每一条「顺手
加上」的自动化都有它自己的道理，加够二十条就又是 5100 行。

拿不准的时候按「不进」处理：加回来永远比拿掉容易。

单进程之后这两关**更好用了**：件跑在主进程里，意味着件拿得到 `electron`——开窗、菜单、
托盘、对话框、协议处理、子进程，全是件的事，内核一条都不用代办。

已经明确不做的那些，连同各自的理由，见[刻意不做什么](/future/not-doing)。

## 插件契约：按最小重定

契约不受「母仓那 11 件不改一行」的约束——按第一性原理定，不照抄。十二件已于
2026-09-09 全部迁到 0.1 并发版，契约面见件仓的[决策记录](/trajectory)。

有一份实测数据支持「词汇表要小」。把母仓 11 件源码全扫一遍，它们从平台包根出口一共只取
了 12 个名字，按使用面分三档：

| 档 | 名字 | 判断 |
| --- | --- | --- |
| 11 件全用 / 7 件 / 6 件 | `GwbContext`、`requireKernel`、`isRecord` | **真属于内核词汇表** |
| 各 2 件（一个提供、一个消费） | `GwbHttpApi`、`GwbSkill`、`GwbSkillsApi`、`gwbCommands` | **插件之间的契约，不是内核契约**——该住提供方那个件自己的包里。内核根本不知道 http 是什么 |
| 各 1 件 | `nodeChildEnv`、`readYamlDoc`、`PLATFORM_RUNTIME_VERSIONS`、`noHandlerError`、`PluginStore` | 实现细节漏出来的。**包里放了实现，就一定会有人引到实现** |

所以内核的词汇表只有七个名字，而不是母仓那 600 行。

**内核信息怎么给插件：运行时状态走 cordis 服务，类型走词汇表包。** 这是两条路，不能混——
`dataDir` 是内核启动时算出来的运行时值，插件 import 一份内核代码拿不到它。把内核的
`src/` 整个发成包给插件用是错的：插件用不着内核入口，而发出去就成了要维护的契约。
