# 刻意不做什么

下面每一条母仓都有。这里没有，不是排期没排到，是**决定不做**。要做，得先推翻
[准入判据](/future/overview#准入判据)那一句。

写下来是为了防一件事：一年之后有人看到某处「缺了个自动化」，顺手补上，理由充分，
然后再来十九次。

这一版多了一节**「曾经做、后来刻意不做」**：单进程重构把旧线上真做过、也真用过的一批
机制整个退役了——它们不是「还没做」，是做完之后又拿掉，拿掉的理由同样要钉在这儿防回潮。

## 装机口

母仓有一台装机，这条线一度也有：`kernel.install` 命令转发 pnpm、首启装一份推荐列表。
2026-09-08 **整口拿掉**——内核不碰 pnpm（判据见[装机口移除](/trajectory/2026-09-08-no-install-port)）。

为什么：装机这台机器的价值在「自动地装」，而自动装的头两件事——判该不该装、装失败怎么
办——正是自动升级那套麻烦的入口，这两条上面已经判了不做。剩下「手动装」根本不需要内核：
进 home、`pnpm add`、`cordis.yml` 写条目（全流程见[跑起来](/docs/getting-started/first-run)）；
图形界面的装件面归件——件仓的 `gwb-plugins` 件，`plugins.install` 命令干这个，件在
主进程里有完整的 node，不必经内核转发。

内核为「装」保留的只有[安家](/docs/kernel/home)：home 是个 pnpm 认得的普通 npm 项目根。

## 自动升级

母仓会在每次启动时判断 home 里的件该不该顶到新版本：首启、升级、补版本标记、已是最新
四路，配一份 base 快照账本记住「上次装的时候推荐值是多少」，据此区分「这个版本是我们
装的」和「这个版本是用户自己钉的」。

这里没有。**装过了就不再动它**。首启装一遍推荐列表，之后 home 归用户。

为什么：那套判定的复杂度全部来自一个需求——自动顶版本的同时不能覆盖用户的选择。不自动
顶，判定就没有存在的必要。母仓约 1200 行服务于此。

## 盘上对账与失败还原

母仓装完会数一遍 `node_modules` 核对清单说的件是不是真在（pnpm 报成功不等于东西都在），
装失败会把 `package.json` 原文还原回去（写清单等于盖了「装过了」的章，失败却留着章，
下次会当成已装好）。

这里没有。**装不上就是装不上**，回一句 pnpm 的原话。

为什么：这两条都是自动升级的配套。没有那台机器反复改写清单，也就没有「章盖了一半」
这种局面。

## 图形界面上的失败兜底页

母仓在窗口里画「正在装底座件」「装不上，点这里重试」「外壳插件未生效，去终端跑
`gwb entry enable shell`」「多条外壳同时启用」。

这里没有那台机器。**有的是一份只读现状**（2026-09-09 晚定的）：外壳没上来、或外壳起不来时，
页面摆出 `cordis.yml` 各条目到了哪一步（cordis 自己的状态词：ACTIVE / PENDING 带缺哪个
服务 / FAILED 带第一行原话 / LOADING / UNLOADING / DISPOSED，外加没有 fiber 的「import
失败」与 disabled）和 logger 缓冲里最近的错误行。数据全是内核已经攥着的（loader 的条目树、
cordis 自带的日志缓冲），随 `gwb:shell` 那条消息一起推，没有新通道；渲染层的 console 也
转进 `ctx.logger`，所以外壳起不来那句也在里面。怎么画见[浏览器那半](/docs/plugins/client)。

**线划在哪**：只读、只画内核已有的数据、外壳在时不露面、**不归因、不重试、不自动恢复**。
「归因」是母仓那句「检查 registry 或网络」——它是往界面上爬的第一步，归因一多就想加一颗
按钮替人修。原始数据（哪条没挂上、错误的第一行）不是归因，人对着看；出路照旧在命令行。

**时态这条线演变过三轮。** 2026-09-08 曾把「还没到」与「已经没了」两个时态从这条不做里
划出去：外壳没上来时窗口摆已装清单（[阶段页](/trajectory/2026-09-08-stage-page)）、
宿主崩了整页换[崩溃页](/trajectory/2026-09-08-crash-page)（退出码＋临近日志原文）。
2026-09-09 上午两张卡随两进程线退役：宿主没了，不存在「宿主崩了」这个局面；清单一并扔了，
页面只剩「没有外壳件」一句话。**当晚重推**：前提消失只证明 WAITING / LOST 那两个等待态该删，
证明不了清单该删——清单的数据源是 loader 的树，跟外壳是谁无关；而件声明了 `inject` 没人
提供时 fiber 停在待命、不报错不进日志，那正是只有内核能报的静默。于是清单以只读现状的
形态回来，先前的「不解释失败」改成「不归因」——摆原始数据不是解释。了断记在阶段页那张
卡的卡尾。

## 插件之间的准入核对

母仓（计划中）会在挂载时读件的 `peerDependencies`，核对平台包版本全等、插件 peer 的
semver 范围、拒绝环依赖，并在装件时自动补装缺的 peer。

这里没有。件之间的依赖关系是件自己的事。

为什么：准入核对的价值是把「装了但跑不起来」提前到「装的时候就拦住」。而这条线的装机
本来就是「管他装不装得上」——拦不拦在同一个位置，收益抵消掉了。

## `cordis.yml` 的模板与自愈

母仓在文件不存在时写一份默认模板（十来条底座件），在文件读不动时把原件备份成 `.bad`
再回写模板。

这里没有。文件不存在就**建一份空表 `[]`**——那既是「一个件都没装」的正当表达，也是 home
起得来的最小形态（读不到这个文件的话 `include` 会抛，那个错在挂载链上，整趟起不来，见
[新 home 那面墙](/trajectory/2026-09-07-wall-fresh-home-no-yml)）。除此之外一条都不写：
不写模板，不写任何条目。读不动就报错说清是哪一句坏了。

为什么：那个文件归用户。首次写模板是一次性的便利，但「读不动就回模板」等于在用户的
配置坏掉时替他做决定，而那份配置可能只是少个引号。

## 曾经做、后来刻意不做（随单进程退役）

这三样在两进程线上是真做过的机制，不是没想过。2026-09-09 拆墙时一起拆了
（了断总账见[单进程重构](/trajectory/2026-09-09-single-process)）：

- **宿主子进程与 fd3 协议**。宿主子进程存在的唯一目的是把件跟 Electron 隔开，而件真正
  要的恰恰是 Electron。隔开之后两个世界要说话，于是长出 fd3：命令 stdin 下行、回执事件
  fd3 上行、按 id 配对、120 秒超时。墙拆了，`gwb:command` 一条 IPC 直达，这整套协议没有
  存在的理由。
- **`gwb://` 资产协议与 exports 解析**。为了让渲染层拿到宿主进程里件的浏览器那半，内核
  注册了自定义协议、维护 exports 定址表、管 MIME 白名单。探针证明页面直接吃 `file://`
  五项全通（动态 import、样式表、importmap 同实例、fetch、JSON 模块），件的浏览器半地址
  改由件自己从 `import.meta.url` 算、注册窗格时自报——内核不再认识任何包的任何导出。
- **日志管道：四路汇总、环形缓冲、preload 两口、按字节轮转**。四路里有两路（宿主、主进程）
  是两个进程硬造出来的，并成一路之后，三路日志都走 `ctx.logger`，内核挂一个 exporter 写
  stderr 加 `<home>/gwb.log` 就完了；页面上要看日志，`gwb-logger` 件自己挂第二个 exporter
  收齐。缓冲与轮转是「内核替窗格铺管道」的旧念头，随[那串轨迹卡](/trajectory)退役。

防回潮的判据就是准入第一关：上面每一样，今天都没有任何一件「第一个件跑起来之前必须
发生的事」要求它回来。

## 不属于「不做」，属于「到期再选」

有一条容易混进来：**安装包**。2026-09-12 内核已经**上架本机 registry**（0.1.0，日常从
固定安装位起不走 build，判据见[上架与安装位](/trajectory/2026-09-12-kernel-on-registry)）
——那是「自己用」的解法，不是「分发」的。electron-builder / Forge 出安装包仍到**真要分发
给别人**的时候才到期，到时候手上会有一个确定的问题——pnpm 怎么进产物——那时再拿两个
工具各试一次。

构建器倒是已经选过了：**没有**——`tsc` 直出 `dist/`，electron-vite 已随旧线退役（它当年
显式 `rollupOptions` 盖掉注入的那面墙见[轨迹](/trajectory/2026-09-07-wall-rollup-external)）。

现在唯一做的准备是零成本的那条：**别让打包器的形状渗进源码**。主进程走正常的包解析，
不依赖任何依赖被内联进束。母仓有一句反面教材，源码的 `import` 写法被 asar 的行为反向
决定了；这里不这么写，将来换任何打包器都不疼。
