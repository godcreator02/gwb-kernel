# 内核装进 home

**本页回答**：把内核从 `app.asar` 挪进每个 home 的 `node_modules` 要改什么、换来什么、要推翻哪些已有决定、分几步做、做到哪儿了。

**状态：人已决定做（2026-09-24），五条待决定按推荐定下，第一步在做。**

## 由来

2026-09-24 在总控台的会话里查实：内核用 `app.asar` 里的 cordis 4.0.0-rc.9 创建 cordis 实例，插件写 `import { Service } from 'cordis'`
时按 home 解析，拿到的是 pnpm 按 peer 在 home 里补装的 rc.10。插件手里的 `ctx` 与它继承的 `Service` 来自两份不同版本的 cordis。
devkit 仓的全生态机制定案第一节记下了这件事，判断是「没有实际发生的故障，不做」。

一般的 Node 插件生态（eslint、vite、koishi 的插件）靠 peer 解决这两件事：宿主是一个 npm 包，和插件装在同一个 `node_modules` 里，
pnpm 把插件的 peer 解析到应用装的那一份，安装时顺带检查版本范围。gwb 做不到，因为宿主在 `app.asar` 里，pnpm 看不见它：
解析上它另装一份，版本检查只能比到自己装的那份。所以另有 `gwb.testedKernel` 这个字段，由插件管理拿运行中的内核版本来比。

同一次会话里先讨论过由内核在主进程里注册解析钩子，把包名 `cordis` 固定解析到 `app.asar` 里那一份；之后人选择先讨论本页的做法，
因为它同时去掉两个问题：cordis 只剩一份，peer 的版本检查也重新有效。

## 方案

- **启动器**：安装包只带 Electron 和一段启动脚本。启动脚本选定 home（规则不变），从
  `<home>/node_modules/@godcreator/gwb-kernel-desktop` import 内核；home 里没有内核包就弹框说明、退出码 1，**不替人安装**
- **home**：`package.json` 除了插件，再列内核包和 `cordis`，版本号与内核包依赖的一致；内核包把 cordis 写成 peer。
  这样 pnpm 只装一份 cordis，内核和所有插件解析到同一份
- **谁把内核装进 home**：和插件一样，由创建 home 的一方装。default 由装机的 agent 照 `INSTALL.md` 装，测试 home 由
  `devkit.home.new` 装。启动器与内核都不运行 pnpm
- **内核发版**：内核包重新发到团队源；安装包只在 Electron 版本或启动脚本变了时重打
- **开发内核**：内核的开发版和插件一样用 `devkit.dev` 装进隔离 home 验证，不用重新安装 exe，也不碰 default

## 已决定（2026-09-24）

- **做**，和 devkit 仓全生态机制定案的第四期一起做：两边都要改 `devkit.home.new` 与 `INSTALL.md` 的首次安装插件集
- **Electron 版本**：内核包在 `package.json` 的 `engines.electron` 写它要的 Electron 版本范围（`engines` 是标准字段，键可以自定，
  VS Code 扩展的 `engines.vscode` 是同样的用法）。启动器 import 内核之前拿它和 `process.versions.electron` 比，不满足就弹框、退出码 1。
  只有 Electron 换主版本时才重打启动器
- **兼容性声明换成 peer**：插件写 `peerDependencies: { "@godcreator/gwb-kernel-desktop": "^<版本>" }`；插件管理的 `list` 拿这个范围和
  home 里装的内核比，照样按包报没测过的；`devkit.release` 改查这个 peer 的写法。`gwb.testedKernel` 与两份比对规则删掉。0.x 下的 `^`
  就是现在的「版本线」比对规则
- **内核单独升级**：`plugin-manager.update-all` 保持热升级、不重启，跳过内核包；另加一条升内核的命令，回执带「要重启」与哪些插件的
  peer 范围不含新内核。重启由人决定，插件管理不自动重启应用
- **各个 home 的内核版本各自独立**：新内核先装进隔离 home 验证，default 验完再升

  `engines.electron` 不含当前 Electron 就弹框、退出码 1；否则 import 内核。选 home 与比对版本是纯函数，有单元测试；

**第二步：devkit 仓（与全生态机制定案第四期一起）**

**第三步：各插件（随定案第三期）**：`gwb.testedKernel` 换成 peer 内核包

**第四步：发布（每一项动手前问人）**：内核的版本号升哪一位先问人（home 布局变了按规矩升 x，但词汇表包没改、与内核同版本号的规矩会让它
也跟着升 x）→ 内核包与词汇表包发到团队源 → `INSTALL.md` 与 README 改成往 home 里装内核包与 `cordis`（在这之前它们描述的是已发布的旧安装包，
团队源上没有内核包，提前改了照着装会 404）→ default home 的 `package.json` 加内核包与 `cordis`
（旧安装包仍从 `app.asar` 加载内核，不读 home 里这份，先加没有影响）→ 装新安装包 → 插件逐个按第三步重发

## 要推翻或改写的已有决定

- [撤 npm 管道](/trajectory/2026-09-18-withdraw-npm-channel)：内核重新发 npm 包
- 「发版就是发 exe」（`installer/SPEC.md`）：exe 变成只装 Electron 的启动器，内核版本不再跟着 exe 走
- [内核 0.1.0 上架本机 registry](/trajectory/2026-09-12-kernel-on-registry)里的「固定安装位」不回来：内核装在每个 home 里，不装在单独的目录里
- devkit 定案第二节「home 里只有插件」：home 里多了内核包与 cordis 两个不是插件的包
- [内核只放内核](/trajectory/2026-09-24-kernel-repo-only-kernel)里的兼容性做法：看上面「兼容性声明换不换」怎么定
- home 布局变了，按接缝约定内核升 x

## 代价

- 内核重新有了一条 npm 发版线，加上启动器，发版物从一个变成两个
- 多出启动器与内核之间的 Electron 版本兼容问题
- 装机步骤多一步（往 home 里装内核包），`INSTALL.md`、`devkit.home.new` 都要改
- 内核升级从「重新安装 exe」变成「装进 home 后重启」，插件管理要处理这种只能重启才生效的升级

## 验收

- [ ] 隔离 home 里，内核与每个写 peer `cordis` 的插件解析到的 cordis 是同一个真实路径，home 的 `node_modules/.pnpm` 里只有一份 cordis
- [ ] 内核的开发版经 `devkit.dev` 装进隔离 home，重启后 `gwbKernel.version` 是新版，没有重新安装 exe
- [ ] home 里没有内核包时，启动器弹框说明并以退出码 1 退出
- [ ] 照新的 `INSTALL.md` 由不带上下文的子代理往临时 home 装一遍，MCP 入口连得上、条目全部 ACTIVE
