# ESM 加戳重载的代价

## 问什么

Node 的 ESM 模块图按 URL 缓存，同一个 URL 永远拿到同一个模块实例。要让一个跑着的件在
**它自己没升级、只有它的依赖升级了**的情况下拿到新代码，常见招数是给 import 的 URL 加一个
变化的戳（`import(url + '?v=' + 戳)`），逼 Node 当成新模块重新求值。**这一招的代价有多大？**

拆成四问：每重载一次净泄漏多少内存、泄漏由什么构成、旧模块的副作用清不清得掉、
Node 有没有清除 ESM 模块图的官方口子。

## 怎么跑

```powershell
node --expose-gc probe.mjs
```

零依赖，只用 Node 内置的东西，不碰仓的依赖树。可选两个位置参数：重载次数（默认 60）与
落进 `runs/` 的文件标签（默认 `baseline`），例如 `node --expose-gc probe.mjs 200 long-200`。
`--expose-gc` 是硬要求——拿不到 `global.gc` 脚本直接退 2，因为不强制 GC 量到的全是噪音。

输出既打屏也按序号落 `runs/<序号>-<标签>.txt`，序号自动往下排。

`fixtures/` 里是四个假模块。`bulky-16k.mjs` / `bulky-64k.mjs` 由 `probe.mjs` 首次跑时按确定内容
生成（缺了才生成），生成物一并入库，所以这个目录不依赖任何外部东西。

四个假模块各自在证一件事：`light.mjs` 什么都不存（量模块本身的底价）、`heavy.mjs` 跟 light
逐字一样只多一个 1 MiB 的模块作用域数组（差值就是闭包持有的东西）、`bulky-*.mjs` 只用注释撑
源码体积（量「模块本身」那笔钱跟源码大小成不成正比）、`ticker.mjs` 求值时起一个 `setInterval`
并给出 `dispose()`（量副作用）。每一小节都带一条**不加戳的对照**跑同样次数，那条的斜率就是
这台机器当天的噪音底线。

## 结论

**加戳重载在 Node 24 上不可逆地泄漏，泄漏量 ≈ 模块源码的 2 倍加上模块作用域里存的全部东西；
但副作用不是「清不掉」——只要件给出 `dispose()` 并且调用方真的调，旧定时器一条不剩。**

| 量的是 | 数字（60 次重载的最小二乘斜率） |
| --- | --- |
| 噪音底线（不加戳，同一 URL 重复 import） | 0.1 ~ 0.3 KiB/次，R² 0.67~0.97（即 0） |
| 一个 0.2 KiB 源码的空模块 | **5.9 KiB/次**，R²=0.9986 |
| 源码 16 KiB 的模块（只有注释） | **37.5 KiB/次**，R²=1.0000 |
| 源码 64 KiB 的模块（只有注释） | **132.9 KiB/次**，R²=1.0000 |
| 空模块 + 1 MiB 模块作用域数组 | **1030.9 KiB/次**，R²=1.0000 |

四条推论，每条都指着上表里的一行：

**一、净泄漏是几 KiB 到几百 KiB 一次，量级由被重载模块的大小定，不是常数。** 空模块 5.9 KiB
听着可以忽略，但斜率跟源码大小几乎正比：64 KiB 源码漏 132.9 KiB，**约 2.08 倍源码大小**
（16 KiB 那档是 2.34 倍，同一量级）。二倍是因为源码文本本身与 V8 编译产物各留一份。真件的
产物是几十到几百 KiB，所以现实里的单次代价该按**「件的 dist 体积 × 2」**估，不是 5.9 KiB。
200 次重载的长跑（`runs/03-long-200.txt`）斜率 5.8 KiB/次、R²=0.9925，跟 60 次那趟一致，
**没有饱和迹象**——它是真线性泄漏，不是热身抖动。

**二、泄漏的构成是「模块本身 + 模块闭包持有的全部东西」，后者是大头。** heavy 与 light 的
斜率之差 **1025.0 KiB**，跟假模块里放的 1024.0 KiB 载荷对得上（误差 0.1%）。也就是说
**模块作用域里存了什么，就一份不落地留在图里**——缓存、连接池、预编译结果，重载一次留一份。

**三、旧模块确实被强引用攥着，跟你还有没有引用无关。** 每次重载都对拿到的命名空间对象存一个
`WeakRef`，跑完强制 GC 三趟再数：带戳那几趟**去重后 60/60 全部存活**；不带戳的对照去重后
只有 1 份（同一个对象被 import 了 60 次）。所以泄漏的机制不是「我们哪里忘了释放」，是
**模块图自己在攥着，从外面够不着**。

**四、副作用清得掉，但得件自己给下车口。** `ticker.mjs` 求值时起一个 20ms 的 `setInterval`。
只加戳重载三次、谁都不 dispose：三个 id 在随后的 200ms 里各自还新增 6~7 次 tick，
**两个旧模块的定时器都还在跳**——那不是浪费空间，是旧代码还在跑。改成每次重载前先调上一个的
`dispose()`：旧的两个 tick 增量都是 **0**，只有最新那个在跳。**这一条完全取决于件有没有
`dispose()` 以及调用方有没有调，Node 帮不上任何忙。**

**五、Node 24.14.1 上没有清除 ESM 模块图的口子——查过，没有。** `node:module` 的 31 个导出里
名字沾边的只有 `_cache` / `_pathCache`（CJS 专用）与 `enableCompileCache` / `flushCompileCache` /
`getCompileCacheDir`（那是磁盘上的编译缓存，跟内存里的模块图无关）。实测 import 过的 `.mjs`
**不出现在 `require.cache` 里**，所以 CJS 时代 `delete require.cache[id]` 那招在 ESM 上没有对应物。
`node --help` 里 `--loader` / `--experimental-vm-modules` / `--experimental-test-module-mocks`
三个沾边的旗子也都不是清缓存的：

- `vm.SourceTextModule`（要 `--experimental-vm-modules`，不带旗子时是 `undefined`）**是另一条路**，
  不是同一条路的补丁：实测同一段源码连造两个实例，`namespace` 互不相同、各自独立求值，
  因为它根本不进全局注册表——代价是链接（`link`）要自己写，import 说明符得自己解析。
- `--experimental-test-module-mocks` 给的 `mock.module()` / `mock.restoreAll()` 是测试替身，
  restore 的是替身不是模块图，不能当热更新用。

## 跑那次的环境

- 日期：2026-09-10
- 平台：win32/x64，Windows 11 Pro 10.0.26200，pwsh 7.6.5
- 运行时：Node **v24.14.1**（`node -v`）
- 被测对象：这次量的是 Node 自己的行为，不是内核代码；跑的时候 `gwb-kernel` 在
  commit **`f845bfd`**（`git rev-parse --short HEAD`），工作区除本目录外无改动

`runs/` 里五次，都是本机同一天跑的：

| 文件 | 跑的是什么 | 那时的 `probe.mjs` |
| --- | --- | --- |
| `01-baseline.txt` | 60 次，头一趟 | 初版：还没有「去重存活」一栏，也没有源码大小那一节 |
| `02-repeat-60.txt` | 60 次，复现 01 | 加了「去重存活」——正是这一栏证出 60 份命名空间全活着 |
| `03-long-200.txt` | **200 次**，看会不会饱和 | 同 02 |
| `04-with-source-size-scaling.txt` | 60 次，加量源码大小那一节 | 加了 bulky-16k / bulky-64k |
| `05-final.txt` | 60 次，收官 | 现在这版（`heavy.mjs` 改用 `Array.from` 过 `pnpm lint` 的 oxlint） |

01→05 跨了脚本的四个版本，但每一版都是**只加不改**测法：斜率数字在五次之间稳定
（空模块 5.8~5.9、1 MiB 载荷 1030.9~1032.3），所以拿哪一份读结论都一样。留全部五份是因为
「200 次不饱和」这条只有 `03` 有，而「去重后 60 份存活」这条 `01` 没有。
